An 8B-parameter model in BF16 on one H100 answers a 1,500-token prompt with 300 tokens. Which stage takes most of the wall-clock time: network, queue, prefill or decode? Roughly what share?
Decode. In the kata it is 2,075 ms of 2,328 ms total, 89%. Prefill, the 1,500-token prompt, is only 49 ms, about 2%.
You move the same model from an A100 to an H100. The H100 has about 3.2x the dense BF16 compute. How much faster is each decoded token?
About 1.64x, not 3.2x (11.40 ms to 6.94 ms in the kata). Decode is limited by memory bandwidth, and bandwidth grew only 1.64x (2.039 to 3.35 TB/s). Prefill, which is compute-bound, does get close to the 3.2x.
A user says the first word takes too long to appear, but once it starts the text streams fine. Which stages of the request do you look at first?
Everything before the first token: network, gateway, queue wait, tokenize and prefill. In the kata the 192 ms to first token is mostly queue wait (97 ms) and prefill (49 ms). Decode speed is not the problem here.

The core idea

Inference engineering is the work of making a trained model answer real requests fast, cheaply and reliably. Training happens once and produces weights. Inference happens for every request, forever, and it is where most of the running cost of an AI product lives. The unit of work is a single request, and the craft starts by knowing what that request crosses on its way through.

A request passes through five layers, and a fleet runs many copies of them. Each layer has its own owner and its own kind of fix. The three numbers you are always trading are latency (how long a user waits), cost (tokens per second per GPU dollar) and reliability (whether it holds under load and failure). Most of the craft is the fact that making one better usually makes another worse.

How it works

One request, two phases

Inside the model, a request has two phases. Prefill reads the whole prompt in one parallel pass and produces the first output token. Decode then produces one token per step, each step depending on the last. Time to first token (TTFT) is everything up to the end of prefill. Time per output token (TPOT) is the length of a decode step. Full definitions come in K08.

Why the phases are limited by different things

Prefill does about 2 x parameters x prompt tokens of arithmetic, so it is limited by compute. Decode must read every weight from GPU memory to produce a single token, so it is limited by memory bandwidth. For 8.03B parameters in BF16 the weights are 16.06 GB, and at 3.35 TB/s that read alone takes 4.8 ms. Arithmetic for one token is about 0.03 ms. The tensor cores wait for memory.

prefill FLOPs  ~ 2 x params x prompt_tokens
decode step    ~ (weight_bytes + KV_bytes_read) / (bandwidth x efficiency)
Check: why does a slower GPU hurt prefill more than decode?
Prefill is compute-bound and the H100 has about 3.2x the A100's dense BF16 compute. Decode is bandwidth-bound and the H100 has only 1.64x the bandwidth. The kata shows prefill 154 ms on A100 against 49 ms on H100 (3.2x), but decode step 11.40 ms against 6.94 ms (1.64x).

Three goals that pull against each other

Because a decode step costs about the same whether it serves one request or many, the engine batches requests into the same step. Derived from the kata's model: 32 concurrent 1,500-token requests read 16.06 GB of weights plus 6.3 GB of KV cache, so the step grows from about 6.9 ms to about 9.5 ms (roughly 38% slower per user) while the GPU emits 32 tokens instead of 1. That is about 23x the throughput. The price is KV memory, which each request consumes, and the extra wait each user feels. This is the central tradeoff of the field. Your clinic voice agents sit at the latency end of it, since a caller feels TTFT. Your SSM edge research sits at batch size 1, where decode is pure bandwidth.

Levels of the craft

A working ladder, which is this curriculum's framing and not a quote from any source. Call: use an API and manage tokens. Run: host a model on one GPU and measure it (K02 to K11). Tune: engine configuration, batching, KV memory, caching (K12 to K18). Go below: quantization, profiling, kernels, the roofline (K19 to K28). Scale: multi-GPU, fleets, routing, autoscaling, economics (K32 to K48). Interviewers listen for which rung you can speak from.

Check: why can batching 32 requests give about 23x the throughput for a step that is only about 38% slower, and where does it stop?
The weights are read once per step and shared by every request in the batch, so the dominant cost does not scale with batch size. Only the KV reads do. It stops when KV memory runs out (each request adds about 197 MB at 1,500 tokens), when compute catches up with memory time, or when the added wait breaks the latency target.

Kata: the request ledger

A simulation of one request through the stack, with the real hardware numbers and a few assumed constants. It prints where each millisecond goes. It needs only Python and no GPU.

Run

python kata.py

kata.py

"""K01 kata: where does each millisecond of ONE LLM request go?
Model: Llama-3-8B-like, BF16. Run: python kata.py [--prompt N] [--out N] [--ahead N] [--gpu h100|a100]
Spec numbers are from NVIDIA datasheets (dense BF16, no sparsity). MFU, bandwidth efficiency and the
CPU/network constants are ASSUMPTIONS: change them and watch the shares move."""
import argparse

GPUS = {  # name: (dense BF16 FLOP/s, HBM bytes/s)
    "h100": (989e12, 3.35e12),   # H100 SXM 80GB
    "a100": (312e12, 2.039e12),  # A100 SXM 80GB
}
P = 8.03e9                       # parameters
W_BYTES = P * 2                  # BF16 weights
KV_PER_TOK = 2 * 32 * 8 * 128 * 2  # K and V * layers * kv_heads * head_dim * 2 bytes = 131072
MFU, BW_EFF = 0.50, 0.70         # assumed: share of peak FLOPs / bandwidth you actually get
NET_UP, NET_DOWN = 20.0, 20.0    # ms, assumed one-way user<->region
GATEWAY = 5.0                    # ms, assumed auth + rate limit + routing
TOKENIZE = 1.0                   # ms, assumed CPU
PER_TOKEN_CPU = 0.2              # ms per output token: sampling, detokenize, stream, assumed

ap = argparse.ArgumentParser()
ap.add_argument("--prompt", type=int, default=1500)
ap.add_argument("--out", type=int, default=300)
ap.add_argument("--ahead", type=int, default=2, help="prefills queued ahead of you")
ap.add_argument("--gpu", default="h100", choices=GPUS)
a = ap.parse_args()
flops, bw = GPUS[a.gpu]

# prefill: all prompt tokens at once. Time is the slower of compute and one pass over the weights.
pf_compute = 2 * P * a.prompt / (flops * MFU) * 1e3
pf_memory = W_BYTES / (bw * BW_EFF) * 1e3
prefill = max(pf_compute, pf_memory)
pf_bound = "compute" if pf_compute >= pf_memory else "memory"

# decode: one token per step. Reads all weights plus the KV cache so far.
avg_ctx = a.prompt + a.out / 2
dec_memory = (W_BYTES + KV_PER_TOK * avg_ctx) / (bw * BW_EFF) * 1e3
dec_compute = 2 * P / (flops * MFU) * 1e3
step = max(dec_memory, dec_compute)
dec_bound = "memory" if dec_memory >= dec_compute else "compute"

queue = a.ahead * prefill        # each prefill ahead of you blocks the GPU for its full duration
decode = step * (a.out - 1)      # first token already came out of prefill
cpu = PER_TOKEN_CPU * a.out

stages = [("network up", NET_UP, "network"), ("gateway", GATEWAY, "cpu"), ("queue wait", queue, "scheduler"),
          ("tokenize", TOKENIZE, "cpu"), ("prefill", prefill, pf_bound), ("decode", decode, dec_bound),
          ("sample+stream", cpu, "cpu"), ("network down", NET_DOWN, "network")]
total = sum(ms for _, ms, _ in stages)
ttft = NET_UP + GATEWAY + queue + TOKENIZE + prefill + NET_DOWN

print(f"{a.gpu.upper()}  prompt={a.prompt} out={a.out} ahead={a.ahead}")
print(f"{'stage':<15}{'ms':>9}{'share':>8}  bound by")
for name, ms, kind in stages:
    print(f"{name:<15}{ms:>9.1f}{ms / total:>7.1%}  {kind:<9} {'#' * round(40 * ms / total)}")
print(f"{'total':<15}{total:>9.1f}")
print(f"TTFT {ttft:.0f} ms | decode step {step:.2f} ms ({1000 / step:.0f} tok/s) | KV for this prompt {KV_PER_TOK * a.prompt / 1e6:.0f} MB")
gpu_ms = prefill + decode
print(f"GPU-bound share (prefill+decode): {gpu_ms / total:.1%}; everything else: {1 - gpu_ms / total:.1%}")

What to notice

  1. Decode is 2,075 ms of 2,328 ms, or 89.2%. The whole 1,500-token prompt costs 48.7 ms, about 7 decode steps (48.7 / 6.94).
  2. Per token, prefill costs about 0.03 ms (48.7 / 1,500) and decode costs 6.94 ms, more than 200 times more. Prefill shares each weight read across all prompt tokens. Decode cannot.
  3. TTFT is 192 ms. Only 49 ms is the GPU doing prompt math. Queue wait is 97 ms, because two prefills run ahead of you.
  4. The "bound by" column flips from compute to memory between prefill and decode. The same GPU is limited by different things in different phases.
  5. Everything outside the GPU phases (network, gateway, tokenize, queue, sampling) adds up to 8.7% of this request. That share depends heavily on the workload, which the second break-it shows.
Break it
  1. Long prompt. Run python kata.py --prompt 30000 --ahead 0. Predict prefill time and TTFT before running.
  2. Short answer. Run python kata.py --out 20. Predict which stage now dominates.
Break it 1: with --prompt 30000 --ahead 0, what happens to prefill, TTFT and the decode step?
Prefill rises about 20x with the prompt, to 974 ms, and TTFT to 1,020 ms. The decode step also grows, from 6.94 to 8.53 ms, because the KV cache is now 3.9 GB to read each step. Decode share falls to 70%. Long prompts move the bottleneck to the front of the request.
Break it 2: with --out 20, which stage dominates, and how big is the non-GPU share?
Decode is still the largest at 40% (131.7 ms), but queue wait is 30% and network 12%. Non-GPU time is 45% of the request. With short answers, queueing and network matter as much as the GPU, so the profile depends on the workload shape.

Stretch. Change W_BYTES to 1 byte per parameter, like FP8 weights, and predict the new decode step before running. Then run --gpu a100 and confirm the 1.64x. This is the doorway to K19.

Interview

Say this aloud against the clock. Three levels, about 90 seconds.

1 Outcome 20 sInference engineering is making a trained model serve real requests fast, cheaply and reliably. One request crosses a stack: client, gateway, engine, kernels and hardware, with a fleet of replicas around it. The job is to keep expensive GPUs busy without making users wait.
2 Mechanism 45 sA request has two phases. Prefill reads the whole prompt in parallel, is compute-bound, and sets time to first token. Decode makes one token per step and must read every weight each step, so it is memory-bandwidth-bound and sets per-token speed. The engine batches many requests into one decode step, since the weights are read once and shared, so throughput climbs while each user's step barely slows. It also manages the KV cache, which holds each active request's history in the memory left after the weights.
3 Internals and limits 25 sTake an 8B model in BF16 on an H100: 16 GB of weights over 3.35 TB/s means decode near 5 ms a token at peak, about 7 in practice. A 300-token answer takes two seconds, a 1,500-token prefill about 50 milliseconds. Batching stops paying when KV memory fills, and it costs latency. A full KV cache or a cold replica shows up as queueing, so I watch TTFT, TPOT and queue depth together.

Traps

Each one sounds right. Say what is wrong with it before you open it.

"Inference is about running the model's math faster, so the best GPU is the one with the most TFLOPS."
Only prefill is compute-bound. Decode, which was 89% of the kata's request, is limited by memory bandwidth. The H100 has 3.2x the A100's compute but 1.64x its bandwidth, and decode got 1.64x faster. For chat workloads, read the bandwidth number first.
"To cut latency for a single user, add more GPU replicas."
Replicas add capacity. They can remove queue wait (97 ms of 2,328 ms in the kata) but do not shorten one request's prefill or decode. To speed one request you need more bandwidth, a smaller or quantized model, speculation, or tensor parallelism across GPUs (K33), which adds communication cost.

Question bank

Answer aloud, then open. Grade yourself honestly.

What is inference engineering, and what does it optimize?
Making a trained model answer real requests fast, cheaply and reliably. The three numbers are latency (TTFT and TPOT), cost (tokens per second per GPU dollar) and reliability under load and failure.
Follow-upWhich two fight each other most? Latency and cost, through batching: bigger batches raise throughput per dollar and slow each user's steps.
Name the layers a request crosses and who owns each.
Client and product, gateway, engine (queue, batching, KV memory), kernels (the math), hardware (bandwidth and compute ceilings), with a fleet layer for replicas, routing, scaling and monitoring.
Follow-upTTFT doubled overnight. Where do you look first? Queue depth and prompt lengths, then prefill time. Decode speed is not part of TTFT.
Why does one decoded token cost so much more time than one prompt token?
Prefill processes all prompt tokens together, so each weight read serves many tokens. Decode reads every weight to produce one token. In the kata, about 0.03 ms per prompt token against 6.94 ms per generated token.
Why does batching raise throughput without much hurting each user, and where does it stop?
Weights are read once per step and shared by the whole batch. Derived: 32 requests take the step from about 6.9 to 9.5 ms and give about 23x the tokens per second. It stops at KV memory, at compute, or at the latency target.
Follow-upWhat grows with each added request? KV cache memory and KV read time, about 197 MB per 1,500-token request here.
A customer says the chatbot feels slow. What do you establish before changing anything?
Whether the first word is slow (TTFT) or the stream is slow (TPOT), the typical prompt and output lengths, concurrency at the bad moments, and then queue depth versus GPU time using a ledger like the kata's.
Follow-upTTFT is bad only at peak. Queue wait is the suspect: add capacity or autoscale, shorten prompts, cache shared prefixes.
How does the ledger tell you which level of the craft a problem lives at?
Network or gateway time points to product and API design. Queue points to capacity and scheduling. Prefill points to prompt length, caching and compute. Decode points to bandwidth, batching and quantization. Fix at the level where most milliseconds sit.

D01: Why does generating 300 tokens take 300 forward passes, and what differs from training?
Each token depends on the ones before it, so tokens come out one at a time and each needs a pass. Training updates weights from a loss over known text. Inference uses fixed weights.
A09: A (1500, 4096) matrix times a (4096, 4096) matrix. What is the output shape and about how many FLOPs?
Output (1500, 4096). That is 1500 x 4096 x 4096 = 2.5e10 multiply-adds, so about 5.0e10 FLOPs. This is the 2 x params x tokens rule for one layer's matrix.
L03: A service gets 1 million requests a day, spread evenly. What is the average requests per second, and what would you plan for?
1,000,000 / 86,400 is about 11.6 per second. Plan for peak, a rule-of-thumb 2 to 3x the average, so roughly 25 to 35 per second.
