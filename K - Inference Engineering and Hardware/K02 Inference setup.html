Inference setup

How do you prove that a fresh GPU machine can serve a model, and which layer do you blame when it cannot? This page covers the GPU, driver, CUDA runtime and PyTorch chain, plus the model hub. Loading and serving a model is K03.

Study path

Before you read

Guess first. A wrong guess now makes the right answer stick later.

nvidia-smi shows "CUDA Version: 12.8" and nvcc is not installed. Can a pip-installed PyTorch built for CUDA 12.8 use this GPU?
Yes, if the driver is new enough. The nvidia-smi number is the highest CUDA version the driver supports. The PyTorch wheel carries its own CUDA runtime libraries, so the toolkit and nvcc are not needed. nvcc matters only when you compile CUDA code yourself.
A box has driver 550. You install a PyTorch build made for CUDA 13.0. Does it work?
No. CUDA 13.x builds need a driver of 580 or higher, and minor version compatibility does not cross a major family. The kata prints this as driver 550 + cu130 FAIL. The same driver 550 is fine for any CUDA 12.x build.
nvidia-smi shows your GPU, but torch.cuda.is_available() prints False. Name three causes.
A CPU-only wheel is installed. The driver is below the minimum for the wheel's CUDA family. The container was started without GPU access. CUDA_VISIBLE_DEVICES is set to an empty value and hides the device.

The core idea

A GPU inference box is a stack of five layers, and each pair of neighbours has a version contract. If one contract breaks, nothing above it works, and the error message usually names the wrong layer. Setup is the habit of testing the layers bottom up so the first red layer is the bug.

You rarely control the bottom two. On Colab or a rented VM the GPU and driver are fixed by the provider. What you choose is the PyTorch build, which carries its own CUDA runtime. So the practical question is always: is this driver new enough for the build I want, and does the build contain kernels for this GPU?

Memory hook

Good Drivers Run PyTorch Scripts. GPU, Driver, Runtime, PyTorch, Script: install and test in that order. Then three numbers that look alike: smi is the ceiling (max CUDA the driver supports), nvcc is the compiler (toolkit you installed, if any), torch.version.cuda is what runs.

How it works

Three version numbers that get confused

nvidia-smi prints a driver version (for example 535.104.05) and a "CUDA Version". That second number is the newest CUDA the driver can serve, not something installed. nvcc --version reports the toolkit compiler, which may be absent. torch.version.cuda reports the runtime the wheel was built against, and that is the one your code uses. They often differ, and that is normal.

Check: smi says 12.8, torch.version.cuda says 12.1, nvcc is missing. Is anything wrong?
No. The driver supports up to 12.8, the wheel uses its own 12.1 runtime, and no compiler is needed to run a prebuilt wheel. This only breaks if the driver is below the 525 minimum for the 12.x family.

The driver contract

Since CUDA 11, a build runs on any driver at or above the minimum for its major family: 450 for 11.x, 525 for 12.x, 580 for 13.x. This is minor version compatibility. Caveats from NVIDIA: some features that span driver and toolkit can fail on an older driver, and code that depends on PTX needs a newer driver. Across a major family you need a newer driver, or the separate forward-compatibility package, which NVIDIA limits to supported platforms and GPUs.

ok = driver_major >= MIN_DRIVER[build_cuda_major]
MIN_DRIVER = {11: 450, 12: 525, 13: 580}

The architecture contract

Every GPU has a compute capability such as 7.5 (T4), 8.0 (A100), 8.9 (L4) or 9.0 (H100). A wheel ships precompiled kernels for a list of architectures. A kernel built for sm_80 also runs on sm_86 and sm_89, because binary code runs on the same major with an equal or higher minor. A wheel with no suitable kernel and no PTX fails at the first GPU operation with "no kernel image is available". An old GPU and a brand-new wheel is the usual cause.

Check: a wheel lists only sm_80 and sm_90. Does it run on an sm_89 GPU? On an sm_75 GPU?
sm_89: yes, through the sm_80 kernels, same major and higher minor. sm_75: no, there is no 7.x kernel in the list. The kata prints both cases.

The box and the hub

Work over SSH inside tmux so a dropped connection does not kill the job, and use a virtual environment so the PyTorch build is pinned. Model weights come from a hub such as Hugging Face. They download into a cache directory, by default under the home folder, which is often the small disk. Point HF_HOME at the large disk before the first download. Gated models need you to accept the license on the hub and pass an access token (HF_TOKEN). A 7B model in 16-bit is about 14 GB of weights, so a full cache disk is a real failure, and K07 shows where that number comes from.

Check: a download dies at 90 percent on a rented VM that has a 500 GB data disk. What do you suspect first?
The cache is writing to the small root disk. Set HF_HOME to the data disk and retry. Confirm with df -h while it downloads.

Kata: stack_check.py

One script tests the layers bottom up and stops at the first red one, then a pure function names the cause from numbers. A real run on a GPU box also times a 4096 by 4096 fp16 matmul. The script is 66 lines and needs no packages until torch is imported.

"""K02 kata: verify the whole inference stack, layer by layer, and say which layer broke.
Run on the GPU box:  python stack_check.py
Run anywhere:        python stack_check.py --simulate
"""
import shutil, subprocess, sys, time

# Minimum Linux driver branch per CUDA toolkit family (NVIDIA CUDA Compatibility doc, minor version compatibility)
MIN_DRIVER = {11: 450, 12: 525, 13: 580}

def diagnose(driver, build_cuda, cc, arch_list):
    """Pure logic. driver='535.104.05', build_cuda='12.1', cc=(8,9), arch_list=['sm_80','sm_90']."""
    need = MIN_DRIVER.get(int(build_cuda.split(".")[0]))
    if need is None:
        return "FAIL", "unknown CUDA family " + build_cuda
    if int(driver.split(".")[0]) < need:
        return "FAIL", "driver %s < %d needed by CUDA %s build: upgrade the driver or pick an older torch build" % (driver, need, build_cuda)
    # SASS runs on the same major arch with an equal or higher minor; PTX can be JIT-compiled forward
    ok = any(a.startswith("compute_") or (a.startswith("sm_") and int(a[3]) == cc[0] and int(a[4:]) <= cc[1]) for a in arch_list)
    if arch_list and not ok:
        return "FAIL", "no kernels runnable on sm_%d%d in this build: pick a build that includes it" % cc
    return "PASS", "driver %s runs CUDA %s build on sm_%d%d" % (driver, build_cuda, *cc)

def step(n, name, status, detail):
    print("%d %-22s %-5s %s" % (n, name, status, detail)); return status != "FAIL"

def probe():
    if not shutil.which("nvidia-smi"):
        return step(1, "driver (nvidia-smi)", "FAIL", "nvidia-smi not found: no NVIDIA driver on this machine")
    q = "driver_version,name,memory.total,compute_cap"
    out = subprocess.run(["nvidia-smi", "--query-gpu=" + q, "--format=csv,noheader,nounits"], capture_output=True, text=True)
    if out.returncode:
        return step(1, "driver (nvidia-smi)", "FAIL", out.stderr.strip()[:80])
    drv, gpu, mib, cc = [x.strip() for x in out.stdout.splitlines()[0].split(",")]
    step(1, "driver (nvidia-smi)", "PASS", "driver %s" % drv)
    step(2, "gpu", "PASS", "%s, %.1f GiB, compute capability %s" % (gpu, int(mib) / 1024, cc))
    try:
        import torch
    except ImportError:
        return step(3, "torch import", "FAIL", "torch not installed: pip install from the index matching your driver")
    step(3, "torch import", "PASS", "torch %s, built for CUDA %s" % (torch.__version__, torch.version.cuda))
    if not step(4, "cuda.is_available", "PASS" if torch.cuda.is_available() else "FAIL", str(torch.cuda.is_available())):
        return False
    major, minor = (int(x) for x in cc.split("."))
    verdict, why = diagnose(drv, torch.version.cuda, (major, minor), torch.cuda.get_arch_list())
    if not step(5, "driver/build/arch", verdict, why):
        return False
    x = torch.randn(4096, 4096, device="cuda", dtype=torch.float16)
    torch.cuda.synchronize(); t = time.perf_counter()
    for _ in range(20): y = x @ x
    torch.cuda.synchronize(); dt = (time.perf_counter() - t) / 20
    tflops = 2 * 4096 ** 3 / dt / 1e12
    return step(6, "fp16 matmul 4096^2", "PASS", "%.1f TFLOPS, %.0f MiB allocated" % (tflops, torch.cuda.memory_allocated() / 2**20))

def simulate():
    print("%-44s %-5s %s" % ("scenario (driver, build, sm)", "", "diagnosis"))
    cases = [("535.104.05", "12.1", (8, 9), ["sm_80", "sm_90"], "driver 535 + cu121 on sm_89 (illustrative)"),
             ("470.57.02", "12.4", (8, 6), ["sm_80", "sm_86"], "driver 470 + cu124"),
             ("550.54.15", "13.0", (9, 0), ["sm_90"], "driver 550 + cu130"),
             ("580.65.06", "13.0", (9, 0), ["sm_90"], "driver 580 + cu130"),
             ("535.104.05", "12.1", (7, 5), ["sm_80", "sm_90"], "build lacks sm_75 (T4), illustrative")]
    for drv, cu, cc, arch, label in cases:
        v, why = diagnose(drv, cu, cc, arch); print("%-44s %-5s %s" % (label, v, why))

if __name__ == "__main__":
    if "--simulate" in sys.argv: simulate()
    else: sys.exit(0 if probe() else 1)

What to notice

  1. Step 1 fails and the script stops with exit code 1. The first red layer is the bug, so nothing above it is tested.
  2. Row 2: driver 470 fails a CUDA 12.4 build because 470 is below 525. The same driver would pass a CUDA 11 build, which needs only 450.
  3. Rows 1 and 3: driver 535 passes cu121 but driver 550 fails cu130. A newer driver number does not help across a family; the threshold is 580.
  4. Row 5: the build lists sm_80 and sm_90 and still fails on sm_75, while sm_89 passed in row 1 through the sm_80 kernels.
Break it
  1. Boundary. In simulate(), change the driver of case 2 from 470.57.02 to 525.60.13. Predict the verdict, then run. It should flip to PASS at exactly 525.
  2. Hidden GPU (needs a GPU box). Run CUDA_VISIBLE_DEVICES= python stack_check.py. Predict which step fails. Steps 1 to 3 should pass and step 4 should fail, which is the "nvidia-smi works but torch cannot see it" symptom.

Stretch. Parse the "CUDA Version" from the nvidia-smi header and add a check that it is at least torch.version.cuda. Then explain why that check is weaker than the driver-minimum check.

Interview

Question: "You are handed a fresh GPU machine. How do you make sure it can serve a model?" Say this aloud against the clock. Three levels, about 90 seconds.

1 Outcome 20 sBefore I load any model I verify the stack from the bottom up, because most setup failures are a broken version contract, not a model problem. One script checks the GPU, the driver and the PyTorch build, then runs a real matmul. If it passes, any later failure is about the model or the engine.
2 Mechanism 45 sThere are four layers to check. The GPU has a compute capability. The driver is installed on the host. The CUDA runtime ships inside the PyTorch wheel, so I do not need a system toolkit, only a driver new enough for the wheel's CUDA family: 450 for 11, 525 for 12, 580 for 13. The CUDA version in nvidia-smi is the ceiling the driver supports, not what is installed. So I run nvidia-smi, import torch, print its CUDA build, check that CUDA is available, and time an fp16 matmul to prove kernels actually run.
3 Internals and limits 25 sThe failures are a CPU-only wheel, a driver below the family minimum, a build with no kernels for the GPU's architecture, or a container started without GPU access. Minor version compatibility does not cross a major family, so a CUDA 13 build on driver 550 fails. I pin the driver, wheel and Python in an image so the box is repeatable.

Traps

Each one sounds right. Say what is wrong with it before you open it.

"nvidia-smi says CUDA 12.8, so CUDA 12.8 is installed and my PyTorch will use it."
That number is the highest CUDA version the driver supports. PyTorch uses the runtime bundled in its own wheel, shown by torch.version.cuda, and nvcc may not exist at all.
"I need to install the full CUDA toolkit on every inference box, or PyTorch cannot use the GPU."
A pip wheel bundles the runtime libraries, so only the driver must be right. The toolkit, with nvcc, is needed only to compile CUDA code, for example some extensions built from source.

Question bank

Answer aloud, then open. Grade yourself honestly.

Walk me through verifying a fresh GPU box, in order.
GPU and driver with nvidia-smi, then import torch and print the version and torch.version.cuda, then is_available(), then check driver against the family minimum and the GPU architecture against the build, then a timed fp16 matmul.
Follow-upWhich step fails if CUDA_VISIBLE_DEVICES is empty? Steps 1 to 3 pass and the availability check fails, because the device is hidden from the process.
What is the difference between the CUDA version in nvidia-smi, in nvcc, and in torch.version.cuda?
smi: the maximum the driver supports. nvcc: the toolkit compiler installed, if any. torch.version.cuda: the runtime the wheel was built with and actually uses.
The same container image works on one host and fails on another. What changed?
The host driver. The image carries the runtime, but the driver comes from the host. The second host's driver is probably below the minimum for the image's CUDA family.
Follow-upWhat does the NVIDIA container runtime do? It exposes the GPU device and the host driver libraries inside the container. From memory, verify.
What is the minimum driver for a CUDA 12 build, and what happens to a CUDA 13 build on a driver that satisfies it?
525 for CUDA 12.x. A CUDA 13 build needs 580, so on 525 to 579 it fails to initialize and is_available() is False, unless the forward-compatibility package applies.
What is compute capability, and why does a wheel care?
It is the GPU's architecture version, such as 8.0 or 9.0. A wheel carries precompiled kernels for a list of them. With no runnable kernel and no PTX, the first GPU operation fails with "no kernel image".
Follow-upWhy does an sm_80 kernel run on sm_89? Binary code runs on the same major with an equal or higher minor.
Why time a matmul instead of trusting is_available()?
is_available() only shows the driver initialized. A matmul proves the kernels load and run, uses real memory, and gives a TFLOPS baseline to compare against the spec sheet and to catch throttled clocks.

Mixed review

Three questions from earlier topics. Nobody tells you the topic in an interview.

K01: Name the layers a request passes through from the client to the GPU, and say where a driver mismatch would show up.
Client, gateway or API, inference server and engine, framework such as PyTorch, CUDA runtime, driver, GPU. A mismatch shows at the runtime to driver boundary, as a failed GPU initialization.
A03: How do you keep a long job alive on a remote box when your SSH session drops?
Run it inside tmux or screen, or start it with nohup and write logs to a file. Reattach later with tmux attach.
D01: What does an LLM produce at each generation step?
A score for every token in the vocabulary (logits). One token is chosen from that distribution, appended to the input, and the step repeats.
