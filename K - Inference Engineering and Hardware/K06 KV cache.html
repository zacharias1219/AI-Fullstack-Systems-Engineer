KV cache

Why autoregressive decoding recomputes the same past tokens without a cache, what exactly gets stored in GPU memory, and how caching trades compute for memory bandwidth.

Study path

Before you read

Guess first. A wrong guess now makes the right answer stick later.

In our 2-layer, d=16 toy model generating 64 tokens after a 16-token prompt (80 tokens total), how much faster is KV-cached generation than uncached generation?
31.52x faster (20.2 ms vs 635.3 ms), cutting total operations by 31.54x (330,240 vs 10,416,640 ops) with zero output difference (max_abs_diff = 0.00e+00).
Why does the KV cache store K and V tensors, and not Q (Query) tensors?
In causal decode, only the newest token's query q_t attends over past tokens. Past queries q_0 .. q_{t-1} are never used again to predict future tokens, so caching them wastes memory with zero reuse.
Does a KV cache make autoregressive decode O(1) constant work per token?
No. Projections become O(1) per step (one token instead of t), but attention still dots the new query against all t cached keys and sums t cached values, which is O(t) linear per step (and O(N^2) total across N generated tokens, down from O(N^3) uncached).

The core idea

An autoregressive LLM generates one token at a time, feeding the full sequence back in to predict the next token. Because of the causal attention mask, token i can only attend to tokens 0 .. i. Adding token t at the end of the sequence never changes the hidden state, Key vector k_i, or Value vector v_i of any earlier token i < t.

Without a cache, every decode step re-projects all t tokens through W_q, W_k, W_v and recomputes the entire t x t attention triangle, throwing away t - 1 rows just to keep the last one. The KV cache stores each layer's past K and V matrices in GPU HBM so each decode step computes only the single new token's q_t, k_t, v_t, appends k_t, v_t to the cache, and attends q_t against the stored history. You trade redundant FLOPs for growing GPU memory and memory bandwidth.

Memory hook

"Q asks once; K and V stay." A new token's Query asks one question and is thrown away; its Key and Value join the shelf in HBM so every future Query can read them in O(t) without re-running past tokens.

How it works

1. Why causal masking makes past K and V immutable

In a decoder-only transformer, self-attention applies a lower-triangular causal mask so position i only attends to positions 0 .. i. Therefore, every layer's residual stream vector h_i at position i is a pure function of tokens 0 .. i. When token t is appended later, no attention weight or hidden state at position i < t can change.

Because k_i = W_k h_i and v_i = W_v h_i depend only on h_i and fixed weights, they are immutable once computed. One crucial detail: models using Rotary Position Embeddings (RoPE) apply the position rotation to q_i and k_i before caching, so the cache stores post-RoPE keys alongside values. Storing raw hidden states h_i instead would force re-running W_k and W_v on all t tokens every step.

2. Inside a single cached decode step

During decode step t, the input tensor has sequence length 1 instead of t: shape [B, 1, d_model]. At each layer l, the model runs three small matrix-vector products to produce q_t, k_t, v_t, applies RoPE at offset t to q_t and k_t, and appends k_t, v_t to that layer's cache buffers K_cache[l] and V_cache[l].

Attention then computes a single row of scores softmax(q_t K_cache[l]^T / sqrt(d_head)) of length t and takes the weighted sum over V_cache[l]. The resulting vector passes through the output projection and MLP for just that one token, yielding identical logits to an uncached full-sequence pass.

Check: Why must RoPE be applied to k_t before writing it into the KV cache?
Because RoPE encodes token t's absolute position into k_t. Caching post-RoPE keys avoids re-rotating all t past keys on every decode step; forgetting the position offset t corrupts attention scores immediately.

3. Complexity derivation: why decode becomes linear

Count the operations to generate N tokens starting from a prompt of length P (ignoring constants like layer count L and hidden dimension d). At step t (where sequence length is t):

Uncached step t:
  Projections (W_q, W_k, W_v):  O(t * d^2)     -> Sum over N steps: O(N^2 * d^2)
  Self-attention (t x t pairs): O(t^2 * d)     -> Sum over N steps: O(N^3 * d)

KV-cached step t:
  Projections (1 new token):    O(d^2)         -> Sum over N steps: O(N * d^2)
  Self-attention (1 x t pairs): O(t * d)       -> Sum over N steps: O(N^2 * d)

Caching saves a full factor of t at every single decode step. Projections drop from O(t) to O(1) per token, and attention drops from O(t^2) to O(t) per token. Across a long 2,000-token response, that is a thousand-fold reduction in redundant compute.

4. Deriving the KV cache memory formula and the bandwidth wall

Every token in every active request stores two tensors (K and V) at every layer L across n_kv key-value heads of width d_head, using b bytes per element (2 bytes for FP16/BF16, 1 byte for FP8):

KV_bytes = 2 * L * n_kv * d_head * S * B * b

For a Llama-3-8B-class model (L = 32, n_kv = 8 with GQA, d_head = 128, BF16 b = 2), one token costs 2 * 32 * 8 * 128 * 2 = 131,072 bytes (128 KiB). At S = 8,192 tokens, a single request needs 1.07 GB of KV cache; a batch of 32 concurrent requests needs 34.4 GB just for KV state, on top of ~16 GB of model weights. (Full GPU memory budgeting belongs to K07; paging and fragmentation belong to K15.)

Worse, every decode step must stream the entire active KV cache plus model weights from GPU HBM into SRAM just to do two FLOPs per loaded byte (low arithmetic intensity, covered in K05). That is why Grouped-Query Attention (GQA) shrinks n_kv by 4x to 8x: it cuts both KV memory capacity and HBM decode traffic by the same factor.

Check: If you double batch size B and halve context length S at the same time, what happens to total KV cache bytes and per-step KV HBM reads?
Both stay unchanged. Because KV_bytes = 2 * L * n_kv * d_head * S * B * b is linear in the product S * B (total active tokens in flight), doubling B and halving S keeps total cached tokens constant.

Kata: Uncached vs KV-cached decoder

A 94-line pure-Python causal self-attention decoder that generates 64 tokens from a 16-token prompt both ways, verifying exact numerical parity while measuring wall-clock time, projection ops, attention ops, and KV cache bytes.

Run

python kata.py

kata.py

"""Tiny causal decoder: uncached vs KV-cached generation (pure Python)."""
import math, random, time

LAYERS, D, PROMPT, GEN = 2, 16, 16, 64
BYTES_PER_ELEM = 2          # fp16 / bf16 accounting for KV cache bytes
USE_POS = True              # Break-it 2: set False to drop decode pos offset
MAX_CACHE_BYTES = 0         # Break-it 3: set 4096 to hit a KV-cache OOM

random.seed(7)
def rand_mat(r, c): return [[random.gauss(0, 0.25) for _ in range(c)] for _ in range(r)]
def dot(a, b): return sum(x * y for x, y in zip(a, b))
def matvec(W, x): return [dot(row, x) for row in W]
def pos_vec(t): return [math.sin(t / (10.0 ** (i / D))) * 0.2 for i in range(D)]

def softmax(xs):
    m = max(xs)
    ex = [math.exp(x - m) for x in xs]
    s = sum(ex)
    return [e / s for e in ex]

WEIGHTS = [(rand_mat(D, D), rand_mat(D, D), rand_mat(D, D)) for _ in range(LAYERS)]
OPS = {"proj": 0, "attn": 0}

def attend_one(q, ks, vs):
    scale = 1.0 / math.sqrt(D)
    scores = [dot(q, k) * scale for k in ks]
    probs = softmax(scores)
    OPS["attn"] += 2 * len(ks) * D
    return [sum(p * v[j] for p, v in zip(probs, vs)) for j in range(D)]

def step_uncached(seq):
    hs = [list(x) for x in seq]
    for Wq, Wk, Wv in WEIGHTS:
        qs = [matvec(Wq, h) for h in hs]
        ks = [matvec(Wk, h) for h in hs]
        vs = [matvec(Wv, h) for h in hs]
        OPS["proj"] += 3 * len(hs) * D * D
        hs = [attend_one(qs[i], ks[: i + 1], vs[: i + 1]) for i in range(len(hs))]
    return hs[-1]

def prefill_cached(seq):
    hs = [list(x) for x in seq]
    cache = []
    for Wq, Wk, Wv in WEIGHTS:
        qs = [matvec(Wq, h) for h in hs]
        ks = [matvec(Wk, h) for h in hs]
        vs = [matvec(Wv, h) for h in hs]
        OPS["proj"] += 3 * len(hs) * D * D
        cache.append((ks, vs))
        hs = [attend_one(qs[i], ks[: i + 1], vs[: i + 1]) for i in range(len(hs))]
    return hs[-1], cache

def decode_cached(token_vec, cache):
    h = list(token_vec)
    for (Wq, Wk, Wv), (ks, vs) in zip(WEIGHTS, cache):
        q, k, v = matvec(Wq, h), matvec(Wk, h), matvec(Wv, h)
        OPS["proj"] += 3 * D * D
        ks.append(k)
        vs.append(v)
        h = attend_one(q, ks, vs)
    return h

def make_token(prev, t, with_pos=True):
    p = pos_vec(t) if with_pos else [0.0] * D
    return [math.tanh(x) + pi for x, pi in zip(prev, p)]

def run(mode):
    OPS["proj"] = OPS["attn"] = 0
    seq = [pos_vec(t) for t in range(PROMPT)]
    t0 = time.perf_counter()
    if mode == "uncached":
        out = step_uncached(seq)
        for step in range(GEN):
            seq.append(make_token(out, PROMPT + step, True))
            out = step_uncached(seq)
        cache_bytes = 0
    else:
        out, cache = prefill_cached(seq)
        for step in range(GEN):
            tok = make_token(out, PROMPT + step, USE_POS)
            out = decode_cached(tok, cache)
            cache_bytes = 2 * LAYERS * len(cache[0][0]) * D * BYTES_PER_ELEM
            if MAX_CACHE_BYTES and cache_bytes > MAX_CACHE_BYTES:
                raise MemoryError(f"KV cache OOM at token {PROMPT + step + 1}: {cache_bytes} B > {MAX_CACHE_BYTES} B")
    dt_ms = (time.perf_counter() - t0) * 1000.0
    return out, dt_ms, OPS["proj"], OPS["attn"], cache_bytes

u_out, u_ms, u_proj, u_attn, _ = run("uncached")
c_out, c_ms, c_proj, c_attn, c_bytes = run("cached")
max_diff = max(abs(a - b) for a, b in zip(u_out, c_out))
print(f"config: layers={LAYERS} d={D} prompt={PROMPT} gen={GEN} total_len={PROMPT + GEN}")
print(f"uncached: {u_ms:7.1f} ms | proj_ops={u_proj:10,d} | attn_ops={u_attn:10,d} | total_ops={u_proj + u_attn:10,d} | cache=     0 B")
print(f"cached:   {c_ms:7.1f} ms | proj_ops={c_proj:10,d} | attn_ops={c_attn:10,d} | total_ops={c_proj + c_attn:10,d} | cache={c_bytes:6,d} B")
print(f"speedup:  {u_ms / c_ms:7.2f}x | ops_ratio={(u_proj + u_attn) / (c_proj + c_attn):6.2f}x | max_abs_diff={max_diff:.2e}")

What to notice

  1. Exact parity: max_abs_diff=0.00e+00 proves the KV cache is a lossless memoization of causal attention, not an approximation.
  2. Projection ops drop 39.00x: proj_ops falls from 4,792,320 to 122,880 because each of the 80 tokens is projected through W_q, W_k, W_v once instead of being re-projected at every subsequent step.
  3. Attention ops drop 27.12x: attn_ops falls from 5,624,320 to 207,360 because cached decode computes only the final row of the causal attention matrix.
  4. Memory is the explicit price: The 31.52x speedup costs 10,240 B (2 * 2 layers * 80 tokens * 16 dims * 2 bytes = 10,240 B), which grows linearly with every new token.
Break it
  1. Double generation length (cubic vs quadratic scaling). Change GEN = 64 to GEN = 128 (total length 144). Predict how much the speedup ratio widens before running: uncached attention grows roughly as (144/80)^3 (~5.8x), while cached grows roughly as (144/80)^2 (~3.2x).
  2. Drop the decode position offset (RoPE offset bug). Set USE_POS = False. Predict what happens to max_abs_diff and runtime: runtime stays identical, but output parity breaks completely because cached decode tokens lose their sequence position.
  3. Hit a KV cache OOM mid-generation. Set MAX_CACHE_BYTES = 4096. Predict the exact token number where generation crashes before running: each token takes 2 * 2 * 16 * 2 = 128 B, so 32 tokens fit (4096 B) and token 33 triggers MemoryError.

Stretch. Add a KV_HEADS = 1 multi-query mode (4 query heads sharing 1 KV head) and verify that cache_bytes drops 4x while decode attention ops stay unchanged.

Scenario: You serve a Llama-3-8B (L=32, n_kv=8, d_h=128, BF16) clinic voice assistant on one 24 GB GPU (~16 GB weights, ~6 GB free for KV cache). Average call length grows from 2,000 to 6,000 tokens. What breaks first and how do you fix it?
  1. Compute per-token KV cost: 2 * 32 * 8 * 128 * 2 = 128 KiB/token.
  2. Calculate concurrency drop: At 2,000 tokens, one call uses ~256 MB, so 6 GB holds ~23 concurrent calls. At 6,000 tokens, one call uses ~768 MB, cutting max concurrency to ~7 calls.
  3. What breaks first: KV cache capacity saturates, causing request queueing, preemptions, or OOMs long before GPU FLOPs saturate; TPOT also rises 3x on the KV-read portion.
  4. Fix order: (1) Enable FP8 KV cache to immediately double capacity to ~15 calls; (2) enable prefix caching if all calls share a large clinic system prompt; (3) summarize older dialogue turns outside a rolling window; (4) move to a higher-VRAM/bandwidth GPU or add replicas.

Traps

Each one sounds right. Say what is wrong with it before you open it.

"KV caching makes LLM decode O(1) constant time per token."
Wrong. Linear projections drop to O(1) per token, but attention still dots q_t against all t cached keys and sums t cached values, which is O(t) linear in both FLOPs and HBM bytes read per token.
"We should cache Q, K, and V together so attention does zero recomputation."
Wrong. Past queries q_0 .. q_{t-1} are never reused during autoregressive decode; only the newest token's q_t attends to past keys. Caching Q increases HBM usage by 50% for zero benefit.
"KV cache memory is small compared to model weights, so it rarely causes OOMs."
Wrong. Model weights are fixed regardless of traffic, while KV cache scales linearly with S * B. On an 8B GQA model (~16 GB weights), 32 concurrent 8k-token requests consume 34.4 GB of KV cache, more than 2x the model weights.
"Caching raw hidden states h_i is better than caching K and V because it saves 50% memory."
Wrong for two reasons: first, with GQA (e.g. 8 KV heads vs 32 query heads), K+V combined is actually smaller than h_i (2 * 1024 = 2048 vs 4096 dims); second, caching h_i forces re-running W_k and W_v across all t tokens every decode step, destroying the projection speedup.

Question bank

Answer aloud, then open. Grade yourself honestly.

Why does causal attention allow reusing past K and V tensors, whereas bidirectional encoder attention (like BERT) cannot reuse them the same way?
In causal attention, token i only sees tokens 0 .. i, so appending token t leaves k_i, v_i unchanged. In bidirectional attention, adding a new token changes every earlier token's attention weights and hidden states, invalidating all prior K and V.
Write the exact formula for KV cache size in bytes and name every variable.
2 * L * n_kv * d_head * S * B * b: 2 for K and V, L layers, n_kv KV heads, d_head head dimension, S sequence length, B batch size, and b bytes per element.
Follow-upWhat is the KV cache size per token for Llama-3-8B (L=32, n_kv=8, d_head=128) in BF16? 2 * 32 * 8 * 128 * 2 = 131,072 bytes (128 KiB/token).
Why does KV caching change total generation complexity over N tokens from O(N^3) to O(N^2)?
Uncached attention recomputes a t x t matrix at every step t = 1..N, summing to O(N^3). Cached attention computes only the single new row of length t at each step, summing 1 + 2 + ... + N = O(N^2).
Why is KV-cached decode memory-bandwidth bound instead of compute bound on modern GPUs?
Each decode step reads the entire model weights and active KV cache from HBM to perform a tiny matrix-vector product (1 query per request), giving very low arithmetic intensity (FLOPs per byte loaded), so tensor cores sit idle waiting on HBM.
Follow-upWhat happens to arithmetic intensity as you increase batch size B? Weight-read intensity rises proportionally with B (weights are shared across requests), but KV-cache reads still scale with B because each request has its own distinct KV history.
How does Grouped-Query Attention (GQA) reduce KV cache pressure without shrinking d_model?
GQA shares one Key/Value head across a group of Query heads (e.g. 32 Q heads sharing 8 KV heads). That cuts n_kv by 4x, shrinking both KV HBM capacity and per-step KV memory reads by 4x.
Follow-upDoes GQA reduce attention FLOPs during decode? No, all 32 query heads still dot against their assigned KV head, so compute FLOPs stay the same; the speedup comes from 4x less KV memory traffic and 4x larger max batch size.
In a RoPE-based transformer, what breaks if you cache pre-RoPE keys versus post-RoPE keys without tracking position offsets?
If you cache post-RoPE keys, each key already encodes its position, so new decode tokens must be rotated by the exact current offset t; forgetting the offset causes attention scores to compare misaligned positions and corrupts generation. Caching pre-RoPE keys avoids offset coupling at write time but forces re-rotating all t keys every step.
Why does KV caching NOT speed up the prefill phase?
Prefill processes all prompt tokens at once from scratch; there is no prior KV history to reuse yet. Prefill only populates the KV cache so that subsequent decode steps can reuse it.
Follow-upWhen CAN prefill reuse a KV cache? Across requests that share an identical prompt prefix (prefix caching / RadixAttention), because causal masking means the shared prefix produces identical K and V tensors.
Suppose you double a model's context window from 4k to 8k while keeping GPU memory fixed. What happens to maximum batch size?
Maximum batch size drops roughly in half (for the KV-bound portion of VRAM), because KV memory is proportional to S * B.
What is the tradeoff of quantizing the KV cache from BF16 to FP8?
You cut KV cache HBM footprint and KV bandwidth traffic by 2x (doubling max concurrency or context length), at the cost of minor quantization noise in attention scores and dequantization logic in the attention kernel.
Follow-upWhich is usually more sensitive to aggressive quantization: K or V? Keys are often more sensitive because errors in K get amplified exponentially through softmax, especially when attention outlier channels exist.
Why do naive contiguous KV cache allocations waste huge amounts of GPU memory even before requests finish?
Because output length is unknown upfront, naive engines pre-allocate a contiguous buffer for max_model_len per request, leaving most of it unused (internal fragmentation). PagedAttention (K15) fixes this by allocating KV cache in small non-contiguous blocks on demand.

Mixed review

Three questions from earlier topics. Nobody tells you the topic in an interview.

K05: Why is prefill compute-bound while decode is memory-bandwidth-bound on the same GPU?
Prefill processes all prompt tokens in parallel as large matrix-matrix multiplications (high arithmetic intensity, saturating tensor cores). Decode processes 1 token per request as matrix-vector products (low arithmetic intensity), spending most of its time streaming weights and KV cache from HBM.
K04: Trace one token end to end from raw text to the next sampled token ID.
Tokenizer splits text into IDs -> embedding table lookup -> L transformer blocks (RMSNorm, self-attention with residual, RMSNorm, MLP with residual) -> final norm -> LM head projection to vocab logits -> softmax + sampling (temperature/top-p) picks next token ID.
A09: If Q has shape [B, H, 1, d_h] and cached K has shape [B, H, S, d_h], what is the output shape of Q @ K^T?
[B, H, 1, S]: the last two dimensions multiply (1, d_h) @ (d_h, S) -> (1, S), producing one attention score per cached key position for each head and batch item.

Short notes

Quick-memorization cheat sheet covering every subtopic on this page and the key facts to remember cold.

All subtopics on this page

  • What is cached: Per-layer past K (post-RoPE) and V tensors in GPU HBM; never past Q (only q_t is needed) and never raw hidden states.
  • Why reuse is exact: Causal masking means token i's k_i and v_i depend only on tokens 0..i, giving 0.00e+00 numerical drift when position offsets match.
  • Why decode becomes linear: Caching cuts projections from O(t) to O(1) and attention from O(t^2) to O(t) per step (O(N^3) to O(N^2) total over N tokens; 31.52x speedup in our 80-token kata).
  • Memory and bandwidth bill: KV_bytes = 2 * L * n_kv * d_head * S * B * b; every decode step streams the whole active cache from HBM, making decode bandwidth-bound and batch-capped.
  • Production failure modes and levers: Watch for KV OOMs, TPOT scaling with context length, and RoPE offset bugs; mitigate with GQA, FP8 KV quantization, prefix caching, and PagedAttention (K15).
Important things to remember
  • Memory hook: "Q asks once; K and V stay."
  • Exact KV formula: 2 * L * n_kv * d_head * S * B * b.
  • Anchor number: Llama-3-8B (32 layers, 8 KV heads, d_h=128, BF16) = 128 KiB/token (~1.07 GB at 8k context).
  • Complexity trap: KV-cached decode is O(t) linear per token, NOT O(1), because q_t still attends over all t cached keys.
  • Interview rule of thumb: Always pair the compute win (O(t^2) -> O(t)) with the HBM bill (capacity caps batch size, bandwidth caps TPOT).
