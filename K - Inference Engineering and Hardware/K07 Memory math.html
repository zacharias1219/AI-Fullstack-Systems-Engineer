Memory math

How to calculate exact GPU VRAM usage across model weights, CUDA runtime and prefill activations, and KV cache per token to predict maximum context length and concurrency before deployment.

Study path

Before you read

Guess first. A wrong guess now makes the right answer stick later.

You deploy Llama-3-8B (8.03B parameters) in BF16 on a single 24 GB L4 GPU. Model weights take 16.06 GB and runtime/activation overhead takes 1.74 GB. At an 8,192-token context window, how many concurrent requests fit before CUDA OOM?
Only 5 concurrent requests (B_max = 5). Subtracting 16.06 + 1.74 = 17.80 GB from 24 GB leaves just 6.20 GB of KV headroom. Because each 8,192-token request consumes 1.074 GB of BF16 KV cache (131,072 B/token), a batch of 8 needs 8.59 GB of KV cache (26.39 GB total) and crashes with OOM.
Why does quantizing Llama-3-8B weights from BF16 (2 B) to INT4 (0.5 B) plus KV cache from BF16 to FP8 (1 B) raise max 8k concurrency on a 24 GB GPU from 5 to 33 (a 6.6x jump instead of 2x or 4x)?
Because KV headroom depends on the difference VRAM - (W + Ovh), not a simple ratio. Shrinking weights from 16.06 GB to 4.01 GB expands free KV headroom nearly 3x (from 6.20 GB to 18.25 GB), and halving KV bytes per token from 128 KiB to 64 KiB doubles the tokens that fit inside each free gigabyte (3x * 2x = ~6.6x).
If you only ever serve batch size B = 1 at a tiny 512-token context, why does a 7B BF16 model (~14 GB weights) still crash with OOM on a 16 GB GPU during prefill of a long prompt?
Two non-weight, non-KV consumers eat the remaining 2 GB: the CUDA runtime context (cuBLAS/cuDNN workspaces, driver, allocator fragmentation: ~1.0 to 1.5 GB) and the transient prefill activation buffer (intermediate QKV and MLP gate/up tensors proportional to prefill chunk tokens), which spikes before being freed.

The core idea

Every byte of GPU High Bandwidth Memory (HBM) during LLM inference goes into one of three buckets: static model weights, runtime and transient activation overhead, and the dynamic KV cache. Engineers who only check whether model weights are smaller than GPU capacity get surprised in production when a 16 GB model crashes a 24 GB card under moderate traffic. Weights are the entry fee; the remaining headroom after weights and runtime overhead is the entire budget for serving concurrent tokens.

Once weights and runtime buffers are allocated at startup, your serving capacity reduces to a single hardware limit: total active tokens in flight (S * B). Every active request holds S tokens of KV state across all layers. Whether you run one 32,768-token document analysis job or sixteen 2,048-token clinic voice calls, both consume the exact same 32,768-token KV pool. Memory math lets you compute on the back of an envelope whether a checkpoint fits, where the prefill activation spike peaks, and the exact context-versus-concurrency boundary.

Memory hook

"W-O-K fills the pot: Weights static, Overhead fixed, KV scales with S times B." First subtract W + O from GPU VRAM to find your usable KV pot, then divide that pot by kv_per_token to get your hard ceiling on total active tokens S * B.

How it works

1. The master VRAM budget equation

To know whether a model deployment fits on one or more GPUs, write total HBM consumption M_total as the sum of four physical allocations:

M_total = M_weights + M_runtime + M_act(T_prefill) + M_kv(S, B)   <=   N_gpu * VRAM_per_gpu

Here M_weights is static checkpoint storage, M_runtime is the CUDA driver and kernel workspace reservation, M_act(T_prefill) is the peak working activation scratchpad for a prefill batch of T_prefill tokens, and M_kv(S, B) is the KV cache holding B active sequences of length S. Notice the separation of timescales: the first two terms are allocated at process boot; the third spikes briefly on each forward pass; the fourth lives across the entire multi-second lifespan of every active request.

2. Model weights and quantization overhead

A transformer with P parameters stored at b_w bytes per parameter occupies M_weights = P * b_w bytes. In FP32 (b_w = 4), 1 billion parameters take 4 GB. Standard serving uses BF16 or FP16 (b_w = 2), giving the universal rule of thumb: 2 GB per billion parameters (so an 8B model takes ~16 GB and a 70B model takes ~140 GB).

Weight-only quantization reduces b_w to 1 byte (FP8/INT8, ~1 GB per billion parameters) or 0.5 bytes (INT4/AWQ/GPTQ, ~0.5 GB per billion parameters). In practice, group-wise quantization (such as group size 128) stores one FP16 scale and zero-point per 128 weights, adding roughly 0.03 to 0.05 bytes per parameter (~6% to 10% overhead on top of raw INT4). Always keep unquantized norms and embeddings in mind when capacity is tight.

3. Runtime overhead and the prefill activation spike

Even with zero requests in flight, PyTorch and the CUDA runtime claim 1.0 to 2.0 GB per GPU for the CUDA context, cuBLAS handle workspaces, compiled FlashAttention kernels, and NCCL communication ring buffers (when running Tensor Parallelism across multiple GPUs). Inference servers like vLLM also configure a safety margin (gpu_memory_utilization = 0.90 by default, reserving 10% of total VRAM).

During a forward pass, the engine only needs to hold intermediate activations for one transformer layer at a time because layer l + 1 overwrites layer l's scratchpad (unlike training, which stores all L layers for backpropagation). With FlashAttention, attention never materializes the quadratic S x S score matrix in HBM; instead, peak activation memory comes from the single-layer QKV and SwiGLU MLP buffers (gate_proj, up_proj, intermediate activation) across the T_prefill tokens processed in one prefill chunk:

M_act_layer ~= T_prefill * (4 * d_model + 3 * d_ff) * b_act

For Llama-3-8B (d_model = 4096, d_ff = 14336, BF16 b_act = 2) with chunked prefill capping T_prefill = 2048 tokens, peak layer scratchpad is only 2048 * (16384 + 43008) * 2 ~= 0.24 GB. Without chunked prefill, feeding a 65,536-token prompt all at once spikes that single layer scratchpad to ~7.78 GB (plus vocabulary logit buffers if all prompt logits are materialized), crashing a GPU that appeared to have plenty of KV space.

Check: Why does inference activation memory scale with the dimensions of a single layer rather than multiplying by all L layers like training does?
Inference runs a forward pass only with torch.no_grad(). Once layer l finishes computing its output residual vector (and writes its K, V slices into the persistent KV cache), its temporary Q, MLP gate, and MLP up activation buffers are immediately reused by layer l + 1.

4. KV cache per token: GQA vs MHA

From K06, each token stores two vectors (Key and Value) at every layer L across n_kv key-value heads of dimension d_head at precision b_kv bytes:

kv_per_token = 2 * L * n_kv * d_head * b_kv
M_kv(S, B)   = (kv_per_token * S * B) / eff_frag

Here eff_frag is your memory allocation efficiency: nearly 0.96 to 1.00 with PagedAttention (K15), but only 0.40 to 0.65 with naive contiguous pre-allocation. Notice how Grouped-Query Attention (GQA) dominates the per-token cost: Llama-3-8B has 32 query heads but only n_kv = 8 KV heads of width d_head = 128 across L = 32 layers. In BF16 (b_kv = 2), that is 2 * 32 * 8 * 128 * 2 = 131,072 B (128 KiB/token). An older MHA 7B model like Llama-2-7B (n_kv = 32) costs 512 KiB/token, 4x larger. Llama-3-70B (L = 80, n_kv = 8, d_head = 128) costs 2 * 80 * 8 * 128 * 2 = 327,680 B (320 KiB/token) in BF16, or 160 KiB/token with FP8 KV cache.

5. Deriving context and concurrency limits

Once you subtract weights and runtime/activation overhead from usable GPU VRAM, the remaining memory is your KV cache budget M_kv_budget:

M_kv_budget  = VRAM_usable - (M_weights + M_runtime + M_act)
Tokens_max   = floor( (M_kv_budget * eff_frag) / kv_per_token )
B_max(at S)  = floor( Tokens_max / S )
S_max(at B)  = floor( Tokens_max / B )

This equation governs capacity planning. Your GPU holds a fixed pool of Tokens_max token slots. Context length S and concurrency B trade off along a hyperbola S * B <= Tokens_max: doubling average conversation length cuts maximum concurrency in half. Even more important is the leverage effect of weight quantization: when weights consume 70% of VRAM (like 16.06 GB on a 24 GB GPU), cutting weights by 4x (to 4.01 GB) does not just add a small buffer. It triples M_kv_budget from 6.20 GB to 18.25 GB, multiplying Tokens_max by nearly 3x before you even touch KV precision.

Check: On a 24 GB GPU with 17.80 GB consumed by weights and overhead (6.20 GB left for KV cache), how many total active tokens can exist across all requests if kv_per_token is 131,072 bytes?
floor(6,200,000,000 / 131,072) = 47,301 tokens total across all concurrent sequences. That single token pool can be sliced into B = 1 request of 47,301 tokens, B = 5 requests of 8,192 tokens, or B = 23 requests of 2,048 tokens.

Kata: Will-it-fit VRAM calculator and buffer verifier

A 71-line Python script that empirically allocates a real layer KV byte buffer to verify exact byte parity against the formula, then computes weights, runtime + prefill activation overhead, KV cache GB, max concurrency B_max, and max context S_max across six production Llama-3-8B and 70B scenarios.

"""Will-it-fit GPU VRAM calculator & buffer allocator for LLM inference."""
import array

MODELS = {
    "Llama-3-8B":  dict(P=8.03e9,  L=32, n_q=32, n_kv=8, d_h=128, d_ff=14336),
    "Llama-3-70B": dict(P=70.6e9,  L=80, n_q=64, n_kv=8, d_h=128, d_ff=28672),
}
RUNTIME_GB = 1.50           # CUDA context, kernels, NCCL/allocator reserve
FRAG_EFF = 1.00             # Break-it 2: set 0.65 for naive contiguous KV fragmentation
MHA_OVERRIDE = False        # Break-it 1: set True to force MHA (n_kv = n_q)
PREFILL_CHUNK = 2048        # Break-it 3: set 32768 to trigger prefill activation OOM

def kv_per_token_bytes(m, b_kv=2):
    n_kv = m["n_q"] if MHA_OVERRIDE else m["n_kv"]
    return 2 * m["L"] * n_kv * m["d_h"] * b_kv

def activation_gb(m, tokens=PREFILL_CHUNK, b_act=2):
    d_model = m["n_q"] * m["d_h"]
    # Peak single-layer scratchpad: QKV + MLP gate/up/act buffers during prefill chunk
    elems = tokens * (4 * d_model + 3 * m["d_ff"])
    return (elems * b_act) / 1e9

def vram_report(model_name, b_w, b_kv, vram_gb, S, B):
    m = MODELS[model_name]
    w_gb = (m["P"] * b_w) / 1e9
    act_gb = activation_gb(m)
    ovh_gb = RUNTIME_GB + act_gb
    kv_tok = kv_per_token_bytes(m, b_kv)
    kv_gb = (kv_tok * S * B) / (1e9 * FRAG_EFF)
    tot_gb = w_gb + ovh_gb + kv_gb
    headroom = vram_gb - (w_gb + ovh_gb)
    if headroom <= 0:
        b_max, s_max = 0, 0
    else:
        max_tokens = int((headroom * 1e9 * FRAG_EFF) // kv_tok)
        b_max = max_tokens // S
        s_max = max_tokens // B
    status = "FIT" if tot_gb <= vram_gb else "OOM"
    return w_gb, ovh_gb, kv_tok, kv_gb, tot_gb, b_max, s_max, status

def verify_layer_buffer(m, S, B, b_kv=2):
    """Allocate 1 layer of actual byte buffers to verify exact byte math."""
    n_kv = m["n_q"] if MHA_OVERRIDE else m["n_kv"]
    elems_per_layer = 2 * n_kv * m["d_h"] * S * B
    buf = array.array("h" if b_kv == 2 else "b", [0]) * elems_per_layer
    measured_layer_b = buf.buffer_info()[1] * buf.itemsize
    return measured_layer_b * m["L"]

print("=== 1. Empirical Buffer Allocation Check (Llama-3-8B, BF16, S=2048, B=4) ===")
m8 = MODELS["Llama-3-8B"]
formula_b = kv_per_token_bytes(m8, 2) * 2048 * 4
measured_b = verify_layer_buffer(m8, 2048, 4, 2)
print(f"kv_per_token = {kv_per_token_bytes(m8, 2):,d} B ({kv_per_token_bytes(m8, 2)//1024} KiB/tok)")
print(f"formula_kv   = {formula_b:,d} B ({formula_b/1e9:.3f} GB) | measured_kv = {measured_b:,d} B | diff = {abs(formula_b - measured_b)} B\n")

print("=== 2. Will-It-Fit Scenarios (VRAM Breakdown & Concurrency Limits) ===")
hdr = f"{'Scenario':<26} | {'GPU':>5} | {'W(GB)':>6} | {'Ovh':>5} | {'KV/tok':>7} | {'KV(GB)':>6} | {'Total':>6} | {'B_max':>5} | {'S_max':>7} | {'Verdict'}"
print(hdr)
print("-" * len(hdr))
cases = [
    ("8B BF16  (S=4096, B=8)",   "Llama-3-8B",  2.0, 2, 24.0, 4096, 8),
    ("8B BF16  (S=8192, B=8)",   "Llama-3-8B",  2.0, 2, 24.0, 8192, 8),
    ("8B INT4w/FP8kv (S=8k,B=8)","Llama-3-8B",  0.5, 1, 24.0, 8192, 8),
    ("70B BF16 (S=4096, B=1)",   "Llama-3-70B", 2.0, 2, 80.0, 4096, 1),
    ("70B INT4w/BF16kv(S=8k,B=8)","Llama-3-70B",0.5, 2, 80.0, 8192, 8),
    ("70B INT4w/FP8kv (S=8k,B=16)","Llama-3-70B",0.5,1, 80.0, 8192, 16),
]
for label, name, bw, bkv, gpu, s, b in cases:

  3. The 6.6x quantization leverage on 24 GB: Dropping 8B weights to INT4 (4.01 GB) expands the free KV pool from 6.20 GB to 18.25 GB (2.94x), and FP8 KV halves per-token cost from 128 KiB to 64 KiB (2x), lifting B_max at 8k from 5 to 33 (and single-stream S_max at B = 8 from 5,909 to 34,793 tokens).

Scenario: You need to serve Llama-3-70B (P=70.6B, L=80, n_kv=8, d_head=128) for an enterprise RAG pipeline with S = 16,384 tokens per request and a target concurrency of B = 16 active requests. You have two hardware options: (A) 1x H100 80 GB with AWQ INT4 weights, or (B) 2x H100 80 GB (160 GB total) with FP8 weights. Walk through the exact memory math for both and pick the configuration that meets the SLA.
  1. Calculate total active tokens and KV cost: S * B = 16,384 * 16 = 262,144 tokens. For Llama-3-70B, BF16 KV costs 2 * 80 * 8 * 128 * 2 = 327,680 B (320 KiB/tok), so 262,144 tokens need 85.90 GB of KV cache. With FP8 KV (b_kv = 1, 160 KiB/tok), 262,144 tokens need 42.95 GB of KV cache.
  2. Evaluate Option A (1x 80 GB H100, INT4 weights): INT4 weights take 70.6B * 0.5 B = 35.30 GB (plus ~2 GB group scales and ~2 GB runtime/activation overhead = ~39.3 GB non-KV base). Leftover KV headroom on one 80 GB card is 80 - 39.3 = 40.7 GB. Even with FP8 KV (42.95 GB needed), Option A falls short (B_max = 15 at zero safety margin, or ~12 at 90% GPU memory utilization).
  3. Evaluate Option B (2x 80 GB H100 = 160 GB, FP8 weights): FP8 weights take 70.6B * 1.0 B = 70.60 GB total (35.30 GB/GPU), plus 2 * 2.0 GB = 4.0 GB runtime/activation overhead across both GPUs = 74.60 GB base. Leftover KV headroom is 160 - 74.60 = 85.40 GB (or 69.40 GB at 90% utilization).
  4. Decision: Pick Option B (2x H100 80 GB with FP8 weights + FP8 KV cache). It uses 74.60 + 42.95 = 117.55 GB out of 160 GB (73.5% utilization), avoids INT4 accuracy loss on enterprise RAG, and leaves ~26 GB of extra KV headroom for traffic bursts plus 2x the HBM bandwidth.

Traps

Each one sounds right. Say what is wrong with it before you open it.

"A 7B BF16 model takes 14 GB, so on a 24 GB GPU you have 10 GB available for the KV cache."
Wrong. You must subtract the 1.5 to 2.0 GB CUDA runtime, cuBLAS workspace, and prefill activation scratchpad first, plus the serving engine's safety margin (e.g. vLLM's 90% utilization cap, which holds back 2.4 GB). Real usable KV space on a 24 GB card with 14 to 16 GB weights is only 4 to 6.5 GB.
"Quantizing model weights from BF16 to INT4 (4x smaller) increases maximum batch size by at most 4x."
Wrong. Max batch size is proportional to leftover KV headroom VRAM - (W + Ovh), not total VRAM. If weights took 20 GB on a 24 GB card (leaving 2 GB for KV after 2 GB overhead), cutting weights 4x to 5 GB expands KV headroom from 2 GB to 17 GB (an 8.5x increase in max batch size).
"During inference, activation memory scales with the number of layers L just like weights and KV cache do."
Wrong. Weights and KV cache persist across all L layers simultaneously, so both multiply by L. Inference activations are transient and overwritten layer by layer during the forward pass, so peak activation scratchpad scales with a single layer's width times the prefill chunk token count.
"Llama-3-70B has 8.75x more parameters than Llama-3-8B, so its KV cache per token is also 8.75x larger."
Wrong. KV cache per token depends only on 2 * L * n_kv * d_head * b_kv, ignoring MLP width and query head count. Both Llama-3-8B and 70B use n_kv = 8 and d_head = 128; only L grows from 32 to 80 (2.5x), so KV per token grows just 2.5x (from 128 KiB to 320 KiB in BF16).

State the full GPU memory budget equation for LLM inference and explain what determines each term.
M_total = M_weights + M_runtime + M_act + M_kv. M_weights = P * b_w depends on parameter count and weight precision; M_runtime (~1 to 2 GB) is fixed per GPU for CUDA kernels and workspaces; M_act scales with prefill chunk tokens and single-layer hidden/MLP width; M_kv = 2 * L * n_kv * d_head * S * B * b_kv / eff_frag scales linearly with active tokens S * B.
Calculate the BF16 KV cache size per token for Llama-3-8B (L=32, n_q=32, n_kv=8, d_head=128) and Llama-3-70B (L=80, n_q=64, n_kv=8, d_head=128).
Llama-3-8B: 2 * 32 * 8 * 128 * 2 = 131,072 B (128 KiB/token). Llama-3-70B: 2 * 80 * 8 * 128 * 2 = 327,680 B (320 KiB/token). Notice n_q is not in the formula.
Follow-upWhy is 70B's KV per token only 2.5x larger than 8B's when its weight footprint is 8.75x larger? Because 70B keeps n_kv = 8 and d_head = 128 identical to 8B (using an 8:1 GQA ratio instead of 4:1), so only the layer ratio 80 / 32 = 2.5x increases KV size.
Why does vLLM profile a dummy forward pass at startup before allocating the KV cache block pool?
Because exact PyTorch activation buffers, custom CUDA workspaces, and NCCL buffers are hard to predict analytically. vLLM loads weights, runs a synthetic prefill batch at max_num_batched_tokens to measure real peak non-KV memory, and assigns all remaining VRAM (up to gpu_memory_utilization) to fixed-size KV blocks.
How does chunked prefill prevent activation OOMs on long-context requests?
Instead of prefilling a 32k or 64k prompt in one giant forward pass (which allocates multi-gigabyte intermediate QKV and MLP buffers for all 64k tokens at once), chunked prefill splits the prompt into fixed chunks (e.g. 2,048 tokens), bounding peak activation memory to a constant ~0.24 GB.
Follow-upWhat other tensor can cause a sudden multi-gigabyte spike at the end of an unchunked prefill pass? The final LM head vocabulary logits tensor: for 64k tokens and a 128,256-token vocabulary in FP32, materializing all prompt logits takes 65,536 * 128,256 * 4 B = 33.6 GB! Engines must slice the hidden state to the last token before the LM head unless prompt logprobs are explicitly requested.
Why do INT4 quantized models (like AWQ or GPTQ with group size 128) use slightly more than 0.5 bytes per parameter in VRAM?
Each group of 128 INT4 weights stores a 16-bit scale and a zero-point (~4 bytes per 128 weights = 0.03125 B/param), and embedding/LM-head/norm layers are often kept in FP16, bringing effective weight bytes to roughly 0.55 to 0.58 B/param.
Suppose you double Tensor Parallelism from TP=1 (one 80 GB GPU) to TP=2 (two 80 GB GPUs) for a 35 GB INT4 70B model. By what factor does your KV cache capacity increase?
On 1x 80 GB GPU, after 35.3 GB weights and ~2 GB overhead, KV headroom is 42.7 GB. On 2x 80 GB GPUs (160 GB total), weights still total 35.3 GB (17.65 GB/GPU) and overhead is ~4 GB (2 GB/GPU), leaving 120.7 GB for KV cache: a 2.83x increase in KV capacity from doubling GPUs.
Follow-upWhat happens to per-GPU KV cache per token under TP=2? Because TP shards the n_kv = 8 KV heads across the 2 GPUs (4 KV heads per GPU), each GPU stores half the KV bytes per token (160 KiB/token instead of 320 KiB/token).
What is the difference between internal fragmentation and external fragmentation in KV cache allocation?
Internal fragmentation wastes reserved slots inside a request's pre-allocated contiguous buffer (e.g. reserving 8,192 tokens when the user stops at 600). External fragmentation leaves unusable gaps between different requests' contiguous buffers in HBM. PagedAttention (K15) eliminates external fragmentation and bounds internal fragmentation to at most one block (e.g. 16 tokens) per request.
You have 12 GB of usable KV pool and a model with kv_per_token = 128 KiB. If your product manager doubles average prompt + output length from 3,000 to 6,000 tokens, how does max concurrency change?
Total token slots are fixed at 12,000,000,000 / 131,072 = 91,552 tokens. At S = 3,000, B_max = floor(91,552 / 3,000) = 30 concurrent requests. At S = 6,000, B_max = floor(91,552 / 6,000) = 15 concurrent requests (halved).
When can Tensor Parallelism duplicate KV cache heads across GPUs instead of splitting them cleanly?
When tp_size > n_kv. For example, Llama-3-8B and 70B have n_kv = 8 KV heads; if you run TP=16 across two 8-GPU nodes, each KV head must be replicated across 2 GPUs so that local query heads can attend without cross-GPU KV transfers, doubling total KV memory across the cluster.

Mixed review

Three questions from earlier topics. Nobody tells you the topic in an interview.

K06: Why does a KV cache store post-RoPE Keys and Values, and never Queries?
In causal decode, only the newest token's query q_t attends over past history, so past queries are never reused. Keys are cached post-RoPE so their absolute sequence positions are baked in once rather than re-rotated on every decode step.
K05: What is arithmetic intensity, and why does it explain the difference between prefill and decode hardware utilization?
Arithmetic intensity is FLOPs executed per byte transferred from HBM. Prefill batches hundreds of prompt tokens into dense matrix-matrix multiplies with high FLOPs/byte (compute-bound), whereas decode runs matrix-vector multiplies for 1 token per sequence with ~1 to 2 FLOPs/byte (HBM bandwidth-bound).
A09: Why do we divide Q @ K^T by sqrt(d_head) before applying softmax?
If components of q and k have zero mean and unit variance, their dot product has variance d_head. Dividing by sqrt(d_head) restores unit variance so large dot products do not push softmax into flat saturation regions with vanishing gradients or peaked one-hot attention.

Short notes

Quick-memorization cheat sheet covering every subtopic on this page and the key facts to remember cold.

All subtopics on this page

  • Four-part VRAM budget: M_total = M_weights + M_runtime + M_act(T_prefill) + M_kv(S, B); static weights and fixed overhead are paid first, leaving the residual pool for KV tokens.
  • Model weights math: M_weights = P * b_w (2.0 GB/1B in BF16, 1.0 GB/1B in FP8/INT8, 0.5 GB/1B in INT4 plus ~6% to 10% group-scale overhead).
  • Runtime and activation overhead: CUDA context/workspaces take ~1.0 to 2.0 GB per GPU; inference activations only hold 1 layer at a time (~0.24 GB for a 2,048-token prefill chunk on 8B, but ~3.89 to 7.78 GB if 32k to 64k prompts run unchunked).
  • KV cache per token: kv_per_token = 2 * L * n_kv * d_head * b_kv; Llama-3-8B BF16 = 128 KiB/tok, Llama-3-70B BF16 = 320 KiB/tok (only 2.5x larger because both use n_kv = 8), and Llama-2-7B MHA = 512 KiB/tok.
  • Context and concurrency limits: Tokens_max = floor((VRAM - W - Ovh) * eff_frag / kv_per_token), giving B_max = floor(Tokens_max / S) and S_max = floor(Tokens_max / B); weight quantization multiplies Tokens_max non-linearly when weights dominate VRAM.
Important things to remember
  • Memory hook: "W-O-K fills the pot: Weights static, Overhead fixed, KV scales with S times B."
  • Anchor calculation (8B BF16 on 24 GB): 16.06 GB weights + 1.74 GB overhead = 17.80 GB base -> 6.20 GB KV pool -> 47,301 max tokens -> B_max = 5 at 8k context (OOM at B=8).
  • Quantization leverage (8B INT4w + FP8kv on 24 GB): 4.01 GB weights + 1.74 GB overhead -> 18.25 GB KV pool at 64 KiB/tok -> B_max = 33 at 8k context (6.6x gain).
  • Three OOM signatures: Startup crash = weights + runtime > VRAM; single long-prompt crash = unchunked prefill activation/logit spike; high-traffic crash/preemption = S * B exceeding KV block pool.
