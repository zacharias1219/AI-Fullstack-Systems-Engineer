Inference metrics

How to measure and decompose streaming LLM performance into TTFT, ITL, TPOT, end-to-end latency, and per-user versus system throughput without getting fooled by averages.

Study path

Before you read

Guess first. A wrong guess now makes the right answer stick later.

A request has TTFT = 8.00 ms and generates N_out = 128 tokens at a mean TPOT = 8.68 ms. Why is End-to-End (E2E) latency 1,110.41 ms instead of 8.00 + 128 * 8.68 = 1,119.04 ms?
Because the first output token is already emitted at TTFT. Only N_out - 1 = 127 decode steps follow the first token, so E2E = TTFT + (N_out - 1) * TPOT = 8.00 + 127 * 8.68 = 1,110.41 ms. Forgetting the - 1 double-counts the first token.
In our kata, 8 active chat streams are joined by two 4,096-token RAG prompts. Mean TPOT barely shifts from 10.16 ms to 12.06 ms (+18.7%), yet users complain the stream freezes mid-sentence. Which metric caught the freeze, and how big was it?
p99 Inter-Token Latency (ITL) jumped 13.4x from 10.31 ms to 138.13 ms. An unchunked 4,096-token prefill monopolizes the GPU for 128 ms mid-generation; averaged across 127 decode steps it adds only ~1.9 ms to mean TPOT, hiding the stall.
When batch concurrency B rises from 1 to 8 in steady chat decode, does token throughput go up or down?
Both, depending on which throughput you name: per-user decode speed drops 14.6% (from 115.20 tok/s to 98.39 tok/s as TPOT rises from 8.68 ms to 10.16 ms), while total system throughput jumps 6.7x (from 115.27 tok/s to 771.81 tok/s). Saying "throughput" without specifying per-user or system-wide is an interview red flag.

The core idea

A traditional REST endpoint returns one payload at the end, so a single latency distribution (p50, p99 response time) describes user experience. A streaming LLM request is fundamentally different: it has a compute-bound startup phase that processes the entire prompt before emitting a single syllable, followed by a memory-bandwidth-bound loop that emits one token at a time over seconds. A request with a 2-second total duration can feel instantaneous if the first token arrives in 40 ms and tokens stream at 90 tok/s, or sluggish if the user stares at a blank spinner for 1.8 seconds before 128 tokens dump all at once.

To engineer or benchmark an inference service, you must track five distinct metrics across two axes. Along the single-stream time axis, you separate initial responsiveness (TTFT: Time To First Token), individual step smoothness (ITL: Inter-Token Latency for each step), average generation cadence (TPOT: Time Per Output Token, the mean of ITLs), and total completion time (E2E: End-to-End latency). Across the system capacity axis, you separate what one user feels (1000 / TPOT tok/s) from what the GPU fleet delivers across all concurrent requests (system output tok/s and completed req/s).

Memory hook

"FTD-ET: First-token, Token-gap, Decode-mean, End-to-end, Throughput." Rebuild the exact timeline identity from left to right: TTFT emits token 1, N_out - 1 individual ITL gaps average to TPOT, their sum is E2E = TTFT + (N_out - 1) * TPOT, and 1000 / TPOT is per-user tok/s while sum(N_out) / wall_time is system tok/s.

How it works

1. Time To First Token (TTFT): queue plus prefill

Time To First Token (TTFT) is the elapsed wall time from the moment the client sends the request (t_0) to the moment the client receives the first streamed token chunk (t_1). Inside the server, TTFT decomposes into four terms: network round-trip time, scheduler queue wait time while current GPU batches finish, optional KV prefix-cache lookup, and the parallel forward pass over all N_in prompt tokens (which also produces the first output token's logits).

TTFT = t_1 - t_0 = T_net + T_queue(B) + T_prefill(N_in)

Because prefill is compute-bound (matrix-matrix multiplications over N_in tokens), T_prefill scales linearly with uncached prompt length N_in at short contexts and quadratically O(N_in^2) once attention dominates at long contexts (32k+ tokens). Under heavy traffic, T_queue dominates TTFT: a 256-token prompt that takes 8 ms of GPU compute can suffer a 400 ms TTFT if queued behind a batch of long RAG prompts.

2. ITL vs TPOT: why averages hide generation stalls

After token 1 arrives at t_1, the model generates tokens 2 .. N_out one step at a time. The wall-clock gap between consecutive tokens k and k + 1 is the Inter-Token Latency (ITL_k = t_{k+1} - t_k for k = 1 .. N_out - 1). The request's Time Per Output Token (TPOT) is the mean of those N_out - 1 gaps:

ITL_k = t_{k+1} - t_k     (for k = 1 .. N_out - 1)
TPOT  = (t_{N_out} - t_1) / (N_out - 1) = (1 / (N_out - 1)) * sum_{k=1}^{N_out-1} ITL_k

Notice the difference: TPOT is one average per request, whereas ITL is a distribution of every step gap across all tokens. Human reading speed is roughly 4 to 6 words per second (5 to 8 tok/s, or ~125 to 200 ms/tok), and voice AI pipelines need smooth audio frames every 20 to 40 ms. If 126 decode steps take 10 ms each and one step stalls for 138 ms while the scheduler prefills a new request, mean TPOT is a healthy 11.0 ms (90.8 tok/s), yet p99 ITL is 138 ms - a visible UI stutter or an audible voice glitch.

Check: Why do we divide by (N_out - 1) instead of N_out when computing exact TPOT from (E2E - TTFT)?
Because token 1 is generated at the end of the prefill pass and its latency is already counted inside TTFT = t_1 - t_0. The remaining time window E2E - TTFT = t_{N_out} - t_1 contains exactly N_out - 1 decode steps (tokens 2 .. N_out). Some benchmark tools approximate TPOT as (E2E - TTFT) / N_out; for short outputs like N_out = 5, that off-by-one error understates true per-step decode latency by 20%.

3. End-to-End latency (E2E) and dominant regimes

End-to-End latency (E2E), also called Request Latency or Time To Last Token (TTLT), is the total time from request submission to final token delivery: E2E = t_{N_out} - t_0. Substituting the definition of TPOT yields the fundamental streaming latency identity:

E2E = TTFT + (N_out - 1) * TPOT

This equation immediately tells you which optimization moves the needle for a given workload. For a classification or router call with N_in = 4,000 and N_out = 1, (N_out - 1) = 0, so E2E = TTFT: only prompt caching, chunked prefill, or higher FLOP/s reduces latency. For a reasoning or code-generation call with N_in = 256 and N_out = 1,024, decode accounts for over 99% of E2E, so only HBM memory bandwidth, weight quantization, or speculative decoding reduces latency.

4. Per-user decode speed vs system throughput and goodput

Throughput is measured in three ways that move in opposite directions when you increase batch size B:

  • Per-user output token throughput (tok/s/user): 1000 / TPOT_ms. Because decode is memory-bandwidth-bound (reading model weights plus growing KV caches from HBM on every step), adding more concurrent requests to the active batch slightly increases each step's duration, nudging TPOT up and per-user tok/s down.
  • System output token throughput (total out tok/s): total output tokens generated across all users divided by wall-clock elapsed time. In steady state with batch concurrency B, one decode step of duration TPOT emits B tokens simultaneously, so system decode throughput scales as B * (1000 / TPOT_ms) until the GPU transitions from memory-bound to compute-bound.
  • Request throughput (req/s) and Goodput: completed requests per second (total_requests / wall_time_s). Goodput is the maximum request throughput req/s that simultaneously satisfies your Service Level Objectives (SLOs), such as p95 TTFT <= 200 ms and p99 ITL <= 40 ms. Raw throughput at B = 128 is useless if 80% of requests breach the SLO.

5. Client-side vs server-side measurement

A production streaming client measures timestamps over Server-Sent Events (SSE, text/event-stream). Three measurement pitfalls corrupt client benchmarks:

  1. HTTP/proxy buffering: if nginx, an ingress proxy, or the Python client buffers chunks before yielding, multiple tokens arrive in a single socket read. The client sees ITL = 0 ms for buffered tokens followed by a fake spike.
  2. Chunk token count (>1 tok/chunk): speculative decoding or server-side detokenization can emit k > 1 tokens in one SSE frame. Per-step latency is chunk gap, while per-token TPOT must divide by actual generated token count from the usage footer.
  3. Tokenizer mismatch: counting whitespace words or UTF-8 characters instead of using the model's exact BPE tokenizer distorts TPOT and tok/s by 20% to 40%.
Check: At B = 8 in our kata, per-user decode speed is 98.39 tok/s (TPOT = 10.16 ms), yet total system throughput is 771.81 tok/s instead of 8 * 98.39 = 787.12 tok/s. Where did the missing 15.3 tok/s go?
System throughput is total_out_tokens / total_wall_time across the full window from the first request's arrival to the 8th request's completion. That wall window includes the initial prefill TTFT (8.00 ms) and the 8 ms arrival stagger across requests before all 8 streams are decoding simultaneously.

import statistics

# Deterministic simulation of a continuous-batching LLM server and streaming client
# Hardware model: H100-80GB class serving Llama-3-8B FP16
# Prefill compute speed: 32,000 prompt tok/s (0.03125 ms/token)
# Decode step latency (memory-bandwidth bound + batch slope):
#   step_ms(B, ctx_avg) = 8.5 + 0.18 * B + 0.0012 * B * (ctx_avg / 1024)

def simulate_scenario(name, reqs, chunk_prefill=None):
    pending = [dict(r, prefill_left=r["n_in"], out_left=r["n_out"],
                    ctx=0, chunks=[]) for r in reqs]
    now = 0.0
    active = []
    done = []

    while len(done) < len(pending):
        for r in pending:
            if r not in active and r not in done and r["arrive_ms"] <= now:
                active.append(r)
        if not active:
            now = min(r["arrive_ms"] for r in pending if r not in done)
            continue

        prefilling = [r for r in active if r["prefill_left"] > 0]
        decoding = [r for r in active if r["prefill_left"] == 0 and r["out_left"] > 0]

        if prefilling:
            r = prefilling[0]
            if not chunk_prefill:
                # Unchunked prefill monopolizes the GPU: active decode streams stall!
                step_ms = r["prefill_left"] * 0.03125
                now += step_ms
                r["ctx"] += r["prefill_left"]
                r["prefill_left"] = 0
                r["chunks"].append(now)
                r["out_left"] -= 1
            else:
                # Chunked prefill piggybacks active decode tokens in the same iteration
                take = min(chunk_prefill, r["prefill_left"])
                B_dec = len(decoding)
                step_ms = take * 0.03125 + (2.5 + 0.12 * B_dec if B_dec else 0.0)
                now += step_ms
                r["prefill_left"] -= take
                r["ctx"] += take
                if r["prefill_left"] == 0:
                    r["chunks"].append(now)
                    r["out_left"] -= 1
                for d in decoding:
                    d["ctx"] += 1
                    d["chunks"].append(now)
                    d["out_left"] -= 1
        else:
            B = len(decoding)
            avg_ctx = sum(d["ctx"] for d in decoding) / B
            step_ms = 8.5 + 0.18 * B + 0.0012 * B * (avg_ctx / 1024.0)
            now += step_ms
            for d in decoding:
                d["ctx"] += 1
                d["chunks"].append(now)
                d["out_left"] -= 1

        for r in list(active):
            if r["out_left"] == 0:
                active.remove(r)
                done.append(r)

    ttfts, tpots, e2es, all_itls = [], [], [], []
    for r in done:
        t0 = r["arrive_ms"]
        c = r["chunks"]
        ttft = c[0] - t0
        e2e = c[-1] - t0
        itls = [c[i] - c[i - 1] for i in range(1, len(c))]
        tpot = (e2e - ttft) / (len(c) - 1)
        ttfts.append(ttft)
        tpots.append(tpot)
        e2es.append(e2e)
        all_itls.extend(itls)

    wall_s = (max(r["chunks"][-1] for r in done) - min(r["arrive_ms"] for r in done)) / 1000.0
    total_out = sum(r["n_out"] for r in done)
    all_itls.sort()
    p50_itl = all_itls[len(all_itls) // 2]
    p99_itl = all_itls[int(len(all_itls) * 0.99)]
    max_itl = all_itls[-1]
    user_tps = 1000.0 / statistics.mean(tpots)
    sys_tps = total_out / wall_s
    req_s = len(done) / wall_s

    print(f"=== {name} (n_req={len(done)}, total_out={total_out} tok) ===")
    print(f"  Mean TTFT : {statistics.mean(ttfts):7.2f} ms | Mean TPOT : {statistics.mean(tpots):6.2f} ms")
    print(f"  ITL p50   : {p50_itl:7.2f} ms | ITL p99   : {p99_itl:6.2f} ms | Max ITL: {max_itl:6.2f} ms")
    print(f"  Mean E2E  : {statistics.mean(e2es):7.2f} ms | Identity TTFT+(N-1)*TPOT = {statistics.mean(ttfts)+(done[0]['n_out']-1)*statistics.mean(tpots):.2f} ms")
    print(f"  User speed: {user_tps:7.2f} tok/s | Sys tput  : {sys_tps:7.2f} tok/s ({req_s:.2f} req/s)\n")

if __name__ == "__main__":
    # 1. Interactive single-user short chat (B=1, N_in=256, N_out=128)
    s1 = [{"id": 0, "arrive_ms": 0.0, "n_in": 256, "n_out": 128}]
    simulate_scenario("1. Single-User Chat (B=1, 256->128)", s1)

    # 2. Batched RAG steady decode (B=8 staggered by 8ms, N_in=256, N_out=128)
    s2 = [{"id": i, "arrive_ms": i * 8.0, "n_in": 256, "n_out": 128} for i in range(8)]
    simulate_scenario("2. Batched Chat Steady (B=8, 256->128)", s2)

    # 3. Mid-decode prefill stall: 8 active decoders hit by two 4096-token RAG arrivals
    s3 = [{"id": i, "arrive_ms": i * 8.0, "n_in": 256, "n_out": 128} for i in range(8)]
    s3.append({"id": 8, "arrive_ms": 250.0, "n_in": 4096, "n_out": 128})
    s3.append({"id": 9, "arrive_ms": 600.0, "n_in": 4096, "n_out": 128})
    simulate_scenario("3a. Prefill Stall Unchunked (B=8 + 2x4096-tok prefills)", s3, chunk_prefill=None)
    simulate_scenario("3b. Chunked Prefill Fix (B=8 + 2x4096-tok in 512-tok chunks)", s3, chunk_prefill=512)

What to notice

  1. The E2E identity holds to the microsecond: in Scenario 1, TTFT = 8.00 ms, TPOT = 8.68 ms, and N_out = 128, giving 8.00 + 127 * 8.68039 = 1,110.41 ms, matching measured mean E2E (1,110.41 ms) identically.
  2. Batching trades 14.6% per-user speed for 6.70x system throughput: moving from B=1 (Scenario 1) to B=8 (Scenario 2) increases mean TPOT from 8.68 ms to 10.16 ms (per-user speed drops from 115.20 to 98.39 tok/s), while total system output throughput jumps from 115.27 tok/s (0.90 req/s) to 771.81 tok/s (6.03 req/s).
  3. Mean TPOT is blind to rare prefill stalls: in Scenario 3a, two 4,096-token prompts arrive at t=250 ms and t=600 ms. Each unchunked prefill takes 4096 * 0.03125 = 128.00 ms, freezing all 8 active decoders for 138.13 ms. Yet averaged over 127 steps, mean TPOT is only 12.06 ms (82.93 tok/s). Only p99 ITL (138.13 ms vs 10.31 ms p50) reveals the 13.4x stall.
  4. Chunked prefill trades a small TTFT bump for 7.05x smoother streaming: splitting the 4,096-token prompts into eight 512-token chunks (Scenario 3b) lets active decode streams emit a token every 19.58 ms instead of waiting 138.13 ms, while mean TTFT rises modestly from 32.66 ms to 46.23 ms and total system throughput stays flat at ~646 tok/s.

  2. Queue explosion above saturation. Change Scenario 2 to launch 64 requests arriving every 2.0 ms with n_in = 1024. Predict which metric degrades more: mean TTFT (from queuing) or p50 ITL.

Traps

Each one sounds right. Say what is wrong with it before you open it.

"End-to-End latency is simply TTFT + N_out * TPOT."
Wrong by one decode step: the first output token is emitted at the end of prefill and its time is already inside TTFT. Only N_out - 1 decode steps follow, so E2E = TTFT + (N_out - 1) * TPOT. At N_out = 1 (classification), decode time is zero and E2E = TTFT.
"If a request's average TPOT is 12 ms (83 tok/s), the user experiences smooth 83 tok/s streaming with no stutters."
Wrong because TPOT averages across all N_out - 1 steps in the request. In our kata's Scenario 3a, 126 decode steps ran at 10.31 ms and one step stalled for 138.13 ms during a 4,096-token prefill. Mean TPOT was 12.06 ms (82.93 tok/s), completely hiding the 138 ms freeze that only p99 ITL catches.
"Increasing batch size always degrades token throughput because each decode step takes longer."
Confuses per-user throughput with system throughput. Raising B from 1 to 8 increases step time slightly (8.68 ms to 10.16 ms), so per-user speed drops 14.6% (115.2 to 98.4 tok/s), but all 8 requests emit a token on each weight read, multiplying system throughput 6.7x from 115.3 to 771.8 tok/s.
"You can measure TTFT and TPOT accurately from standard server request logs or a non-streaming HTTP client."
A non-streaming client only records total response time (E2E) after the last token arrives; it cannot separate TTFT from (N_out - 1) * TPOT. And server-side logs miss network transit, reverse-proxy buffering, and client SSE queueing delays.

Question bank

Answer aloud, then open. Grade yourself honestly.

1. Derive the exact formula relating E2E latency, TTFT, TPOT, and N_out from token arrival timestamps t_0 .. t_{N_out}.
Let t_0 be request submission and t_1 .. t_{N_out} be the arrival timestamps of tokens 1 .. N_out. By definition, TTFT = t_1 - t_0, ITL_k = t_{k+1} - t_k for k = 1 .. N_out - 1, and TPOT = (1 / (N_out - 1)) * sum(ITL_k) = (t_{N_out} - t_1) / (N_out - 1). Since E2E = t_{N_out} - t_0 = (t_1 - t_0) + (t_{N_out} - t_1), substituting yields E2E = TTFT + (N_out - 1) * TPOT.
Follow-upWhat happens to this equation when N_out = 1, and what workload has N_out = 1? For N_out = 1, (N_out - 1) = 0, so E2E = TTFT and TPOT is undefined; this occurs in single-token classification, guardrails, and logprob scoring.
2. What is the difference between TPOT and ITL, and when do their p99 values diverge sharply?
ITL is the per-step latency sample t_{k+1} - t_k measured on every individual token transition, whereas TPOT is a per-request summary statistic equal to the arithmetic mean of all N_out - 1 ITLs in that request. Their p99 values diverge whenever transient mid-stream stalls occur (such as unchunked long-prompt prefills or KV block preemption): the stall spikes one ITL sample to 138 ms (p99 ITL = 138.13 ms) but gets diluted by 126 fast steps inside the request's mean TPOT (12.06 ms).
Follow-upWhich metric matters more for a live voice-AI TTS stream vs a background document summarizer? Voice-AI TTS depends on p99 ITL because a single 140 ms gap starves the audio buffer, whereas background summarization cares only about E2E and system throughput.
3. Why does TTFT scale differently with prompt length N_in than TPOT scales with output length N_out?
TTFT is dominated by the parallel prefill pass over all N_in tokens at once, which is compute-bound: latency scales linearly O(N_in) with prompt tokens for linear layers and quadratically O(N_in^2) for attention at long contexts. TPOT is a single decode step generating 1 token while reading fixed model weights plus the current KV cache from HBM: each step is memory-bandwidth-bound and grows only slowly with context length O(N_in + t), though total decode time (N_out - 1) * TPOT scales linearly with N_out.
4. Why does increasing batch concurrency B from 1 to 8 raise system tok/s by 6.7x while reducing per-user tok/s by only 14.6%?
During autoregressive decode at low batch size, the GPU spends most of each step reading model weights from HBM into SRAM (e.g., ~16 GB for an 8B FP16 model) while Tensor Cores sit underutilized. Batching B = 8 requests reuses that single weight read across 8 tokens simultaneously. Step time increases only slightly (from 8.68 ms to 10.16 ms due to larger KV cache reads and compute slope), so per-user speed drops 14.6%, while 8 tokens emitted per step lifts system throughput 6.7x to 771.81 tok/s.
Follow-upWhat happens if you keep increasing B past the roofline ridge point (e.g., B = 128 or 256)? Decode becomes compute-bound or HBM-capacity-bound: TPOT begins scaling linearly with B, so system tok/s plateaus while per-user TPOT and queuing TTFT explode.
5. Explain how chunked prefill works and cite the exact tradeoff it makes between TTFT and p99 ITL in our kata.
Without chunked prefill, a newly scheduled 4,096-token prompt runs its entire prefill in one 128 ms GPU iteration, pausing all active decode requests and pushing p99 ITL to 138.13 ms. Chunked prefill slices that 4,096-token prompt into eight 512-token chunks and batches the active decode tokens alongside each chunk. In our kata, this cuts p99 ITL 7.05x (from 138.13 ms to 19.58 ms) at the cost of raising mean TTFT from 32.66 ms to 46.23 ms.
Follow-upWhy does piggybacking decode tokens onto a prefill chunk improve GPU utilization? Prefill chunks are compute-bound while decode steps are memory-bandwidth-bound; fusing them lets decode piggyback on weights already loaded into SRAM for the prefill chunk.
6. Define "goodput" for an LLM inference service and explain why maximizing raw tok/s is dangerous without it.
Goodput is the rate of completed requests per second (or tokens/s) that satisfy all latency SLO thresholds (for example, TTFT <= 200 ms and p99 ITL <= 30 ms). If you crank batch concurrency to maximize raw system tok/s, queuing delay pushes TTFT to seconds and batch slope pushes TPOT above the user threshold, causing valid SLO goodput to collapse toward zero even while GPU tok/s looks high.
7. A colleague benchmarks a streaming endpoint using Python `requests.post(url, json=payload)` without `stream=True`, or behind an nginx proxy with default settings. What happens to their measured TTFT and ITL?
Without stream=True (or when nginx buffers the upstream response), the client blocks until the entire HTTP body finishes and receives all SSE chunks at once at t_{N_out}. Measured TTFT erroneously equals full E2E latency, and every subsequent chunk appears to arrive with ITL ~ 0 ms.
8. How does speculative decoding (emitting 3 to 5 accepted tokens per verification step) affect ITL, TPOT, and client benchmarking?
A single verification step takes slightly longer than one standard decode step (higher per-chunk ITL), but emits k tokens at once in a single SSE chunk. Therefore, Time Per Output Token (TPOT) must be computed as (t_{last} - t_1) / (total_output_tokens - 1) rather than mean time per SSE chunk, or you will underestimate the 2x-3x token speedup.
Follow-upHow should you compute ITL when one SSE frame contains multiple tokens? Record both inter-chunk latency (what the network/UI buffer sees) and normalized per-token ITL (chunk gap divided by tokens in that chunk).
9. Two workloads hit your cluster: Workload A is an agent router (N_in = 3,000, N_out = 2) and Workload B is a coding assistant (N_in = 300, N_out = 800). Which metric dominates E2E for each, and which hardware resource bounds each?
For Workload A (3000 -> 2), TTFT accounts for ~99% of E2E and is bound by GPU Tensor Core FLOP/s (and prefix cache hit rate). For Workload B (300 -> 800), 799 * TPOT accounts for ~99% of E2E and is bound by GPU HBM memory bandwidth.

Mixed review

Three questions from earlier topics. Nobody tells you the topic in an interview.

K05: Why is prompt prefill compute-bound while autoregressive decode at small batch sizes is memory-bandwidth-bound?
Prefill processes all N_in prompt tokens in parallel using matrix-matrix multiplications (GEMMs), reusing each weight byte loaded from HBM across N_in tokens (high arithmetic intensity). Decode at B=1 generates one token per step using matrix-vector multiplies (GEMVs), reading the entire model weight matrix from HBM for just 2 FLOPs per weight byte.
K06: Why does the KV cache store K and V tensors for past tokens but never store past Q (Query) tensors?
Under causal masking, decode step t only computes attention for the newest token's query q_t against all past keys k_0 .. k_t and values v_0 .. v_t. Past queries q_0 .. q_{t-1} are never referenced again in future steps.
K07: Write the exact formula for KV cache bytes per token across all layers of a transformer with GQA, and compute it for Llama-3-8B in FP16 (L=32, n_kv_heads=8, d_head=128).
Bytes/tok = 2 (K and V) * L * n_kv_heads * d_head * bytes_per_elem. For Llama-3-8B in FP16 (2 bytes): 2 * 32 * 8 * 128 * 2 = 131,072 bytes = 128 KiB per token (or 128 MiB per 1,024 tokens).

Short notes

Quick-memorization cheat sheet covering every subtopic on this page and the key facts to remember cold.

All subtopics on this page

  • Time To First Token (TTFT): elapsed time t_1 - t_0 from request arrival to first token chunk; sums network transit, scheduler queue wait, and compute-bound parallel prompt prefill over N_in tokens (8.00 ms at B=1, 256 prompt tokens in kata).
  • Inter-Token Latency (ITL): per-step wall gap ITL_k = t_{k+1} - t_k between consecutive streamed tokens (k = 1 .. N_out - 1); its p99 exposes mid-stream generation freezes (138.13 ms during unchunked 4096-tok prefill).
  • Time Per Output Token (TPOT): per-request arithmetic mean of all N_out - 1 ITL steps, (t_{N_out} - t_1) / (N_out - 1); measures average decode cadence (8.68 ms at B=1, 10.16 ms at B=8) and determines per-user speed 1000 / TPOT_ms.
  • End-to-End Latency (E2E): total request duration t_{N_out} - t_0 governed by the exact identity E2E = TTFT + (N_out - 1) * TPOT (8.00 + 127 * 8.68 = 1,110.41 ms).
  • Per-User vs System Throughput & Goodput: raising batch concurrency B from 1 to 8 slightly lowers per-user speed (115.20 -> 98.39 tok/s) while multiplying total system output throughput 6.7x (115.27 -> 771.81 tok/s); goodput counts only req/s meeting both TTFT and p99 ITL SLOs.
  • Chunked Prefill & Client Measurement: slicing 4,096-token prefills into 512-token chunks cuts p99 ITL stalls 7.05x (138.13 -> 19.58 ms); streaming clients must disable HTTP/proxy buffering and divide by actual BPE token counts.
Important things to remember
  • Exact latency identity: E2E = TTFT + (N_out - 1) * TPOT. Never multiply TPOT by N_out because token 1 is emitted at the end of prefill inside TTFT.
  • Why mean TPOT lies: one 138 ms prefill stall averaged across 127 steps shifts mean TPOT by less than 2 ms (10.16 -> 12.06 ms). Always monitor p99 ITL to catch user-visible stutters.
  • Always qualify "throughput": state both per-user decode speed (1000 / TPOT) and total system output throughput (sum(N_out) / wall_s), plus SLO-constrained goodput (req/s).
  • Memory hook (FTD-ET): First-token (TTFT), Token-gap (ITL), Decode-mean (TPOT), End-to-end (E2E), Throughput (user vs system tok/s).
