Prefill vs decode

Why does an LLM process your 256-token prompt at nearly 6,000 tokens per second, then slow down 23x when generating the 32-token reply one word at a time?

Study path

Before you read

Guess first. A wrong guess now makes the right answer stick later.

In our kata (3.82M parameters, 7.63 MB in FP16), prefill on a 256-token prompt reads 7.90 MB of weights and KV state. How many megabytes must the hardware read to generate just 1 new decode token right after?
It reads 7.91 MB for that single decode token. Even though decode computes only 1 token instead of 256 (8.75 M FLOPs vs 1,688.21 M FLOPs), every linear layer still has to stream the entire 7.63 MB weight matrices from memory plus the saved KV cache (0.28 MB).
In that same run (batch size B=1, prompt S=256), prefill achieves 5,930.2 tok/s in 43.17 ms. Does per-token decode run at roughly the same token throughput, half as fast, or more than 20x slower?
More than 20x slower: decode runs at 257.1 tok/s (3.89 ms per token), making prefill 23.06x faster in tokens per second. In prefill, one weight read is amortized across all 256 prompt tokens (213.8 FLOP/Byte); in single-stream decode, that weight read serves only 1 token (1.11 FLOP/Byte, a 193.4x drop in arithmetic intensity).
Suppose you generate N=32 new tokens after a 256-token prompt without saving intermediate key-value projections, re-running the full prefix at each step. How many total token positions do you process compared to caching?
You process 8,688 token positions instead of 287 positions, which is 30.3x redundant work. Without saved prefix state, step t must recompute all 256 + t tokens from scratch because causal attention needs every past token's key and value vectors.

The core idea

Autoregressive generation is sequential by definition: you cannot sample token t + 1 until you have computed the logits for token t, sampled a token ID, and fed it back as the next input. However, when a user sends a prompt of S tokens, all S input tokens are already known upfront. Inference engines therefore split every request into two distinct phases: prefill (processing all S prompt tokens in one parallel forward pass to emit the first generated token and save each layer's key-value projections) and decode (running one forward pass per generated token, feeding only the newly sampled token of shape [B, 1, d_model] while reading the saved prefix state).

Although prefill and decode execute the exact same model weights, they behave like two completely different workloads on hardware. Prefill multiplies a thick activation matrix [B*S, d_model] against each weight matrix (General Matrix-Matrix Multiplication, or GEMM), reusing every weight byte fetched from High-Bandwidth Memory (HBM) across B*S tokens and saturating the GPU's compute units. Decode at batch size B=1 multiplies a single row vector [1, d_model] against each weight matrix (General Matrix-Vector Multiplication, or GEMV), streaming gigabytes of weights out of HBM just to do two floating-point operations per weight parameter and leaving the GPU's tensor cores starving for data.

Memory hook

Remember P-D-R-B to reconstruct the spine of prefill vs decode from scratch: Prefill runs parallel GEMM over S tokens (sets TTFT, compute-bound); Decode runs serial GEMV over 1 token (sets TPOT, HBM-bandwidth-bound); Roofline ridge point is Peak FLOP/s / HBM BW (~295 FLOP/B on H100, ~156 FLOP/B on A100); Batching B requests raises decode arithmetic intensity from ~1 to ~B FLOP/Byte by reusing each weight read across B tokens.

How it works

1. Why naive autoregression recomputes work

In a causal transformer, the self-attention output at position t depends on the query vector q_t and on the key and value vectors k_1..t, v_1..t of every token at or before t. Because the causal mask blocks position i from attending to any future position j > i, the hidden representations and (k_i, v_i) projections of prefix tokens 1..t never change when token t + 1 is appended. If you ignore this invariance and feed the growing sequence of lengths S, S+1, ..., S+N-1 into a stateless forward pass at every step, you recompute the entire prefix N times:

Uncached positions processed = sum_{t=0..N-1} (S + t) = N * S + N * (N - 1) / 2
Cached positions processed   = S (in prefill) + (N - 1) (in decode) = S + N - 1

For S = 256, N = 32 (our kata):
  Uncached = 32 * 256 + (32 * 31) / 2 = 8,192 + 496 = 8,688 positions
  Cached   = 256 + 31 = 287 positions  (30.3x redundant work eliminated)

2. Linear GEMM in prefill vs GEMV in decode

Caching eliminates redundant FLOPs during decode, yet decode tokens still take far longer per token than prefill tokens. To see why, look at a single linear projection with weight matrix W of shape [d_in, d_out] containing P = d_in * d_out parameters (2P bytes in FP16). Multiplying an input activation matrix of T tokens (where T = B * S in prefill and T = B * 1 in decode) by W requires 2 * T * P FLOPs (one multiply and one add per weight per token). Across a full model with P_total linear parameters, L layers, H query heads, and head dimension d_head, the per-step FLOPs and FP16 bytes read are:

Prefill step (all S tokens in parallel):
  Linear FLOPs = 2 * B * S * P_layer_total + 2 * B * d_model * V
  Attn FLOPs   = 4 * B * L * H * (S^2) * d_head
  Bytes moved  = 2 * P_total + 4 * B * S * L * KVH * d_head  (weights read + KV written)

Decode step (1 token per sequence at context length S):
  Linear FLOPs = 2 * B * 1 * P_total
  Attn FLOPs   = 4 * B * L * H * S * d_head
  Bytes moved  = 2 * P_total + 4 * B * S * L * KVH * d_head  (weights read + KV read)
Check: Why does linear projection FLOP count drop by roughly S (from 2*B*S*P to 2*B*P) between prefill and one decode step, while bytes read stays almost identical at B=1?
Because only 1 new token vector enters the linear layers during a decode step (reducing multiply-adds by S), but computing the dot product of that 1 token vector with every column of W still requires reading every single weight parameter in W from HBM.

3. Arithmetic intensity and the Roofline model

The Roofline model bounds the achievable compute performance (FLOP/s) of any kernel using two hardware ceilings: peak compute F_peak (FLOP/s) and peak memory bandwidth BW (Bytes/s). The ratio of work done to memory traffic is the kernel's arithmetic intensity, I = FLOPs / Bytes. A kernel's throughput is capped by min(F_peak, I * BW). The crossover where memory bandwidth can finally feed the compute units at full speed is the hardware's ridge point:

I_ridge = F_peak / BW

Hardware examples (dense FP16/BF16 Tensor Cores):
  NVIDIA A100-80GB SXM: 312 TFLOP/s / 2.00 TB/s = 156.0 FLOP/Byte
  NVIDIA H100-80GB SXM: 989 TFLOP/s / 3.35 TB/s = 295.2 FLOP/Byte

Linear layer arithmetic intensity (when weight bytes 2*P dominate KV bytes):
  I_prefill ≈ (2 * B * S * P) / (2 * P) = B * S  FLOP/Byte
  I_decode  ≈ (2 * B * 1 * P) / (2 * P) = B      FLOP/Byte

Notice how cleanly the 2 * P parameter count cancels out! For moderate context lengths where model weights are much larger than the KV cache, arithmetic intensity in FP16 is approximately B * S FLOP/Byte in prefill and B FLOP/Byte in decode. At B = 1 and S = 256, our kata measures I_prefill = 213.8 FLOP/Byte (compute-bound on A100, approaching the ridge on H100) and I_decode = 1.11 FLOP/Byte (deep in the memory-bound slope, utilizing less than 1.11 / 295.2 = 0.38% of an H100's tensor cores).

4. Latency equations (TTFT vs TPOT) and batching B

User-perceived latency splits neatly across the two phases. Time to First Token (TTFT) is the prefill duration plus network/scheduling overhead, governed by peak FLOP/s: TTFT ≈ (2 * B * S * P + 4 * B * L * H * S^2 * d_head) / F_peak. Notice the quadratic S^2 attention term: for short prompts (S < 2,048), linear projections (O(S)) dominate TTFT, whereas for long prompts (S > 16,384), quadratic self-attention (O(S^2)) dominates. Time Per Output Token (TPOT) is the duration of a single decode step, governed by HBM bandwidth:

TPOT_min (at small B) ≈ (Weight_Bytes + KV_Cache_Bytes(B, S)) / BW

Example (7B parameter model in FP16 = 14 GB weights, on A100 with BW = 2,000 GB/s):
  TPOT_min >= 14 GB / 2,000 GB/s = 0.007 s = 7.0 ms/token  (max 142.9 tok/s at B=1)

This gives you an ironclad physical speed limit for interviews: no matter how many TFLOPs a chip advertises, a single unbatched decode stream cannot run faster than the time required to read the model weights once from memory. When you batch B requests together during decode, the weight read 2P is shared across all B requests while the KV cache read grows linearly with B * S. Total token throughput scales almost linearly with B until either arithmetic intensity crosses the ridge point or KV cache bytes exceed weight bytes.

Check: On an A100 (ridge point 156 FLOP/Byte), roughly what batch size B is needed in decode for a short-context FP16 model before linear layers transition from memory-bound to compute-bound?
A batch size of roughly B = 156 requests (since I_decode ≈ B FLOP/Byte in FP16 when weight bytes dominate KV cache bytes). On an H100 (ridge point ~295 FLOP/Byte), it takes roughly B = 295 concurrent requests!

Kata: Timing prefill GEMM vs decode GEMV and arithmetic intensity

A self-contained NumPy implementation of a 4-layer Grouped-Query Attention (GQA) transformer that runs parallel prefill and step-by-step cached decode, measures wall-clock latency and token throughput, computes exact FLOPs, bytes moved, and arithmetic intensity, and tests naive uncached autoregression and batched decode.

"""
K05 Kata: Prefill vs decode
Times prefill (compute-bound GEMM) and per-token decode (memory-bandwidth-bound GEMV)
separately on a miniature Grouped-Query Attention transformer, computes exact FLOPs,
bytes moved, and Arithmetic Intensity (FLOPs/Byte), and demonstrates three failure modes.
"""
import time
import numpy as np

np.random.seed(42)

# Model dimensions (miniature Llama-style GQA architecture)
L = 4            # transformer layers
d_model = 256    # hidden dimension
d_ff = 688       # SwiGLU intermediate size (~8/3 * d_model)
H = 8            # query heads
KVH = 2          # key-value heads (4:1 GQA)
d_head = d_model // H  # 32
V = 4096         # vocabulary size
BYTES_FP16 = 2   # 2 bytes per parameter in FP16/BF16

# Initialize random FP32 weights for timing on CPU
layers = []
for _ in range(L):
    layers.append({
        "wq": np.random.randn(d_model, H * d_head).astype(np.float32) * 0.05,
        "wk": np.random.randn(d_model, KVH * d_head).astype(np.float32) * 0.05,
        "wv": np.random.randn(d_model, KVH * d_head).astype(np.float32) * 0.05,
        "wo": np.random.randn(H * d_head, d_model).astype(np.float32) * 0.05,
        "wg": np.random.randn(d_model, d_ff).astype(np.float32) * 0.05,
        "wu": np.random.randn(d_model, d_ff).astype(np.float32) * 0.05,
        "wd": np.random.randn(d_ff, d_model).astype(np.float32) * 0.05,
    })
w_lm = np.random.randn(d_model, V).astype(np.float32) * 0.05

# Count linear weight parameters per layer and total
params_per_layer = (
    d_model * (H * d_head)
    + 2 * d_model * (KVH * d_head)
    + (H * d_head) * d_model
    + 3 * d_model * d_ff
)
total_params = L * params_per_layer + d_model * V
weight_bytes_fp16 = total_params * BYTES_FP16

def rmsnorm(x):
    return x / np.sqrt(np.mean(x * x, axis=-1, keepdims=True) + 1e-5)

def forward_prefill(x):
    """Parallel forward pass over all S tokens [B, S, d_model]; returns last logits and KV cache."""
    B, S, _ = x.shape
    kv_cache = []
    mask = np.triu(np.full((S, S), -1e9, dtype=np.float32), k=1)
    for lyr in layers:
        h = rmsnorm(x)
        q = (h @ lyr["wq"]).reshape(B, S, H, d_head).transpose(0, 2, 1, 3)
        k = (h @ lyr["wk"]).reshape(B, S, KVH, d_head)
        v = (h @ lyr["wv"]).reshape(B, S, KVH, d_head)
        kv_cache.append((k, v))
        kr = np.repeat(k, H // KVH, axis=2).transpose(0, 2, 1, 3)
        vr = np.repeat(v, H // KVH, axis=2).transpose(0, 2, 1, 3)
        scores = (q @ kr.transpose(0, 1, 3, 2)) / np.sqrt(d_head) + mask
        scores -= np.max(scores, axis=-1, keepdims=True)
        probs = np.exp(scores) / np.sum(np.exp(scores), axis=-1, keepdims=True)
        attn_out = (probs @ vr).transpose(0, 2, 1, 3).reshape(B, S, d_model)
        x = x + attn_out @ lyr["wo"]
        h2 = rmsnorm(x)
        gate = h2 @ lyr["wg"]
        up = h2 @ lyr["wu"]
        act = (gate / (1.0 + np.exp(-gate))) * up
        x = x + act @ lyr["wd"]
    logits_last = rmsnorm(x[:, -1:, :]) @ w_lm
    return logits_last, kv_cache

def forward_decode_step(x_tok, kv_cache):
    """Single-token decode step [B, 1, d_model] appending to existing KV cache."""
    B = x_tok.shape[0]
    new_cache = []
    x = x_tok
    for idx, lyr in enumerate(layers):
        h = rmsnorm(x)
        q = (h @ lyr["wq"]).reshape(B, 1, H, d_head).transpose(0, 2, 1, 3)
        k_new = (h @ lyr["wk"]).reshape(B, 1, KVH, d_head)
        v_new = (h @ lyr["wv"]).reshape(B, 1, KVH, d_head)
        k_all = np.concatenate([kv_cache[idx][0], k_new], axis=1)
        v_all = np.concatenate([kv_cache[idx][1], v_new], axis=1)
        new_cache.append((k_all, v_all))
        kr = np.repeat(k_all, H // KVH, axis=2).transpose(0, 2, 1, 3)
        vr = np.repeat(v_all, H // KVH, axis=2).transpose(0, 2, 1, 3)
        scores = (q @ kr.transpose(0, 1, 3, 2)) / np.sqrt(d_head)
        scores -= np.max(scores, axis=-1, keepdims=True)
        probs = np.exp(scores) / np.sum(np.exp(scores), axis=-1, keepdims=True)
        attn_out = (probs @ vr).transpose(0, 2, 1, 3).reshape(B, 1, d_model)
        x = x + attn_out @ lyr["wo"]
        h2 = rmsnorm(x)
        gate = h2 @ lyr["wg"]
        up = h2 @ lyr["wu"]
        act = (gate / (1.0 + np.exp(-gate))) * up
        x = x + act @ lyr["wd"]
    logits_last = rmsnorm(x) @ w_lm
    return logits_last, new_cache

def phase_math(B, S, is_prefill=True):
    """Compute exact FLOPs, bytes moved (FP16), and Arithmetic Intensity (FLOPs/Byte)."""
    if is_prefill:
        linear_flops = 2 * B * S * (L * params_per_layer) + 2 * B * d_model * V
        attn_flops = L * 4 * B * H * (S ** 2) * d_head
        kv_bytes = B * S * L * 2 * KVH * d_head * BYTES_FP16
    else:
        linear_flops = 2 * B * 1 * total_params
        attn_flops = L * 4 * B * H * S * d_head
        kv_bytes = B * S * L * 2 * KVH * d_head * BYTES_FP16
    total_flops = linear_flops + attn_flops
    total_bytes = weight_bytes_fp16 + kv_bytes
    return total_flops, total_bytes, total_flops / total_bytes

# Warm-up
_ = forward_prefill(np.random.randn(1, 16, d_model).astype(np.float32))

print(f"=== K05 KATA: PREFILL VS DECODE (L={L}, d={d_model}, d_ff={d_ff}, H={H}, KVH={KVH}, V={V}) ===")
print(f"Total parameters: {total_params:,} ({weight_bytes_fp16 / 1e6:.2f} MB in FP16)")
print("\n1. PHASE COMPARISON (Batch B=1, Prompt S=256, Generate N=32 tokens)")
x_prompt = np.random.randn(1, 256, d_model).astype(np.float32)

t0 = time.perf_counter()
for _ in range(5):
    _, cache = forward_prefill(x_prompt)
prefill_ms = (time.perf_counter() - t0) * 1000 / 5
prefill_tok_s = 256 / (prefill_ms / 1000.0)

x_step = np.random.randn(1, 1, d_model).astype(np.float32)
t1 = time.perf_counter()
cur_cache = cache
for _ in range(32):
    _, cur_cache = forward_decode_step(x_step, cur_cache)
decode_total_ms = (time.perf_counter() - t1) * 1000
decode_tpot_ms = decode_total_ms / 32
decode_tok_s = 1000.0 / decode_tpot_ms

pf_flops, pf_bytes, pf_ai = phase_math(1, 256, is_prefill=True)
dc_flops, dc_bytes, dc_ai = phase_math(1, 256 + 16, is_prefill=False)

print(f"{'Phase':<18} | {'Latency (ms)':>12} | {'Throughput':>14} | {'FLOPs/step':>12} | {'Bytes Read':>10} | {'Arith Intensity':>15}")
print("-" * 92)
print(f"{'Prefill (S=256)':<18} | {prefill_ms:>12.2f} | {prefill_tok_s:>10.1f} tok/s | {pf_flops/1e6:>9.2f} M | {pf_bytes/1e6:>7.2f} MB | {pf_ai:>10.1f} FLOP/B")
print(f"{'Decode (1 tok)':<18} | {decode_tpot_ms:>12.2f} | {decode_tok_s:>10.1f} tok/s | {dc_flops/1e6:>9.2f} M | {dc_bytes/1e6:>7.2f} MB | {dc_ai:>10.2f} FLOP/B")
print(f"Prefill-to-Decode throughput ratio: {prefill_tok_s / decode_tok_s:.2f}x faster tok/s in prefill")
print(f"Arithmetic intensity gap (S=256 vs B=1): {pf_ai / dc_ai:.1f}x higher FLOP/Byte in prefill")

print("\n2. BREAK IT #1: NAIVE AUTOREGRESSION WITHOUT KV STATE (Re-running full prefix every token)")
naive_positions = sum(256 + t for t in range(32))
cached_positions = 256 + 31
print(f"Positions processed (S=256, N=32): Cached={cached_positions} vs Uncached={naive_positions} ({naive_positions/cached_positions:.1f}x redundant work)")

print("\n3. BREAK IT #2: BATCHING DECODE TO RAISE ARITHMETIC INTENSITY (S=256)")
for B in (1, 8, 32):
    _, _, ai_b = phase_math(B, 256, is_prefill=False)
    xb = np.random.randn(B, 1, d_model).astype(np.float32)
    cb = [(np.zeros((B, 256, KVH, d_head), dtype=np.float32), np.zeros((B, 256, KVH, d_head), dtype=np.float32)) for _ in range(L)]
    ts = time.perf_counter()
    for _ in range(10):
        forward_decode_step(xb, cb)
    step_ms = (time.perf_counter() - ts) * 1000 / 10
    print(f"  Batch B={B:<2} -> AI={ai_b:>5.1f} FLOP/B | step={step_ms:>6.2f} ms | total={B * 1000.0 / step_ms:>8.1f} tok/s")

What to notice

  1. Identical memory traffic, 193x different FLOPs: Prefill over S=256 tokens performs 1,688.21 M FLOPs and moves 7.90 MB (213.8 FLOP/B), whereas one decode step performs only 8.75 M FLOPs but still reads 7.91 MB (1.11 FLOP/B). That 193.4x drop in arithmetic intensity is why decode runs at 257.1 tok/s vs prefill's 5,930.2 tok/s (23.06x slower).
  2. Why prefill latency (43.17 ms) is only 11.1x one decode step (3.89 ms): Doing 256x more tokens in prefill costs only 11.1x more wall-clock time (43.17 ms / 3.89 ms) because matrix-matrix multiplication reuses weight cache lines across all 256 token rows.
  3. Uncached autoregression explodes quadratically: In Break It #1, generating N=32 tokens after S=256 without saving the KV state processes 8,688 token positions instead of 287 (30.3x redundant work).
  4. Batching raises arithmetic intensity (and why CPU vs GPU differs): In Break It #2, increasing decode batch size from B=1 to B=8 and B=32 lifts arithmetic intensity from 1.1 to 7.1 and 17.3 FLOP/B. On a single laptop CPU core with a tiny 7.63 MB model that already fits in L3 cache, total tok/s rises modestly (302.9 to 324.1 tok/s) because the CPU is already near its SIMD FLOP ceiling; on an H100 where a 14 GB model spills to HBM and the ridge point is 295 FLOP/B, that same jump from 1.1 to 17.3 FLOP/B scales total GPU decode throughput by nearly 15x.

Scenario: You build a real-time clinical voice agent using a 70B FP16 model (140 GB weights) across 2x H100-80GB GPUs (combined HBM bandwidth 6.7 TB/s). First-word latency (TTFT) is 120 ms, which meets your SLA, but voice playback stutters because decode runs at only 38 tokens/s even with 1 user (B=1). Why is decode capped near 38 to 45 tok/s, and what three concrete levers will double it without changing the base model?
  1. Diagnose the physical bandwidth floor: At B=1, every decode token must stream all 140 GB of FP16 weights across the two GPUs' combined 6.7 TB/s HBM bus. Even at 100% ideal bandwidth efficiency with zero communication overhead, TPOT_min = 140 GB / 6,700 GB/s = 20.9 ms/tok (47.8 tok/s max). With real kernel and all-reduce overhead (~80% efficiency), you get ~26 ms/tok (38 tok/s). Adding prompt caching will NOT help TPOT because weights (140 GB), not the tiny single-user KV cache, dominate the byte read.
  2. Lever 1 - Weight quantization (FP8 or AWQ INT4): Quantizing weights from FP16 (2 bytes) to FP8 (1 byte) or INT4 (0.5 bytes) cuts weight traffic from 140 GB to 70 GB or 35 GB per token, immediately doubling or tripling single-stream decode speed to 75 to 120+ tok/s.
  3. Lever 2 - Speculative decoding: Use a tiny draft model (or Medusa/EAGLE heads) to propose K=4..5 tokens and verify them in a single 70B forward pass. Verify reads the 140 GB weights once for all K tokens, raising arithmetic intensity by K and cutting effective TPOT by 2x to 3x at B=1.
  4. Lever 3 - Higher Tensor Parallelism (TP=4 or TP=8): Spreading the 140 GB weights across 4 or 8 H100 GPUs multiplies aggregate HBM bandwidth by 2x or 4x (to 13.4 or 26.8 TB/s), cutting per-GPU weight bytes read per step down to 35 GB or 17.5 GB.

Interview

Say this aloud against the clock. Three levels, about 90 seconds.

1 Outcome 20 sServing an autoregressive transformer splits every request into two hardware regimes: prefill and decode. Prefill processes all prompt tokens in parallel to produce the first output token and populate the key-value state, governing Time to First Token (TTFT). Decode then generates one token per forward pass by feeding each newly sampled token back as input, governing Time Per Output Token (TPOT). Because prefill multiplies a token matrix against model weights while decode multiplies a single token vector against those same weights, prefill is compute-bound while decode is memory-bandwidth-bound.
2 Mechanism 45 sWithout caching, generating N tokens after a prompt of length S requires recomputing all previous tokens at every step, turning linear work into quadratic O(N squared) work. By saving each layer's key and value projections during prefill, each decode step computes query, key, and value projections only for the single new token. However, linear layers still must stream every model weight from high-bandwidth memory into the registers just to perform two floating-point operations per parameter for batch size one, yielding an arithmetic intensity of roughly one FLOP per byte.
3 Internals and limits 25 sOn an H100 GPU, the ridge point separating memory-bound from compute-bound execution is 989 teraFLOPs divided by 3.35 terabytes per second, or 295 FLOPs per byte. Single-stream decode sits near 1 FLOP per byte, leaving over 99 percent of tensor cores idle unless we batch B concurrent requests.

Say it like an engineer

"Prefill reads the user prompt and is fast because it runs in parallel, while decode generates the response one token at a time so it is slower and costs more per output token."

"Prefill runs a matrix-matrix multiply (GEMM) over all S prompt tokens at once, giving an arithmetic intensity of roughly B*S FLOPs per byte - well above an A100's 156 FLOP/Byte ridge point, so TTFT is compute-bound. Decode generates one token per step via matrix-vector multiply (GEMV), streaming all 2P bytes of FP16 weights from HBM for just 2P FLOPs at B=1, or 1 FLOP/Byte, so TPOT is pinned to HBM memory bandwidth unless we batch B requests or quantize weights."

The strong answer names the exact linear algebra kernels (GEMM vs GEMV), derives the arithmetic intensity (B*S vs B FLOP/Byte), anchors against a real hardware ridge point (156 FLOP/B on A100, 295 on H100), and links each phase to its SLA metric (TTFT vs TPOT).

Traps

Each one sounds right. Say what is wrong with it before you open it.

"Adding the KV cache makes per-token decode compute-bound because we no longer recompute the prompt tokens."
Wrong - it makes decode even more memory-bandwidth-bound. Saving the KV cache removes the redundant O(S) linear FLOPs over past tokens, shrinking compute per step to a single token vector [B, 1, d_model] while still requiring the GPU to read 100% of the model weights plus the growing KV cache from HBM.
"Since a single decode step does S times fewer FLOPs than an S-token prefill, one decode step is S times faster than prefill."
Wrong. In our kata (S=256), one decode step does 193x fewer FLOPs (8.75 M vs 1,688.21 M), yet its latency is only 11.1x shorter (3.89 ms vs 43.17 ms), meaning per-token throughput is 23.06x slower. Latency does not scale down by S because both steps read the same 7.9 MB of memory and decode hits the memory-bandwidth wall.
"Upgrading to a GPU with 2x more TFLOPs but the same HBM bandwidth will cut single-user (B=1) decode latency in half."
Wrong - single-user decode latency will not budge. At B=1, arithmetic intensity is ~1 FLOP/Byte, hundreds of times below the GPU ridge point. Tensor cores are already waiting on HBM data transfers over 99% of the time; only higher HBM bandwidth, fewer bytes read (quantization), or multi-token verification (speculative decoding) reduces B=1 TPOT.
"Increasing decode batch size from B=1 to B=16 increases per-token step latency (TPOT) by 16x."
Wrong on a GPU. Because B=1 and B=16 both sit on the memory-bandwidth-bound slope (below the 156 to 295 FLOP/B ridge point) and share the same single read of the model weights from HBM, step latency stays nearly flat (increasing only slightly for the extra KV cache reads) while total system throughput increases by nearly 16x.

Question bank

Answer aloud, then open. Grade yourself honestly.

Why can prefill process all S prompt tokens in a single forward pass while decode must run N separate forward passes for N output tokens?
In prefill, all S input tokens are already known from the user's prompt, and causal masking allows every position 1..S to be computed in parallel inside one matrix pass. In decode, token t+1 does not exist until token t's logits have been computed and sampled, creating a strict sequential data dependency between steps.
Follow-upDoes teacher forcing during training look like prefill or decode? It looks like prefill: the entire ground-truth target sequence is known upfront, so training runs 100% as parallel compute-bound GEMMs with a causal mask.
Derive the approximate arithmetic intensity (in FLOP/Byte) of an FP16 linear layer with P parameters during prefill (batch B, length S) versus decode (batch B, 1 token), assuming weight size dominates activation size.
A linear layer with P parameters performs 2 * T * P multiply-add FLOPs for T tokens and reads 2 * P bytes of FP16 weights. In prefill, T = B * S, so I_prefill ≈ (2 * B * S * P) / (2 * P) = B * S FLOP/Byte. In decode, T = B * 1, so I_decode ≈ (2 * B * P) / (2 * P) = B FLOP/Byte.
Follow-upWhat happens to that formula if weights are quantized to INT4 (0.5 bytes/param) while activations remain FP16? The denominator drops by 4x to 0.5 * P bytes, multiplying arithmetic intensity by 4x (to 4 * B FLOP/Byte in decode).
What is the hardware ridge point on an H100 SXM GPU (989 TFLOP/s dense FP16, 3.35 TB/s HBM3), and what does it tell you about unbatched decode?
The ridge point is F_peak / BW = 989 TFLOP/s / 3.35 TB/s = 295.2 FLOP/Byte. Any kernel with arithmetic intensity below 295.2 FLOP/Byte is memory-bandwidth-bound. Because unbatched FP16 decode sits near 1 FLOP/Byte, it utilizes only 1 / 295.2 ≈ 0.34% of the H100's compute capacity.
Calculate the theoretical minimum single-stream (B=1) decode TPOT and maximum tokens/sec for a 13B parameter model in FP16 on a GPU with 2.0 TB/s memory bandwidth.
A 13B model in FP16 occupies 13 * 10^9 * 2 bytes = 26 GB of weights. Streaming 26 GB at 2,000 GB/s takes at least 26 / 2,000 = 0.013 seconds = 13.0 ms/token. Maximum possible throughput at B=1 is 1,000 / 13.0 = 76.9 tokens/sec.
Follow-upWhy is real-world throughput typically 15% to 25% lower than this theoretical ceiling? Kernel launch overhead, reading the KV cache, non-linear layers (RMSNorm, softmax), and imperfect HBM bus utilization (~80-85% achievable bandwidth).
How does prompt length S affect prefill latency (TTFT), and why does the scaling regime change between S = 512 and S = 32,768?
Prefill FLOPs are the sum of linear projections (2 * B * S * P, which scales linearly as O(S)) and self-attention (4 * B * L * H * S^2 * d_head, which scales quadratically as O(S^2)). At S = 512, P is much larger than L * H * S * d_head, so TTFT scales linearly with S; by S = 32,768, the S^2 term dominates and doubling S quadruples attention FLOPs.
Why do cloud LLM APIs charge 3x to 5x more per million output (decode) tokens than per million input (prefill) tokens?
Because an output token occupies the GPU's HBM bandwidth and KV cache memory at much lower arithmetic intensity and hardware utilization than an input token. As shown in our kata, generating tokens in decode delivers an order of magnitude fewer tokens per second per GPU than parallel prefill.
Follow-upWhy do cached input tokens get an additional 50% to 90% discount? Because prefix caching skips both the linear and attention prefill FLOPs for the cached prefix and simply loads or references the precomputed KV blocks.
In our kata, generating N=32 tokens after S=256 without a KV cache required processing 8,688 token positions versus 287 with caching. Write the exact formula for both counts.
Uncached processes sum_{t=0}^{N-1} (S + t) = N * S + N * (N - 1) / 2 positions (32 * 256 + 32 * 31 / 2 = 8,688). Cached processes S positions in prefill plus N - 1 single-token decode steps, totaling S + N - 1 positions (256 + 31 = 287).
When you batch B concurrent requests during decode, what two factors eventually stop total token throughput from scaling linearly with B?
First, KV cache memory capacity and bandwidth: unlike model weights (shared across all B requests), each request has its own KV cache of size O(S), so total KV bytes read grows as O(B * S) until it exceeds weight bytes or causes an HBM OOM. Second, crossing the Roofline ridge point: once B reaches the ridge point (~156 on A100, ~295 on H100), tensor cores saturate and step time grows linearly with B.
What happens to ongoing decode requests when a naive continuous batching scheduler inserts a 4,096-token prefill into the middle of a decode batch?
All co-scheduled decode requests freeze for the entire duration of the 4,096-token compute-bound prefill pass (often 100 to 500+ ms), causing a severe spike in p99 Time Per Output Token (TPOT).
Follow-upName the two standard architectural fixes for this interference. Chunked prefill (splitting the 4,096 prompt into smaller chunks piggybacked onto decode steps) and disaggregated serving (running prefill and decode on separate GPU pools).

Mixed review

Three questions from earlier topics. Nobody tells you the topic in an interview.

K04: Trace the exact tensor shapes through a single Grouped-Query Attention (GQA) layer with batch B, sequence length S, hidden size d_model, H query heads, and KVH key-value heads (head size d_head = d_model / H).
Input X is [B, S, d_model]. Linear projections produce Q of shape [B, H, S, d_head] and K, V of shape [B, KVH, S, d_head]. Each K/V head is shared across H / KVH query heads to compute attention scores Q @ K^T / sqrt(d_head) of shape [B, H, S, S], softmax probabilities of [B, H, S, S], weighted values of [B, H, S, d_head], reshaped back to [B, S, d_model] and multiplied by W_o of shape [d_model, d_model].
K04: Why do modern LLMs place RMSNorm before the attention and SwiGLU blocks (Pre-Norm) rather than after the residual addition (Post-Norm), and what statistics does RMSNorm skip compared to LayerNorm?
Pre-Norm leaves an clean identity highway along the residual stream so gradients flow directly from the loss to early layers without vanishing or requiring a delicate learning-rate warmup. RMSNorm skips subtracting the mean and omits the learnable bias beta, normalizing solely by x / sqrt(mean(x^2) + eps) * gamma, saving memory traffic with equivalent quality.
D10: During autoregressive decoding, in what order should temperature scaling, top-k filtering, and top-p (nucleus) filtering be applied to the raw vocabulary logits before sampling?
First divide raw logits by temperature T (or short-circuit to argmax if T = 0), then apply top-k to keep the k highest logits (setting others to -inf), then convert to probabilities via softmax and apply top-p to keep the smallest prefix of sorted tokens whose cumulative probability reaches p, and finally renormalize and sample.

Short notes

Quick-memorization cheat sheet covering every subtopic on this page and the key facts to remember cold.

All subtopics on this page

  • Why two phases exist: All S prompt tokens are known upfront and run in one parallel pass (prefill), whereas each generated token depends on sampling the previous token and runs in a serial 1-token loop (decode).
  • Redundant work without caching: Stateless autoregression over S prompt and N output tokens processes N*S + N*(N-1)/2 positions vs S + N - 1 with KV caching (8,688 vs 287 positions, or 30.3x redundant work in our kata).
  • GEMM (prefill) vs GEMV (decode): Prefill multiplies [B*S, d] @ [d, d] (high weight reuse across B*S tokens); single-stream decode multiplies [1, d] @ [d, d] (zero weight reuse across tokens, streaming all weights for 1 token).
  • Arithmetic intensity & Roofline: For FP16 linear layers where weights dominate KV cache, I_prefill ≈ B * S FLOP/Byte and I_decode ≈ B FLOP/Byte; in our kata at B=1, S=256, prefill hits 213.8 FLOP/B (5,930.2 tok/s) while decode drops 193.4x to 1.11 FLOP/B (257.1 tok/s, 23.06x slower).
  • TTFT vs TPOT & batching B: TTFT is prefill latency (compute-bound, O(S) linear + O(S^2) attention); TPOT is per-token decode latency (HBM-bandwidth-bound, floor >= Weight_Bytes / BW); batching B requests raises decode AI to ~B FLOP/B and scales system tok/s until KV traffic or the ridge point saturates.
Important things to remember
  • Memory hook (P-D-R-B): Prefill = parallel GEMM (sets TTFT, compute-bound); Decode = serial GEMV (sets TPOT, HBM-bound); Ridge point = F_peak / BW; Batching B raises decode AI from ~1 to ~B FLOP/B.
  • Must-know GPU ridge points (FP16): NVIDIA A100 SXM = 312 TFLOP/s / 2.0 TB/s = 156 FLOP/B; NVIDIA H100 SXM = 989 TFLOP/s / 3.35 TB/s = 295 FLOP/B.
  • Physical decode speed limit at B=1: TPOT_min >= Weight_Bytes / BW_HBM. A 7B FP16 model (14 GB) on a 2,000 GB/s A100 cannot decode faster than 14 / 2000 = 7.0 ms/tok (143 tok/s) at B=1 without quantization or speculative decoding.
  • Interview rule of thumb: Never optimize TTFT and TPOT with the same lever. Fix high TTFT with FlashAttention, prefix caching, or more FLOPs; fix high TPOT with weight quantization (FP8/INT4), speculative decoding, GQA, or higher HBM bandwidth.
