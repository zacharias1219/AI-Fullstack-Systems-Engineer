Study path

Before you read

Guess first. A wrong guess now makes the right answer stick later.

A 1.5B parameter model is loaded in fp16. How much GPU memory do the weights alone take?
About 3 GB: 1.5 billion parameters times 2 bytes. People say "1.5 GB" because they count parameters, not bytes. The real footprint is larger still, because the KV cache, activations and the CUDA context come on top.
The kata model has 200 MB of weights. If the machine can move about 12 GB/s from memory, roughly how many tokens per second can it generate at batch size 1?
About 60. Each token reads every weight once, so tokens/s is about 12 GB/s divided by 0.2 GB. The measured run gave 63.3 tokens/s, which is 12.7 GB/s of implied bandwidth.
Streaming and non-streaming take the same total time for the same 64 tokens. In the kata, what was the time to first byte for each, and why does that gap matter?
17 ms streaming against 1011 ms non-streaming. The user starts reading after one token instead of after the last one, so the same speed feels about 60 times faster to start.

The core idea

Running an LLM is one loop wrapped in plumbing. The plumbing gets the weights onto the GPU and the text in and out. The loop is the model producing one token per pass, and every pass has to read all the weights from GPU memory. That one fact explains most of what you measure: how big a model fits, how fast it talks, and what you see in the monitoring tools.

This topic stays at the level of "get it running and read the dials". The internals of the forward pass are K04, the split between prefill and decode is K05, and the KV cache is K06. Slice for this page: fit, load, generate, stream, serve, watch.

Memory hook

Fit, Load, Stream, Watch. Fit: parameters times bytes per parameter, plus cache and overhead, must be under VRAM. Load: hub to disk to GPU once, dtype set, device checked. Stream: one chunk per token so the first byte arrives early. Watch: memory used, utilization, power, and tokens per second. Picture a bucket the size of the model carried from memory to the compute units for every single token.

How it works

Fit before you download

Weights take parameters times bytes per parameter: 4 for fp32, 2 for fp16 or bf16, 1 for int8, 0.5 for 4-bit. A 1.5B model in fp16 is about 3 GB, 3B is about 6 GB, 7B is about 14 GB. Add the KV cache (grows with context and users, see K07), activations, and a few hundred MB for the CUDA context. A 7B fp16 model does not leave usable room on a 16 GB card. Pick the model so weights take well under the card, not nearly all of it.

Download and load

The first from_pretrained call pulls the config, tokenizer and weight files from the hub into a local cache. Later calls read the cache. Weights usually arrive as safetensors. Gated models need an access token. Set the dtype yourself (dtype=torch.float16; older code says torch_dtype) instead of trusting a default, and pass device_map="cuda" so shards go straight to the GPU. Then confirm: print where the parameters live. A model that quietly stayed on the CPU is the most common first-run failure.

Check: you load a model and it runs at 2 tokens/s. What is the first thing you print?
Where the parameters live, for example next(model.parameters()).device, and whether torch.cuda.is_available() is true. A CPU-only PyTorch build or a missing device_map leaves the model on the CPU.

Generate

The tokenizer applies the chat template and turns text into ids. One pass over the whole prompt (prefill) produces the first token. Then each decode step feeds back the last token and produces the next. Use greedy decoding (do_sample=False) while measuring, so runs are repeatable. Each decode step at batch size 1 reads all the weights, so speed is capped near memory bandwidth divided by weight bytes.

Stream and serve

generate blocks until it finishes. To stream, run it in a worker thread with a TextIteratorStreamer and let the HTTP handler forward each piece as it appears, as chunked transfer or server-sent events. Load the model once at startup, never per request. Warm it up with one dummy request before taking traffic. Time to first token is prefill plus one decode step, and that is the number a user feels.

Check: why run generate in a worker thread behind an async HTTP handler?
It blocks for seconds. Called directly on the event loop, it freezes every other request and every other stream chunk until it returns. In a worker thread the loop stays free to send chunks as the streamer yields them.

Watch it

In a second terminal run nvidia-smi --query-gpu=utilization.gpu,memory.used,power.draw --format=csv -l 1. Memory jumps at load by roughly weights plus overhead. Utilization is the share of the sample window in which at least one kernel was running, not how much of the chip's compute was used. Power shows how hard the hardware works against its limit; decode at batch 1 usually draws less than prefill or training, so compare against your own run.

Kata: serve it, stream it, time it

A tiny HTTP server streams tokens from a toy decode loop, and a client in the same file measures first-byte time, tokens per second and the memory traffic that speed implies. The toy is a stack of matrix-vector products over float32 weights: it has no attention, no prefill and no KV cache, but it keeps the one property that matters here, which is that every token reads all the weights. No download, no GPU, no API key.

kata.py

"""K03 kata: serve a model over HTTP, stream tokens, measure TTFT and tokens/s.
Toy backend with the same memory-bound decode loop as a real LLM, so no download is needed.
Run: python kata.py        Change size: D=4096 python kata.py   or   L=16 python kata.py"""
import logging, os, threading, time, urllib.request
import numpy as np, psutil
from flask import Flask, Response, request

D, L, V, N = int(os.getenv("D", 2048)), int(os.getenv("L", 8)), 8000, int(os.getenv("N", 64))
rng = np.random.default_rng(0)
E = rng.standard_normal((V, D), dtype=np.float32) / D**0.5      # embedding, reused as unembedding
W = [rng.standard_normal((D, D), dtype=np.float32) / D**0.5 for _ in range(L)]
weight_bytes = E.nbytes + sum(w.nbytes for w in W)

def next_token(tok):                 # one decode step reads every weight once
    x = E[tok]
    for w in W:
        x = np.tanh(w @ x)
    return int(np.argmax(E @ x))     # logits over the vocab, greedy pick

app = Flask(__name__)
logging.getLogger("werkzeug").setLevel(logging.ERROR)

@app.get("/generate")
def generate():
    n, stream = int(request.args.get("n", N)), request.args.get("stream", "1") == "1"
    def tokens():
        tok = 1
        for _ in range(n):
            tok = next_token(tok)
            yield f"{tok}\n"
    if stream:
        return Response(tokens(), mimetype="text/plain")             # sent token by token
    return Response("".join(tokens()), mimetype="text/plain")       # sent after the last token

def call(stream):
    t0 = time.perf_counter()
    r = urllib.request.urlopen(f"http://127.0.0.1:5055/generate?n={N}&stream={stream}")
    first, count = None, 0
    for _ in r:
        first = first or time.perf_counter() - t0
        count += 1
    return first, time.perf_counter() - t0, count

if __name__ == "__main__":
    print(f"model: d={D} layers={L} vocab={V} weights={weight_bytes/1e6:.0f} MB (float32), cpus={os.cpu_count()}")
    threading.Thread(target=lambda: app.run(port=5055, threaded=True), daemon=True).start()
    time.sleep(1); call(1)                                         # warm up caches and the connection
    print(f"process memory: {psutil.Process().memory_info().rss/1e6:.0f} MB")
    for stream in (1, 0):
        first, total, count = call(stream)
        print(f"stream={stream}: first byte {first*1000:6.0f} ms | total {total*1000:6.0f} ms | {count/total:5.1f} tokens/s"
              f" | implied bandwidth {weight_bytes*count/total/1e9:5.1f} GB/s")

What to notice

  1. Weights are 200 MB but the process uses 285 MB. Memory is weights plus runtime, never weights alone.
  2. Both modes take about 1010 ms in total. Streaming reaches the client at 17 ms, non-streaming at 1011 ms. Streaming changes when you see output, not how fast it is made.
  3. 63.3 tokens/s times 200 MB is 12.7 GB/s. That number is the machine's usable memory bandwidth, and it is the ceiling the whole run sits under.
Break it
  1. Double the layers. Run L=16 python kata.py. Weights become 334 MB. Predict tokens/s from bytes before you run it. In my run: about 38 tokens/s, implied bandwidth unchanged near 12.5 GB/s.
  2. Make each layer 4 times bigger. Run D=4096 python kata.py. Weights become 668 MB. Predict, then run. In my run: about 18 tokens/s, process memory 722 MB, implied bandwidth still near 12.3 GB/s. The model got slower in proportion to its bytes while the bandwidth stayed put.

# Colab version of the same kata with a real model. NOT RUN in the workspace that built this page (no GPU, no hub access).
import time, torch
from threading import Thread
from transformers import AutoModelForCausalLM, AutoTokenizer, TextIteratorStreamer

name = "Qwen/Qwen2.5-1.5B-Instruct"
tok = AutoTokenizer.from_pretrained(name)
model = AutoModelForCausalLM.from_pretrained(name, dtype=torch.float16, device_map="cuda")
wbytes = sum(p.numel() * p.element_size() for p in model.parameters())
print(f"weights {wbytes/1e9:.2f} GB, on {next(model.parameters()).device}, "
      f"allocated {torch.cuda.memory_allocated()/1e9:.2f} GB")

msgs = [{"role": "user", "content": "Explain a KV cache in two sentences."}]
ids = tok.apply_chat_template(msgs, add_generation_prompt=True, return_tensors="pt", return_dict=True).to("cuda")
streamer = TextIteratorStreamer(tok, skip_prompt=True, skip_special_tokens=True)
t0 = time.perf_counter()
Thread(target=model.generate, kwargs=dict(**ids, max_new_tokens=128, do_sample=False, streamer=streamer)).start()
text, ttft = "", None
for piece in streamer:
    ttft = ttft or time.perf_counter() - t0
    text += piece
total = time.perf_counter() - t0
n = len(tok(text).input_ids)
print(f"TTFT {ttft*1000:.0f} ms | {n/total:.1f} tokens/s | implied bandwidth {wbytes*n/total/1e9:.0f} GB/s")

Traps

Each one sounds right. Say what is wrong with it before you open it.

"A 1.5B model needs about 1.5 GB of GPU memory."
That counts parameters, not bytes. In fp16 it is 2 bytes each, so about 3 GB for weights, and the KV cache, activations and CUDA context sit on top.
"nvidia-smi shows 100% GPU utilization, so the GPU is fully used and the model is running efficiently."
Utilization only reports the share of the sample window in which some kernel was running. A kernel that uses a sliver of the chip, or waits on memory, still counts. Batch-1 decode shows high utilization while being limited by memory bandwidth.

Question bank

Answer aloud, then open. Grade yourself honestly.

You have a 16 GB T4. Can you serve a 7B model in fp16? Show the arithmetic.
7B times 2 bytes is 14 GB of weights. Add the CUDA context and a KV cache and there is no usable headroom, so it fails or allows almost no context. Options: a 3B model in fp16 (about 6 GB), or the 7B in 4-bit (about 3.5 GB, with a quality cost to check).
Follow-upWhat does 4-bit cost you? Some quality, measured on your own task, and extra dequantization work in the kernels. It cuts bytes per token, so it usually speeds up decode.
Why does tokens per second fall when the model gets bigger on the same hardware?
Each decode step reads all the weights, so speed is about bandwidth divided by weight bytes. In the kata, weights went from 200 MB to 334 MB and speed went from 63 to about 38 tokens/s, while implied bandwidth stayed near 12.5 GB/s.
Follow-upWhat raises the single-stream ceiling? Fewer bytes (quantization), or a GPU with more bandwidth. Batching raises total throughput across users but does not speed up one stream.
Why stream, and what changes in the server?
Total time stays the same, but the first token arrives after prefill plus one decode step. In the kata that was 17 ms against 1011 ms. The server runs generation in a worker thread with a streamer and sends each piece as a chunk or server-sent event.
Follow-upStreaming works locally but not behind nginx. Why? The proxy buffers the response. Turn proxy buffering off for that route.
Which three fields do you read from nvidia-smi while a model serves, and what does each tell you?
memory.used: whether it fits and whether it grows over time. utilization.gpu: how often a kernel was running, not how saturated the chip is. power.draw: how hard the hardware works against its limit (70 W on a T4). Query them with nvidia-smi --query-gpu=utilization.gpu,memory.used,power.draw --format=csv -l 1.
The model loads fine, runs at 2 tokens/s, and utilization shows 0%. Diagnose it.
It is almost certainly on the CPU. Print the parameter device and torch.cuda.is_available(). Causes: a CPU-only PyTorch wheel, a driver or CUDA mismatch, or loading without device_map or .to("cuda").
After a deploy, the first request takes 40 seconds and later ones take 2. What happened and what do you change?
The model, tokenizer or CUDA kernels were initialized on the first call. Load the model at process start, run a dummy generation as warm-up, and only then report ready to the load balancer.

Mixed review

Three questions from earlier topics. Nobody tells you the topic in an interview.

K02: torch.cuda.is_available() returns False on a machine that has a GPU. Name three causes.
A CPU-only PyTorch build, a missing or mismatched NVIDIA driver for the CUDA version PyTorch was built with, or a container started without GPU access.
K01: Name the stages a request passes through from the client to the GPU and back.
Client, HTTP server, tokenizer, the model forward pass on the GPU in a loop, sampling, detokenizing, then streamed back. Each stage adds time, and the GPU loop is where most of it goes.
A02: What goes wrong if an async server calls a blocking function directly in a handler?
The event loop is blocked for the whole call, so no other request or stream chunk makes progress. Move the blocking work to a thread or process and await it.
