Python for AI engineering

How do you keep bad input out of an AI system at the boundary, and make the project reproducible on someone else's machine? This page covers type hints, dataclasses, pydantic validation and uv packaging.

Study path

Before you read

Guess first. A wrong guess now makes the right answer stick later.

You annotate max_tokens: int in a dataclass and pass "512". What does Python do at runtime?
Nothing. The dataclass stores the string as is. Type hints are not enforced by the interpreter. The kata's plain dataclass accepted max_tokens='512' and temperature='hot'.
A teammate writes max_token: 512 (missing the s) in a config file. With a default pydantic model, is that an error?
No. Pydantic ignores extra keys by default, so the typo is dropped and max_tokens silently falls back to its default (1024 in the kata). You need extra="forbid" to catch it.
Pydantic gets "512" for an int field. Accept, reject, or depends?
Depends on the mode. Lax mode (the default) coerces "512" to 512. Strict mode rejects it. The kata runs strict and rejects it; BREAK=2 runs lax and accepts it.

The core idea

Python is dynamic, and AI systems feed it messy data from every side: env vars (always strings), JSON from users, JSON from a model, YAML configs. A type hint says what you meant. Nothing checks it unless you add a checker. So you split the world in two: a messy outside and a typed inside, with one validation gate between them.

The gate is a pydantic model. Raw input goes in. Either a fully valid, typed, frozen object comes out, or you get every error at once with the field path and the bad value. Past the gate, the rest of your code can trust the types. The same gate also checks structured output from an LLM, which is why this tool shows up all over AI code.

Memory hook

Gate, not guard. Four verbs at the gate: parse (coerce or not), check (ranges and lengths), forbid (unknown keys), freeze (no later mutation). Then lock the environment with uv so the gate runs the same everywhere.

How it works

Type hints are metadata

The interpreter stores annotations and ignores them. Tools read them: mypy or pyright statically, pydantic and dataclass-style libraries at runtime. A static checker catches a wrong call in your own code. It cannot see a string that arrives from a file at runtime. That is the gap validation fills.

Check: your code passes mypy. Why can max_tokens still be a string at runtime?
mypy checks code you wrote against annotations. Data loaded from env vars or JSON arrives at runtime and bypasses it. Only runtime validation (pydantic) checks that data.

Dataclasses: structure without checks

@dataclass generates __init__, __repr__ and __eq__ from the annotated fields. Use it for internal records you build yourself. frozen=True makes instances immutable. It does no validation, so it suits data that is already trusted.

Pydantic: parse, check, report

A BaseModel validates on construction. Field(ge=0, le=2) adds bounds. All errors are collected and reported together, each with a location, a message and the bad input. Key settings: extra="forbid" rejects unknown keys, strict=True disables coercion, frozen=True blocks mutation. Pydantic v2 runs its core in Rust, which is why validation is fast enough to sit on hot paths.

Check: when do you pick a plain dataclass over a pydantic model?
Dataclass for internal data you construct yourself and already trust. Pydantic at the boundary, where input is untrusted: config files, API requests, LLM output.

uv: one tool for the environment

uv init creates a project with pyproject.toml. uv add pydantic records the dependency and writes uv.lock, which pins exact versions of everything, including transitive dependencies. uv sync rebuilds the environment from the lock. uv run python kata.py runs inside that environment. Commit the lock file; a teammate or a CI job then gets the same versions you tested.

Check: why commit uv.lock as well as pyproject.toml?
pyproject.toml lists version ranges. The lock pins exact resolved versions, so every machine gets the same environment. Without it, a new release of a dependency can change behavior between two installs.

Kata: typed config loader

Load an LLM config from a dict. A plain dataclass accepts garbage. A pydantic model rejects it and lists every problem with the field path and the bad value.

Run

uv add pydantic   # or: pip install pydantic
python kata.py

kata.py

"""A01 kata: a typed config loader that rejects bad input with clear errors.
Run: python kata.py            (try BREAK=1 python kata.py, then BREAK=2 python kata.py)
"""
import os
from dataclasses import dataclass
from typing import Annotated
from pydantic import BaseModel, ConfigDict, Field, ValidationError

BREAK = os.environ.get("BREAK", "")

# --- 1. Plain dataclass: type hints are documentation only. Nothing is checked. ---
@dataclass
class PlainConfig:
    model: str
    temperature: float
    max_tokens: int

# --- 2. Pydantic model: the same shape, but checked at the boundary. ---
class LLMConfig(BaseModel):
    # BREAK=1 drops extra="forbid", so typos in keys vanish silently.
    # BREAK=2 turns on lax coercion for everything (strict False is the default).
    model_config = ConfigDict(
        extra=None if BREAK == "1" else "forbid",
        strict=False if BREAK == "2" else True,
        frozen=True,
    )
    model: Annotated[str, Field(min_length=1)]
    temperature: Annotated[float, Field(ge=0.0, le=2.0)] = 0.7
    max_tokens: Annotated[int, Field(gt=0, le=200_000)] = 1024
    retries: Annotated[int, Field(ge=0, le=5)] = 2

def load(raw: dict) -> LLMConfig | None:
    try:
        return LLMConfig(**raw)
    except ValidationError as e:
        print(f"  REJECTED with {e.error_count()} error(s):")
        for err in e.errors():
            loc = ".".join(str(p) for p in err["loc"])
            print(f"    - {loc}: {err['msg']} (got {err['input']!r})")
        return None

CASES = {
    "good":        {"model": "llama-3.1-8b", "temperature": 0.2, "max_tokens": 512},
    "bad values":  {"model": "", "temperature": 7.5, "max_tokens": -5},
    "wrong types": {"model": "llama-3.1-8b", "temperature": "hot", "max_tokens": "512"},
    "typo in key": {"model": "llama-3.1-8b", "max_token": 512},
}

print("== plain dataclass (no checks) ==")
for name, raw in CASES.items():
    try:
        c = PlainConfig(**{k: v for k, v in raw.items() if k in PlainConfig.__annotations__})
        print(f"{name:12s} accepted: {c}")
    except TypeError as e:
        print(f"{name:12s} crashed: {e}")

print(f"\n== pydantic LLMConfig (BREAK={BREAK or 'off'}) ==")
for name, raw in CASES.items():
    print(f"{name:12s}")
    c = load(raw)
    if c:
        print(f"  accepted: {c.model_dump()}")

print("\n== frozen: mutation is blocked ==")
good = load(CASES["good"])
try:
    good.temperature = 9.9
except ValidationError as e:
    print("  blocked:", e.errors()[0]["type"])

What to notice

  1. The dataclass accepted temperature=7.5, max_tokens=-5 and an empty model name. It stored 'hot' and '512' as strings.
  2. "bad values" produced 3 errors in one report, not 1. You fix everything in one pass.
  3. The typo max_token is rejected because of extra="forbid".
  4. "512" is rejected for an int field because the model is strict. In production, env vars are always strings, so you must parse them deliberately.
  5. Assigning to a frozen model raises frozen_instance, so config cannot drift mid-run.
Break it
  1. Drop forbid. Run BREAK=1 python kata.py. Predict first: what happens to the "typo in key" case, and what value does max_tokens end up with? (Accepted, with max_tokens at its default 1024. The typo is silent.)
  2. Go lax. Run BREAK=2 python kata.py. Predict first: which of the "wrong types" errors disappear? ("512" is coerced to 512; only 'hot' still fails.)

Stretch. Add a field validator that checks model against an allowed list, and load the values from environment variables with pydantic-settings.

Caveat: the dataclass "typo in key" crash in the output comes from the kata's own filter, which drops unknown keys before building. It is a contrived case; the point is the first three rows.

Say this aloud against the clock. Three levels, about 90 seconds.

1 Outcome 20 sIn AI systems, most failures start with bad data crossing a boundary: a mistyped config key, a string where a number belongs, a model returning malformed JSON. I put a typed validation gate at every boundary so the rest of the code can trust its inputs, and I pin the environment with a lock file so it behaves the same on every machine.
2 Mechanism 45 sType hints are only metadata; Python ignores them at runtime. So I use pydantic models at the edges. Construction parses and checks the input, applies bounds like temperature between 0 and 2, and collects all errors with field paths in one ValidationError. I set extra to forbid so typos fail loudly, strict so a string never silently becomes an int, and frozen so config cannot change mid-run. Internal records that I build myself are plain dataclasses. For packaging I use uv: pyproject lists ranges, uv.lock pins exact versions, uv sync rebuilds the environment.
3 Internals and limits 25 sPydantic defaults are lax and ignore unknown keys, so the safe settings are opt-in. Strict mode makes env vars awkward since they are always strings, so parse them on purpose. Validation checks shape and ranges, not truth: a model can return valid JSON with wrong content. Track validation failure rate as a signal.

Traps

Each one sounds right. Say what is wrong with it before you open it.

"We annotate everything with type hints, so wrong types raise errors at runtime."
Wrong. The interpreter ignores annotations. A dataclass with max_tokens: int happily stored '512' in the kata. Only a checker (mypy statically) or a validating library (pydantic at runtime) acts on hints.
"Pydantic always rejects bad input, so a typo in a config key will be caught."
Wrong. By default pydantic ignores extra keys. With the typo max_token the kata (BREAK=1) accepted the config and used the default 1024. You need extra="forbid".

Question bank

Answer aloud, then open. Grade yourself honestly.

Explain in 90 seconds how you keep bad input out of an AI service and make the project reproducible.
Use the three-level answer above: boundary validation with strict, forbid and frozen pydantic models, dataclasses for trusted internals, uv.lock for reproducible installs, and a failure-rate metric.
Dataclass or pydantic model for a record that came from a user request?
Pydantic. The data is untrusted, so it must be parsed and checked. Dataclasses do no validation.
Follow-upWhere do you use a dataclass then? For internal records you construct from already-validated values.
What is the difference between lax and strict validation, and which do you want for env vars?
Lax coerces compatible types ("512" becomes 512). Strict rejects them. Env vars are always strings, so either parse them explicitly or use a settings class that is meant to coerce, and keep strict for API payloads.
A model returns JSON that sometimes breaks your parser. What do you do?
Validate with a pydantic model, catch ValidationError, and retry with the error message fed back or fall back. Log failure rate by field.
Follow-upWhat does validation not catch? Wrong content that is well-formed, like a plausible but incorrect number. That needs evals.
Why does a project need both pyproject.toml and uv.lock?
pyproject.toml declares what you want (ranges). The lock records what was resolved (exact versions, transitive included). Commit both for reproducible installs.
What does frozen=True buy you on a config object?
Immutability. Code cannot change a setting mid-run, which removes a class of bugs where one component mutates shared config. It also makes the object hashable.

Mixed review

A01 is the first topic, so there is no earlier topic to draw from. These three use the Python you already know.

Prereq: what is the difference between a list and a tuple, and why does it matter for a config object?
Lists are mutable, tuples are immutable. Immutable values are hashable and safe to share, which matches the goal of a frozen config.
Prereq: what does a virtual environment isolate?
The installed packages for one project, so two projects can use different versions of the same library without conflict.
Prereq: why is a mutable default argument like def f(x=[]) a bug?
The default is created once at function definition, so every call shares the same list and mutations persist across calls.
