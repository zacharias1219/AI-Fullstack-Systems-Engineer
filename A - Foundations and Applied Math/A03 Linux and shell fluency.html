Linux and shell fluency

How do you find what a machine is really doing, stop one bad process without corrupting its work, and keep long jobs alive on a remote GPU box? This page covers processes, signals, pipes, memory columns, tmux and nvidia-smi. It does not cover Docker or systemd internals.

Before you read

Guess first. A wrong guess now makes the right answer stick later.

A Python worker allocates exactly 150 MB and touches every page. What RSS does ps report for it, roughly?
About 161 MB in the kata run. The interpreter itself adds about 11 MB, and the 20 MB and 60 MB workers showed 31 MB and 71 MB. RSS is real resident memory, not your allocation.
You reach for kill -9 as your first move on a stuck worker. What can that cost you?
SIGKILL cannot be caught, so the process gets no chance to flush buffers, write a checkpoint or release locks. SIGTERM first, a short wait, then SIGKILL only if it is still alive.
In yes | head -1, yes runs forever by design. Why does the pipeline end, and what are the two exit statuses?
head exits after one line and closes the pipe. The next write by yes raises SIGPIPE and kills it. The kata box printed 141 and 0, and 141 is 128+13.

The core idea

Everything running on a Linux box is a process with a PID. You control a process by sending it a signal, and you connect processes by pipes, where the output of one is the input of the next. Fluency means you can answer three questions fast: what is running, who is using the memory or GPU, and how do I stop it without losing work.

The safe stop is a short protocol, not one command. You ask politely, wait, force only if needed, then check the result. The diagram shows the timing from the kata.

Memory hook

Safe stop is a landlord story: find the room (ps sorted by RSS), knock (SIGTERM), wait a few seconds, break the door (SIGKILL), check the room is empty (kill -0), move the new tenant in (restart).

How it works

Processes and signals

A signal is a small numbered message to a PID. The ones to know: SIGHUP 1 (terminal hung up), SIGINT 2 (Ctrl-C), SIGKILL 9, SIGTERM 15, SIGSTOP 19 on x86-64. A process may catch or ignore SIGTERM, which is how it flushes a checkpoint. SIGKILL and SIGSTOP cannot be caught. A process that dies from a signal reports an exit status of 128 plus the signal number: 143 for SIGTERM, 137 for SIGKILL.

Check: a container job exits with status 137 and no error in its logs. What is the first thing you suspect?
It received SIGKILL. In containers that is most often the kernel out-of-memory killer, so check dmesg or the container's OOM event and its memory limit before anything else.

Pipes

Each stage of a pipeline is its own process and all of them run at once. The kernel pipe between them holds 65,536 bytes by default on this box, so a fast writer blocks when the buffer is full. If the reader exits early, the next write raises SIGPIPE. The pipeline's exit status is the last command's unless you run set -o pipefail, and then it is the last failing one.

Check: false | true; echo $? prints what, and how do you make it report the failure?
It prints 0, because only the last command counts. Run set -o pipefail first and it prints 1. This is how broken stages hide in CI scripts.

Reading memory and the machine

In ps and top, RSS is the pages the process holds in RAM right now, and VSZ is the virtual address space it has mapped, which can be huge and harmless. Shared library pages count in every process that maps them, so summed RSS overcounts. For whole-machine memory read the available column of free -h, not free. htop shows load per core and per process at a glance.

Remote work and the GPU

When an SSH connection drops, the shell sends SIGHUP to its jobs and a plain foreground training run dies. tmux keeps a session alive on the server: tmux new -s train, detach with Ctrl-b then d, return with tmux attach -t train. nvidia-smi lists GPU memory used and total, utilization, and the PIDs holding memory. Its utilization number is the share of time any kernel was running, not how much of the chip was busy.

Check: nvidia-smi says 40 GB used and you have no job running. Which two commands find the holder?
Read the PID column in nvidia-smi, then ps -fp PID to see what it is. In containers the PID may be hidden, so fuser -v /dev/nvidia* is the fallback. Stop it with SIGTERM, then SIGKILL.

Kata: find the hog, stop it cleanly, restart it

It starts three Python workers that hold 20, 60 and 150 MB, finds the biggest with one pipeline, stops it with the SIGTERM protocol, verifies it is gone, and restarts a smaller one. It needs bash, python3 and Linux ps. On macOS use a Linux shell, since the ps flags differ.

Run

bash kata.sh

kata.sh

#!/usr/bin/env bash
# A03 kata: find the memory hog with one pipeline, stop it cleanly, restart it.
# Run: bash kata.sh        Break it: STUBBORN=1 bash kata.sh   or   NOWAIT=1 bash kata.sh
set -u
MB=${MB:-150}
PIDS=()

hog() {  # name, megabytes, ignore_sigterm(0/1): hold real memory until signalled
  python3 -c "
import signal, sys, time
buf = bytearray($2 * 1024 * 1024)
for i in range(0, len(buf), 4096): buf[i] = 1      # touch pages so RSS is real
if $3: signal.signal(signal.SIGTERM, signal.SIG_IGN)
else: signal.signal(signal.SIGTERM, lambda *a: (print('  [$1] got SIGTERM, cleaning up', flush=True), sys.exit(0)))
print('  [$1] up, holding $2 MB', flush=True)
while True: time.sleep(0.2)
" &
  PIDS+=($!)
}
top3() { ps -p "$(IFS=,; echo "${PIDS[*]}")" -o pid=,rss= --sort=-rss 2>/dev/null | awk 'NR<=3 {printf "%s %.0f MB\n",$1,$2/1024}'; }
now_ms() { echo $(( $(date +%s%N) / 1000000 )); }

echo "== 1. start three workers (20, 60, $MB MB)"
hog small 20 0; hog medium 60 0; hog big "$MB" "${STUBBORN:-0}"
sleep 1.5

echo; echo "== 2. one pipeline: top memory hogs (by resident memory)"
top3 | tee /tmp/a03_top.txt
BIG_PID=$(head -1 /tmp/a03_top.txt | cut -d' ' -f1)

echo; echo "== 3. stop PID $BIG_PID: SIGTERM, wait up to 3s, then SIGKILL"
t0=$(now_ms); kill -TERM "$BIG_PID"
while kill -0 "$BIG_PID" 2>/dev/null; do
  [ -n "${NOWAIT:-}" ] && break
  [ $(( $(now_ms) - t0 )) -ge 3000 ] && break
  sleep 0.1
done
if kill -0 "$BIG_PID" 2>/dev/null; then
  echo "  still alive after $(( $(now_ms) - t0 )) ms: escalating to SIGKILL"; kill -KILL "$BIG_PID"
else
  echo "  exited after SIGTERM in $(( $(now_ms) - t0 )) ms"
fi
wait "$BIG_PID" 2>/dev/null; echo "  exit status: $? (0 = handled SIGTERM, 137 = SIGKILL)"

echo; echo "== 4. verify it is gone, then restart it smaller"
sleep 0.2
kill -0 "$BIG_PID" 2>/dev/null && echo "  FAIL: PID $BIG_PID still running" || echo "  PID $BIG_PID gone"
hog big2 40 0; sleep 1

echo; echo "== 5. memory now"
top3

echo; echo "== 6. cleanup (SIGKILL our own PIDs only)"
kill -KILL "${PIDS[@]}" 2>/dev/null; wait 2>/dev/null; echo "  done"

What to notice

  1. RSS read 161, 71 and 31 MB for allocations of 150, 60 and 20 MB. The constant 11 MB is the interpreter, so sorting by RSS finds the right process but the number is not your data size.
  2. The worker caught SIGTERM, printed its cleanup line and exited with status 0 in 106 ms. That status 0 is the proof it handled the signal itself.
  3. The restarted worker has a new PID (537 in this run). A restart is a new process, not the old one coming back.
  4. After the kill, step 5 shows 71, 51 and 31 MB. The 161 MB hog is gone and the 40 MB replacement (51 MB with overhead) took its place.
Break it
  1. A worker that ignores SIGTERM. Run STUBBORN=1 bash kata.sh. Predict first: how long until the script escalates, and what exit status do you get? (Run result: still alive after 3042 ms, status 137.)
  2. No waiting. Run NOWAIT=1 bash kata.sh. Predict whether the cleanup line still prints before the kill. (Run result: it often does, but the escalation came after 1 ms and the status was 137, so the cleanup was racing the SIGKILL and cannot be relied on.)

Stretch. Run MB=400 bash kata.sh inside a shell with ulimit -v set low and watch the allocation fail, then read dmesg for OOM lines if your box has a real memory limit.

Traps

Each one sounds right. Say what is wrong with it before you open it.

"kill -9 is the reliable way to stop a process, so I just use it every time."
It always works, which is the problem. SIGKILL cannot be caught, so the process cannot flush a checkpoint or release locks, and you get status 137 with possibly corrupt output. Use SIGTERM, wait, then SIGKILL.
"I sorted ps by RSS and added up the numbers, so the box is using that much memory."
RSS counts shared pages once per process that maps them, so the sum overcounts. For whole-machine use read the available column in free -h.

Question bank

Answer aloud, then open. Grade yourself honestly.

How do you find the top memory hog on a server and stop it safely?
Sort ps by RSS and take the top rows. Send SIGTERM, wait a few seconds, send SIGKILL only if it is still alive, confirm with kill -0 that the PID is gone, then restart.
Follow-upWhat if it ignores SIGTERM? Then it stays alive past the wait, you escalate to SIGKILL, and you accept losing unflushed work. Our run took 3042 ms to reach that decision.
What is the difference between SIGTERM and SIGKILL, and what exit codes do they give?
SIGTERM (15) can be caught or ignored and allows cleanup. SIGKILL (9) cannot be caught. Exit status is 128 plus the signal, so 143 and 137.
What are RSS and VSZ, and why can summed RSS exceed physical memory?
RSS is pages currently in RAM, VSZ is the mapped virtual address space. Shared pages are counted in every process that maps them, so the sum overcounts.
How does a pipeline's exit status work, and what does pipefail change?
By default it is the last command's status, so false | true gives 0. With pipefail it is the last non-zero status, so 1.
Follow-upWhy did yes stop in yes | head -1? head closed the pipe, the next write raised SIGPIPE, and yes exited with 141.
Your training job dies every time your SSH connection drops. Why, and what do you do?
The shell sends SIGHUP to its jobs on disconnect. Run it in tmux, detach with Ctrl-b d and reattach later, or use nohup with a log file.
nvidia-smi shows 20 GB of GPU memory used and nothing of yours is running. What do you do?
Read the PIDs in nvidia-smi, inspect them with ps, and stop the leftover python or dataloader worker with SIGTERM then SIGKILL. In containers use fuser -v /dev/nvidia* if the PID column is empty.
Follow-upDoes 90 percent utilization mean the GPU is 90 percent busy? Not exactly. It means a kernel was running for 90 percent of the sample period, however small that kernel was (from memory, verify).

Mixed review

Three questions from earlier topics. Nobody tells you the topic in an interview.

A02: You fire 50 LLM calls with asyncio.gather. What does adding a Semaphore change?
Gather alone starts all 50 at once. A semaphore caps in-flight calls at N, which protects you from rate limits and connection exhaustion while still overlapping the waiting.
A02: Does the GIL stop threads from speeding up a batch of LLM API calls?
No. The GIL is released while waiting on network I/O, so threads overlap those waits. It does block parallel speedup for CPU-bound Python code.
A01: Type hints exist, so why validate config with pydantic?
Hints are not enforced at runtime. Pydantic checks and coerces values at the boundary and raises clear errors, so bad input fails at load time instead of deep in a run.
