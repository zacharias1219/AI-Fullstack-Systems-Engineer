Async Python

How does one Python process keep dozens of LLM calls in flight, how do you cap them so the provider does not reject you, and what breaks it? This page covers the event loop, gather, semaphores, the GIL and the failure modes that interviews probe.

Study path

Before you read

Guess first. A wrong guess now makes the right answer stick later. The kata fires 50 fake LLM calls, each taking 0.1 s of pure waiting.

Called one after another with await, how long do the 50 calls take?
About 5.0 s. Latency adds up: 50 x 0.1 s. The kata measured 5.02 s.
You start all 50 at once with gather. The fake server rejects any call that arrives while 20 are already in flight. How long does it take, and how many calls succeed?
About 0.10 s, because everything waits at the same time. But only 20 succeed. The other 30 fail with a 429, since all 50 are in flight together. Fast and wrong.
Inside each call you replace await asyncio.sleep(0.1) with time.sleep(0.1) and run gather again. What is the total time?
About 5.0 s. time.sleep never yields, so the event loop is frozen for 0.1 s per call and nothing overlaps. The code still looks concurrent and is not.

The core idea

An LLM call is almost all waiting. Your code sends a request, then sits idle while the provider prefills, decodes and streams tokens back. The CPU cost on your side is microseconds; the wall-clock cost is seconds. Sequential code wastes that idle time because it waits for call 1 to finish before it starts call 2.

Concurrency means many things are in progress at once. Parallelism means many things are executing at the same instant on different cores. Asyncio gives you concurrency on one thread: a single event loop runs one coroutine at a time, but whenever a coroutine hits an await on something that is not ready, it steps aside and the loop runs another. Fifty waits overlap, so the total is roughly one wait, not fifty.

Mental model: one cook, many timers. The cook never stands staring at one pot. They start every pot, then handle whichever timer rings. This works only if the cook never does a long job without looking up, and only if the stove has enough burners.

Memory hook

Cook with timers. Never stare at a pot (no blocking calls). Start all the pots (gather). Only as many burners as you own (semaphore). A timer on every pot (timeout). A second cook for the chopping (process pool for CPU work). Five clauses, five parts of the topic.

How it works

Coroutines do nothing until something runs them

Calling an async def function returns a coroutine object and runs no code. Two things run it. await coro runs it inline, to completion, before your line continues, so awaiting in a loop is sequential. asyncio.create_task(coro) or gather hands it to the event loop as a Task that runs alongside others. The first kata variant, a list comprehension of awaits, is the sequential trap people write by accident.

The event loop is a ready queue plus a selector

Each turn the loop does three things: run every callback in the ready queue, ask the operating system which sockets are ready (the selector, epoll on Linux), and move tasks whose I/O or timer has finished back to the ready queue. A task only gives up the thread at an await that actually suspends. Between awaits it runs uninterrupted. That is why a single blocking call, time.sleep, a synchronous requests.get, a big JSON parse, stalls every other task.

Check: your coroutine awaits a function that returns immediately without waiting on anything. Does the loop switch to another task at that await?
No. Awaiting a coroutine that completes without suspending just continues; the loop only regains control when something suspends on I/O, a timer or a future. A long loop of such awaits can still starve other tasks.

Concurrency, parallelism and the GIL

In the standard CPython build, the Global Interpreter Lock lets one thread execute Python bytecode at a time per process. Threads still help with I/O, because the lock is released while a thread waits on a socket. They do not speed up pure-Python CPU work. For CPU work you use processes (ProcessPoolExecutor) or native code that releases the lock, such as NumPy. Python 3.13 added an experimental free-threaded build, and 3.14 made it officially supported, but it is still optional and the GIL build remains the default. In an async service, push blocking or CPU work off the loop with asyncio.to_thread (threads, good for blocking I/O libraries) or run_in_executor with a process pool (good for CPU).

Check: you must call a library that only has a blocking client, from an async service. What do you do, and why does it not freeze the loop?
Wrap it in asyncio.to_thread. The blocking call runs in a worker thread, the GIL is released while it waits on the network, and the loop thread stays free. The default thread pool is limited (here min(32, cpus + 4) = 6 on 2 CPUs), so it is not unlimited either.

Bounding concurrency: the semaphore and Little's law

Unbounded gather is the beginner bug. Providers enforce limits on requests and tokens per minute, your HTTP client has a connection pool, and each in-flight call holds memory. An asyncio.Semaphore(C) lets at most C coroutines past the gate at once. With N calls of latency L, total time is about ceil(N / C) x L. Throughput follows Little's law: in-flight = rate x latency, so rate = C / L. A cap of 10 at 0.1 s gives 100 calls per second. In production, work backwards: to sustain 20 requests per second at 2 s latency you need about 40 in flight, and you set the cap just under the provider's limit, not at it.

Check: latency is 2 s, the provider allows 50 requests per second, and you want to stay near 80 percent of that. What cap?
Target rate 40 per second. In-flight = 40 x 2 = 80, so a semaphore of about 80. If limits are in tokens per minute, requests are not the binding constraint and you need a token-aware limiter.

Failure, cancellation and timeouts

By default gather raises the first exception to the caller and leaves the other awaitables running, so you can return an error to a user while forty calls keep spending money in the background. return_exceptions=True turns exceptions into results, which is what the kata uses. asyncio.TaskGroup (3.11+) is the structured version: if one child fails, it cancels the siblings and raises an ExceptionGroup. Always bound a wait with asyncio.timeout (3.11+) or wait_for, because a hung provider connection otherwise holds a semaphore slot forever. Retry 429 and 5xx with exponential backoff and jitter, respect Retry-After, and let CancelledError propagate rather than swallowing it.

Check: why add jitter to retry backoff?
Without it, every client that failed at the same moment retries at the same moment, recreating the burst that caused the 429. Random spread breaks the synchronization.

Kata: 50 fake LLM calls, three ways

It shows the three timings, the 429 failure when you skip the cap, and the collapse back to sequential when one blocking call sits inside a coroutine. No API key, no network, about a minute to run.

Run

python kata.py

kata.py

"""A02 kata: 50 fake LLM calls, three ways. Run: python kata.py [--block] [--limit N]"""
import asyncio, sys, time

N, LATENCY, SERVER_LIMIT = 50, 0.1, 20   # server rejects the 21st in-flight call
BLOCK = "--block" in sys.argv            # break it 1: blocking sleep inside the coroutine
SEM = int(sys.argv[sys.argv.index("--limit") + 1]) if "--limit" in sys.argv else 10

in_flight = peak = 0

async def fake_llm(i):
    global in_flight, peak
    in_flight += 1
    peak = max(peak, in_flight)
    try:
        if in_flight > SERVER_LIMIT:
            raise RuntimeError("429 too many requests")
        if BLOCK:
            time.sleep(LATENCY)              # blocks the whole event loop
        else:
            await asyncio.sleep(LATENCY)     # yields to the loop while "waiting on the network"
        return i
    finally:
        in_flight -= 1

async def sequential():
    return [await fake_llm(i) for i in range(N)]

async def gather_all():
    return await asyncio.gather(*(fake_llm(i) for i in range(N)), return_exceptions=True)

async def with_semaphore():
    sem = asyncio.Semaphore(SEM)
    async def guarded(i):
        async with sem:
            return await fake_llm(i)
    return await asyncio.gather(*(guarded(i) for i in range(N)), return_exceptions=True)

async def run(name, fn):
    global peak
    peak = 0
    t = time.perf_counter()
    out = await fn()
    dt = time.perf_counter() - t
    bad = sum(isinstance(r, Exception) for r in out)
    print(f"{name:<14} {dt:6.2f}s  ok={len(out) - bad:<3} failed={bad:<3} peak_in_flight={peak}")

async def main():
    print(f"N={N} latency={LATENCY}s server_limit={SERVER_LIMIT} semaphore={SEM} block={BLOCK}")
    print(f"ideal: sequential={N * LATENCY:.1f}s  fully parallel={LATENCY:.1f}s  "
          f"semaphore={-(-N // SEM) * LATENCY:.1f}s")
    await run("sequential", sequential)
    await run("gather(all)", gather_all)
    await run(f"semaphore({SEM})", with_semaphore)

asyncio.run(main())

sequential       5.02s  ok=50  failed=0   peak_in_flight=1
gather(all)      0.10s  ok=20  failed=30  peak_in_flight=21

What to notice

  1. Sequential took 5.02 s, almost exactly 50 x 0.1 s. No surprise: nothing overlapped.
  2. gather finished in 0.10 s, which is one latency, not fifty. All 50 waits overlapped.
  3. That speed was fake: 30 of 50 calls failed. Peak in flight was 21, because the 21st call increments the counter before it is rejected, and all 50 coroutines start before any finishes.
  4. The semaphore run took 0.50 s, five waves of 10, and peak in flight stayed at 10 with zero failures. It is 5x slower than the unsafe run, but it is the only fast run that is also correct.
Break it
  1. Block the loop. Run python kata.py --block. Predict the three timings first. Result: all three take about 5.0 s, peak in flight 1, no 429s. The single blocking time.sleep serialized everything, and gather could not help.
  2. Cap exactly at the limit. Run python kata.py --limit 20. Predict the time and failures. Result: 0.30 s, zero failures, because ceil(50 / 20) = 3 waves.
  3. Cap above the limit. Run python kata.py --limit 25. Predict. Result: 0.10 s with 30 failures, the same as no semaphore at all. A cap larger than the server's limit protects nothing, and the cap must be derived from the limit, not guessed.

Stretch. Replace the semaphore with a queue and 10 worker tasks that pull from it, and confirm the same 0.50 s. Then add a failure that raises on one call, remove return_exceptions=True, and watch what happens to the other 49 (hint: count how many still run to completion).

Monitor: in-flight count, time spent waiting for the semaphore, event loop lag (schedule a tiny task and measure its delay), 429 and timeout rates, and p99 latency by endpoint.

Scenario: your voice AI service for clinics streams audio over WebSockets in one asyncio process. After you add on-device embedding with NumPy inside the handler, callers report audio stuttering for everyone while one call is processing. What do you check and fix?
  1. Suspect the loop is blocked. The embedding runs synchronously inside a coroutine, so every other call's audio frames wait for it.
  2. Confirm with debug mode (PYTHONASYNCIODEBUG=1), which logs callbacks slower than 0.1 s, and with a loop-lag metric.
  3. Fix: move the embedding to run_in_executor with a process pool (NumPy may release the GIL, but a model with Python overhead may not), or to a separate service.
  4. Cap concurrent embeddings so the pool does not queue unboundedly, and add a timeout.
  5. Add a regression alert on loop lag so the next blocking call is caught in staging.

1 Outcome 20 sAsync lets one Python process keep many LLM calls in flight on a single thread, because those calls are almost all network wait. In my kata, fifty 100 millisecond calls took 5 seconds one after another and half a second with a concurrency cap of ten. That is the difference between a usable batch job or chat backend and a slow one.
2 Mechanism 45 sAn event loop runs coroutines on one thread. Say it like an engineer

Question: "How would you run 1,000 LLM calls quickly?"

"I would use async so the calls run in parallel and it is much faster."

"The calls are latency-bound, so I fan out with asyncio behind a semaphore. I size the cap from the provider's limit and Little's law: at a 2 second latency and a ceiling of 50 requests per second, steady state is about 100 in flight, so I would start lower, near 80 percent, and tune. Every call gets a timeout, 429s retry with jittered backoff, and I use return_exceptions so one failure does not orphan the rest. The numbers here are illustrative, not from my own results."

The strong answer names the mechanism, derives a number, states the failure mode and the tradeoff. The weak one says "parallel", which is also technically wrong.

Traps

Each one sounds right. Say what is wrong with it before you open it.

"Async makes Python run on multiple cores in parallel."
Wrong. Asyncio runs one thread. It gives concurrency of waiting, not parallel execution. For CPU work on several cores you need processes (or the optional free-threaded build).
"If I mark the function async def, it will not block."
Wrong. The keyword changes how the function is called, not what is inside it. A time.sleep or synchronous HTTP call in the body blocks the whole loop. In the kata, --block took gather from 0.10 s back to 5.01 s.
"asyncio.gather cancels the other calls as soon as one fails."
Wrong by default. The first exception is propagated to the caller but the other awaitables keep running. TaskGroup is the one that cancels siblings. Use return_exceptions=True if you want every result.
"Because of the GIL, threads are useless in Python."
Wrong. The lock is released while a thread waits on I/O, so threads work fine for blocking network calls (that is what to_thread relies on). They are useless only for pure-Python CPU-bound work.

Question bank

Answer aloud, then open. Grade yourself honestly.

Explain concurrency versus parallelism, and say which one asyncio gives you.
Concurrency is many tasks in progress, interleaved; parallelism is many executing at the same instant on separate cores. Asyncio gives concurrency on one thread. Waiting overlaps; computation does not.
Follow-upHow would you get parallelism? Processes (ProcessPoolExecutor or multiple worker processes), native code that releases the GIL, or the optional free-threaded build.
Why does async help with LLM API calls but not with computing embeddings locally on the CPU?
API calls spend nearly all their time waiting on the network, and waits overlap on one thread. Local embedding is CPU work: it holds the thread the whole time, so nothing overlaps, and in the loop it blocks everyone else.
Follow-upWhere does it go? A process pool or separate service, with a cap on concurrent jobs.
For 50 calls at 0.1 s, predict sequential, gather and semaphore(10) times.
About 5.0 s, 0.1 s and 0.5 s, from N x L, L and ceil(N / C) x L.
Follow-upWhat if the server allows only 20 in flight and you set the semaphore to 25? You get the gather result: 0.1 s and 30 failures. The cap must sit at or below the real limit.
What exactly happens at an await?
If the awaited thing is not ready, the coroutine suspends and control returns to the event loop, which runs another ready task. When the I/O or timer completes, the selector reports it and the task resumes where it left off.
Follow-upWhat if it is already done? Execution continues with no switch, so a tight loop of already-complete awaits can starve other tasks.
How do you choose the semaphore size?
Start from the provider's requests and tokens per minute limits and Little's law: in-flight = target rate x latency. Stay below the limit (around 80 percent), check connection pool size and memory, then tune on measured 429 rate and p99.
Follow-upThe limit is tokens per minute, not requests. A semaphore counts calls, so you need a token-aware limiter such as a token bucket.
Compare gather and TaskGroup.
gather returns results in order and, by default, raises the first exception while siblings keep running; return_exceptions=True collects everything. TaskGroup (3.11+) is structured: scope exit waits for children, and a failure cancels the siblings and raises an ExceptionGroup.
Follow-upWhich for a batch where partial results matter? gather with return_exceptions, or per-task try/except inside a TaskGroup.
Your async service gets slow for every user when one endpoint is busy. How do you find the cause?
Suspect a blocking call on the loop. Enable asyncio debug mode, which logs callbacks slower than 0.1 s, chart event loop lag, and look at the stack of the slow callback. Then move that work to to_thread or a process pool.
Follow-upHow do you stop it recurring? A loop-lag alert in staging and a lint rule against blocking calls in async functions.
When do you choose asyncio, threads or processes?
Asyncio for very many concurrent waits with async-capable libraries. Threads for blocking I/O libraries you cannot change. Processes for CPU-bound Python. Mixed services combine them: loop for I/O, pools for the rest.
How do you handle timeouts and retries on LLM calls?
Wrap each call in asyncio.timeout, retry 429 and 5xx with exponential backoff plus jitter, honor Retry-After, cap total attempts, and make sure the call is safe to repeat. Let CancelledError propagate.
Follow-upWhy not retry forever? It multiplies load during an outage and holds semaphore slots, turning a provider incident into your own.
What does the GIL do, and what changed in Python 3.13 and 3.14?
In the standard build it lets one thread run Python bytecode at a time per process, protecting interpreter internals. 3.13 added an experimental free-threaded build; 3.14 made it officially supported (PEP 779), still optional, with the GIL build as default.

Mixed review

Three questions from the prerequisites, which are scheduled the same day. Nobody tells you the topic in an interview.

A01: Why parse an LLM's JSON output with a pydantic model instead of reading dict keys directly?
Models return malformed or missing fields at some nonzero rate. Pydantic fails at the boundary with a clear error, so you can retry or repair, instead of a KeyError deep in your code.
A01: When do you use a dataclass and when a pydantic model?
Pydantic where untrusted data enters and needs parsing and validation. Dataclasses for plain internal structures where types are already trusted, since they do no runtime validation.
D01: Why can't you parallelize the generation of one response across its output tokens?
Decoding is autoregressive: each token depends on all previous ones. Within a request it is sequential; you parallelize across requests, which is exactly where async fan-out helps.
