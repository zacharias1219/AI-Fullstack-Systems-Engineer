Debugging method

How do you find a bug you have never seen before, fast, and know the fix is real? This page covers the loop (reproduce, isolate, hypothesize, instrument), the written hypothesis log, and how to say it in an interview.

Study path

Before you read

Guess first. A wrong guess now makes the right answer stick later. The numbers come from the kata in station 6.

The check check_cost_second_batch prints cost=0.0, want 0.5 in the full run, but passes when you run it alone. What does that tell you before you read any code?
Something carries state from one check to the next. Alone it returns 0.5, in the full run an earlier call has already changed shared state. Look for a mutable default argument, a global, a cache or a file. The isolation result is itself evidence, and it costs one command.
Four checks fail at the start but only three bugs are planted. How can that be, and what do you chase first?
One bug can produce several symptoms. check_chunk_count and check_chunk_cover both come from chunk(). Group failures by the function they touch, then chase one group at a time, starting with the one whose symptom is most specific.
You change three things at once and the failure disappears. What have you learned?
Almost nothing. You do not know which change mattered, or whether you only hid the failure. Change one thing per hypothesis, so each run can confirm or kill exactly one idea.

The core idea

Debugging is the scientific method with a notebook. A bug is a gap between what you believe the program does and what it does. Your job is to shrink that gap with experiments, not to stare at code until the gap closes by luck.

Every step shrinks the search space. Reproducing makes the failure testable. Isolating cuts the space in half again and again. A hypothesis names one suspect and the observation it predicts. Instrumentation is the experiment that confirms or kills the suspect. Then you verify the fix with a test that failed before and passes now.

Memory hook

Detective's four verbs: Replay the crime so it happens on demand, Isolate the suspect by halving, Hypothesize one motive and write it down, Instrument the scene to test it. Then Verify with a test that flips from red to green, and keep the log.

How it works

Reproduce

Make it fail on demand. Pin the random seed, freeze the input, record the environment (versions, flags, config). Then shrink the input until nothing can be removed without the failure vanishing. A bug you cannot reproduce is a bug whose fix you cannot verify. For LLM work, log the full prompt, model, temperature and seed with every call, so a bad answer can be replayed.

Check: a failure happens in 1 of 10 runs. About how many runs do you need to see it at least once with 95% confidence?
n = ln(0.05) / ln(0.9) = 28.4, so about 29 runs. At 1 in 100 it is about 299 runs. Loop it in a script instead of retrying by hand, and count failures to get the rate.

Isolate by halving

Do not read everything. Cut the search space in half with each test. Across commits that is git bisect. Across a pipeline it is a print or assert at the stage boundary: if the data is right at the midpoint, the bug is downstream; if wrong, upstream. Across inputs it is deleting half and seeing if it still fails. Halving needs at most ceil(log2 n) tests: 20 commits cost 5, 1,000 cost 10. Running one check alone, as in the kata, is the same move on shared state.

Hypothesize, in writing

A good hypothesis is falsifiable and names its prediction: "the loop stops one window early, so the last tokens will be uncovered". Write it in the log before you test. Writing stops you from forgetting what you have ruled out, and from rationalizing a wrong idea after the fact. Change one thing per test. Mark each hypothesis confirmed, killed or unclear.

Check: why log the prediction before running the test, not just the result?
A prediction made first can be wrong, so the test actually tests something. A prediction written after the result always fits. It also lets you read the log later and see which ideas are dead, so you never test the same suspect twice.

Instrument

Add the cheapest probe that answers the current hypothesis. A print or log at a stage boundary shows data in flight. breakpoint() in Python drops you into the debugger to inspect state at one moment. An assert turns an assumption into an alarm. Traces with a request id follow one request across services. For a voice AI pipeline (speech to text, LLM, speech to speech), log the input and output of each stage, then bisect the pipeline. Remove or demote the probes once the bug is fixed.

Verify and prevent

Before the fix, make a test that fails for the reason you believe. After the fix, it must pass, and every other check must still pass. Then ask whether you fixed the cause or the symptom: can you explain, step by step, why the old code failed? Keep the test as a regression test. If you cannot explain the failure, you have not fixed it, only moved it.

Check: your fix makes the error stop. Name two reasons that is not enough to call the bug fixed.
The change may mask the symptom (a try/except, a retry, a different input path) while the cause remains. And you may not have a test that failed before, so you cannot show the fix caused the change. Require a red-to-green test and a causal explanation.

Kata: three planted bugs and a hypothesis log

A small pipeline for LLM work has a chunker, a cost ledger and a latency percentile. Six checks, three bugs. Your job is to find each bug with the method, not by reading every line, and to keep a written log. Do the run first, write your first hypothesis, then read the code.

Run

python kata.py
python kata.py check_cost_second_batch

kata.py

"""A06 kata: three planted bugs, six checks. Run it, then keep a hypothesis log.
python kata.py              run every check
python kata.py NAME [NAME]  run only the named checks (isolation)
"""
import random
import sys


def chunk(tokens, size, overlap):
    """Windows of `size` tokens; neighbours share `overlap` tokens."""
    step = size - overlap
    out = []
    for i in range(0, len(tokens) - size, step):
        out.append(tokens[i:i + size])
    return out


def add_cost(calls, price_per_1k, seen=[]):
    """Cost of (call_id, tokens) pairs; a call id is billed only once."""
    total = 0.0
    for cid, n in calls:
        if cid in seen:
            continue
        seen.append(cid)
        total += n / 1000 * price_per_1k
    return total


def p95(samples):
    """Nearest-rank 95th percentile."""
    k = max(0, int(len(samples) * 0.95) - 1)
    return samples[k]


def check_chunk_count():
    got = len(chunk(list(range(10)), 4, 1))
    return got == 3, f"chunks={got}, want 3"


def check_chunk_cover():
    seen = {t for c in chunk(list(range(10)), 4, 1) for t in c}
    missing = sorted(set(range(10)) - seen)
    return not missing, f"uncovered tokens={missing}"


def check_cost_basic():
    got = add_cost([(1, 2000), (2, 1000)], 0.5)
    return abs(got - 1.5) < 1e-9, f"cost={got}, want 1.5"


def check_cost_second_batch():
    got = add_cost([(1, 1000)], 0.5)
    return abs(got - 0.5) < 1e-9, f"cost={got}, want 0.5"


def check_p95_sorted():
    got = p95(list(range(1, 21)))
    return got == 19, f"p95={got}, want 19"


def check_p95_unsorted():
    data = random.Random(7).sample(range(100, 300), 20)
    want, got = sorted(data)[18], p95(data)
    return got == want, f"p95={got}, want {want}"


CHECKS = [check_chunk_count, check_chunk_cover, check_cost_basic,
          check_cost_second_batch, check_p95_sorted, check_p95_unsorted]

if __name__ == "__main__":
    names, failed = sys.argv[1:], 0
    for fn in CHECKS:
        if names and fn.__name__ not in names:
            continue
        ok, note = fn()
        print(f"{'PASS' if ok else 'FAIL'}  {fn.__name__:<24} {note}")
        failed += not ok
    print(f"{failed} failing")

Hypothesis log template

| # | Observation | Hypothesis (and what it predicts) | One change or probe | Result |
|---|-------------|-----------------------------------|---------------------|--------|
| 1 | latency spike after deploy | new retry loop doubles calls; predicts 2x request count | count calls per request | confirmed |

What to notice

  1. Four checks fail but they point at three functions. check_chunk_count and check_chunk_cover both trace to chunk(), so you group before you hunt.
  2. check_cost_basic passes with cost=1.5 and check_cost_second_batch fails with cost=0.0 in the full run. Run alone, the second prints cost=0.5 and passes. The difference between those two runs is the clue.
  3. The sorted p95 check passes and the unsorted one fails, p95=161, want 249. The gap between the two inputs names the cause.
  4. The coverage check gives the most specific symptom: uncovered tokens=[7, 8, 9]. A symptom that names the missing items beats a bare count.
Name the three planted bugs and the one-line fix for each. Open this only after you have fixed them, or after 25 minutes.
  1. chunk(): range(0, len(tokens) - size, step) stops before the last full window. Fix: len(tokens) - size + 1. Gives 3 chunks and no uncovered tokens.
  2. add_cost(): seen=[] is created once when the function is defined, so billed ids leak across calls. Fix: seen=None, then seen = [] if seen is None else seen.
  3. p95(): it indexes the samples without sorting. Fix: samples = sorted(samples) first. Gives p95=249.
Break it
  1. Put the shared state back. After fixing bug 2, restore seen=[]. Predict the output of python kata.py check_cost_second_batch and then of the full run, before you run either.
  2. Plant your own. In chunk(), change step = size - overlap to size + overlap. Predict how many chunks come back and which check names fail, then compare with the output. Then log it as if you had never seen the code.

Stretch. Make the script exit with status 1 when any check fails, put it in a git repo with one commit per bug, and run git bisect run python3 kata.py to find the first bad commit automatically.

Say this aloud against the clock. Three levels, about 90 seconds.

1 Outcome 20 sDebugging is the scientific method with a notebook. I make the failure happen on demand, shrink the search space until I know where it lives, state one falsifiable guess, and test it. A fix only counts when a test that failed now passes, because that is what separates a repair from luck.
2 Mechanism 45 sFirst I reproduce it: pin the seed, the input and the environment, then shrink the input. Next I isolate by halving. Then I write one hypothesis in my log with the observation it predicts, change one thing, and run. If it is wrong I cross it out, so I never retest a dead idea. I pick the cheapest probe: a log line at a boundary, an assert, or a breakpoint where the data crosses.
3 Internals and limits 25 sFlaky bugs need a loop: about 29 runs to see a 10% failure at 95% confidence, about 300 for 1%. Passes alone, fails in the suite means shared mutable state, like a default list argument. The failure mode of my own process is changing three things at once. Say it like an engineer

"I would read the code, find where it breaks, add some prints and fix it."

"I make it fail on demand with a pinned seed and a minimal input, then halve the search space. Git bisect needs at most 5 runs for 20 commits. I write one hypothesis with its predicted result, change one thing and run. The fix counts when a test that failed now passes, and I keep that test."

The strong one has a mechanism (halving), a number (5 runs for 20 commits), a failure mode (changing many things, fixes that only mask) and a stated standard for done. The weak one is a list of activities.

Traps

Each one sounds right. Say what is wrong with it before you open it.

"If I cannot reproduce the bug, the best use of my time is to read the code until I spot it."
Reading finds plausible suspects but cannot confirm any, and you cannot verify a fix for a failure you cannot trigger. First measure how often it fails and loop it: for a 10% rate that is about 29 runs. If it will not reproduce, add logging that captures the state at the failure so the next occurrence is replayable.
"The error stopped after my change, so the bug is fixed."
The error may have stopped because the change masked the symptom or changed the path. In the kata, check_cost_second_batch passes if you run it alone, even though the bug is still there. You need a test that failed for the right reason before and passes after, plus a step-by-step explanation of why the old code failed.

Question bank

Answer aloud, then open. Grade yourself honestly.

Walk me through how you debug a failure you have not seen before.
Reproduce (seed, input, environment, then shrink), isolate by halving (bisect commits or probe a stage boundary), write one hypothesis with a prediction, change one thing and test it, and verify with a red-to-green test. Keep a log of what is ruled out.
Follow-upWhat do you do when you cannot reproduce it? Measure the failure rate by looping, about 29 runs for a 10% rate, and add logging that captures the state so the next failure is replayable.
A test passes alone but fails when the whole suite runs. What are your first two hypotheses?
Shared mutable state carried between tests (default argument, global, cache, file, database), and test order dependence. Run the failing test alone, then with one earlier test at a time, to find which one pollutes it. In the kata the culprit is seen=[] in add_cost().
A regression appeared somewhere in the last 500 commits. How many steps to find it, and what must be true for that to work?
At most 9 tests, since ceil(log2 500) = 9. It needs a pass or fail test that is reliable at every commit. A flaky test points bisect at the wrong commit.
Follow-upWhat if some commits do not build? Mark those as skipped in bisect, and the search continues around them. If the test is flaky, loop it per commit until the rate is clear.
Why do you write the hypothesis down before testing it?
A prediction made first can be wrong, so the test is real. It stops you changing several things at once, and the log shows which suspects are dead so you do not retest them.
When do you reach for a debugger, a print, an assert or a trace?
Print or log line for data flow across stages. Debugger for inspecting all state at one moment in a local, repeatable run. Assert for an assumption that should always hold, so it fails near the cause. Traces with a request id in production or across services.
Follow-upWhere does a debugger fail you? Timing and concurrency bugs, because stepping changes the timing, and production, where you cannot attach.
Your LLM agent gives a wrong answer about one run in twenty. How do you debug it?
Replay first: log prompt, model, parameters, seed where supported, and tool calls per run. Loop the same input to confirm the rate. Then compare a good and a bad trace step by step to find the first divergence. Bisect the pipeline: retrieval, prompt, model, tool, parsing. Write an eval case for it once found.
How do you know your fix addresses the root cause and not the symptom?
A test failed before for the reason I believed and passes now, and I can explain step by step why the old code failed. Other checks still pass. I also ask whether the same cause can produce the failure elsewhere, and add a regression test.

Mixed review

Three questions from earlier topics. Nobody tells you the topic in an interview.

A02: You fire 50 fake LLM calls of 100 ms each. Estimate the total time sequentially, with asyncio.gather, and with a semaphore of 10.
Sequential: 50 x 100 ms = 5 s. Gather: about 100 ms, since the waits overlap. Semaphore of 10: 5 waves x 100 ms = about 0.5 s. This is concurrency on one thread for I/O waits. CPU-bound work still needs processes, because the GIL lets one thread run Python bytecode at a time in standard CPython builds.
A01: Why load config into a pydantic model instead of passing a raw dict around?
The model validates and converts types once at load and fails fast with a field-level error. A raw dict fails later and deeper, as a KeyError or TypeError far from the cause, which is exactly the kind of bug this page teaches you to hunt.
A03: A process is eating memory. Which signal do you send first, and why not kill -9 straight away?
SIGTERM (15) first: the process can catch it, flush state and exit cleanly. SIGKILL (9) cannot be caught, so there is no cleanup, and it can leave locks, temp files or half-written data. Use -9 only if SIGTERM is ignored. Find the hog with ps aux --sort=-%mem | head on GNU ps.
