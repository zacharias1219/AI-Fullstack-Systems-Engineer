No. Negative numbers break monotonicity. When the window sum exceeds K and you advance l, you might miss a future negative element at r + 1 that would bring the wider window back below K. In our kata's first break-it, enabling negative values makes the sliding window miss valid longer windows.

The core idea

A naive nested scan over n items inspects n(n + 1)/2 pairs or ranges because it throws away everything it learned when advancing the outer index. Every O(n) array pattern replaces that repeated inner scan with a single state invariant that updates in O(1) time per step.

Four invariants cover almost every linear array problem in systems and coding interviews. A prefix sum turns any range sum into a subtraction of two cumulative checkpoints: sum(l..r) = P[r+1] - P[l]. A hash map remembers previously seen values or prefix sums so a backward search becomes an O(1) complement lookup. Two pointers exploit sorted order so each comparison eliminates an entire row or column of pairs in O(1) auxiliary space. A sliding window maintains a valid contiguous range [l..r] over monotonic data, advancing r to expand and l to repair in at most 2n pointer moves.

Memory hook

Remember the four linear scan weapons by P-H-T-S ("Prefix Hashes Tame Scans"): Prefix difference (P[r+1] - P[l]), Hash complement (seen[pref - K] in O(n) space), Two pointers on sorted data (O(1) space pruning), Sliding window on monotonic data (expand r, shrink l in <= 2n moves).

How it works

Pattern 1: Prefix sums and hash-complement lookup

Define the prefix sum array P where P[0] = 0 and P[i] = arr[0] + ... + arr[i-1]. Any contiguous subarray arr[l..r] has sum P[r+1] - P[l]. Once precomputed in O(n) time, any fixed range sum query takes O(1) subtraction.

When you need to count or locate subarrays whose sum equals a target token budget K, rewrite the condition P[r+1] - P[l] = K as P[l] = P[r+1] - K. As you iterate r from 0 to n - 1 maintaining the running prefix sum pref = P[r+1], a hash map storing prior prefix sums answers "how many earlier indices l had P[l] == pref - K?" in O(1) expected time. Always seed the map with {0: 1} (or {0: -1} when tracking earliest index for max length) to account for the empty prefix P[0] = 0.

sum(arr[l..r]) = P[r+1] - P[l] == K  <=>  P[l] == P[r+1] - K
Base case: counts = {0: 1}  (or first_idx = {0: -1} for longest subarray)

Pattern 2: Opposite-direction and same-direction two pointers

Two pointers eliminate the O(n) memory table of a hash map by exploiting order or in-place partitioning. In opposite-direction two pointers on a sorted array (l = 0, r = n - 1), you evaluate s = arr[l] + arr[r] against a target T. If s < T, pairing arr[l] with any index below r gives an even smaller sum, so l is dead and you increment l += 1. If s > T, pairing arr[r] with any index above l gives an even larger sum, so you decrement r -= 1. Each comparison eliminates an entire row or column of the n-by-n pair matrix in O(1) time and O(1) space.

In same-direction (read/write or fast/slow) two pointers, write marks the boundary of kept deduplicated tokens while read scans ahead, compacting arrays like sorted vocabulary lists or stream buffers in-place without allocating a second buffer.

Sorted invariant (arr[l] <= arr[r]):
  arr[l] + arr[r] < T  =>  l += 1   (rules out all pairs (l, j) for j <= r)
  arr[l] + arr[r] > T  =>  r -= 1   (rules out all pairs (i, r) for i >= l)
Check: Why does opposite-direction two-sum fail on an unsorted array unless you pay O(n log n) to sort first?
Because the pruning step relies on sorted monotonicity: knowing arr[l] + arr[r] > T only rules out other partners for arr[r] if every element to the right of l is at least arr[l].

Pattern 3: Monotonic sliding window (expand and shrink)

A variable-size sliding window finds the longest or shortest contiguous subarray satisfying a monotonic constraint, such as total tokens <= W or distinct token IDs <= M. For each step of the outer loop, r advances by 1 and adds arr[r] to the window state. An inner while loop advances l and removes arr[l] until the invariant is restored.

The crucial condition is monotonicity: expanding the window (r += 1) must never make an invalid window valid, and shrinking the window (l += 1) must monotonically move toward validity. That holds for sums of non-negative numbers and for unique-element counts. By amortized accounting, each element enters the window once when r visits it and leaves at most once when l passes it, costing at most 2n state updates.

for r in range(n):
    add(arr[r])                  # entered once: n times total
    while violated(window):
        remove(arr[l]); l += 1   # exited at most once: <= n times total
    best = max(best, r - l + 1)

Problem 1 (Prefix Sum + Hash Map, 5 min): Given an array turns[0..n-1] of integer token deltas (which may be positive, zero, or negative) and an exact budget target K, return both (a) the total number of contiguous turn ranges summing to K, and (b) the maximum length of any contiguous turn range summing to K.

Invariant & Algorithm: Maintain running prefix sum pref += turns[r]. For part (a), store a frequency table counts = {0: 1}; at each step add counts.get(pref - K, 0) to total_ranges and increment counts[pref]. For part (b), store first_idx = {0: -1}; if pref - K is in first_idx, update max_len = max(max_len, r - first_idx[pref - K]), and only insert first_idx[pref] = r if pref is not already present (to keep the leftmost index).

def budget_ranges(turns, k):
    counts, first_idx = {0: 1}, {0: -1}
    pref = total = max_len = 0
    for r, x in enumerate(turns):
        pref += x
        total += counts.get(pref - k, 0)
        counts[pref] = counts.get(pref, 0) + 1
        if pref - k in first_idx:
            max_len = max(max_len, r - first_idx[pref - k])
        if pref not in first_idx:
            first_idx[pref] = r
    return total, max_len

Complexity: Time O(n) expected (one hash lookup and insert per index). Auxiliary space O(n) to store up to n + 1 distinct prefix sums.

Problem 2 (Two Pointers, 5 min): Given a sorted array ids[0..n-1] of strictly increasing embedding token IDs and a target sum T, count all index pairs (l, r) with l < r such that ids[l] + ids[r] == T using O(1) auxiliary memory. Then explain how to modify it if ids contains duplicates and you must skip duplicate value pairs.

Invariant & Algorithm: Place l = 0 and r = len(ids) - 1. While l < r, compute s = ids[l] + ids[r]. If s == T, increment pairs += 1, l += 1, r -= 1 (and if skipping duplicate values, advance while l < r and ids[l] == ids[l-1]: l += 1 and similarly for r). If s < T, increment l += 1; if s > T, decrement r -= 1.

def count_sorted_pairs(ids, target):
    l, r, pairs = 0, len(ids) - 1, 0
    while l < r:
        s = ids[l] + ids[r]
        if s == target:
            pairs += 1; l += 1; r -= 1
            while l < r and ids[l] == ids[l - 1]: l += 1
            while l < r and ids[r] == ids[r + 1]: r -= 1
        elif s < target: l += 1
        else: r -= 1
    return pairs

Complexity: Time O(n) because each comparison narrows the distance r - l by at least 1 (at most n - 1 steps). Auxiliary space O(1) (three scalar integers).

Problem 3 (Sliding Window, 5 min): Given a stream tokens[0..n-1] of positive turn token counts and a context window capacity W (plus a variant with at most M unique token IDs), find the length of the longest contiguous window whose token sum is <= W.

Invariant & Algorithm: Maintain a valid window [l..r] with running sum s. Advance r across 0..n-1, adding tokens[r] to s. While s > W, subtract tokens[l] and advance l += 1. After the while loop, s <= W is guaranteed, so update best = max(best, r - l + 1). For the <= M unique token IDs variant, replace s with a frequency dict freq and shrink while len(freq) > M, deleting keys when their count hits 0.

def longest_prompt_window(tokens, cap):
    l = s = best = 0
    for r, x in enumerate(tokens):
        s += x
        while s > cap:
            s -= tokens[l]; l += 1
        if r - l + 1 > best: best = r - l + 1
    return best

Complexity: Time O(n) amortized (at most 2n pointer increments across outer and inner loops). Auxiliary space O(1) for the sum variant, or O(M) for the unique-token frequency map.

import random, time

# --- Break-it flags ---
ALLOW_NEGATIVE_TOKENS = False   # 1) Set True: negative weights break sliding-window monotonicity
DROP_PREFIX_BASE_CASE = False   # 2) Set True: omit prefix_counts[0]=1 and miss ranges starting at index 0
COLLIDE_HASH_KEYS     = False   # 3) Set True: force mod-4 hash collisions -> O(n^2) bucket scans

class Key(int):
    def __hash__(self):
        return int(self) % 4 if COLLIDE_HASH_KEYS else super().__hash__()

random.seed(42)
N = 5000
TARGET_PAIR = 5000
WINDOW_CAP = 1200

turns = [random.randint(-15 if ALLOW_NEGATIVE_TOKENS else 10, 50) for _ in range(N)]
BUDGET_K = sum(turns[:5])       # Guarantees prefix turns[0..4] sums to exact BUDGET_K (130)
sorted_ids = sorted(random.sample(range(1, 10000), N))

# --- Problem 1: Subarray Token Budget Match (Count ranges summing to exact K) ---
def p1_brute(arr, k):
    ops, hits = 0, 0
    for i in range(len(arr)):
        s = 0
        for j in range(i, len(arr)):
            s += arr[j]; ops += 1
            if s == k: hits += 1
    return hits, ops

def p1_optimal(arr, k):
    counts = {} if DROP_PREFIX_BASE_CASE else {Key(0): 1}
    pref, hits, ops = 0, 0, 0
    for x in arr:
        pref += x; ops += 1
        hits += counts.get(Key(pref - k), 0)
        key = Key(pref)
        counts[key] = counts.get(key, 0) + 1
    return hits, ops

# --- Problem 2: Sorted Embedding ID Pair Match (Count pairs a[l] + a[r] == T) ---
def p2_brute(arr, target):
    ops, pairs = 0, 0
    for i in range(len(arr)):
        for j in range(i + 1, len(arr)):
            ops += 1
            if arr[i] + arr[j] == target: pairs += 1
    return pairs, ops

def p2_optimal(arr, target):
    l, r, ops, pairs = 0, len(arr) - 1, 0, 0
    while l < r:
        ops += 1
        s = arr[l] + arr[r]
        if s == target:
            pairs += 1; l += 1; r -= 1
        elif s < target:
            l += 1
        else:
            r -= 1
    return pairs, ops

# --- Problem 3: Longest Prompt Window Under Token Budget Cap (sum <= W) ---
def p3_brute(arr, cap):
    ops, best = 0, 0
    for i in range(len(arr)):
        s = 0
        for j in range(i, len(arr)):
            s += arr[j]; ops += 1
            if s <= cap:
                if j - i + 1 > best: best = j - i + 1
            elif not ALLOW_NEGATIVE_TOKENS:
                break
    return best, ops

def p3_optimal(arr, cap):
    l, s, best, ops = 0, 0, 0, 0
    for r, x in enumerate(arr):
        s += x; ops += 1
        while s > cap and l <= r:
            s -= arr[l]; l += 1; ops += 1
        if r - l + 1 > best: best = r - l + 1
    return best, ops

Traps

Each one sounds right. Say what is wrong with it before you open it.

"A sliding window has a while loop inside a for loop, so its worst-case time complexity is O(n^2)."
Wrong. A single outer iteration can advance l up to n times, but l starts at 0, only increments, and never exceeds n. Across the entire for loop, the inner body executes at most n times total, giving n + n = 2n = O(n) amortized time.
"You can use a variable-size sliding window to find the longest subarray with sum <= K or sum == K even when the array has negative numbers."
Wrong. Negative numbers destroy monotonicity: advancing l past a negative number increases the window sum, and stopping expansion early misses later negative numbers that would pull the sum back down to K. Use a prefix-sum hash map (for == K) or prefix sums with a monotonic deque (for shortest >= K).
"Two-pointer pair sum is always faster than hash-map two-sum."
Wrong on unsorted inputs. Opposite-direction two pointers require sorted order; if the array is unsorted, sorting first costs O(n log n) time, whereas a hash map solves unsorted two-sum in O(n) expected time (at the cost of O(n) space).
"When finding the longest subarray summing to K with a prefix-sum hash map, you should always update index_map[pref] = r on every step."
Wrong. Overwriting index_map[pref] with a later index r shrinks future distances r_new - l. To maximize subarray length, you must keep the earliest index where pref first appeared (if pref not in index_map: index_map[pref] = r).

Question bank

Answer aloud, then open. Grade yourself honestly.

Prove using amortized accounting why a monotonic sliding window takes at most 2n operations.
Assign 2 credits to each of the n array elements: 1 credit pays for the outer loop when r enters the element into the window, and 1 credit pays for the inner while loop when l removes it. Because l never decrements, each element is removed at most once, bounding total operations at 2n.
Follow-upWhat is the worst-case time of a single outer iteration, and why does that not contradict O(n) total time? A single step can do O(n) shrinks if l catches all the way up to r, which uses up all previously unspent shrink credits in one batch.
Why does prefix-sum subarray counting require initializing counts = {0: 1} before the loop?
Because P[0] = 0 represents the empty prefix before index 0. When a subarray starting at index 0 (arr[0..r]) has sum K, its running prefix is P[r+1] = K and the lookup searches for P[r+1] - K = 0.
Follow-upWhat initial dictionary do you use instead if the problem asks for the longest subarray summing to K? Use first_idx = {0: -1} so a prefix match at index r computes length r - (-1) = r + 1.
How do you choose between a hash map, two pointers, and a sliding window on a new array problem?
Ask two questions: (1) Am I pairing arbitrary indices or scanning a contiguous range? For pairs, use two pointers if sorted (O(1) space) or a hash map if unsorted (O(n) space). (2) For contiguous ranges, is the constraint monotonic (non-negative weights / unique counts)? If yes, use a sliding window (O(1) or O(U) space); if negative numbers exist, use a prefix-sum hash map.
In sorted two-sum, prove that advancing l when arr[l] + arr[r] < T cannot skip a valid pair.
At state (l, r), every index j > r was already eliminated in earlier steps because arr[i] + arr[j] > T for all i >= l. And for any remaining j < r, sorted order guarantees arr[l] + arr[j] <= arr[l] + arr[r] < T. Thus index l has no valid partner and can be safely discarded.
Follow-upWhat changes if you need 3Sum (three elements summing to T)? Sort in O(n log n), fix index i in an outer loop, and run opposite-direction two pointers on i+1..n-1 in O(n^2) time and O(1) auxiliary space.
When maintaining a sliding window of at most M distinct token IDs, why must you delete a token key from the frequency map when its count drops to 0?
Because Python's len(freq) counts dictionary keys regardless of whether their value is 0. Leaving zero-count keys in the map makes len(freq) overestimate distinct tokens in the active window and shrink prematurely.
Follow-upWhat is the space complexity of the frequency map if you delete zero-count keys vs if you keep them? Deleting zero-count keys bounds space at O(M); keeping them grows to O(min(n, V)) over the whole stream.
Why does calling window.pop(0) on a Python list inside a sliding window turn an O(n) algorithm into O(n^2)?
A Python list is a contiguous dynamic array, so pop(0) shifts all remaining elements left by one memory slot in O(w) time. Instead, increment an integer index l += 1 over the original array or use collections.deque.popleft().
How can you answer Q range-sum queries on a static array of length n in O(n + Q) total time?
Build a prefix array P of length n + 1 where P[0] = 0 and P[i+1] = P[i] + arr[i] in O(n) time, then answer each query sum(l..r) as P[r+1] - P[l] in O(1) time.
What happens to a Python dict-based O(n) scan if keys have pathological hash collisions, and how does CPython mitigate it?
If all n keys collide into the same bucket/probe chain, each lookup scans O(n) existing keys, degrading total runtime to O(n^2) (as shown in our kata's third break-it). CPython mitigates this for strings and bytes via per-process random SipHash seeding (PYTHONHASHSEED).
Follow-upCan a Python list be used as a dict key for prefix or frequency grouping? No, lists are mutable and unhashable; convert to a tuple or fixed integer state first.
How do you deduplicate a sorted token ID array in-place in O(n) time and O(1) space?
Use same-direction read/write pointers: set write = 1 and scan read from 1 to n - 1. Whenever arr[read] != arr[write - 1], copy arr[write] = arr[read] and increment write += 1. The deduplicated prefix has length write.

Mixed review

Three questions from earlier topics. Nobody tells you the topic in an interview.

A01: Why does a standard Python dataclass with field: int still accept a string at runtime, and why do you use Pydantic at external API boundaries instead?
Standard Python type hints and @dataclass annotations are not enforced at runtime by default; Pydantic parses, coerces, and validates untrusted input payloads at runtime and raises structured validation errors on schema mismatches.
A02: Why does asyncio.gather speed up 50 concurrent LLM API calls by ~30x despite Python's Global Interpreter Lock (GIL), yet gives zero speedup on 50 CPU-bound matrix multiplications?
Network socket waits release the GIL and yield control to the event loop so 50 I/O requests overlap concurrently; pure Python CPU loops hold the GIL continuously on one OS thread and block the event loop.
A07: When profiling a slow Python data pipeline, what is the difference between cProfile and py-spy, and when do you reach for each?
cProfile is a deterministic tracing profiler that hooks every function call (adding 2x-5x overhead), while py-spy is a low-overhead sampling profiler that reads stack frames out-of-process and can attach to a live production PID without code changes.

Short notes

Quick-memorization cheat sheet covering every subtopic on this page and the key facts to remember cold.

All subtopics on this page

  • Prefix sums P[0..n]: P[0] = 0, P[i+1] = P[i] + arr[i]; answers any range sum sum(l..r) = P[r+1] - P[l] in O(1) time after O(n) build.
  • Prefix-sum + hash map: Rewrites P[r+1] - P[l] == K as P[l] == P[r+1] - K; counts or finds longest exact-sum subarrays in O(n) time and O(n) space even when negative numbers exist.
  • Opposite-direction two pointers: Starts at l = 0, r = n - 1 on sorted input; each comparison prunes a full row or column of pairs in O(n) time and O(1) auxiliary space.
  • Same-direction two pointers: Uses read and write indices to compact or deduplicate arrays in-place in O(n) time and O(1) space.
  • Monotonic sliding window: Expands r every step and shrinks l in a while loop while violated; runs in at most 2n pointer moves and O(1) (or O(U)) space when weights are non-negative.
Important things to remember
  • Base case rule: Always seed counts = {0: 1} for subarray counting and first_idx = {0: -1} for longest subarray length, or you miss every range starting at index 0.
  • First-seen rule: For longest subarray summing to K, only set first_idx[pref] = r if pref is not already in the map.
  • Negative-number boundary: Never use a variable-size sliding window for subarray sums when elements can be negative; switch to a prefix-sum hash map.
  • Amortized 2n proof: A sliding window's nested while loop is O(n) total because l starts at 0, only increments, and cannot exceed n.
  • Python implementation traps: Delete zero-count keys from window frequency dicts so len(freq) stays accurate, and advance an index l += 1 instead of calling O(n) list.pop(0).
