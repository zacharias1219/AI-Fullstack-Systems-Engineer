Profiling Python

How do you find the exact line or allocation making a Python pipeline slow without guessing? This page covers deterministic tracing (cProfile, pstats), statistical sampling (py-spy), line and memory profilers (tracemalloc), and Amdahl's law. GPU and CUDA kernel profiling belongs to K22.

Study path

Before you read

Guess first. A wrong guess now makes the right answer stick later. The numbers come from the kata in station 6.

In the kata's baseline run, tokenize_v0_naive shows cumtime=107.1ms and tottime=1.2ms, while lookup_naive shows cumtime=96.9ms and tottime=96.4ms. Which function actually burns the CPU, and why?
lookup_naive burns the CPU. cumtime includes time spent inside all functions called from a function, so the outer wrapper tokenize_v0_naive inherits almost the entire 107.1 ms run. tottime excludes subcalls and measures where the interpreter actually spent 96.4 ms (90% of the run).
Stage 1 of the kata speeds up vocabulary lookup and drops wall-clock time from 108.06 ms to 15.78 ms (6.8x faster), yet tracemalloc peak memory stays stuck at 18,505.5 KB. How can a 6.8x CPU speedup leave peak memory unchanged?
Time hotspots and memory hotspots are often different functions. Stage 1 fixed the O(V) list scan in lookup_naive, which burned 90% of CPU time but allocated almost nothing. The 18.5 MB peak comes from assemble_naive saving 600 growing prefix strings in a list, which took only 6.3 ms in Stage 0.
A function takes 90% of total runtime. Even if you rewrite that function in C so it runs 1,000x faster, what is the maximum end-to-end speedup you can get?
At most 10x. By Amdahl's law, the remaining 10% of the program is untouched and sets a floor of 0.10 of the original runtime (1 / 0.10 = 10x). With a 1,000x local speedup, total speedup is 1 / (0.10 + 0.90/1000) = 9.91x.

The core idea

Optimizing code before profiling is guessing where the clock goes. Human intuition treats every line of source code as equal weight, but runtime follows a power law: one inner loop, uncached regex, or hidden quadratic copy usually accounts for 80% to 95% of wall-clock time or heap memory. Profiling replaces opinions with a table of call counts, exclusive times, and byte allocations.

The profiling loop has five disciplined steps: establish a repeatable wall-clock baseline, choose the lowest-overhead profiler that answers your question, separate high-cumtime wrappers from high-tottime leaf hotspots, fix the single highest-share bottleneck, and re-profile to verify the gain against Amdahl's law before hunting the next bottleneck.

Memory hook

B-T-L-A-V (BeTheLAVa): Baseline wall clock (perf_counter), Tool choice (cProfile hooks vs py-spy samples vs tracemalloc bytes), Leaf tottime over wrapper cumtime, Amdahl check (1 / (1 - p)), Verify output and re-profile.

How it works

Deterministic tracing: cProfile and pstats

cProfile is CPython's built-in deterministic profiler, implemented in C via _lsprof. It hooks every Python function call, C-function call, and return, recording exact call counts and elapsed time. You inspect results with pstats.Stats. Five columns matter: ncalls (total calls; written total/primitive when recursive), tottime (exclusive time spent in the function body itself, excluding subcalls), percall (tottime / ncalls), cumtime (inclusive time in the function plus all its callees), and the second percall (cumtime / primitive_calls). Always sort by cumtime first to find which subsystem owns the latency, then sort by tottime to find the leaf function doing the work. Because cProfile fires on every call, tight Python loops with millions of tiny function calls add 20% to 50% profiling overhead, inflating call-heavy paths relative to C extensions.

python -m cProfile -s tottime kata.py
# Or programmatically with pstats:
st = pstats.Stats(prof).strip_dirs().sort_stats("tottime")
st.print_stats(10)

Statistical sampling: py-spy and flame graphs

A statistical profiler like py-spy (or scalene and Linux perf) does not hook function calls. Instead, it runs in a separate OS process, reads the target Python process memory at a fixed frequency (default 100 Hz, or once every 10 ms), and reconstructs the call stack. At 100 Hz, overhead is under 2%, making it safe to attach to a live production worker by PID (py-spy top --pid 12345 or py-spy record -o profile.svg --pid 12345). Unlike cProfile, py-spy can unwind native C/C++/Rust extensions (--native), distinguish active CPU threads from threads waiting on the GIL or I/O, and render flame graphs where the horizontal width of a bar is the fraction of samples in which that function was on the stack.

Check: on a flame graph, what does a wide flat plateau at the top of a tower mean, versus a wide bar at the bottom that splits into many narrow needles?
A wide flat plateau at the top edge is a leaf hotspot (high tottime): the CPU was caught directly inside that function across many samples. A wide bar at the bottom is a wrapper with high cumtime; if it splits into dozens of tiny needles, no single callee dominates.

Line-level, memory, and Amdahl's law

cProfile stops at function boundaries. When a 60-line function has high tottime, use line_profiler (@profile with kernprof -l -v) to time each line, or extract suspected lines into small helper functions so cProfile times them directly. For memory, CPU profilers are blind: a function can allocate 500 MB in 5 ms via C calls and barely register in tottime. Python's built-in tracemalloc hooks the CPython block allocator to track current and peak heap bytes per filename and line number with zero external dependencies.

Before optimizing any hotspot that takes a fraction p of runtime, apply Amdahl's law. If you speed up that fraction by a factor k, the new runtime is (1 - p) + p/k, giving total speedup:

S(p, k) = 1 / ((1 - p) + p / k)    --> ceiling as k -> inf is 1 / (1 - p)
Check: why measure end-to-end wall time with time.perf_counter() outside the cProfile run, as the kata does?
Because cProfile adds per-call hook overhead that slows down call-heavy Python code more than C extensions. Measuring wall time separately with time.perf_counter() gives the true speedup without observer distortion.

Kata: profile a slow tokenizer pipeline to a 15.2x speedup

A clinical voice intake pre-tokenizer runs across 600 documents against a 1,205-token vocabulary. Stage 0 has three performance bugs: dynamic regex compilation, an O(V) list scan per token, and a prefix snapshot accumulator that copies strings on every document. Run the script to see how cProfile and tracemalloc expose them in sequence.

Run

python kata.py

kata.py

"""A07 kata: profile a slow tokenizer pipeline across 3 stages with cProfile & tracemalloc."""
import cProfile
import io
import pstats
import re
import time
import tracemalloc

DOCS = 600
VOCAB_LIST = [f"tok_{i}" for i in range(1200)] + ["clinic", "patient", "intake", "voice", "agent"]
VOCAB_SET = set(VOCAB_LIST)
CORPUS = ["Patient intake call: schedule clinic voice agent follow-up for tok_42 and tok_999!"] * DOCS
PAT_STR = r"[a-zA-Z0-9_]+|[^\s\w]"
PAT_COMPILED = re.compile(PAT_STR)


def split_naive(doc):
    return re.compile(PAT_STR).findall(doc.lower())


def lookup_naive(words):
    out = []
    for w in words:
        out.append(w if w in VOCAB_LIST else "<unk>")
    return out


def assemble_naive(all_doc_tokens):
    snapshots = []
    acc = ""
    for doc_toks in all_doc_tokens:
        acc = acc + " ".join(doc_toks) + "\n"
        snapshots.append(acc)
    return snapshots[-1]


def tokenize_v0_naive(corpus):
    """Stage 0: dynamic re.compile + O(V) list lookup + prefix snapshot copies."""
    all_tokens = [lookup_naive(split_naive(doc)) for doc in corpus]
    return assemble_naive(all_tokens)


def tokenize_v1_lookup_fixed(corpus):
    """Stage 1: hoisted regex + O(1) set lookup, but still O(N^2) assemble_naive."""
    all_tokens = [
        [w if w in VOCAB_SET else "<unk>" for w in PAT_COMPILED.findall(doc.lower())]
        for doc in corpus
    ]
    return assemble_naive(all_tokens)


def tokenize_v2_fast(corpus):
    """Stage 2: hoisted regex + O(1) set lookup + single-pass ''.join."""
    lines = [
        " ".join([w if w in VOCAB_SET else "<unk>" for w in PAT_COMPILED.findall(doc.lower())])
        for doc in corpus
    ]
    return "\n".join(lines) + "\n"


def fmt_stat(st, func):
    cc, nc, tt, ct, _ = st.stats[func]
    return f"{func[2]} (ncalls={nc}, tottime={tt*1000:.1f}ms, cumtime={ct*1000:.1f}ms)"


def profile_stage(name, fn, corpus, base_ms=None):
    tracemalloc.start()
    t0 = time.perf_counter()
    res = fn(corpus)
    wall_ms = (time.perf_counter() - t0) * 1000.0
    _, peak_bytes = tracemalloc.get_traced_memory()
    tracemalloc.stop()

    pr = cProfile.Profile()
    pr.enable()
    fn(corpus)
    pr.disable()

    st = pstats.Stats(pr, stream=io.StringIO())
    st.sort_stats("cumtime")
    top_cum = [fmt_stat(st, f) for f in st.fcn_list[:2]]
    st.sort_stats("tottime")
    top_tot = [fmt_stat(st, f) for f in st.fcn_list[:2]]
    speedup = (base_ms / wall_ms) if base_ms else 1.0
    print(f"=== {name} ===")
    print(f"  wall={wall_ms:6.2f} ms | speedup={speedup:5.1f}x | peak_mem={peak_bytes/1024:7.1f} KB | len={len(res)}")
    print(f"  by cumtime: {' ; '.join(top_cum)}")
    print(f"  by tottime: {' ; '.join(top_tot)}")
    return wall_ms, res


if __name__ == "__main__":
    ms0, r0 = profile_stage("Stage 0: Naive (re.compile + list scan + prefix copies)", tokenize_v0_naive, CORPUS)
    ms1, r1 = profile_stage("Stage 1: Hoisted regex + O(1) set (still prefix copies)", tokenize_v1_lookup_fixed, CORPUS, ms0)
    ms2, r2 = profile_stage("Stage 2: Hoisted regex + O(1) set + batched join", tokenize_v2_fast, CORPUS, ms0)
    assert r0 == r1 == r2, "Outputs diverged!"

What to notice

  1. In Stage 0, sorting by cumtime puts tokenize_v0_naive first (cumtime=107.1ms, tottime=1.2ms). Sorting by tottime immediately points to lookup_naive (ncalls=600, tottime=96.4ms, or 90.0% of profiled time).
  2. Replacing w in VOCAB_LIST (O(V) scan of 1,205 items) with w in VOCAB_SET (O(1) hash lookup) and hoisting re.compile drops wall time from 108.06 ms to 15.78 ms (6.8x speedup).
  3. After Stage 1 removes the lookup bottleneck, assemble_naive jumps from 6% of the profile to the #1 tottime hotspot (7.1ms out of 10.6ms), and peak_mem is still 18,505.5 KB because snapshots.append(acc) holds all 600 growing prefix strings in memory at once.
  4. Stage 2 replaces assemble_naive with a single batched "\n".join(lines), cutting wall time to 7.11 ms (15.2x faster than Stage 0) and dropping peak memory from 18,508.6 KB to 155.4 KB (a 119x reduction).
Break it
  1. Defeat the regex LRU cache. CPython caches up to 512 compiled regex patterns (re._MAXCACHE = 512). In split_naive(doc), change PAT_STR to f"{PAT_STR}|doc_{id(doc)}" or pass a unique pattern per doc past 512 docs. Predict what happens to _compile in pstats, then run it.
  2. Double the document count. Change DOCS = 600 to DOCS = 1200. Predict whether Stage 0 wall time and Stage 1 peak_mem scale linearly (2x) or quadratically (4x) before running.

Stretch. Call snap = tracemalloc.take_snapshot() inside assemble_naive before returning, and print snap.statistics("lineno")[:3] to see the exact line number and byte count of the 18.5 MB allocation.

Traps

Each one sounds right. Say what is wrong with it before you open it.

"To find the bottleneck in cProfile, sort by cumtime and optimize the function at the top of the list."
Sorting by cumtime always puts main() or your top-level request handler at the top, because cumtime includes every child call. Optimizing the wrapper does nothing when 96.4 ms of a 107.1 ms run lives inside a leaf callee. Sort by cumtime to trace the call chain, then sort by tottime to find the leaf function executing the slow code.
"We can enable cProfile on all production API requests so we always have exact function timings."
cProfile instruments every function entry and exit, adding 15% to 50% CPU overhead on call-heavy Python code and distorting the very latency you want to measure. In production, use a statistical sampling profiler like py-spy at 100 Hz (under 2% overhead), or turn on deterministic profiling only for a tiny sampled fraction of canary requests.

Question bank

Explain the difference between a deterministic profiler (cProfile) and a statistical sampling profiler (py-spy).
cProfile hooks every function call and return inside the interpreter, giving exact call counts (ncalls) and timings at the cost of 15% to 50% overhead on call-heavy Python code. py-spy reads the process call stack from outside at a fixed rate like 100 Hz, adding under 2% overhead, working on live PIDs without code changes, and seeing native C frames and GIL wait.
Follow-upWhen can a sampling profiler mislead you? When a function runs very rarely for a few microseconds between 10 ms sample ticks, or when you need exact call counts to prove an O(N^2) call-count bug.
In pstats, a function shows ncalls = 600, tottime = 96.4 ms, cumtime = 96.9 ms. Another shows ncalls = 1, tottime = 1.2 ms, cumtime = 107.1 ms. Interpret both rows.
The second function is a high-level orchestrator called once: its own body took 1.2 ms, and its callees took 105.9 ms. The first function is the leaf bottleneck called 600 times: virtually all of its 96.9 ms cumulative time was spent directly inside its own body (96.4 ms, or 0.16 ms per call), with almost no time in subcalls.
You profile an ingestion job and find JSON serialization takes 80% of runtime. You switch to orjson, which is 10x faster on that step. What is the overall job speedup, and what is the theoretical ceiling?
By Amdahl's law, S = 1 / ((1 - 0.80) + 0.80 / 10) = 1 / (0.20 + 0.08) = 1 / 0.28 = 3.57x. Even if serialization became infinitely fast (0 ms), the remaining 20% serial work limits total speedup to 1 / 0.20 = 5x.
Why does cProfile bias you toward inlining Python helper functions, and how do you guard against that bias?
cProfile fires a hook on every Python function call and return, so a function called 1,000,000 times pays hook overhead 1,000,000 times, making it look slower in the profile than it really is. Guard against this by timing end-to-end wall clock with time.perf_counter() outside the profiler before and after any change, or by cross-checking with py-spy.
How do you find a Python memory leak or peak allocation spike in a worker without installing third-party C extensions?
Use standard library tracemalloc. For a peak spike, wrap the code with tracemalloc.start() and tracemalloc.get_traced_memory(). For a leak over time, take two snapshots across N requests (s1 = tracemalloc.take_snapshot(), then s2) and inspect s2.compare_to(s1, "lineno")[:10] to see which exact line grew monotonically.
Follow-upWhat memory will tracemalloc miss? Memory allocated outside CPython's allocator, such as NumPy arrays, PyTorch tensors on CPU or GPU, or raw C/Rust heap allocations.
In the kata, Stage 0 calls re.compile(PAT_STR) 600 times, yet _compile barely registers in tottime. Why, and when does un-hoisted regex compilation actually hurt?
CPython caches the last 512 compiled regex patterns in re._cache, so repeating the exact same pattern string hits a dict lookup in C. It still pays a function call per document, and it blows up in production when patterns are built dynamically (for example, interpolating user IDs or query terms) and thrash the 512-entry cache.

Mixed review

Three questions from earlier topics. Nobody tells you the topic in an interview.

A06: A test passes when run alone but fails in the full test suite, and a flaky bug appears on 10% of runs. What causes the first, and how many runs give 95% confidence of seeing the second?
Passing alone and failing in the suite indicates shared mutable state carried across tests (default mutable argument, global, cache, or database row). For a 10% failure rate, n = ln(0.05) / ln(0.9) = 28.4, so loop about 29 runs.
A02: Why does calling synchronous time.sleep(0.1) or a 100 ms CPU tokenizer loop inside an async def FastAPI endpoint ruin concurrency for all other requests on that worker?
An asyncio event loop runs on a single OS thread and switches tasks only at await points. A blocking call or CPU loop never yields control, freezing every concurrent coroutine on that worker for the full 100 ms.
A01: Why does checking membership with w in vocab_list inside a token loop scale as O(N * V), whereas w in vocab_set scales as O(N)?
A Python list checks membership by scanning elements one by one from index 0 (O(V) comparisons per lookup). A set or dict is a hash table that hashes the key once and probes the bucket directly in O(1) average time.
