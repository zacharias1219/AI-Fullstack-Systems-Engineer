Operating system essentials

How virtual memory, the kernel page cache, mmap, context switches, epoll, and zero-copy I/O govern model weight loading and high-concurrency LLM serving.

Before you read

Guess first. A wrong guess now makes the right answer stick later.

In our kata on a 64 MB weight file already warm in the OS page cache, how much faster and how much less Python user-space heap does mmap take to inspect one 4 MB layer tensor compared with f.read()?
61.2x faster (0.42 ms vs 25.62 ms) and 7,214x less user heap (0.009 MB vs 64.008 MB). f.read() allocates a 64 MB buffer in user space and copies every byte across the kernel-user boundary, whereas mmap maps virtual page table entries directly to the kernel page cache without copying bytes.
When you call mmap() on a 70 GB safetensors weight file, does the operating system immediately read 70 GB from NVMe into RAM?
No. mmap() only creates a virtual memory area (vm_area_struct) in the process address space with zero physical pages wired. Physical 4 KB pages are faulted in lazily via demand paging only when your CPU actually touches those virtual addresses (a minor fault if in page cache, or a major fault if fetched from NVMe).
Four Gunicorn/FastAPI worker processes on the same machine load the same 16 GB model file. Why does f.read() consume 64 GB of RAM while mmap() consumes only 16 GB?
f.read() copies the file into private anonymous heap pages inside each process (4 * 16 GB = 64 GB). Read-only mmap() maps all four processes' virtual page tables to the same physical 4 KB frames in the OS kernel page cache, sharing a single 16 GB copy in RAM.

The core idea

Every byte of model weights loaded from disk and every SSE token streamed to a user crosses the boundary between kernel space (Ring 0, which owns physical RAM, NVMe drives, and network cards) and user space (Ring 3, where Python and PyTorch run inside a virtual address space). Engineers who treat the OS as a black box pay twice: once by copying multi-gigabyte weight files redundantly between kernel and user buffers, and again by burning CPU cycles switching between thousands of blocked threads.

Two kernel mechanisms eliminate these bottlenecks. First, the OS caches disk blocks in unused physical RAM called the page cache. Standard read() copies bytes from the page cache into a newly allocated user-space buffer, whereas mmap() points your process's virtual page table entries directly at the kernel page cache frames (zero user-space copy, lazy demand paging, and instant cross-process sharing). Second, for network concurrency, epoll lets a single event-loop thread sleep until the kernel signals which sockets are ready, avoiding the stack memory and CPU cache-flushing overhead of thread-per-connection context switches.

Memory hook

"VPM-CEZ: Virtual pages, Page cache, Mmap, Context switch, Epoll, Zero-copy." The first three (VPM) explain zero-copy weight loading (safetensors maps virtual pages to the kernel page cache via mmap); the last three (CEZ) explain high-concurrency streaming servers (replace thread context switches with epoll readiness and zero-copy DMA).

How it works

1. Virtual memory, 4 KB page tables, and page faults

Every Linux/Windows process sees its own contiguous 64-bit virtual address space. The CPU's Memory Management Unit (MMU) translates virtual addresses into physical RAM frames in 4 KB pages (or 2 MB huge pages) using per-process Page Table Entries (PTEs) cached inside the CPU's Translation Lookaside Buffer (TLB). Because virtual memory is decoupled from physical RAM, two powerful metrics diverge in top/ps: VIRT (VSZ) is total virtual address space reserved (which can be 100 GB at zero RAM cost), while RES (RSS) is the actual physical RAM pages currently wired to the process.

When your code touches a virtual address whose PTE is not marked present, the CPU triggers a page fault trap into the kernel:

  • Minor (soft) page fault (~1-2 us): the 4 KB page is already in physical RAM inside the kernel page cache (or newly allocated zero page). The kernel simply updates the PTE to point at that frame and resumes execution.
  • Major (hard) page fault (~50-200 us on NVMe): the page is not in RAM. The kernel puts the thread to sleep, issues an NVMe block read into the page cache, wires the PTE, and wakes the thread.

2. Page cache and read() vs mmap() for model weights

The kernel uses free physical RAM as the page cache to store recently accessed file blocks. When you load a PyTorch or safetensors checkpoint via standard f.read(), the OS first populates the page cache (if cold) and then CPU-copies every byte from the kernel page cache into a newly allocated user-space buffer. You now hold two copies of the weights in physical RAM: one in the kernel page cache and one in your process's private heap.

With mmap() (used by Hugging Face safetensors and llama.cpp), the kernel maps a virtual address range directly to the file's page-cache pages. No bytes are copied into user heap (zero-copy into user space), only touched layers fault in (demand paging), and multiple worker processes share the exact same physical RAM frames.

read() RAM cost (W workers) = Page_Cache(Size) + W * Private_Heap(Size)
mmap() RAM cost (W workers) = Page_Cache(Size)   [shared across all W workers]
Check: Why does our kata's 4th benchmark (`mmap` touching 1 byte per 4 KB page across all 16,384 pages) take 27.22 ms while slicing a single 4 MB tensor takes 0.42 ms?
Because mmap() is lazy: creating the mapping and slicing one 4 MB tensor only faults in the few touched pages (0.42 ms). Stepping through all 16,384 pages at stride 4,096 triggers 16,384 separate minor page faults (plus Python loop overhead) to wire every 4 KB page into the process page table, costing 27.22 ms while still using only 0.009 MB of user heap.

3. Context switches, epoll, and zero-copy I/O

A syscall switches the CPU from user mode to kernel mode within the same process (~0.1-0.3 us). A process/thread context switch is much heavier (~1-5 us direct, plus tens of microseconds of indirect L1/L2/TLB cache pollution): the kernel must save CPU registers and stack pointers, swap page tables (if switching processes), and load the next thread. In our kata, reading 64 MB via 1,024 chunked read(64KB) syscalls takes 14.43 ms purely from syscall and copy overhead.

If an LLM gateway spawns 10,000 OS threads for 10,000 slow SSE streaming clients, default 8 MB thread stacks consume 80 GB of virtual memory and the scheduler thrashes CPU caches context-switching between sleeping threads. Instead, async frameworks (asyncio, uvloop, nginx) use epoll (Linux) / kqueue (macOS) / IOCP (Windows): the kernel monitors all 10,000 socket file descriptors in an internal red-black tree and returns only the active ready list in O(1) per ready event, while zero-copy primitives (sendfile, splice, GPU GPUDirect Storage DMA) move bytes directly between storage/NIC and memory without bouncing through user space.

Check: Why is `select()` or `poll()` slower than `epoll_wait()` when 10,000 SSE clients are connected but only 5 sockets receive a token chunk in a given millisecond?
select() and poll() pass the entire 10,000-descriptor array from user space to kernel space on every call and linearly scan all 10,000 sockets in O(N). epoll registers sockets once via epoll_ctl and uses NIC interrupt callbacks to push only the 5 active sockets onto a ready list, returning in O(k) where k = 5 ready events.

Kata: 64 MB weight loader benchmark (f.read vs chunked syscalls vs mmap)

Build a 64 MB binary tensor file (16 layers of 4 MB, 16,384 OS pages of 4 KB), warm the OS page cache, and measure wall time and peak Python user-space heap (tracemalloc) across four access patterns: full f.read(), 1,024 chunked read(64KB) syscalls, zero-copy mmap layer slicing, and a full 16,384-page mmap stride scan.

Run

python kata.py

kata.py

import mmap
import os
import struct
import tempfile
import time
import tracemalloc

# Simulate a 64 MB safetensors weight file with 16 tensor blocks of 4 MB each
NUM_TENSORS = 16
TENSOR_BYTES = 4 * 1024 * 1024  # 4 MB per layer tensor
TOTAL_BYTES = NUM_TENSORS * TENSOR_BYTES  # 64 MB total

def build_weight_file(path):
    block = (b"\x01\x02\x03\x04" * (TENSOR_BYTES // 4))
    with open(path, "wb") as f:
        for i in range(NUM_TENSORS):
            # Stamp layer index into first 4 bytes of each 4 MB tensor block
            f.write(struct.pack("<I", i) + block[4:])
        f.flush()
        os.fsync(f.fileno())

def bench_full_read(path, target_layer=11):
    tracemalloc.start()
    t0 = time.perf_counter()
    with open(path, "rb") as f:
        buf = f.read()  # Copies entire 64 MB from OS page cache into Python user heap
    offset = target_layer * TENSOR_BYTES
    layer_view = memoryview(buf)[offset : offset + TENSOR_BYTES]
    tag = struct.unpack("<I", layer_view[:4])[0]
    checksum = layer_view[0] + layer_view[-1]
    ms = (time.perf_counter() - t0) * 1000.0
    _, peak_bytes = tracemalloc.get_traced_memory()
    tracemalloc.stop()
    return ms, peak_bytes / (1024 * 1024), tag, checksum

def bench_chunked_read(path):
    tracemalloc.start()
    t0 = time.perf_counter()
    total = 0
    with open(path, "rb") as f:
        while True:
            chunk = f.read(64 * 1024)  # 1024 syscalls of 64 KB each
            if not chunk:
                break
            total += chunk[0]
    ms = (time.perf_counter() - t0) * 1000.0
    _, peak_bytes = tracemalloc.get_traced_memory()
    tracemalloc.stop()
    return ms, peak_bytes / (1024 * 1024), total

def bench_mmap_slice(path, target_layer=11):
    tracemalloc.start()
    t0 = time.perf_counter()
    with open(path, "rb") as f:
        with mmap.mmap(f.fileno(), 0, access=mmap.ACCESS_READ) as mm:
            offset = target_layer * TENSOR_BYTES
            mv = memoryview(mm)[offset : offset + TENSOR_BYTES]
            tag = struct.unpack("<I", mv[:4])[0]
            checksum = mv[0] + mv[-1]
            del mv
    ms = (time.perf_counter() - t0) * 1000.0
    _, peak_bytes = tracemalloc.get_traced_memory()
    tracemalloc.stop()
    return ms, peak_bytes / (1024 * 1024), tag, checksum

def bench_mmap_touch_all(path):
    tracemalloc.start()
    t0 = time.perf_counter()
    with open(path, "rb") as f:
        with mmap.mmap(f.fileno(), 0, access=mmap.ACCESS_READ) as mm:
            # Touch 1 byte per 4 KB OS page across all 16,384 pages
            total = sum(mm[i] for i in range(0, TOTAL_BYTES, 4096))
    ms = (time.perf_counter() - t0) * 1000.0
    _, peak_bytes = tracemalloc.get_traced_memory()
    tracemalloc.stop()
    return ms, peak_bytes / (1024 * 1024), total

if __name__ == "__main__":
    tmp = os.path.join(tempfile.gettempdir(), "r25_weights_64mb.bin")
    build_weight_file(tmp)
    try:
        # Warm page cache with one pass so we compare warm OS cache behavior
        with open(tmp, "rb") as f:
            _ = f.read()

        r_ms, r_mb, tag1, cs1 = bench_full_read(tmp)
        c_ms, c_mb, _ = bench_chunked_read(tmp)
        m_ms, m_mb, tag2, cs2 = bench_mmap_slice(tmp)
        p_ms, p_mb, _ = bench_mmap_touch_all(tmp)

        print(f"File size: {TOTAL_BYTES // (1024*1024)} MB ({TOTAL_BYTES // 4096} OS pages of 4 KB)")
        print(f"1. Full f.read() + slice   : {r_ms:6.2f} ms | Peak heap: {r_mb:6.3f} MB | layer={tag1} cs={cs1}")
        print(f"2. Chunked read (1024x64K) : {c_ms:6.2f} ms | Peak heap: {c_mb:6.3f} MB | syscalls=1024")
        print(f"3. mmap zero-copy slice    : {m_ms:6.2f} ms | Peak heap: {m_mb:6.3f} MB | layer={tag2} cs={cs2}")
        print(f"4. mmap touch 16384 pages  : {p_ms:6.2f} ms | Peak heap: {p_mb:6.3f} MB | stride=4096B")
        print(f"Speedup (mmap slice vs read): {r_ms / m_ms:.1f}x faster, {r_mb / max(m_mb, 0.001):.0f}x less user heap")
    finally:
        if os.path.exists(tmp):
            os.remove(tmp)

What to notice

  1. Full f.read() pays a 64.008 MB heap tax even when you only need one 4 MB tensor: in Method 1, copying all 64 MB from the kernel page cache into Python's heap takes 25.62 ms and allocates 64.008 MB of private user memory.
  2. mmap + memoryview is true zero-copy in user space: in Method 3, mapping the 64 MB file and slicing layer 11's 4 MB block takes 0.42 ms (61.2x faster) and allocates just 0.009 MB (9 KB) for Python wrapper structs (7,214x less heap) while verifying the exact same layer tag (11) and checksum (15).
  3. Chunked read(64KB) bounds heap at the cost of 1,024 syscalls: Method 2 reuses a 64 KB buffer (0.134 MB peak heap) and finishes in 14.43 ms because reusing a warm L2-cache-sized buffer avoids allocating a fresh 64 MB contiguous block, though it still executes 1,024 user-kernel transitions.
  4. Demand paging faults pages only when touched: Method 4 steps across all 16,384 pages at a 4,096-byte stride, forcing a minor page fault on every single 4 KB frame in the 64 MB file (27.22 ms total, or ~1.66 us/page including Python's generator loop) while still keeping user heap at 0.009 MB.

Traps

Each one sounds right. Say what is wrong with it before you open it.

"If a Python process shows 70 GB of VIRT (virtual memory) in top after mmap-ing a model, it is using 70 GB of physical RAM."
Wrong: VIRT (VSZ) only measures reserved virtual address space entries, which cost almost zero physical RAM. Physical RAM usage is measured by RES (RSS), and even within RSS, file-backed mmap pages live in the shared kernel page cache and can be reclaimed by the OS under memory pressure.
"mmap() is always faster than read() for loading large model files on any storage backend."
Wrong on high-latency network filesystems (NFS, AWS EFS, GCS FUSE) or cold spinning disks when accessed randomly: demand paging triggers thousands of tiny 4 KB synchronous major page faults over the network, whereas large sequential read() (or madvise(MADV_WILLNEED) readahead) coalesces I/O into high-throughput multi-megabyte transfers.

Question bank

Answer aloud, then open. Grade yourself honestly.

1. Walk through what happens in the kernel and MMU when a process calls `mmap()` on a 64 MB weight file and then reads the first byte of layer 11.
Calling mmap() creates a virtual memory mapping (vm_area_struct) in the process address space without allocating physical RAM or reading disk. When the CPU reads the virtual address for layer 11 (offset 44 MB), the MMU sees an unmapped PTE and raises a page fault. If that 4 KB block is already in the kernel page cache, the kernel resolves a minor page fault (~1-2 us) by wiring the PTE to the existing page cache frame; if not, it issues a major page fault (~50-200 us) to DMA the block from NVMe into the page cache first.
Follow-upIn Python, why must you wrap the `mmap` object in `memoryview(mm)[start:end]` instead of slicing `mm[start:end]` directly? Direct slicing `mm[start:end]` allocates a new Python `bytes` object and copies the slice into user heap, defeating zero-copy; `memoryview` creates a zero-copy buffer pointer.
2. Why does Hugging Face `safetensors` or `torch.load(..., mmap=True)` prevent container OOM kills when running multiple worker processes on a single node?
Because standard file reads copy tensor data into each process's private anonymous heap (anon pages in cgroups), so W workers multiply RAM usage by W. Read-only mmap maps every worker's virtual page table entries to the same physical frames in the kernel page cache (file pages), so W workers share a single copy in physical RAM.
3. Compare a system call, a voluntary thread context switch, and a process context switch in terms of CPU state and cache overhead.
A system call transitions privilege level (Ring 3 to Ring 0) inside the same thread without changing the virtual address space (~0.1-0.3 us). A thread context switch within the same process saves/restores CPU registers and stack pointers to run a different thread (~1-5 us, plus L1/L2 cache pollution) while keeping the same page table and TLB. A process context switch also swaps the page table base register (CR3 on x86), flushing non-PCID TLB entries and causing expensive TLB misses.
Follow-upWhen does a voluntary context switch occur versus an involuntary one? Voluntary occurs when a thread blocks on a syscall (like `read`, `epoll_wait`, or a mutex); involuntary occurs when the OS scheduler's time slice expires or a higher-priority thread preempts it.
4. How does `epoll` solve the C10K problem for an LLM streaming gateway holding 10,000 open SSE connections?
Instead of allocating 10,000 OS threads (80 GB of virtual stack space and constant scheduler thrashing) or scanning 10,000 file descriptors linearly on every loop with select()/poll() (O(N)), epoll registers sockets once in an in-kernel red-black tree via epoll_ctl. When a NIC interrupt arrives, the kernel pushes only the ready socket onto a linked list, so epoll_wait wakes the single event-loop thread in O(1) per active event.
5. What does "zero-copy" mean in the context of `sendfile()` or GPUDirect Storage, and how many data copies does a naive `read()` + `write()` file server make?
A naive read(disk_fd, buf) followed by write(sock_fd, buf) makes 4 context switches and 3 data copies (1: Disk DMA to kernel page cache, 2: CPU copy from page cache to user buffer, 3: CPU copy from user buffer to kernel socket buffer, followed by NIC DMA). sendfile() eliminates the two user-space CPU copies and two mode switches by instructing the kernel to DMA directly from the page cache descriptors to the NIC (and GPUDirect Storage DMAs directly from NVMe into GPU HBM without bouncing through CPU bounce buffers).
6. You deploy a 30 GB `mmap`-backed model on a Kubernetes pod running over a cloud network volume, and the first inference request takes 40 seconds while subsequent requests take 50 ms. What happened and how do you fix it?
On the first forward pass, every layer access triggered a synchronous 4 KB major page fault over the high-latency network volume. Subsequent requests hit the now-warm kernel page cache via fast minor faults. Fix it by calling madvise(MADV_WILLNEED) (or sequential pre-read) during pod readiness probe so the kernel prefetches the file in large sequential chunks before traffic arrives, or stage checkpoints onto local NVMe SSDs.

Quick-memorization cheat sheet covering every subtopic on this page and the key facts to remember cold.

All subtopics on this page

  • Virtual Memory & Page Faults: the MMU and TLB translate 64-bit virtual addresses into physical RAM frames in 4 KB pages (or 2 MB HugePages); minor faults (~1-2 us) wire a page already in RAM, whereas major faults (~50-200 us) block on NVMe disk I/O.
  • Kernel Page Cache: the OS caches accessed disk blocks in unused physical RAM; standard read() CPU-copies bytes from the page cache into private user heap (25.62 ms and 64.008 MB heap for 64 MB in our kata).
  • mmap() & Zero-Copy Tensor Loading: maps process virtual PTEs directly to kernel page-cache frames with lazy demand paging and cross-process RAM sharing; slicing a 4 MB tensor from a 64 MB file takes 0.42 ms (61.2x faster) and 0.009 MB heap (7,214x less).
  • Context Switches vs Syscalls: a syscall switches Ring 3 to Ring 0 inside the same process (~0.1-0.3 us), whereas a thread/process context switch (~1-5 us direct, 10-30 us with L1/L2/TLB cache warmup) swaps registers, 8 MB thread stacks, and page tables.
  • epoll & Zero-Copy Network/Storage I/O: epoll returns only ready sockets in O(1) per active event (vs select/poll O(N) scan), while sendfile() and GPUDirect Storage DMA transfer bytes directly without bouncing through user-space buffers.
Important things to remember
  • Why safetensors uses mmap: zero user-space copy on load, lazy page-by-page demand paging, and W inference workers share a single physical copy in the OS page cache instead of multiplying RAM by W.
  • Python zero-copy rule: always wrap mmap in memoryview(mm)[start:end] (or torch.frombuffer); slicing mm[start:end] directly allocates a copied Python bytes object in user heap.
  • When mmap hurts: cold network filesystems (NFS/EFS/FUSE) turn random layer accesses into thousands of slow 4 KB major page faults; pre-warm with madvise(MADV_WILLNEED) or copy to local NVMe first.
  • Memory hook (VPM-CEZ): Virtual pages (4 KB), Page cache (RAM), Mmap (zero user-copy), Context switch (cache/TLB flush), Epoll (O(1) ready events), Zero-copy (sendfile/DMA).
