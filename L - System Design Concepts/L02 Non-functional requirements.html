Non-functional requirements and tradeoffs

How do you turn "make it reliable and fast" into numbers you can design against, and say what each number costs? This page covers the five NFRs interviewers push on for an LLM chat API: availability, durability, consistency, latency and cost. SLO alerting is L76, CAP and consistency models are L35, capacity math is L03.

Study path

Before you read

Guess first. A wrong guess now makes the right answer stick later.

Your chat API sits behind four dependencies in series: load balancer 99.99%, app tier 99.95%, database 99.95%, LLM provider 99.9%. What is the combined availability, how many minutes a month is that, and does it meet a 99.9% SLO? Would a second LLM provider fix it?
Combined: 99.79%, about 91 minutes of downtime a month. A 99.9% SLO allows 43.2. It misses. With a second, independent provider the chain reaches 99.89%, about 48 minutes, which still misses, because the app tier and the database now set the ceiling.
You keep each chat log on three replicas with a 2% annual failure rate each and a one-day rebuild. A teammate says loss risk is about 1.8e-10 a year. When is that number badly wrong?
The model assumes independent failures. Put all three replicas in one zone with a 0.1% yearly zone-loss chance and the risk is about 1e-3 a year, millions of times worse. A seven-day rebuild instead of one also makes the independent figure about 50 times worse (8.8e-9).
A user posts a message and reloads 200 ms later. Reads go to an async replica with a mean lag of 50 ms. What fraction of reloads show stale data? What if lag spikes to 500 ms?
1.8% at 50 ms mean lag, 66.9% at 500 ms. If lag is exponential, the stale fraction after d ms is e^(-d / mean lag).

The core idea

A non-functional requirement (NFR) says how well the system does its job, not what the job is. A usable one has five parts: a metric, a number, a percentile or window, a scope, and a price. "Fast" is not an NFR. "p95 time to first token under 800 ms for prompts up to 2,000 tokens, measured at the gateway over 30 days" is one. If you cannot test it, it is a wish.

For an LLM chat API there are five dials: availability, durability, consistency, latency and cost. They are coupled. More nines cost spare capacity and a fallback. More durability costs copies and slower writes. Stronger consistency costs latency and sometimes availability. Lower latency costs GPUs. Interviewers are checking that you set each dial per data class, because a streamed answer, a stored transcript and a billing counter need different settings.

Memory hook

"A Dull Cat Chews Lemons": Availability, Durability, Consistency, Cost, Latency. Each has one unit and one price. Nines (price: spares). Copies (price: storage and write time). Staleness in milliseconds (price: latency). Dollars per good request. Percentile milliseconds (price: GPUs).

How it works

Availability is a product, not a target

Availability is the fraction of valid requests that are good. Downtime per 30-day month is (1 minus availability) times 43,200 minutes. That gives 432 minutes at 99%, 43.2 at 99.9%, 4.3 at 99.99%. Each extra nine shrinks the error budget (1 minus the SLO) tenfold. Dependencies in series multiply: 0.9999 x 0.9995 x 0.9995 x 0.999 = 0.9979. Dependencies in parallel fail only when all fail: two independent 99.9% providers give 1 minus 0.001 x 0.001 = 99.9999%. The word independent is doing the work. Two providers behind the same DNS, region or your own gateway are not independent.

For an LLM API, "good" needs a latency and a completion clause

A request that returns 200 after 40 seconds, or a stream that stalls after ten tokens, counts as up on a status-code dashboard and as broken to the user. Define the availability SLI as good events over valid events, where good means the first token arrived inside the TTFT target and the stream finished with a normal stop reason. This is also why the LLM provider sits in your series chain: you inherit its timeouts and its brownouts, not only its outages.

Check: your only LLM provider is 99.9% and you promise 99.9%. Why can you not hit it?
Availabilities multiply, so the product of the chain is below the weakest link. Add a fallback provider or a degraded mode (smaller model, cached answer, queued reply) so a provider outage no longer counts as downtime.

Durability is about not losing, availability about being reachable

Durability is the probability a stored object survives a year. A database can be down for an hour and lose nothing. With n replicas, each failing at annual rate r and rebuilt in d days, the window in which another replica can die is w = r x d / 365. Loss needs the first failure, then every other replica dying inside the window: roughly n x r x w^(n-1). For r = 2%, d = 1, n = 3 that is about 1.8e-10 a year. The model breaks on correlated failure: a lost zone, a bad migration, an operator delete, a software bug that corrupts every copy. Spread replicas across zones, keep versioned backups, and rehearse restores (RPO and RTO are L79). AWS documents S3 Standard as designed for 99.999999999% durability, a design claim built on checksums, repair and multi-zone storage, not on a replica count.

Durability differs by data class

A cached completion can be regenerated, so it needs none. A chat transcript is the product, so it needs cross-zone copies and backups. A billing ledger needs the highest level plus an audit trail. Durability also collides with privacy: backups that keep data forever fight an erasure request under GDPR or DPDPA, the tension ForgetMeNot exists to resolve.

Consistency is a promise about what a read may see

With async replication a replica trails the primary by a lag. If lag is exponential with mean L, a read d ms after a write is stale with probability e^(-d / L). At L = 50 ms and d = 200 ms that is 1.8%; at L = 500 ms it is 66.9%. Specify consistency per data class. Own messages: read-your-writes, so a user always sees what they just wrote (route that user to the primary or pass a session token for a short window). Quota and billing counters: strong, because a stale read means overspend. Dashboards and analytics: eventual. Strong everywhere buys safety you do not need and pays latency you do. Formal models and CAP are L35.

Check: where would you pay for strong consistency in a chat product, and where not?
Pay for it on quota, billing and idempotency state, where a stale read causes real loss. Use read-your-writes for a user's own messages. Use eventual consistency for search, analytics and admin dashboards.

Latency for a streaming LLM is two numbers

Users feel the time to first token (TTFT), then the reading speed set by time per output token (TPOT). End to end is TTFT + tokens x TPOT. With TTFT 600 ms, TPOT 25 ms and a 300-token answer, that is 600 + 7,500 = 8,100 ms. A single "under 2 seconds end to end" target is wrong for long streamed answers and meaningless for short ones. Write p95 TTFT and p95 TPOT, and use percentiles because the tail, driven by queueing, is what users remember. Metrics detail is K08 and G15.

Cost is an NFR with its own formula

Per-attempt cost is (input tokens x input price + output tokens x output price). Cost per successful request is per-attempt cost x expected attempts / success probability. With f the attempt failure rate and up to R retries, expected attempts = 1 + f + ... + f^R and success = 1 minus f^(R+1). Retries quietly raise both your bill and the load on a provider that is already struggling. Architecture-level cost thinking is L07; token levers are G01.

How to pick the numbers

Start from user harm, not from a nines table. Ask who is hurt, for how long, and what it costs the business, then derive the number and state its price. Keep the internal SLO tighter than any published SLA so you have a margin. Offer tiers: when a product owner says "five nines", show that it is 26 seconds a month, then price the multi-region design it implies and ask which flows really need it.

Check: a stakeholder asks for 99.999%. What do you do?
Convert it: 0.001% of 43,200 minutes is about 26 seconds a month. Ask which user flows truly need that, price the redundancy it implies (multi-region, independent fallbacks, no single dependency), and propose tiers such as 99.99% for the call path and 99.9% for the dashboard.

Kata: NFR calculator for an LLM chat API

One stdlib script that prints the numbers for all five dials, with four flags that each break one assumption on purpose. It runs in under a second.

Run

python kata.py

kata.py

"""L02 kata: NFRs with numbers for an LLM chat API. Stdlib only.
Run:  python kata.py            (baseline)
      python kata.py chain      (add more dependencies in series)
      python kata.py repair     (slow replica rebuild, 7 days)
      python kata.py lag        (replication lag spike, mean 500 ms)
      python kata.py incident   (provider failure rate 30%)
"""
import random, sys
MODE = sys.argv[1] if len(sys.argv) > 1 else ""
random.seed(7)
MONTH_MIN = 30 * 24 * 60
down = lambda a: (1 - a) * MONTH_MIN          # minutes of downtime per 30-day month

print("1. Nines to downtime (30-day month)")
for a in (0.99, 0.999, 0.9995, 0.9999):
    print(f"   {a*100:.2f}%  -> {down(a):7.1f} min/month")

print("\n2. Availability of a chain: series multiplies, parallel fails only if all fail")
chain = {"load balancer": .9999, "app tier": .9995, "database": .9995, "LLM provider": .999}
if MODE == "chain":
    chain.update({"vector db": .999, "auth service": .999, "rate limiter": .999})
total = 1.0
for a in chain.values():
    total *= a
print(f"   {len(chain)} dependencies in series: {total*100:.3f}%  -> {down(total):.0f} min/month")
two_providers = 1 - (1 - .999) * (1 - .999)   # assumes independent failures
with_fallback = total / chain["LLM provider"] * two_providers
print(f"   with a 2nd LLM provider:    {with_fallback*100:.3f}%  -> {down(with_fallback):.0f} min/month")

print("\n3. Durability: chance of losing a chat log in a year (simplified model)")
AFR = 0.02                                     # annual failure rate per replica (assumed)
REPAIR_DAYS = 7.0 if MODE == "repair" else 1.0
w = AFR * REPAIR_DAYS / 365                    # chance another replica dies inside the repair window
for n in (1, 2, 3):
    p = n * AFR * w ** (n - 1)                 # first failure, then the other n-1 die before repair
    print(f"   {n} replica(s), independent failures: {p:.1e} per year")
AZ_LOSS = 0.001                                # chance per year a whole zone is lost (assumed)
print(f"   3 replicas in ONE zone:  {AZ_LOSS + 3*AFR*w**2:.1e} per year (zone loss takes all three)")
print(f"   3 replicas in 3 zones:   {3*AFR*w**2 + AZ_LOSS**3:.1e} per year")

print("\n4. Consistency: stale reads from an async replica")
MEAN_LAG = 500 if MODE == "lag" else 50        # ms, replication lag, exponential (assumed)
print(f"   mean replica lag {MEAN_LAG} ms")
for d in (0, 50, 200, 1000):                   # read happens d ms after the write
    n = 100_000
    s = sum(random.expovariate(1 / MEAN_LAG) > d for _ in range(n)) / n
    print(f"   read {d:4d} ms after write: {s*100:5.1f}% stale")
print("   read-your-writes (user's reads go to primary for 1 s): ~0% stale for that user,")
print("   cost: every user who just wrote adds primary load for a second")

print("\n5. Cost and latency per chat request (illustrative prices, not a quote)")
IN_TOK, OUT_TOK = 1500, 300
PRICE_IN, PRICE_OUT = 3.0, 15.0                # USD per million tokens (illustrative)
TTFT_MS, TPOT_MS = 600, 25
f = 0.30 if MODE == "incident" else 0.02       # chance an attempt fails (timeout, 5xx)
RETRIES = 2
cost = (IN_TOK * PRICE_IN + OUT_TOK * PRICE_OUT) / 1e6
attempts = sum(f ** k for k in range(RETRIES + 1))   # expected attempts per request
ok = 1 - f ** (RETRIES + 1)                          # chance a request eventually succeeds
print(f"   one attempt: ${cost:.4f}   TTFT {TTFT_MS} ms   full answer {TTFT_MS + OUT_TOK*TPOT_MS} ms")
print(f"   failure rate {f:.0%}, up to {RETRIES} retries: {attempts:.2f} attempts per request,"
      f" success {ok*100:.2f}%")
print(f"   cost per successful request: ${cost*attempts/ok:.4f}   load on provider: x{attempts:.2f}")
print(f"   cost per 1M requests: ${cost*attempts/ok*1e6:,.0f}")

What to notice

  1. Four dependencies at 99.99, 99.95, 99.95 and 99.9 give 99.790%, which is 91 minutes a month. Your 99.9% promise allows 43.2.
  2. A second provider lifts the chain only to 99.890% (48 minutes). Once the provider is parallel, the app tier and database are the ceiling.
  3. Replicas buy durability fast: one copy is 2.0e-02 a year, two is 2.2e-06, three is 1.8e-10. Three replicas in one zone is 1.0e-03, almost six orders of magnitude worse than three zones (1.2e-09) in the same model.
  4. Stale reads fall off exponentially: 100% at 0 ms, 36.8% at 50 ms, 1.8% at 200 ms, 0.0% at 1,000 ms.
  5. The full answer takes 8,100 ms while TTFT is only 600 ms. The streaming NFR must be about TTFT and TPOT, not the total.
Break it
  1. chain. Run python kata.py chain. It adds a vector database, an auth service and a rate limiter at 99.9% each. Predict the new chain availability before running. Result: 99.491%, 220 minutes a month.
  2. repair. Run python kata.py repair. Rebuild takes 7 days instead of 1. Predict the factor for three replicas. Result: 8.8e-09 versus 1.8e-10, about 50x worse.
  3. lag. Run python kata.py lag. Mean lag becomes 500 ms. Predict the stale rate at 200 ms. Result: 66.9%, and still 13.5% a full second after the write.
  4. incident. Run python kata.py incident. The provider fails 30% of attempts. Predict the load multiplier on the provider. Result: x1.39, with cost per success rising from $0.0092 to $0.0129.

Stretch. Replace the fixed TTFT with 10,000 samples from a lognormal distribution and print p50, p95 and p99 plus the share of requests over 800 ms. Notice how far the p99 sits from the p50.

Scenario: your 99.9% monthly SLO is in force. The only LLM provider has a 40-minute full outage on day 9. What does that do to the budget, and what do you do?
  1. Math: 40 / 43.2 is about 93% of the monthly budget gone in one incident. Under a typical error budget policy, risky releases freeze for the rest of the window.
  2. During the incident: trip the circuit breaker, route to a fallback provider or a smaller model, return a clear degraded message, stop retries from piling on.
  3. After: add an independent fallback. In the kata that lifts the chain from 99.790% to 99.890%, which still misses 99.9%, so also look at the app tier and database.
  4. Revisit the target: is 99.9% right for every flow, or should the call path and the dashboard have different SLOs?

Traps

Each one sounds right. Say what is wrong with it before you open it.

"We keep three replicas, so our durability is eleven nines."
Replica math multiplies only if failures are independent. Three replicas in one zone sit near 1e-3 a year in the kata, and deletes, bad migrations and software bugs hit every copy. Eleven nines is a design claim for a system built on checksums, repair and multi-zone storage, not the output of "3 copies".
"Our provider is 99.9% and our SLO is 99.9%, so we are covered."
Series availabilities multiply, so the chain is below its weakest link. Four dependencies gave 99.79% (91 minutes a month) against a 43.2 minute budget. You need a fallback or a degraded mode, and even then the other dependencies cap the total.
"Strong consistency everywhere is the safe default."
It is safe and expensive: it adds write latency and can lower availability when a replica is down. Pay for it on billing and quota state. Use read-your-writes for a user's own messages and eventual consistency for analytics, where the cost of staleness is small.
"Our latency NFR is end to end under 2 seconds."
With TTFT 600 ms and TPOT 25 ms, a 300-token answer takes 8,100 ms end to end. A single end-to-end target is unmeetable for long streamed answers and says nothing about the part users feel first. Set p95 TTFT and p95 TPOT, and tie output length to a separate limit.

Question bank

Answer aloud, then open. Grade yourself honestly.

What is a non-functional requirement, and what does a well-formed one for an LLM chat API look like?
An NFR says how well the system works, not what it does. Well-formed means metric, number, percentile or window, scope and price: "p95 TTFT under 800 ms for prompts up to 2,000 tokens, measured at the gateway over 30 days". It can be tested and monitored.
Follow-upWhy p95 and not the average? The average hides the queueing tail. A few slow requests barely move the mean, but they are what a share of users experience every day.
Your SLO is 99.9% and your only LLM provider offers 99.9%. Can you meet it?
No. Availabilities multiply, so any chain with that provider in series sits below 99.9%. Add a fallback provider or a degraded mode so a provider outage is not user-visible downtime. In the kata, four dependencies came to 99.79%.
Follow-upIs the second provider's 99.9% independent of the first? Often not: shared region, DNS, your own gateway, or the same upstream cloud. Independence is an assumption to test, not a given.
What is the difference between availability and durability?
Availability is whether requests succeed right now. Durability is whether stored data survives over time. A database can be down for an hour with zero data lost, and a database can be up while having silently lost rows. They use different metrics and different mechanisms: redundancy and failover for one, copies, checksums and backups for the other.
How many replicas do you need for the durability of a chat transcript, and how do you reason about it?
Loss needs the first failure and then the other n-1 replicas failing before rebuild finishes: roughly n x r x w^(n-1) with w = r x days / 365. Three replicas at 2% and a one-day rebuild is about 1.8e-10 a year. Three is the usual starting point, spread across zones, plus backups.
Follow-upWhat breaks that number? Correlated failures (one zone, bad deploy, delete, corruption) and slow rebuilds. A seven-day rebuild made it about 50 times worse in the kata.
What consistency does a chat product need for message history?
Read-your-writes for the author: they must see what they just sent. Eventual consistency is fine for other readers, search and analytics. Strong consistency is reserved for quota and billing state. That limits the latency and availability cost to where it buys something.
Follow-upHow do you implement read-your-writes? Route that user's reads to the primary for a short window after a write, or carry a session token (last write position) and only read from replicas that have caught up.
What latency NFRs would you write for a streaming LLM API?
p95 TTFT and p95 TPOT, each with a prompt-size scope, plus a maximum output length. End to end is TTFT + tokens x TPOT, so total time follows from output length. Example: 600 ms TTFT, 25 ms TPOT, 300 tokens is 8.1 seconds, which is acceptable while it streams.
Follow-upWhat drives the tail? Queueing and batching delay at the inference server, long prompts in prefill, and provider brownouts. Details in K08 and K10.
How do you put cost into an NFR, and what do retries do to it?
State cost per successful request at a given prompt and output size. Compute it as per-attempt cost x expected attempts / success probability. At 30% failure with two retries the kata showed x1.39 provider load and $0.0129 per success against $0.0090 per attempt.
A 40-minute outage happens under a 99.9% monthly SLO. What is the impact?
The budget is 43.2 minutes, so 40 minutes spends about 93% of it in one incident. The error budget policy then typically freezes risky releases, and the postmortem should target a fallback and a degraded mode.
The product owner asks for five nines. What do you say?
Convert it: about 26 seconds of downtime a month. Ask which flows need it, price what it implies (multi-region, independent fallbacks, no shared single dependency) and offer tiers by flow. Do not agree to a number you cannot test or afford.
Follow-upWhat is the difference between an SLO and an SLA? The SLO is your internal target. The SLA is the contractual promise, usually looser, with credits attached. The gap is your safety margin. Depth in L76.
Write the NFRs for a voice assistant that answers calls for a clinic.
Latency: the dial that dominates. Time to first audio decides whether it feels like a conversation, so TTFT is budgeted across speech recognition, the model and speech synthesis. Availability: a missed call is a lost patient, so define a fallback to voicemail or a human when the provider is down. Durability and privacy: call records need retention, but erasure requests under GDPR or DPDPA mean backups must be deletable, which pulls against durability. Cost: per minute of call, including retries.

Mixed review

Three questions from earlier topics. Nobody tells you the topic in an interview.

L01: In requirements clarification, how do functional requirements differ from non-functional ones, and why ask about NFRs before drawing boxes?
Functional requirements say what the system does. Non-functional ones say how well, with numbers. They come early because they decide the architecture: a 99.99% target or a strict latency budget changes what you can draw.
A02: You fire 50 LLM calls sequentially, with gather, and with a semaphore. Which is fastest, and why would you still use the semaphore?
Gather is fastest because the calls overlap. A semaphore caps concurrency, so you stay under provider rate limits and avoid a burst of 429 errors. Sequential takes about 50 times one call's latency.
V01: Rewrite "we made the chatbot faster and cheaper" as an engineer answer.
Name the mechanism, a number, a failure mode and a tradeoff. For example: "We cut p95 time to first token by moving the static system prompt to the front so the prefix cache hits, and cut input cost by sending fewer retrieved chunks. The tradeoff is lower recall on long-tail questions, which we watch in the eval suite." Business framing follows in one sentence.
