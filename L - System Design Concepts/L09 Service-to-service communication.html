Service-to-service communication

How to choose and engineer internal service protocols across REST/JSON, gRPC/Protobuf over HTTP/2, GraphQL, and TCP vs UDP/QUIC so east-west AI microservice hops do not burn your latency budget on text serialization or head-of-line blocking.

Study path

Before you read

Guess first. A wrong guess now makes the right answer stick later.

An internal RAG embedding service returns 16 chunks, each holding a 768-dimensional float32 vector (12,288 floats = 49,152 raw float bytes). How many bytes does REST/JSON take on the wire compared to gRPC/Protobuf packed float32, and how much faster is binary SerDe in Python?
REST/JSON takes 96,390 bytes (94.1 KiB, 7.84 bytes/float) because every float is formatted as 6 to 9 ASCII characters plus commas. gRPC/Protobuf takes 49,376 bytes (48.2 KiB, 4.02 bytes/float) - only 224 bytes of framing overhead above the 49,152 raw IEEE-754 float bytes (1.95x smaller) - and serializes/deserializes 11.18x faster (272.4 ms vs 3,045.6 ms per 1,000 calls).
Why does HTTP/2 multiplexing over a single TCP connection eliminate application-layer head-of-line (HOL) blocking, yet still suffer from transport-layer HOL blocking under packet loss?
HTTP/2 interleaves frames from hundreds of concurrent RPC streams over one TCP connection, so a slow response on Stream 1 does not block frames for Stream 2 at the HTTP layer. However, TCP enforces strict in-order byte delivery across the entire socket: if a single TCP segment carrying a frame for Stream 1 is dropped on the network, the OS kernel holds back all subsequent arrived segments (even those belonging to Streams 2 through 100) until the lost segment is retransmitted. QUIC (HTTP/3 over UDP) fixes this by moving stream multiplexing into the transport layer so packet loss blocks only the affected stream.
When a BFF (Backend-for-Frontend) exposes a GraphQL query that fetches 20 conversation threads and their latest model runs, what causes the N+1 RPC storm to internal services, and what mechanism collapses it?
A naive GraphQL field resolver executes 1 RPC to fetch the 20 thread IDs and then fires 20 separate per-thread RPCs to the model-run service (1 + 20 = 21 sequential or parallel RPCs). A DataLoader collects all child keys requested during a single event-loop tick and dispatches one batched RPC (GetModelRuns(thread_ids=[1..20])), reducing N+1 calls to 2.

The core idea

Every service-to-service call makes two coupled engineering choices: a wire serialization format (text JSON vs binary Protobuf) and a transport framing protocol (HTTP/1.1, HTTP/2 over TCP, or QUIC over UDP). Text-based REST/JSON and GraphQL optimize for browser compatibility, human readability, and flexible schema evolution at the edge. Inside an AI cluster where an orchestrator calls embedding, vector-search, feature-store, and reranker microservices tens of times per user prompt, parsing megabytes of UTF-8 floating-point arrays burns CPU cores and inflates p99 tail latency.

For internal east-west traffic, gRPC over HTTP/2 with Protocol Buffers replaces verbose field names and ASCII numbers with 1-byte field tags, base-128 varints, and contiguous IEEE-754 binary float arrays, while multiplexing thousands of concurrent RPCs and bidirectional token streams over persistent connections.

Memory hook

R-G-Q-U (REST-Edge, gRPC-East-West, Query-BFF, UDP-RealTime): REST for external simplicity, gRPC for binary internal speed, GraphQL + DataLoader for BFF fan-out, UDP/QUIC to kill TCP head-of-line blocking.

How it works

1. Protobuf TLV binary encoding vs JSON text parsing

JSON repeats every field name as a UTF-8 string on every object and converts 32-bit IEEE-754 floats into base-10 ASCII text, requiring slow lexical scanning (strtod) on the receiver. Protocol Buffers uses a schema-compiled Tag-Length-Value (TLV) wire layout. Each field header is a single varint combining field number and wire type: tag = (field_num << 3) | wire_type. Integers use base-128 varints (7 payload bits per byte; MSB 1 means more bytes follow). Repeated float32 vectors use wire type 2 (length-delimited packed array): one tag byte (0x1A for field 3), a varint byte length (3072 for 768 floats), and 3072 contiguous IEEE-754 bytes copied directly into a tensor buffer with zero text parsing.

Protobuf packed float32 field 3:  [0x1A] [0x80 0x18 (len=3072)] [768 x 4-byte IEEE-754 floats]
Total per 768-dim chunk:          14 bytes framing + 3,072 float bytes = 3,086 bytes (4.02 B/float)

2. HTTP/1.1 vs HTTP/2 multiplexing and gRPC streaming

HTTP/1.1 uses text headers and processes one request at a time per TCP connection; handling 200 concurrent RPCs requires a pool of 200 TCP sockets. HTTP/2 splits messages into binary HEADERS and DATA frames tagged with a 31-bit Stream ID, multiplexing hundreds of concurrent RPCs over a single TCP connection and compressing repetitive headers with HPACK. This framing unlocks four gRPC call patterns: unary RPC, server streaming (LLM token generation), client streaming (audio chunk upload), and bidirectional streaming (full-duplex voice AI agents).

3. GraphQL N+1 problem and TCP vs UDP transport

GraphQL shifts field selection to the client but creates two server hazards: deeply nested cyclic queries and the N+1 resolver problem, which must be guarded by query depth limits, persisted query allowlists, and per-request DataLoader batching. Underneath HTTP, TCP provides reliable, ordered, congestion-controlled byte streams via a 3-way SYN/SYN-ACK/ACK handshake (1 RTT + 1 TLS RTT), whereas UDP adds only an 8-byte header with no handshake, retransmission, or ordering delay - vital for voice AI WebRTC media and QUIC's 0-RTT/1-RTT independent streams.

Check: What are the three golden rules for backward-compatible Protobuf schema evolution?
Never change the numeric field tag of an existing field; never reuse a deleted field's tag number (mark both the tag number and field name as reserved); and give new fields new tag numbers so old readers safely skip unknown tags and new readers apply default values when reading old messages.
Check: Why would a clinical voice AI agent use WebRTC over UDP for the patient's audio stream, gRPC bidirectional streaming internally between the VAD/ASR and LLM workers, and REST/JSON for the clinic's EHR webhook?
Patient audio requires sub-100 ms jitter-free media transport where retransmitting a dropped 20 ms audio packet over TCP would stall live speech (UDP wins). Internal ASR-to-LLM streaming requires reliable ordered token/audio frames with strict binary schemas over persistent connections (gRPC over HTTP/2 wins). External third-party EHR integrations require universal curl/webhook debuggability without custom client stubs (REST/JSON wins).

Kata: REST/JSON vs Protobuf binary wire benchmark

Encode and decode an internal AI reranker/embedding payload (16 chunks, each with an integer ID, relevance score, and 768-dim float32 vector) in both UTF-8 JSON and binary Protobuf TLV wire format (varint + packed IEEE-754 struct floats) to measure exact byte size and CPU serialization throughput.

Run

kata.py

import json
import struct
import time

# Build deterministic payload: 16 document chunks, each with 768-dim float32 embedding + metadata
N_CHUNKS, DIM, N_ITER = 16, 768, 500
chunks = [{
    "id": idx + 1001,
    "score": round(0.985 - idx * 0.012, 4),
    "vec": [round(((idx + 1) * 0.0013 + d * 0.0007) % 1.0 - 0.5, 6) for d in range(DIM)]
} for idx in range(N_CHUNKS)]

# 1. REST JSON encoding (UTF-8 text floats)
json_bytes = json.dumps({"chunks": chunks}, separators=(",", ":")).encode("utf-8")

# 2. Protobuf binary wire encoding (varint tags/lengths + packed IEEE-754 float32)
def encode_varint(n):
    out = bytearray()
    while n > 0x7F:
        out.append((n & 0x7F) | 0x80)
        n >>= 7
    out.append(n & 0x7F)
    return bytes(out)

def encode_proto_batch(items):
    buf = bytearray()
    for item in items:
        msg = bytearray()
        # field 1: id (tag = (1<<3)|0 = 0x08, varint)
        msg.append(0x08)
        msg.extend(encode_varint(item["id"]))
        # field 2: score (tag = (2<<3)|5 = 0x15, float32)
        msg.append(0x15)
        msg.extend(struct.pack("<f", item["score"]))
        # field 3: packed repeated float32 vec (tag = (3<<3)|2 = 0x1A, length + 4*DIM bytes)
        packed_floats = struct.pack(f"<{len(item['vec'])}f", *item["vec"])
        msg.append(0x1A)
        msg.extend(encode_varint(len(packed_floats)))
        msg.extend(packed_floats)
        # outer field 1: repeated Chunk (tag = 0x0A, length + submessage)
        buf.append(0x0A)
        buf.extend(encode_varint(len(msg)))
        buf.extend(msg)
    return bytes(buf)

def decode_proto_batch(raw, dim=DIM):
    pos, out = 0, []
    stride = 4 * dim
    while pos < len(raw):
        pos += 1  # outer tag 0x0A
        while raw[pos] & 0x80:
            pos += 1
        pos += 1
        pos += 1  # id tag 0x08
        cid, shift = 0, 0
        while True:
            b = raw[pos]; pos += 1
            cid |= (b & 0x7F) << shift
            if not (b & 0x80): break
            shift += 7
        pos += 1  # score tag 0x15
        score = struct.unpack_from("<f", raw, pos)[0]; pos += 4
        pos += 1  # vec tag 0x1A
        while raw[pos] & 0x80:
            pos += 1
        pos += 1
        vec = struct.unpack_from(f"<{dim}f", raw, pos); pos += stride
        out.append((cid, score, vec))
    return out

proto_bytes = encode_proto_batch(chunks)
decoded_check = decode_proto_batch(proto_bytes)
raw_f32_bytes = N_CHUNKS * DIM * 4

# 3. Benchmark CPU encode + decode time for 500 calls
t0 = time.perf_counter()
for _ in range(N_ITER):
    b = json.dumps({"chunks": chunks}, separators=(",", ":")).encode("utf-8")
    _ = json.loads(b.decode("utf-8"))
json_ms_per_1k = (time.perf_counter() - t0) * 1000.0 * (1000.0 / N_ITER)

t0 = time.perf_counter()
for _ in range(N_ITER):
    b = encode_proto_batch(chunks)
    _ = decode_proto_batch(b)
proto_ms_per_1k = (time.perf_counter() - t0) * 1000.0 * (1000.0 / N_ITER)

print(f"Batch: {N_CHUNKS} chunks x {DIM}-dim float32 ({N_CHUNKS*DIM:,} floats = {raw_f32_bytes:,} raw float bytes)")
print(f"REST/JSON payload     : {len(json_bytes):7,d} bytes ({len(json_bytes)/1024:.1f} KiB) | {len(json_bytes)/(N_CHUNKS*DIM):.2f} B/float")
print(f"gRPC/Protobuf payload : {len(proto_bytes):7,d} bytes ({len(proto_bytes)/1024:.1f} KiB) | {len(proto_bytes)/(N_CHUNKS*DIM):.2f} B/float")
print(f"Wire reduction        : {len(json_bytes)/len(proto_bytes):.2f}x smaller ({100*(1 - len(proto_bytes)/len(json_bytes)):.1f}% saved)")
print(f"PROTO framing overhead: {len(proto_bytes) - raw_f32_bytes} bytes total ({(len(proto_bytes)-raw_f32_bytes)/N_CHUNKS:.1f} B/chunk)")
print(f"CPU SerDe (per 1k RPC): JSON = {json_ms_per_1k:.1f} ms | Protobuf = {proto_ms_per_1k:.1f} ms ({json_ms_per_1k/proto_ms_per_1k:.2f}x faster)")

What to notice

  1. Only 14 bytes of Protobuf framing per 768-float chunk: Raw memory for 16 * 768 float32 numbers is 49,152 bytes. Protobuf's TLV wire format takes 49,376 bytes (4.02 B/float), adding just 224 bytes across all 16 submessages, whereas JSON balloons to 96,390 bytes (7.84 B/float).
  2. 11.18x CPU serialization speedup: Converting 12,288 floats to and from decimal ASCII strings in JSON takes 3,045.6 ms per 1,000 RPCs (3.05 ms of pure CPU per call), while packing and unpacking contiguous IEEE-754 floats takes 272.4 ms per 1,000 RPCs (0.27 ms per call).
  3. Varint tag efficiency: Field tags 1 (0x08), 2 (0x15), and 3 (0x1A) each fit in a single byte because their field numbers are <= 15 (4 bits for field number + 3 bits for wire type + MSB 0).
Break it
  1. Unpack the repeated float field (remove packed encoding). Instead of writing one length-delimited block (0x1A + length + 768 floats), write a 1-byte tag before every single float (768 * 5 bytes). Predict how much the Protobuf payload grows: it adds 16 * 768 = 12,288 bytes of tag overhead (rising from 49.4 KB to 61.6 KB), proving why Protobuf v3 enables packed=true by default on repeated numeric fields.
  2. Increase decimal precision in JSON from 6 digits to full float64 string representation. Remove round(..., 6) when generating vec. Predict the JSON byte count: Python formats IEEE-754 floats with 17-19 ASCII characters (-0.49800000000000005), inflating JSON above 230 KB (nearly 5x larger than Protobuf).

Stretch. Add zlib.compress (gzip) on top of both payloads and measure the CPU-versus-bandwidth tradeoff: compressing random or high-entropy float32 mantissas saves under 15% bandwidth while doubling CPU latency.

Traps

Each one sounds right. Say what is wrong with it before you open it.

"Because HTTP/2 multiplexes streams, moving from HTTP/1.1 to gRPC over HTTP/2 completely eliminates head-of-line blocking."
Wrong. HTTP/2 only eliminates application-layer head-of-line blocking (a slow handler on Stream 1 does not block frames on Stream 2). Because all HTTP/2 streams share a single TCP byte stream, a single lost TCP packet on the network causes the OS TCP stack to hold back delivery of all subsequent packets across every multiplexed stream until the lost packet is retransmitted. Eliminating transport-layer HOL blocking requires QUIC (HTTP/3 over UDP).
"Putting a standard Kubernetes ClusterIP (L4 TCP) load balancer in front of gRPC pods evenly distributes RPC requests across replicas."
Wrong. An L4 load balancer balances at TCP connection establishment (SYN). Because a gRPC client opens one long-lived HTTP/2 TCP connection and multiplexes thousands of RPCs over that single socket, every RPC lands on whichever pod accepted the initial TCP connection. You must balance per-request at L7 (Envoy, Linkerd) or enable gRPC client-side load balancing with MAX_CONNECTION_AGE.

Question bank

How does Protocol Buffers encode a field tag and a packed float32 array on the wire, and why should frequent fields use tag numbers 1 through 15?
A Protobuf tag byte stores (field_number << 3) | wire_type as a base-128 varint. Because 3 bits hold the wire type and 1 MSB bit is the varint continuation flag, field numbers 1 through 15 fit in the remaining 4 bits of a single byte; field numbers 16 through 2047 require 2 bytes. A packed float32 array uses wire type 2 (length-delimited): 1 tag byte, a varint byte count (4 * N), and 4 * N raw IEEE-754 bytes.
Follow-upWhy is packed=true useless or harmful for an array of string embeddings? Strings are already length-delimited (wire_type=2), whereas packed eliminates repeated tag bytes across fixed-width or varint numeric primitives.
Compare the payload size and CPU SerDe cost of 16 x 768-dim float32 embeddings in REST/JSON vs gRPC/Protobuf from our kata.
The 12,288 raw float32 values occupy 49,152 bytes in memory. REST/JSON encodes them as 96,390 bytes (7.84 B/float) and takes 3,045.6 ms per 1,000 SerDe cycles. Binary Protobuf encodes them as 49,376 bytes (4.02 B/float, only 224 bytes of TLV framing) and takes 272.4 ms per 1,000 cycles - a 1.95x bandwidth reduction and 11.18x CPU speedup.
When should you use GraphQL, and what two server-side safeguards are mandatory before exposing a GraphQL endpoint in production?
Use GraphQL at a BFF (Backend-for-Frontend) when diverse web/mobile views need flexible subsets of nested entities in a single network round trip. You must enforce (1) request-scoped DataLoader batching so nested field resolvers do not trigger N+1 RPC storms to internal microservices, and (2) query depth/complexity limits (or persisted query allowlists) so malicious deeply nested queries cannot exhaust server CPU.
Follow-upWhy is HTTP CDN caching harder with GraphQL than REST? GraphQL sends queries inside a POST /graphql JSON body rather than distinct GET /resource/{id} URLs, bypassing standard URL-keyed HTTP caches unless Automatic Persisted Queries (APQ) with GET hashes are enabled.
Explain the four gRPC RPC streaming modes and map each to a real AI system component.
(1) Unary (Req -> Resp): synchronous reranker or embedding lookup. (2) Server streaming (Req -> stream Resp): LLM token-by-token generation stream from an inference worker. (3) Client streaming (stream Req -> Resp): streaming audio frames into a batch transcription utterance endpoint. (4) Bidirectional streaming (stream Req <-> stream Resp): full-duplex real-time voice AI session with barge-in interruption.
Why does live voice AI (such as a clinic phone agent) use RTP/WebRTC over UDP at the client edge instead of gRPC over TCP?
Live conversation requires mouth-to-ear latency under 200-300 ms. Over TCP, a single lost packet on a cellular link halts the entire audio stream for 1 to 3 RTTs (50-250 ms) while the kernel waits for retransmission, causing audible robotic freezes. UDP delivers every arriving 20 ms opus audio frame immediately without retransmission stalls, letting the jitter buffer interpolate a single missing frame imperceptibly.
What happens if you pass a 12 MB tensor or image batch through a default gRPC channel, and how should large blobs be transferred?
gRPC enforces a default 4 MB (4 * 1024 * 1024 bytes) maximum inbound message size and rejects the call with RESOURCE_EXHAUSTED to prevent OOM buffer allocations. Either chunk the payload across a gRPC stream (64 KB to 1 MB frames), raise grpc.max_receive_message_length cautiously for bounded tensors, or pass large media via pre-signed object storage / shared memory pointers.

Mixed review

Three questions from earlier topics. Nobody tells you the topic in an interview.

L08: Why should a paginated list API under concurrent writes use cursor/keyset pagination (WHERE created_at < :cursor_ts) instead of OFFSET/LIMIT?
OFFSET N forces the database to scan and discard N rows (O(N) latency at deep pages) and shifts row positions whenever a new row is inserted at the top, causing clients to see duplicate items or skip items across pages. Keyset pagination seeks directly to the B-tree index position in O(log N) time with zero drift.
A12: Why does omitting zero_grad() before loss.backward() break standard SGD training, yet deliberately omitting it for K steps enables large-batch training on a single GPU?
Because autograd VJPs use += accumulation into p.grad, omitting zero_grad() across optimizer steps compounds stale gradients from old weights. However, running K micro-batch backward passes (each scaled by 1/K) before calling optimizer.step() and zero_grad() sums the exact full-batch gradient while freeing each micro-batch's activation DAG immediately.
A11: Why is the gradient grad f(x) always orthogonal to the level set (contour line) {x : f(x) = c}?
For any smooth curve x(t) moving along the level set f(x(t)) = c, differentiating with respect to t by the chain rule gives d/dt f(x(t)) = grad f(x) . x'(t) = 0. Since the dot product with every tangent vector x'(t) is zero, grad f(x) is perpendicular to the contour and points in the direction of steepest ascent.

Short notes

Quick-memorization cheat sheet covering every subtopic on this page and the key facts to remember cold.

All subtopics on this page

  • REST/JSON vs gRPC/Protobuf on Float Embeddings: On 16 x 768 float32 vectors (49,152 raw bytes), JSON takes 96,390 B (7.84 B/float, 3,045.6 ms/1k SerDe) while packed Protobuf takes 49,376 B (4.02 B/float, only 224 B framing, 272.4 ms/1k SerDe) - 1.95x smaller and 11.18x faster.
  • Protobuf TLV Wire Layout: Tag byte = (field_num << 3) | wire_type; fields 1-15 fit in 1 byte. Packed float32 uses wire type 2 (length-delimited contiguous IEEE-754 array) to avoid per-element tags and text parsing.
  • HTTP/2 Multiplexing & gRPC Streaming: Binary frames tagged by Stream ID allow concurrent unary, server-stream (LLM tokens), client-stream, and bi-di stream (voice AI) RPCs over one TCP socket, but require L7 load balancing so one pinned TCP socket does not overload a single pod.
  • GraphQL & DataLoader Batching: Best for BFF client-driven field selection; must pair with per-tick DataLoader batching to collapse N+1 downstream RPC storms into 2 calls and enforce query depth/cost limits.
  • TCP vs UDP / QUIC: TCP guarantees in-order byte delivery across the whole socket, so 1 lost packet stalls all multiplexed HTTP/2 streams (transport HOL blocking); QUIC (HTTP/3 over UDP) isolates loss per stream, and WebRTC/RTP over UDP skips retransmission for sub-200 ms live voice audio.
Important things to remember
  • Spine (R-G-Q-U): REST at external north-south edge; gRPC/Protobuf for internal east-west microservices; GraphQL + DataLoader at BFF; UDP/WebRTC/QUIC to eliminate TCP HOL blocking.
  • Protobuf evolution rules: Never change or reuse numeric field tags; mark deleted tags/names reserved; keep hot fields in tags 1-15.
  • Production gRPC trap: Kubernetes L4 ClusterIP balances TCP connections, not HTTP/2 streams - always use L7 Envoy/Istio or gRPC client-side round-robin.
