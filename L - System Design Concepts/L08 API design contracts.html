API design contracts

How do you design an HTTP API contract around resources, idempotent writes, structured RFC 9457 error envelopes, backward-compatible evolution, and composite keyset cursor pagination so that retries never double-charge, concurrent writes never leak duplicate rows across pages, and deep paging stays O(limit) instead of grinding the database at O(offset + limit)?

A clinic dashboard fetches Page 1 (`LIMIT 50 OFFSET 0`) of an audit log sorted by `created_at_ms DESC, id DESC`. While the doctor reads Page 1, 3 new calls arrive. When the client requests Page 2 (`LIMIT 50 OFFSET 50`), how many duplicate rows from Page 1 reappear on Page 2 under `OFFSET` versus composite keyset cursor pagination?
Under `OFFSET`, 3 duplicate rows from the bottom of Page 1 shift right into positions 51 to 53 and reappear on Page 2. Under composite keyset cursor pagination (`WHERE (created_at_ms, id) < (?, ?)`), the query anchors to the exact tuple of the 50th item on Page 1, returning 0 duplicate rows and 0 skipped rows.
In our 50,000-row SQLite kata, jumping to Page 800 (`offset = 39,950`, `limit = 50`) takes `0.394 ms` with `OFFSET` versus `0.051 ms` (`7.7x` faster) with a keyset cursor. How many index rows must the database touch in each query, and why?
`OFFSET 39950 LIMIT 50` must walk and discard 39,950 index entries before returning 50, scanning 40,000 rows (`O(offset + limit)`). A keyset cursor performs a B-tree seek (`O(log N)`) directly to `(ts, id)` and reads only 50 rows (`O(limit)`), which stays constant whether you are on Page 1 or Page 800.
A mobile client sends `POST /v1/payments` or `POST /v1/agent-runs`, and the TCP connection drops after the server commits the database transaction but before the response reaches the phone. Why does an automatic retry create a duplicate run unless the API contract requires an `Idempotency-Key` header?
By HTTP semantics (RFC 9110), `POST` is neither safe nor idempotent: calling it `N` times creates `N` distinct resources. When the client passes `Idempotency-Key: <uuid>`, the server hashes the request parameters and stores `(client_id, key, params_hash, status, response_body)` in an atomic idempotency table (for example, 24h TTL), so any retry returns the stored response without re-executing the side effect.

The core idea

An API is not a thin wrapper around your database tables; it is a long-lived behavioral contract between independent systems that fail, retry, upgrade on different schedules, and read data while writes are in flight. Most production API incidents happen not because a single happy-path call fails, but because the contract leaves ambiguity under stress: a network timeout triggers a `POST` retry that double-charges a patient, an `OFFSET` query shifts under live inserts and drops records during an audit export, or a vague `500 Internal Server Error` causes a client SDK to retry a permanently invalid payload in a tight loop.

The mental model is a four-pillar contract pipeline across every request and response: Resources and Idempotency define nouns and retry safety (`GET/PUT/DELETE` idempotent by spec, `POST` made idempotent via `Idempotency-Key`), Version and Schema Evolution keep old clients working via additive changes and explicit version pinning, Composite Keyset Cursors anchor collection scans to an opaque HMAC-signed `(timestamp, tiebreaker_id)` tuple in `O(limit)` time, and Structured Error Envelopes (RFC 9457) tell callers deterministically whether to fix their code or back off and retry.

Memory hook

"R-E-V-P" (Resilient Endpoints Verify Payloads): Resources & `Idempotency-Key` (nouns + safe `POST` retries) -> Errors via RFC 9457 (`status`, `code`, `retryable`, `request_id`) -> Versioning via additive fields + Postel's Law (`Sunset` header for breaking deprecations) -> Pagination via opaque HMAC-signed composite keyset cursors `(ts, id) < (?, ?)`.

How it works

1. Resource modeling, HTTP method semantics, and `Idempotency-Key`

A resource-oriented API models domain state as hierarchical plural nouns (`/v1/tenants/{id}/conversations/{cid}/messages`) and maps state transitions to standard HTTP methods defined in RFC 9110. Two mathematical properties govern every method: a method is safe if it performs read-only queries without mutating server state, and idempotent if executing the exact same request `N > 1` times leaves the server in the same state as executing it once.

Method   Safe?   Idempotent?   Contract & Retry Rule
GET      Yes     Yes           Read resource/collection; always safe to auto-retry on network drop
PUT      No      Yes           Replace full resource at known URI; idempotent by state replacement
DELETE   No      Yes           Remove resource; repeat calls return 200/204 or 404 (state is gone)
POST     No      NO*           Create child / trigger job; *MUST pair with Idempotency-Key for retries
PATCH    No      NO*           Partial update; idempotent for set-field, non-idempotent for increment

Because mobile networks, load balancers, and LLM tool-calling loops frequently drop TCP connections after the server has already committed a write, `POST` endpoints that charge money, trigger background jobs, or append conversation messages must support an Idempotency-Key header (a client-generated UUIDv4 or UUIDv7). The server stores (tenant_id, idempotency_key, request_hash, status, response_blob) in an atomic key-value or SQL table with a 24-hour TTL. If a retry arrives with the same key and matching request_hash while the first request is still running, the server returns 409 Conflict (or waits and streams the result); if the first request already finished, it replays the stored status and body verbatim. If the client reuses the same key with a different payload hash, the server immediately rejects it with 422 Unprocessable Content.

2. Structured error contracts and RFC 9457 Problem Details

Never return 200 OK with {"success": false, "error": "..."}; doing so blinds reverse proxies, CDN caches, OpenTelemetry tracing, and circuit breakers. Instead, pair an accurate HTTP status code with a deterministic JSON body standardized by RFC 9457 (Problem Details for HTTP APIs), extended with a machine-readable code, a boolean retryable flag, and a request_id for log correlation.

HTTP/1.1 400 Bad Request
Content-Type: application/problem+json

{
  "type": "https://api.example.com/errors/invalid-cursor",
  "title": "Invalid pagination cursor",
  "status": 400,
  "code": "INVALID_CURSOR",
  "detail": "Cursor failed verification (HMAC signature mismatch); restart from page 1.",
  "retryable": false,
  "request_id": "req_01J8X9K2P4"
}

Distinguish five failure buckets so client SDKs never guess whether to retry: 400 Bad Request for malformed syntax or tampered cursor tokens (`retryable: false`); 422 Unprocessable Content for valid JSON that violates domain or schema validation such as `temperature: 9.5` (`retryable: false`, include a `fields` array); 409 Conflict for optimistic concurrency (`ETag` / `If-Match`) or in-flight idempotency collisions; 429 Too Many Requests for rate or token-per-minute quota exhaustion (`retryable: true`, always include a `Retry-After` header in seconds); and 503 Service Unavailable when an upstream dependency or GPU pool is overloaded (`retryable: true` with exponential backoff and jitter).

Check: What is the difference between HTTP 400, 422, and 409, and how should a client SDK's automatic retry middleware treat all three compared to 429 and 503?
400 means malformed wire syntax or invalid parameters (such as a corrupted cursor), 422 means syntactically valid JSON that fails semantic/domain validation, and 409 means a state conflict against current resource state or an in-flight idempotency key. Automatic retry middleware must never blindly retry 400 or 422 (`retryable: false`), may reconcile state before retrying 409, and should retry 429 and 503 (`retryable: true`) respecting `Retry-After` or exponential backoff with jitter.

3. Versioning, additive evolution, and Postel's Law

The cheapest version bump is the one you never ship. Follow Postel's Law (the Robustness Principle) on the wire: servers evolve through additive, backward-compatible changes (adding optional request fields with sensible defaults, adding new response fields), while clients use tolerant readers that ignore unknown JSON keys instead of crashing on strict schema deserialization.

A change is breaking if you remove or rename a field, change a field's type (for example, `id: 123` to `id: "evt_123"`), tighten a validation constraint on an existing field, or alter fundamental side-effect semantics. When a breaking change is unavoidable, choose one of three routing schemes: URI path major versions (`/v1/`, `/v2/`) for public major rewrites; Header or content-negotiation versioning (`Accept: application/vnd.clinic.v2+json`); or Date-pinned header versioning (`API-Version: 2026-11-20`, popularized by Stripe), where the core URL stays `/v1/logs` forever and a compatibility translation layer transforms request and response shapes based on the account's pinned date. Announce deprecations in every response using the standard Deprecation: true and Sunset: Sat, 01 May 2027 00:00:00 GMT headers (RFC 8594) and monitor per-version traffic down to zero before retiring the old transformer.

4. Pagination contracts: Why `OFFSET` breaks and Composite Keyset Cursors win

Any endpoint that returns a list must enforce a bounded page contract (`limit` default 50, hard maximum 100 to 500) or a single large tenant will eventually trigger a multi-gigabyte response OOM. Naive APIs expose offset pagination (`GET /v1/logs?limit=50&offset=100`), which executes `ORDER BY created_at_ms DESC, id DESC LIMIT 50 OFFSET 100`. Offset pagination suffers from two fatal production flaws:

  • Data drift under concurrent writes: Offset numbers row positions dynamically at query time. As shown in the stepper below, if 3 new rows are inserted at the head of the feed while a user reads Page 1 (`rows 0..49`), those 3 rows push every existing row down by 3 indices. When the client asks for Page 2 (`OFFSET 50`), the last 3 rows of Page 1 now sit at indices `50, 51, 52` and are returned a second time. Conversely, if 3 rows on Page 1 are deleted, 3 unread rows shift up into indices `47, 48, 49` and are permanently skipped when the client requests `OFFSET 50`.
  • Linear `O(offset + limit)` database scan cost: Relational B-trees cannot jump directly to the 40,000th row of an arbitrary `WHERE` filter by offset count; the engine must walk 39,950 index entries, discard them, and return 50.

Keyset (cursor) pagination replaces row-count offsets with a value-based anchor from the last item of the previous page. Because timestamps are rarely unique at scale (in our kata, 5 events arrive within the same millisecond), a cursor on `created_at_ms` alone is buggy: `WHERE created_at_ms < last_ts` will permanently skip any remaining rows that shared `last_ts` across a page boundary. You must use a composite keyset cursor pairing the sort column with a unique tie-breaker column `(created_at_ms, id)` indexed by `CREATE INDEX idx_logs_keyset ON logs(created_at_ms DESC, id DESC)`:

-- Row-value (tuple) comparison seeks directly in the composite B-tree index in O(log N + limit):
SELECT created_at_ms, id, tenant, msg
FROM logs
WHERE (created_at_ms, id) < (:cursor_ts, :cursor_id)
ORDER BY created_at_ms DESC, id DESC
LIMIT :page_size;

-- Equivalent expanded predicate if a SQL dialect lacks row-value comparison:
WHERE created_at_ms < :cursor_ts
   OR (created_at_ms = :cursor_ts AND id < :cursor_id)

Finally, wrap `{"ts": 1700000099900, "id": "evt_49950"}` plus an HMAC-SHA256 signature inside a URL-safe base64 opaque token (`next_cursor`). Keeping the cursor opaque prevents clients from hardcoding your column names or spoofing arbitrary database offsets, allowing you to swap the underlying storage engine or index columns later without breaking the public API contract.

Check: Why does a cursor that encodes only `WHERE created_at_ms < :last_ts` silently drop records in production, and how does the composite tuple `(created_at_ms, id)` fix it?
When multiple events share the same millisecond timestamp (for example, 5 rows at `ts = 1700000099900`) and the `LIMIT 50` boundary cuts right through the middle of that timestamp group, `WHERE created_at_ms < 1700000099900` skips all remaining rows that also have `ts = 1700000099900`. Pairing `created_at_ms` with a unique tie-breaker `id` in `WHERE (created_at_ms, id) < (:ts, :id)` establishes a strict total ordering so the next page resumes at the exact next `id` within the same millisecond.

Kata: Paginated API with HMAC-signed composite cursor tokens & RFC 9457 errors

This standalone SQLite script populates 50,000 audit log rows (with 5 events sharing each millisecond timestamp), proves how 3 concurrent inserts corrupt `OFFSET` pagination while composite keyset cursors `(created_at_ms, id)` return zero duplicates, benchmarks Page 800 (`offset 39,950`) scan cost and latency, and validates tampered cursor tokens into an RFC 9457 Problem Details envelope.

"""
L08 Kata: API design contracts (resources, errors, versioning, pagination)
Compares OFFSET vs HMAC-signed Composite Keyset Cursor pagination on:
1) Correctness under concurrent inserts (duplicate/shifted rows)
2) Deep-page query cost & latency (page 1 vs page 800 on 50,000 rows)
3) Contract validation & RFC 9457 structured error envelope on tampered tokens
"""
import base64, hashlib, hmac, json, sqlite3, sys, time

SECRET = b"l08-contract-hmac-key"
TOTAL_ROWS, PAGE_SIZE, DEEP_PAGE = 50_000, 50, 800
DROP_TIEBREAKER = "--no-tiebreaker" in sys.argv


def setup_db():
    db = sqlite3.connect(":memory:")
    db.execute("CREATE TABLE logs (created_at_ms INT, id TEXT, tenant TEXT, msg TEXT)")
    # 5 rows share each millisecond timestamp to test tie-breaking
    rows = [(1700000000000 + (i // 5) * 10, f"evt_{i:05d}", "t_clinic", f"turn_{i}")
            for i in range(TOTAL_ROWS)]
    db.executemany("INSERT INTO logs VALUES (?, ?, ?, ?)", rows)
    db.execute("CREATE INDEX idx_logs_keyset ON logs(created_at_ms DESC, id DESC)")
    return db


def encode_cursor(ts_ms, row_id):
    payload = json.dumps({"ts": ts_ms, "id": row_id}, separators=(",", ":")).encode()
    sig = hmac.new(SECRET, payload, hashlib.sha256).hexdigest()[:16].encode()
    return base64.urlsafe_b64encode(payload + b"." + sig).decode()


def decode_cursor(token):
    try:
        raw = base64.urlsafe_b64decode(token.encode())
        payload, sig = raw.rsplit(b".", 1)
        expected = hmac.new(SECRET, payload, hashlib.sha256).hexdigest()[:16].encode()
        if not hmac.compare_digest(sig, expected):
            raise ValueError("HMAC signature mismatch")
        return {"ok": True, "data": json.loads(payload)}
    except Exception as exc:
        return {"ok": False, "error": {
            "type": "https://api.example.com/errors/invalid-cursor",
            "title": "Invalid pagination cursor",
            "status": 400, "code": "INVALID_CURSOR",
            "detail": f"Cursor failed verification ({exc}); restart from page 1.",
            "retryable": False, "request_id": "req_01J8X9K2P4"
        }}


def fetch_offset(db, page):
    offset = (page - 1) * PAGE_SIZE
    return db.execute(
        "SELECT created_at_ms, id FROM logs ORDER BY created_at_ms DESC, id DESC LIMIT ? OFFSET ?",
        (PAGE_SIZE, offset)).fetchall()


def fetch_cursor(db, token=None):
    if not token:
        rows = db.execute(
            "SELECT created_at_ms, id FROM logs ORDER BY created_at_ms DESC, id DESC LIMIT ?",
            (PAGE_SIZE,)).fetchall()
    else:
        c = decode_cursor(token)["data"]
        sql = ("SELECT created_at_ms, id FROM logs WHERE created_at_ms < ? "
               "ORDER BY created_at_ms DESC LIMIT ?") if DROP_TIEBREAKER else (
               "SELECT created_at_ms, id FROM logs WHERE (created_at_ms, id) < (?, ?) "
               "ORDER BY created_at_ms DESC, id DESC LIMIT ?")
        params = (c["ts"], PAGE_SIZE) if DROP_TIEBREAKER else (c["ts"], c["id"], PAGE_SIZE)
        rows = db.execute(sql, params).fetchall()
    nxt = encode_cursor(rows[-1][0], rows[-1][1]) if rows else None
    return rows, nxt


if __name__ == "__main__":
    db = setup_db()
    # 1. Correctness under 3 concurrent inserts between Page 1 and Page 2
    off_p1 = fetch_offset(db, page=1)
    cur_p1, cur_tok = fetch_cursor(db, token=None)
    for k in range(3):
        db.execute("INSERT INTO logs VALUES (?, ?, 't_clinic', 'live')",
                   (1700000999999 + k, f"evt_new_{k}"))
    off_p2 = fetch_offset(db, page=2)
    cur_p2, _ = fetch_cursor(db, token=cur_tok)
    off_dups = len({r[1] for r in off_p1} & {r[1] for r in off_p2})
    cur_dups = len({r[1] for r in cur_p1} & {r[1] for r in cur_p2})

    # 2. Deep page latency & index rows scanned (Page 1 vs Page 800, offset=39,950)
    deep_tok = encode_cursor(1700000020100, "evt_10050")
    t0 = time.perf_counter()
    for _ in range(200): fetch_offset(db, page=DEEP_PAGE)
    t_off_ms = (time.perf_counter() - t0) * 1000 / 200
    t0 = time.perf_counter()
    for _ in range(200): fetch_cursor(db, token=deep_tok)
    t_cur_ms = (time.perf_counter() - t0) * 1000 / 200
    off_scanned = (DEEP_PAGE - 1) * PAGE_SIZE + PAGE_SIZE

    # 3. Contract error envelope on tampered cursor
    tampered = cur_tok[:-4] + "AAAA"
    err = decode_cursor(tampered)["error"]

    print("=== L08 KATA: API PAGINATION & ERROR CONTRACTS (50,000 LOG ROWS) ===")
    print(f"1) Concurrent Inserts (3 new rows arrive between Page 1 and Page 2):")
    print(f"   OFFSET (LIMIT 50 OFFSET 50):   {off_dups} duplicate rows leaked into Page 2")
    print(f"   Keyset Cursor (ts, id) < (?,?): {cur_dups} duplicate rows, 0 skipped rows")
    print(f"2) Deep Pagination Cost at Page {DEEP_PAGE} (offset = {(DEEP_PAGE-1)*PAGE_SIZE:,} rows):")
    print(f"   OFFSET index rows scanned:     {off_scanned:6,d} rows | avg latency: {t_off_ms:.3f} ms")
    print(f"   Keyset Cursor rows scanned:    {PAGE_SIZE:6,d} rows | avg latency: {t_cur_ms:.3f} ms ({t_off_ms/t_cur_ms:.1f}x faster)")
    print(f"   Opaque cursor token sample:    {cur_tok[:44]}... ({len(cur_tok)} chars)")
    print(f"3) Tampered Cursor Validation (RFC 9457 Structured Error Envelope):")
    print(f"   HTTP {err['status']} | code={err['code']} | retryable={err['retryable']} | req_id={err['request_id']}")

What to notice

  1. When 3 new log events arrive between Page 1 and Page 2, `LIMIT 50 OFFSET 50` shifts the window and leaks 3 duplicate rows from Page 1 onto Page 2, whereas `WHERE (created_at_ms, id) < (?, ?)` returns 0 duplicate rows.
  2. At Page 800 (`offset = 39,950`), `OFFSET` must scan 40,000 index entries (`0.394 ms`), whereas the keyset cursor seeks directly in the `(created_at_ms DESC, id DESC)` B-tree and reads only 50 rows (`0.051 ms`, 7.7x faster).
  3. The cursor token (`72 chars`) encodes both `ts` and the tie-breaker `id` plus a 16-hex-character HMAC-SHA256 signature (`base64url(payload.sig)`), keeping pagination state stateless on the server while tamper-proof on the client.
  4. Modifying the last 4 characters of the cursor token triggers `hmac.compare_digest` failure and returns an RFC 9457 error envelope with `status: 400`, `code: "INVALID_CURSOR"`, `retryable: false`, and `request_id: "req_01J8X9K2P4"`.
Break it
  1. Non-unique cursor column (missing tie-breaker `id`). Run python kata.py --no-tiebreaker, which switches the query from WHERE (created_at_ms, id) < (?, ?) to WHERE created_at_ms < ?. Because 5 rows share each millisecond timestamp and `PAGE_SIZE = 50` is divisible by 5 (or try setting `PAGE_SIZE = 52` so every page cuts inside a 5-row timestamp bucket), predict how many rows are silently skipped across pages when `created_at_ms < ?` skips the rest of the current millisecond bucket.
  2. Unsigned raw ID cursor leakage (IDOR / scraping). Replace `encode_cursor` with plain `str(row_id)` without HMAC signing. Predict what an attacker can do by guessing sequential `evt_00001..evt_50000` or crafting a cursor with a forged timestamp, and why signing (or encrypting) plus scoping queries by `WHERE tenant = :auth_tenant` is mandatory.
  3. HTTP 200 with embedded error (`{"ok": false}`). Change `status: 400` in `decode_cursor` to `status: 200` and `retryable: true`. Predict how an API gateway cache or client retry interceptor behaves when a permanently corrupted cursor is marked HTTP 200 or `retryable: true`.

Stretch. Add bidirectional pagination (`prev_cursor` and `next_cursor`) by encoding a `dir: "next" | "prev"` field inside the signed JSON payload, flipping the SQL predicate to `WHERE (created_at_ms, id) > (?, ?) ORDER BY created_at_ms ASC, id ASC LIMIT ?`, and reversing the 50 returned rows in Python so the client still receives items in descending order.

Their script uses `?page=1..4000&limit=50`, complains that 1,200 transcripts are duplicated or missing, and triggers database read-replica CPU alerts at page 2,500. Walk through your 4-step engineering fix.
  1. Diagnose both root causes: At 40 inserts/sec, every 1-second pause between `OFFSET` requests shifts all row indices by 40, guaranteeing duplicate rows (and skipped rows if any transcripts are purged). By page 2,500 (`OFFSET 124950`), each query scans `125,000` index rows (`O(offset + limit)`), burning replica CPU.
  2. Create a composite keyset index and cursor contract: Add index `(tenant_id, created_at_ms DESC, call_id DESC)` and accept `?limit=50&cursor=<opaque_token>` executing `WHERE tenant_id = ? AND (created_at_ms, call_id) < (?, ?) ORDER BY created_at_ms DESC, call_id DESC LIMIT 50`.
  3. Sign the opaque cursor and return a structured envelope: Base64url-encode `{"ts": last_ts, "id": last_call_id}` with an HMAC-SHA256 signature as `next_cursor`, and return an RFC 9457 `400 INVALID_CURSOR` (`retryable: false`) if tampered or expired.
  4. Protect the database and evolve without breaking old callers: Keep `?page=` working temporarily for shallow UI pages (`offset <= 1,000`), emit a `Deprecation` + `Sunset` header and an RFC 9457 `400 OFFSET_TOO_DEEP` error past offset 1,000 pointing callers to `next_cursor`.

Interview

Say this aloud against the clock. Three levels, about 90 seconds.

1 Outcome 20 sA production API contract guarantees that clients and servers can fail, retry, page through millions of records, and deploy independently without corrupting data. We lock down four pillars: resource nouns with idempotent writes, structured RFC 9457 error envelopes, additive versioning, and opaque composite keyset cursors.
2 Mechanism 45 sFirst, `GET`, `PUT`, and `DELETE` are idempotent by HTTP spec, while state-creating `POST` routes require an `Idempotency-Key` header stored with a 24-hour TTL and SHA-256 payload hash so network retries replay the saved response instead of duplicating side effects. Second, for collections, we avoid `OFFSET` pagination and use a composite keyset cursor `WHERE (created_at_ms, id) < (?, ?)` backed by a descending composite B-tree index, encoding the last tuple and an HMAC signature into an opaque base64 token. Third, failures return RFC 9457 JSON with HTTP status, machine `code`, `request_id`, and a `retryable` boolean.
3 Internals and limits 25 s`OFFSET` scans `O(offset + limit)` rows and leaks duplicates under concurrent inserts; in our 50,000-row benchmark, Page 800 scanned 40,000 rows in 0.394 ms versus 50 rows in 0.051 ms with keyset cursors. Keyset cursors trade away random page jumps, require a unique tie-breaker `id` so identical timestamps never drop rows, and use date-pinned headers with `Sunset` warnings when breaking schema changes are unavoidable.

Traps

Each one sounds right. Say what is wrong with it before you open it.

"Cursor pagination on `WHERE created_at < :last_created_at LIMIT 50` is completely safe and never skips rows."
Wrong whenever two rows share the same timestamp. If 5 events occur in the same millisecond and the `LIMIT 50` cutoff lands after the 2nd event, the next page requests `WHERE created_at < :ts`, permanently skipping the remaining 3 events at `:ts`. You must use a composite cursor with a unique tie-breaker: `WHERE (created_at, id) < (:ts, :id)`.
"Adding a database index on `created_at DESC` makes `LIMIT 50 OFFSET 40000` just as fast as cursor pagination."
Wrong. Even with an index, a B-tree does not store positional row offsets for arbitrary queries. The database still has to walk 40,000 index entries one by one (`O(offset + limit)`) to count past the offset, whereas a keyset cursor performs an `O(log N)` B-tree seek directly to the `(ts, id)` tuple and reads only 50 entries (`O(limit)`).
"Every time we add a new field to a JSON response, we should bump `/v1/` to `/v2/` so we adhere to strict versioning."
Wrong. Bumping major URI versions for additive fields fragments your ecosystem and forces every client to migrate unnecessarily. Under Postel's Law, adding optional request fields or new response fields is backward-compatible as long as clients use tolerant readers that ignore unknown keys. Reserve version bumps (or date-pinned transformers) for true breaking changes like removing fields, changing types, or altering semantics.
"Returning HTTP 200 OK with `{\"success\": false, \"error\": \"Rate limit exceeded\"}` is cleaner for frontend developers because `fetch()` will not throw an HTTP error."
Wrong. Returning `200 OK` on errors breaks HTTP semantics across your entire infrastructure: CDNs and browser caches may cache the error response as valid data, API gateways and Prometheus metrics report 100% success rates during an outage, and SDK retry/circuit-breaker middleware cannot inspect `429`/`503` status codes or `Retry-After` headers.

Question bank

Answer aloud, then open. Grade yourself honestly.

Why are `PUT` and `DELETE` naturally idempotent while `POST` is not, and when can `PATCH` fail to be idempotent?
`PUT` replaces the target resource with a known state and `DELETE` ensures the resource at that URI no longer exists; repeating either leaves the resource in the same final state. `POST` creates a new subordinate resource or triggers an action on every call. `PATCH` is idempotent if it sets fields to literal values (`{"status": "closed"}`), but non-idempotent if it applies relative operations (`{"op": "increment", "field": "tokens", "by": 100}`).
Follow-upIf you call `DELETE /v1/jobs/123` twice and the second call returns `404 Not Found` instead of `204 No Content`, did that violate idempotency? Answer: No. Idempotency in RFC 9110 is defined by the server state side effect (job 123 remains deleted), not by returning an identical HTTP status code on repeat calls, though returning 200/204 with a deleted marker is often preferred by SDKs.
What exact columns belong in an `idempotency_keys` table, and what should the server return if a client reuses the same `Idempotency-Key` with a different request body?
Store `(tenant_id, idempotency_key, method, path, request_sha256, status_code, response_body, locked_until, created_at)`. If the same key arrives with a different `request_sha256`, immediately return `422 Unprocessable Content` (or `409 Conflict`) with `code: "IDEMPOTENCY_KEY_PAYLOAD_MISMATCH"` so a client bug never silently gets a cached response for a different operation.
Follow-upWhat happens if the first request crashes halfway through before committing? Answer: Wrap the domain write and the idempotency status update in the same local DB transaction (or release the lock on rollbacks before external side effects) so a retry can safely execute.
Write the SQL predicate for descending keyset pagination on `(created_at_ms, id)` both as a row-value tuple comparison and as an expanded `OR` clause.
Tuple form: `WHERE (created_at_ms, id) < (:ts, :id) ORDER BY created_at_ms DESC, id DESC LIMIT :n`. Expanded form: `WHERE created_at_ms < :ts OR (created_at_ms = :ts AND id < :id) ORDER BY created_at_ms DESC, id DESC LIMIT :n`.
Follow-upWhat happens to index usage if the query sorts by `created_at_ms DESC, id ASC` while the index is `(created_at_ms DESC, id DESC)`? Answer: The B-tree cannot scan in index order without a sort step; the index direction of every column must match the `ORDER BY` direction (or both be strictly inverted).
Why should a pagination cursor be encoded as an opaque, HMAC-signed token rather than passing `?after_ts=1700000099900&after_id=evt_49950` in the query string?
Exposing raw column parameters couples clients to your internal schema and sort implementation. An opaque HMAC-signed base64url token stops clients from constructing ad-hoc queries or tampering with internal IDs, lets you detect corrupted cursors immediately (`400 INVALID_CURSOR`), and lets you migrate from SQLite/Postgres to Elasticsearch or change tie-breaker columns without changing the public parameter contract.
How does an API server determine `has_more: true | false` in a paginated response without running an expensive `SELECT COUNT(*)` query?
Request `LIMIT (page_size + 1)` from the database (for example, `LIMIT 51` when the client asks for `limit=50`). If 51 rows come back, `has_more` is `true`, you trim the 51st row, and build `next_cursor` from the 50th row. If 50 or fewer rows come back, `has_more` is `false` and `next_cursor` is `null`.
Follow-upWhy should you avoid returning `total_count` on every paginated call? Answer: `COUNT(*)` on large filtered tables requires a full index or table scan (`O(N)`), destroying the `O(limit)` benefit of keyset pagination.
What fields does RFC 9457 (Problem Details for HTTP APIs) standardize, and what three operational fields should you add for production SDKs?
RFC 9457 standardizes `type` (URI identifying the error class), `title` (human summary), `status` (HTTP status integer), `detail` (occurrence explanation), and `instance` (request URI). In production, add a stable machine-readable `code` enum (such as `"INVALID_CURSOR"`), `retryable` (`true`/`false`), and `request_id` (trace correlation ID), plus optional `fields` for `422` validation errors.
Which changes to a JSON endpoint are backward-compatible (additive), and which changes are breaking?
Backward-compatible: adding a new endpoint, adding an optional request field with a default, or adding a new field to a response object (assuming tolerant readers). Breaking: removing or renaming a field, changing a field's type or nullability, making an optional request field required, tightening input bounds, or changing error code/status semantics.
Compare URI path versioning (`/v1`, `/v2`) with Stripe-style date-pinned header versioning (`API-Version: 2026-11-20`).
URI versioning is explicit and easy to route at an API gateway, but forces coarse "big-bang" migrations where `/v2` duplicates entire controllers. Date-pinned header versioning keeps URLs permanent, pins each tenant's default version in their account settings, and runs modular request/response compatibility transformers at the edge whenever a caller's pinned date predates a breaking change.
Follow-upWhat HTTP headers notify automated clients that their pinned version is scheduled for removal? Answer: `Deprecation: true` (or `@timestamp`) and `Sunset: <HTTP-date>` (RFC 8594).
How do you design an API contract for a slow 45-second LLM agent run so it does not time out mobile gateways or load balancers?
Do not hold a synchronous blocking `POST` open for 45 seconds without bytes flowing. Either return `202 Accepted` immediately with a job resource (`Location: /v1/runs/run_123`, `status: "queued"`) that the client polls or receives via webhook, or stream incremental Server-Sent Events (`Content-Type: text/event-stream`) with periodic heartbeat comments and a final structured event.

L01: When clarifying requirements at the start of a system design interview, what are the four buckets you lock down before drawing boxes?
Core functional scope (top 3 user flows and explicit non-goals), workload scale and shape (DAU, read:write ratio, payload/token sizes), non-functional targets (p95/p99 latency SLO, availability, consistency vs durability), and logical domain entities with their external API signatures.
L02: If a payment or clinical record service calls three downstream microservices synchronously, each with a 99.9% (`three nines`) availability SLA, what is the combined serial availability and how much downtime per year does that allow?
Serial availability multiplies (`0.999^3 ~ 99.7%`), tripling the failure budget from `0.1%` (`8.76 hours/year`) to `0.3%` (`~26.3 hours/year`).
L04: Why does a single-threaded `asyncio` event loop handle 1,000 concurrent 50 ms I/O waits `14.2x` faster than a 50-thread pool, and what two limits still break the event loop?
The event loop parks all 1,000 non-blocking sockets in the kernel via `epoll`/`kqueue` (`~2 KB` state per coroutine) and overlaps every wait in one wave (`72.6 ms`), whereas a 50-thread pool drains 20 sequential waves (`1,028.2 ms`). It breaks if a single handler runs blocking CPU/sync I/O (freezing all clients) or if open sockets hit OS caps like `ulimit -n` (`1,024` default FDs).

All subtopics on this page

  • Resource modeling & HTTP idempotency: Model nouns (`/v1/tenants/{id}/logs`); `GET` is safe + idempotent, `PUT` and `DELETE` are idempotent, `POST` is non-idempotent and requires an `Idempotency-Key` header stored for 24h with a SHA-256 request body hash.
  • Structured error contracts (RFC 9457): Return `application/problem+json` with `type`, `title`, `status`, `detail`, plus machine `code`, `retryable` (`false` for `400/422`, `true` for `429/503` with `Retry-After`), and `request_id`.

  • Composite keyset cursor pagination: Replace `LIMIT k OFFSET n` (`O(offset + limit)`, `40,000` rows / `0.394 ms` at Page 800, leaks `3` duplicates on `3` inserts) with `WHERE (created_at_ms, id) < (?, ?)` (`O(limit)`, `50` rows / `0.051 ms`, `0` duplicates) encoded as an opaque HMAC-signed base64url token.
Important things to remember
  • Memory hook (R-E-V-P): Resources + `Idempotency-Key` -> Errors (RFC 9457 + `retryable`) -> Versioning (additive + `Sunset`) -> Pagination (opaque HMAC composite keyset cursor).
  • Composite keyset SQL & index: `WHERE (created_at_ms, id) < (:ts, :id) ORDER BY created_at_ms DESC, id DESC LIMIT :n` backed by `CREATE INDEX ... ON tbl(created_at_ms DESC, id DESC)`. Without the unique tie-breaker `id`, identical timestamps silently drop rows across page boundaries.
  • The `LIMIT N+1` trick: Fetch `page_size + 1` rows (51 for a page of 50) to compute `has_more` in `O(limit)` without running an `O(N)` `SELECT COUNT(*)`.
  • Kata numbers to quote cold: On 50,000 rows, 3 concurrent inserts leak 3 duplicates on `OFFSET` vs 0 on Keyset; Page 800 (`offset 39,950`) scans 40,000 rows (`0.394 ms`) with `OFFSET` vs 50 rows (`0.051 ms`, `7.7x` faster) with Keyset.
