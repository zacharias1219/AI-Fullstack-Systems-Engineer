Cost-aware architecture and when not to add infrastructure

How to compute cost per 1,000 successful requests across traffic tiers, find the exact break-even RPS where self-hosted GPUs beat managed APIs, and avoid the 99.9% idle-waste trap of resume-driven infrastructure.

The core idea

Architectural fitness is never absolute; it is a function of traffic volume. Every design decomposes into a fixed monthly baseline floor F (control planes, reserved GPUs, dedicated database nodes, NAT gateways, on-call maintenance) and a variable per-request slope v (managed LLM token charges, serverless duration, egress bytes). The metric that exposes over-engineering immediately is cost per 1,000 successful requests:

Cost_per_1k_succ = (F + N * (v / 1000)) / ((N * p_succ) / 1000) = (1000 * F) / (N * p_succ) + v / p_succ

When request volume N is small (10k to 500k requests/month, or 0.004 to 0.2 RPS), the fixed term (1000 * F) / N dominates completely: provisioning a Multi-AZ Kubernetes cluster, a dedicated vector database, and self-hosted GPUs results in 96% to 99.9% idle dollar waste. When N is large (10M to 50M+ requests/month, or 4 to 20+ sustained RPS), fixed cost amortizes toward zero and the variable term v dominates, justifying dedicated GPU capacity to slash per-request token costs from $1.05/1k down to $0.14/1k.

Memory hook

F-V-B-O ("Fixed, Variable, Break-even, Ops tax"): Fixed floor F dominates below 1 RPS (99.9% idle GPU waste at 50k/mo) -> Variable slope v dominates above 10 RPS ($1.05 vs $0.14 per 1k) -> Break-even volume N_be = (F_C - F_A) / (v_A - v_C) = 7.96M req/mo (3.07 RPS) -> Operational tax (SWE maintenance hours) pushes real break-even even higher.

How it works

1. The unit-economics equation and break-even crossover

Why do we measure cost per 1,000 successful requests instead of total monthly cloud bill? Because a system that fails 20% of requests or drops traffic under load looks artificially cheap on a raw monthly invoice while destroying unit margin. Let F be the fixed monthly infrastructure bill (paid at N = 0 requests), v be the variable cost per 1,000 attempted requests, and p_succ be the end-to-end success rate (0.992 in our kata). Total monthly cost is C(N) = F + (N / 1000) * v, and unit cost per 1,000 successful requests is:

UnitCost(N) = (F + (N / 1000) * v) / ((N * p_succ) / 1000)   [USD per 1k successful requests]

To decide when to migrate from a low-fixed, high-variable architecture (Arch A: F_A, v_A) to a high-fixed, low-variable self-hosted architecture (Arch C: F_C, v_C), set C_A(N) = C_C(N) and solve for the break-even request volume N_be:

N_be = ((F_C - F_A) / (v_A - v_C)) * 1000   requests/month,   RPS_be = N_be / 2,592,000

Plugging in our RAG benchmark numbers (F_C = $7,400 for 2x H100 + Multi-AZ EKS/Qdrant/Redis, F_A = $155 for a redundant VM + Postgres, v_A = $1.05/1k with 70% prompt cache hits, and v_C = $0.14/1k marginal power/egress) yields N_be = (7245 / 0.91) * 1000 = 7,961,538 req/mo, or 3.07 sustained RPS every second of the month.

2. When NOT to add infrastructure: The "Boring Stack" replacements

Every new infrastructure box on a system design diagram adds three costs: (1) its 24/7 fixed cloud floor F, (2) cross-AZ network transfer and serialization latency, and (3) a new failure mode your team must monitor, upgrade, back up, and debug at 3 AM. In interviews and production reviews, apply these four thresholds before adding a component:

  • Do not add a dedicated Vector DB (Pinecone/Qdrant/Milvus cluster) below ~5M-10M vectors: Postgres with pgvector (HNSW index in shared RAM) handles 1M to 5M 768-dim vectors at < 15 ms p95 query latency inside your existing ACID database with zero dual-write sync bugs and zero extra fixed bill.
  • Do not add Kafka or RabbitMQ below ~1,000 jobs/sec: A Postgres table polled with SELECT ... FOR UPDATE SKIP LOCKED (or an existing Redis instance using Redis Streams / BullMQ) reliably processes ratusan to thousands of background jobs per second without a 3-broker ZooKeeper/KRaft cluster costing $300+/mo.
  • Do not self-host LLM GPUs (vLLM / TGI on A100/H100) for bursty or low-RPS workloads: Because human traffic peaks during business hours and drops 80% overnight, a reserved 24/7 GPU node sits idle during troughs. Until your trough or sustained average exceeds ~3 to 5 RPS (or strict HIPAA/air-gapped data residency forbids external APIs), managed APIs with prompt caching and batch APIs (50% discount) are dramatically cheaper.
  • Do not add Multi-Cluster Kubernetes + Service Mesh for a 5-engineer team: An EKS control plane ($73/mo), 3 Multi-AZ NAT Gateways (~$100/mo + $0.045/GB), and DaemonSet overhead (Datadog/Istio eating 15-25% of every node) burn $400-$800/mo before running a single pod, whereas 2 stateless containers on ECS Fargate, Render, or a load-balanced VM pair cost $45-$90/mo.
Check: A startup founder asks you to provision a self-hosted 2x H100 vLLM cluster ($6,200/mo) to avoid paying OpenAI/Anthropic $400/mo in token bills. Using unit economics, how do you explain why this loses money?
At $400/mo in managed API spend (roughly 380,000 requests/month, or 0.15 avg RPS), the workload utilizes less than 5% of a 2x H100 cluster's capacity. Switching to self-hosted GPUs replaces a $400/mo variable bill with a $6,200/mo fixed floor (a 15.5x cost increase, raising unit cost from ~$1.05/1k to ~$16.30/1k) plus ~20-40 hours/month of engineering maintenance that costs another $2,000-$4,000 in SWE time.

Kata: Unit cost per 1,000 successful requests across 3 traffic tiers

We model the exact monthly invoice, fixed-cost percentage, and cost per 1,000 successful requests across 50k, 2M, and 50M monthly requests for three architectures, and compute the exact break-even request volume and sustained RPS.

kata.py

# Unit-economics comparison across 3 architectures and 3 traffic tiers
# Workload: RAG assistant (1,500 input tokens [70% cached], 300 output tokens, 99.2% success rate)

SUCCESS_RATE = 0.992
SECONDS_PER_MONTH = 30 * 86400  # 2,592,000s

def cost_lean_monolith(req_mo):
    """Arch A: Single VM + Postgres/pgvector ($45/mo) + Managed LLM API with prompt caching."""
    # $1.05 per 1k requests (70% cached input + output tokens + telemetry)
    fixed = 45.0
    # Add 2nd stateless app replica + read replica only above 5M req/mo
    if req_mo > 5_000_000:
        fixed += 110.0
    variable = (req_mo / 1000.0) * 1.05
    return fixed, variable

def cost_serverless_managed(req_mo):
    """Arch B: Serverless functions + API Gateway + Managed Vector DB ($95 floor) + Managed LLM API."""
    # Higher per-request markup ($1.38 per 1k requests: API GW + function duration + vector RU + LLM)
    fixed = 95.0
    variable = (req_mo / 1000.0) * 1.38
    return fixed, variable

def cost_k8s_self_hosted_gpu(req_mo):
    """Arch C: Multi-AZ EKS + NAT Gateways + Dedicated Qdrant/Redis + 2x H100 GPUs ($7,400/mo fixed)."""
    # Self-hosted inference marginal power/egress/storage cost is only $0.14 per 1k requests
    # 2x H100 cluster handles up to 18M req/mo before needing a 3rd GPU ($3,100/mo step)
    extra_gpus = max(0, (req_mo - 1) // 18_000_000)
    fixed = 7400.0 + extra_gpus * 3100.0
    variable = (req_mo / 1000.0) * 0.14
    return fixed, variable

archs = [
    ("A: Lean Monolith + Managed API", cost_lean_monolith),
    ("B: Serverless + Managed Vector", cost_serverless_managed),
    ("C: Multi-AZ K8s + 2x H100 GPU", cost_k8s_self_hosted_gpu),
]

for req_mo in [50_000, 2_000_000, 50_000_000]:
    avg_rps = req_mo / SECONDS_PER_MONTH
    succ_k = (req_mo * SUCCESS_RATE) / 1000.0
    print(f"=== Traffic Tier: {req_mo:>10,d} req/mo ({avg_rps:6.2f} avg RPS) ===")
    print(f"{'Architecture':<32} | {'Fixed $':>8} | {'Total $/mo':>10} | {'Fixed %':>7} | {'$/1k Succ Req':>13}")
    print("-" * 82)
    for name, fn in archs:
        fix, var = fn(req_mo)
        tot = fix + var
        c_per_1k = tot / succ_k
        print(f"{name:<32} | ${fix:7.0f} | ${tot:9.0f} | {100*fix/tot:6.1f}% | ${c_per_1k:12.3f}")
    print()

# Exact break-even where Arch C (single 2x H100 pod, $7,400 fixed + $0.14/1k) beats Arch A ($155 fixed + $1.05/1k)
be_req = ((7400.0 - 155.0) / (1.05 - 0.14)) * 1000.0
print(f"Break-even volume (Arch C vs Arch A): {be_req:,.0f} req/mo ({be_req/SECONDS_PER_MONTH:.2f} sustained RPS)")
print(f"At 50k req/mo, Arch C costs ${(7407.0/52.5):.1f}x more than Arch A ($149.33 vs $1.97 per 1k successful reqs).")

What to notice

  1. The 99.9% fixed-waste trap at 50k req/mo (0.02 RPS): At startup volume, Arch C spends $7,400 on fixed capacity and only $7 on marginal request execution (99.9% fixed). Every 1,000 successful requests cost $149.335 versus $1.966 on Arch A.
  2. Even at 2,000,000 requests/month (0.77 RPS), managed APIs win by 3.6x: Two million requests/month sounds high, but spread across 2.592 million seconds in a month it is only 0.77 RPS. Arch A costs $2,145/mo ($1.081/1k) vs Arch C's $7,680/mo ($3.871/1k).
  3. Break-even requires 7.96M req/mo (3.07 sustained RPS): Only after traffic crosses 7,961,538 req/mo does Arch C's $0.91/1k variable savings pay back its $7,245/mo fixed premium.
  4. At 50M req/mo (19.29 RPS), self-hosting saves $32,055/mo: Even after stepping from 2 to 4 H100 GPUs ($13,600 fixed), Arch C delivers $0.415/1k ($20,600/mo) versus Arch A's $1.062/1k ($52,655/mo).

"Self-hosting an open-source LLM on our own GPU instance is always cheaper than paying per-token to a commercial LLM API."
Wrong below ~3 sustained RPS. Self-hosted GPUs convert a variable per-token bill into a 24/7 fixed monthly lease ($3,000-$7,000+/mo). At 50,000 requests/month (0.02 RPS), our 2x H100 cluster sits 99.9% idle and costs $149.34 per 1k requests versus $1.97 on a managed API with prompt caching.

1. Write the formula for cost per 1,000 successful requests and explain why dividing by successful requests rather than total requests matters in AI systems.
Cost_per_1k_succ = (Fixed_Monthly + (N / 1000) * Variable_per_1k) / ((N * Success_Rate) / 1000). 2. Derive the break-even request volume between a managed LLM API ($1.05/1k variable, $155/mo fixed) and a self-hosted 2x H100 cluster ($0.14/1k variable, $7,400/mo fixed), and convert it to sustained RPS.

3. Name three "boring Postgres" capabilities that let you avoid adding dedicated Redis, Kafka, and Pinecone clusters in an early-to-mid-stage AI product.
(1) Vector search: pgvector with HNSW indexes handles 1M-5M embeddings in-database with full SQL metadata filtering. (2) Job queues: A jobs table queried with SELECT ... FOR UPDATE SKIP LOCKED gives ACID transactional background queues up to ~1,000 jobs/sec without Kafka. (3) JSON document & cache tables: JSONB with GIN indexes and unlogged tables cover document and session lookup workloads without a separate NoSQL cluster.
Follow-upWhat is the single biggest reliability win of keeping vectors, relational metadata, and job state in one Postgres database early on? Answer: Atomic single-node ACID transactions - no dual-write drift where a document exists in Postgres but fails to index in Pinecone or publish to Kafka.
4. What are the three largest hidden networking and observability cost traps in AWS Kubernetes deployments?
(1) Managed NAT Gateways: $0.045/hr per AZ plus $0.045/GB processed for S3, ECR, or external LLM API traffic (solved with free S3/DynamoDB VPC Gateway Endpoints). (2) Cross-AZ data transfer: $0.02/GB round-trip whenever pods in AZ-a talk to pods or caches in AZ-b. (3) Observability & DaemonSet tax: Logging verbose payloads and running monitoring/mesh agents that consume 20% of cluster CPU and 30%+ of the cloud invoice.
5. How do you architect an LLM inference tier when traffic averages 5 RPS during an 8-hour workday peak but drops to 0.4 RPS overnight and on weekends?
Use a hybrid base-plus-burst architecture: provision a smaller self-hosted GPU footprint sized for the high-utilization base load (e.g., 1x GPU saturated 12+ hours/day where unit cost is ~$0.42/1k) and dynamically overflow excess peak concurrency or overnight troughs (signing down the GPU node if auto-scalable) to a managed pay-per-token LLM API so you never pay for idle 24/7 peak-provisioned GPUs.
Follow-upWhat software pattern in your gateway makes routing between self-hosted vLLM and a managed fallback API seamless? Answer: An OpenAI-compatible router (e.g., LiteLLM or custom Envoy/Python gateway) that monitors local vLLM in-flight queue depth and spills requests over a concurrency threshold to the managed API.
6. How do you quantify the "operational complexity tax" when comparing a managed service against self-hosting open-source infrastructure on VMs?
Add engineering maintenance hours times fully loaded SWE hourly cost (typically $100-$150/hr) to the self-hosted fixed monthly floor F. If self-hosting Kafka or vLLM requires just 10 hours/week (40 hours/month) of upgrades, security patching, capacity tuning, and on-call incident response, that adds $4,000-$6,000/mo to F, shifting the financial break-even volume up by millions of requests per month.

Mixed review

Three questions from earlier topics. Nobody tells you the topic in an interview.

L05: Why does placing 4 workers with in-memory session dictionaries behind a round-robin load balancer cause 100% of follow-up chat turns to fail, and how does Gunther's USL model the scalability ceiling once you externalize state to Redis?
Under strict round-robin across 4 workers, Turn 1 lands on Worker 0 while Turns 2, 3, and 4 land on Workers 1, 2, and 3, none of which hold Worker 0's local RAM dict. Once stateless with Redis, capacity follows C(N) = N / (1 + alpha(N-1) + beta N(N-1)), peaking at N_peak = sqrt((1 - alpha) / beta) before retrograde scaling.
A11: Why does centered finite difference achieve O(eps^2) truncation error while forward difference achieves O(eps), and why does eps = 1e-14 fail in FP64?
Subtracting f(x + eps) - f(x - eps) cancels the even quadratic (eps^2 / 2) f''(x) Taylor terms, leaving O(eps^2) cubic error. At eps = 1e-14, the two evaluations share 14 leading decimal digits, so subtraction causes catastrophic cancellation with rounding error O(u / eps) ~ 3.35e-2.
L04: What are the three queuing-theory variables in Little's Law (L = lambda * W), and what happens to p99 latency as server utilization rho approaches 100%?
L is average concurrent requests in the system, lambda is average arrival/throughput rate (RPS), and W is average time spent in the system (latency). By Kingman's equation, queueing delay scales proportional to rho / (1 - rho), shooting asymptotically to infinity as utilization rho -> 1.
