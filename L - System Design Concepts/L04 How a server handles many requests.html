How a server handles many requests

How one server multiplexes thousands of concurrent I/O-bound connections with thread pools, thread-per-request, or an event loop, and where OS connection limits stop it. Horizontal scaling lives in L05, concurrency primitives in M03, and OS internals in R25.

Before you read

Guess first. A wrong guess now makes the right answer stick later.

1,000 clients hit your API at once, and each request waits 50 ms on an upstream LLM. Roughly how long does a 50-thread pool take versus a single-threaded asyncio event loop?
The 50-thread pool runs 20 waves of 50 requests, taking 1,028.2 ms in our kata. The single-threaded event loop overlaps all 1,000 waits and finishes in 72.6 ms (14.2x faster).
If you spawn 1,000 OS threads (one per request) instead of using a 50-thread pool, why does it still finish slower than 1 event-loop thread even though all 1,000 threads run in parallel?
Creating 1,000 OS threads, allocating their stacks, and context-switching them adds 123.4 ms of overhead on top of the 50 ms wait (173.4 ms total vs 72.6 ms for asyncio).
Your single-threaded FastAPI server handles 10,000 idle streaming clients with 5% CPU, then suddenly rejects new connections with "Too many open files". What limit did you hit?
The per-process file descriptor limit (ulimit -n, often 1,024 by default on Linux). Every open TCP socket consumes one file descriptor even when the event loop is idle.

The core idea

A modern AI backend spends most of its wall-clock time waiting: waiting on LLM token streams, vector database queries, or downstream webhooks. The server's concurrency model decides what happens to a CPU core and RAM while a request sits idle waiting for network bytes.

A thread-per-request server parks an entire OS thread (and its multi-megabyte stack) on every waiting socket. An event-loop server puts every socket in non-blocking mode, registers them with the OS kernel (epoll on Linux, kqueue on macOS, IOCP on Windows), and uses one thread to wake only when a socket actually has bytes ready.

Memory hook

T-E-C rebuilds the three layers: Threads burn stacks (1-8 MB each) or queue when bounded; Event loops park sockets in epoll (~2 KB each) until a blocking call freezes the single thread; Caps stop both at file descriptors, listen backlog, and ephemeral ports.

How it works

1. Thread-per-request and bounded thread pools

In a thread-per-request server, the OS kernel assigns each connection a kernel thread with its own call stack (8 MB virtual default on Linux, 1 MB on Windows). When a thread calls a blocking read(), the kernel puts it to sleep and context-switches another runnable thread onto the CPU, flushing CPU cache lines. To prevent out-of-memory crashes under traffic spikes, servers like Gunicorn sync or Tomcat cap concurrency with a fixed pool of W worker threads. Once active requests exceed W, extra clients wait in a queue, so total drain time for N slow clients scales as:

drain_time = ceil(N / W) * T_io   (e.g., ceil(1000 / 50) * 50 ms = 1000 ms)

2. Event loops and non-blocking I/O

An event loop (Node.js, Nginx, Python asyncio/uvicorn) flips sockets to non-blocking mode and hands the full list of socket file descriptors to the kernel via epoll_wait() (Linux) or kqueue() (macOS). Instead of scanning all N sockets every tick (O(N) like legacy select()), epoll returns only the ready sockets in O(1) per event. Each in-flight request lives as a tiny heap object (a coroutine frame, roughly 1.6 to 4 KB) rather than a megabyte stack. The catch is cooperative multitasking: if one handler runs CPU work or a synchronous library call for 50 ms without yielding, all 999 other clients freeze for 50 ms.

Check: Why does adding more threads to a bounded pool eventually hurt throughput instead of helping?
Past a few hundred to a few thousand threads, stack memory exhausts RAM and the OS scheduler spends more CPU time context-switching and thrashing L1/L2 caches than running application code.

3. Connection limits and OS caps

Replacing threads with an event loop solves the C10K concurrency wall, but every active TCP connection still consumes kernel resources. First, every socket is a file descriptor (FD); Linux defaults to a soft limit of 1,024 FDs per process (ulimit -n), throwing EMFILE once exceeded. Second, incoming TCP handshakes sit in the kernel accept queue capped by somaxconn (often 128 to 4,096); if the app accepts too slowly, new SYNs drop. Third, outbound proxy calls to one upstream IP:port share the ephemeral port range (roughly 28,000 ports by default on Linux), which exhausts under high churn unless you pool keep-alive connections.

Check: An event loop server opens a fresh TCP connection to an LLM gateway on every request at 5,000 RPS. What OS resource runs out first?
Outbound ephemeral ports (roughly 28,000 on Linux). Closed sockets linger in TIME_WAIT for ~60 seconds, so 5,000 new connections per second exhausts the port table in under 6 seconds unless you reuse keep-alive pools.

Kata: 1,000 slow clients across three concurrency models

Benchmarks 1,000 concurrent clients each waiting 50 ms on simulated upstream I/O across a 50-thread pool, 1,000 OS threads, and a single-threaded asyncio event loop.

Run

python kata.py

kata.py

import asyncio, concurrent.futures, sys, threading, time, tracemalloc

CLIENTS = 1000
WAIT_S = 0.05        # 50 ms simulated upstream I/O (e.g. LLM token or DB wait)
POOL_WORKERS = 50    # typical WSGI/thread-pool worker count
BLOCK_CALLS = 0      # Break-it 1: set to 10 (or pass --block) to stall the loop
MAX_FDS = 1024       # Break-it 2: set to 256 (or pass --fd-cap) to hit EMFILE


def slow_io():
    time.sleep(WAIT_S)


def bench_thread_pool():
    tracemalloc.start()
    t0 = time.perf_counter()
    with concurrent.futures.ThreadPoolExecutor(max_workers=POOL_WORKERS) as ex:
        list(ex.map(lambda _: slow_io(), range(CLIENTS)))
    dt = time.perf_counter() - t0
    _, peak = tracemalloc.get_traced_memory()
    tracemalloc.stop()
    return dt, peak / 1024


def bench_thread_per_req():
    tracemalloc.start()
    t0 = time.perf_counter()
    threads = [threading.Thread(target=slow_io) for _ in range(CLIENTS)]
    for t in threads:
        t.start()
    for t in threads:
        t.join()
    dt = time.perf_counter() - t0
    _, peak = tracemalloc.get_traced_memory()
    tracemalloc.stop()
    return dt, peak / 1024


async def handle_async(idx, active, stats):
    if active[0] >= MAX_FDS:
        stats["rejected"] += 1
        return
    active[0] += 1
    try:
        if idx < BLOCK_CALLS:
            time.sleep(WAIT_S)          # accidental blocking call on event loop
        else:
            await asyncio.sleep(WAIT_S) # non-blocking yield back to event loop
        stats["ok"] += 1
    finally:
        active[0] -= 1


def bench_event_loop():
    tracemalloc.start()
    t0 = time.perf_counter()
    active, stats = [0], {"ok": 0, "rejected": 0}
    async def runner():
        await asyncio.gather(*(handle_async(i, active, stats) for i in range(CLIENTS)))
    asyncio.run(runner())
    dt = time.perf_counter() - t0
    _, peak = tracemalloc.get_traced_memory()
    tracemalloc.stop()
    return dt, peak / 1024, stats


if __name__ == "__main__":
    if "--block" in sys.argv:
        BLOCK_CALLS = 10
    if "--fd-cap" in sys.argv:
        MAX_FDS = 256

    t_pool, m_pool = bench_thread_pool()
    t_tpr, m_tpr = bench_thread_per_req()
    t_loop, m_loop, stats = bench_event_loop()

    print(f"Clients: {CLIENTS} | Simulated I/O wait: {WAIT_S*1000:.0f} ms | FD cap: {MAX_FDS}")
    print(f"1) Bounded thread pool ({POOL_WORKERS} threads): {t_pool*1000:7.1f} ms | py heap: {m_pool:6.0f} KB | OS threads: {POOL_WORKERS}")
    print(f"2) Thread-per-request ({CLIENTS} threads): {t_tpr*1000:7.1f} ms | py heap: {m_tpr:6.0f} KB | OS threads: {CLIENTS}")
    print(f"3) Asyncio event loop  (1 thread):     {t_loop*1000:7.1f} ms | py heap: {m_loop:6.0f} KB | OS threads: 1")
    print(f"   Event loop status: ok={stats['ok']}, rejected(EMFILE)={stats['rejected']}, blocking_calls={BLOCK_CALLS}")
    print(f"Speedup (event loop vs {POOL_WORKERS}-thread pool): {t_pool / t_loop:.1f}x")

What to notice

  1. The 50-thread pool takes 1,028.2 ms, matching Little's Law queueing: 1000 / 50 * 50 ms = 1,000 ms plus 28.2 ms of scheduling overhead.
  2. Spawning 1,000 OS threads cuts queueing, yet still takes 173.4 ms (123.4 ms of pure thread creation and switching overhead) and allocates 1,000 OS thread stacks outside Python's heap.
  3. The single-threaded event loop finishes in 72.6 ms using 1 OS thread and 1,605 KB of traced Python heap (~1.6 KB per concurrent client).
  4. Python's tracemalloc only tracks Python heap objects, not native OS thread stacks, which is why native RSS explodes faster than Python heap numbers suggest when spawning thousands of threads.
Break it
  1. Event loop stall. Run python kata.py --block (10 of the 1,000 async handlers call blocking time.sleep(0.05) instead of await asyncio.sleep(0.05)). Before running, predict the new event-loop wall time. (Answer: ~550 to 580 ms, because 10 sequential 50 ms blocks freeze the entire loop for 500 ms before the remaining 990 coroutines can resume.)
  2. FD cap exhaustion. Run python kata.py --fd-cap (lowers MAX_FDS to 256, simulating a tight ulimit -n). Predict how many of the 1,000 simultaneous clients fail with simulated EMFILE. (Answer: 744 rejected, 256 ok.)

Stretch. Wrap the 10 blocking calls in await asyncio.to_thread(time.sleep, WAIT_S) and confirm that the event loop drops back near 75 ms even with blocking work present.

Interview

Say this aloud against the clock. Three levels, about 90 seconds.

1 Outcome 20 sA server handles thousands of concurrent requests by matching its concurrency model to the workload. For I/O-bound services like LLM gateways or voice AI clinics where requests mostly wait on network sockets, an event loop multiplexes thousands of connections on one thread, avoiding the memory bloat and queueing of thread-per-request servers.
2 Mechanism 45 sIn a thread-per-request model, every open socket pins an OS thread with a 1 to 8 MB virtual stack. To avoid out-of-memory crashes, servers cap threads in a pool, say 50 workers, which means 1,000 clients waiting 50 ms must drain in 20 waves and take over a second. An event loop flips sockets to non-blocking mode and registers them with the kernel via epoll or kqueue. One thread sleeps in epoll_wait and wakes only for sockets that have bytes ready, storing each in-flight request as a tiny 2 to 4 KB coroutine state instead of a megabyte stack.
3 Internals and limits 25 sEvent loops still break in two places. First, because one thread drives every request, a single synchronous call or 50 ms CPU task stalls all other clients, so heavy work must be offloaded to a worker pool. Second, every socket consumes a kernel file descriptor, so you must raise ulimit -n above the default 1,024, size somaxconn, and pool outbound keep-alive connections to avoid exhausting ephemeral ports.

Say it like an engineer

"We switched from threads to async because async is much faster and scales better for high traffic."

"Our voice-agent gateway holds 2,000 open streaming sockets waiting on LLM tokens. A 50-worker sync pool queued requests behind slow streams, while 2,000 OS threads would reserve gigabytes of stack. Moving to an epoll-backed asyncio loop cut per-connection state to a few kilobytes, and we raised ulimit -n to 65,536 while offloading audio resampling to a process pool so it cannot stall the loop."

Traps

Each one sounds right. Say what is wrong with it before you open it.

"Event loops are faster than threads for every workload because they avoid context switching."
Wrong for CPU-bound work. A single-threaded event loop uses only one CPU core and executes CPU work serially, stalling every other request. CPU-heavy tasks need multiple OS threads (in non-GIL runtimes) or multiple processes to use all cores.
"With asyncio or Node.js, one server can handle unlimited concurrent connections as long as CPU stays below 100%."
Wrong. Even at 5% CPU, every open TCP connection consumes a kernel file descriptor (default ulimit -n is 1,024), kernel socket buffers (~few KB each), and for outbound calls, ephemeral ports (~28,000 per target IP:port).

Question bank

Answer aloud, then open. Grade yourself honestly.

Why does a 50-thread pool collapse under slow upstream LLM responses even when server CPU is almost idle?
Each waiting request holds a thread hostage until the upstream replies. Once 50 slow requests are in flight, the 51st client queues even though CPU utilization is near zero.
Follow-upHow do you calculate the drain time for N simultaneous clients each waiting T ms? Answer: ceil(N / W) * T.
What does epoll (Linux) or kqueue (macOS) actually do inside an event-loop server?
It lets one thread monitor thousands of non-blocking file descriptors inside the kernel and returns only the subset that became readable or writable, in O(1) time per ready event instead of scanning all N sockets.
How can one buggy endpoint in an async server ruin p99 latency for every other endpoint?
Because an event loop is cooperatively multitasked on one thread. A synchronous network call or heavy CPU loop never yields control back to the loop, delaying every other ready socket until that call finishes.
Follow-upHow do you detect this in production? Answer: measure event-loop lag (schedule a periodic 10 ms timer and alert when actual delay exceeds e.g. 50 ms).
How do you use all 8 CPU cores with a single-threaded event loop like Node.js or Python Uvicorn?
Run one event-loop worker process per CPU core (e.g. 8 Uvicorn workers behind a load balancer or SO_REUSEPORT) and offload any blocking CPU tasks to a bounded thread or process pool.
What are the three OS-level connection limits you must check before serving 10,000 concurrent clients on one box?
Per-process file descriptors (ulimit -n, default 1,024), the kernel TCP accept backlog (somaxconn), and outbound ephemeral ports (~28,000 per destination IP:port) plus kernel socket buffer memory.
Follow-upWhat error code appears when you hit ulimit -n? Answer: EMFILE (Errno 24, Too many open files).
When would you deliberately choose a bounded thread pool over an event loop?
When concurrency is modest (tens of clients), requests are CPU-heavy or rely on mature synchronous libraries (e.g. blocking DB drivers), and you want simpler debugging without async viral coloring.

Mixed review

Three questions from earlier topics. Nobody tells you the topic in an interview.

A02: Why does calling time.sleep(1) inside a Python async def function break concurrency, whereas await asyncio.sleep(1) does not?
time.sleep blocks the OS thread running the event loop so no other coroutine can execute; await asyncio.sleep registers a timer and yields control back to the loop immediately.
L02: Why does reusing an HTTP keep-alive connection cut latency compared to opening a fresh connection per request?
It avoids paying a new TCP 3-way handshake (1 RTT) and TLS handshake (1 to 2 RTTs) plus TCP slow start on every request.
L03: Using Little's Law, how many concurrent connections are open if your API receives 200 RPS and each LLM response streams for 3 seconds?
L = lambda * W = 200 req/s * 3 s = 600 concurrent open connections.

Short notes

Quick-memorization cheat sheet covering every subtopic on this page and the key facts to remember cold.

All subtopics on this page

  • Bounded thread pools: Cap RAM by fixing worker count W, but queue requests when concurrent I/O exceeds W (drain time = ceil(N / W) * T_io; 50 threads took 1,028.2 ms for 1,000 x 50 ms waits).
  • Thread-per-request: Removes pool queueing, but reserves 1 to 8 MB virtual stack per OS thread and pays heavy creation and context-switch overhead (173.4 ms for 1,000 threads).
  • Event loop (epoll / kqueue): Multiplexes thousands of non-blocking sockets on 1 OS thread using O(1) kernel readiness events and ~1.6 to 4 KB per task (72.6 ms in kata, 14.2x faster than the 50-thread pool).
  • OS connection limits: Every open TCP socket consumes 1 file descriptor (default Linux ulimit -n is 1,024 -> EMFILE), plus TCP accept backlog (somaxconn) and outbound ephemeral ports (~28,000 per target).
Important things to remember
  • Memory hook (T-E-C): Threads burn stacks, Event loops watch FDs, Caps stop both.
  • Numbers to know cold: 8 MB Linux / 1 MB Windows default thread stack; ~2 to 4 KB coroutine state; 1,024 default ulimit -n; ~28,000 Linux ephemeral ports.
  • Golden rule of async servers: Never run blocking I/O or heavy CPU directly on the event loop; offload to a thread or process pool and monitor event-loop lag.
  • Multi-core pattern: Run 1 event-loop worker process per CPU core, raise LimitNOFILE, and reuse outbound HTTP keep-alive connection pools.
