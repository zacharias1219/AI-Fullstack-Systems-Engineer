Scaling out

Why round-robin load balancing breaks stateful workers immediately, how externalized state unlocks horizontal elasticity, and how the Universal Scalability Law and synchronous RPC hops cap real-world cluster throughput.

The core idea

When a single server hits 100% CPU or RAM, you have two choices: scale up (vertical scaling) by buying a bigger machine, or scale out (horizontal scaling) by adding more commodity instances behind a load balancer. Vertical scaling requires zero code changes and keeps all communication in fast local memory, but it hits hard hardware ceilings, requires downtime for instance resizes, and leaves a Single Point of Failure (SPOF). Horizontal scaling removes the single-machine ceiling and survives node crashes, but it introduces a strict architectural contract: every application worker must be stateless.

If worker instances keep mutable conversation history, auth sessions, or local file uploads in process RAM, a load balancer cannot route consecutive requests from the same user to arbitrary nodes without triggering state misses. Moving mutable state out of the compute tier into a shared data tier (Redis for ephemeral sessions, Postgres/S3 for durable records) makes workers interchangeable cattle. However, scaling out is never infinitely linear: shared database locks (contention alpha), cross-node coordination (coherency beta), and premature microservice chains impose a mathematical ceiling on horizontal scale.

How it works

1. Vertical scaling (scale up) vs horizontal scaling (scale out)

Vertical scaling increases the CPU cores, RAM, or GPU VRAM of a single node (e.g., moving from an 8-vCPU VM to a 128-vCPU metal instance). Its primary advantage is zero distributed-systems tax: inter-component calls are nanosecond function pointers, transactions use local ACID locks without two-phase commit, and consistency is trivial. However, vertical cost scales super-linearly at the high end, hardware hits a physical ceiling (you cannot buy a 10,000-core single socket), upgrades require reboot windows, and one motherboard or AZ failure takes down 100% of capacity.

Horizontal scaling runs N independent commodity instances behind a reverse proxy or load balancer (nginx, Envoy, AWS ALB). Capacity scales in smooth increments, deploys run zero-downtime rolling updates, and losing one node costs only 1 / N of capacity. The price is that you now run a distributed system where local disk and process RAM are ephemeral.

2. Statelessness and why round-robin breaks local session memory

A service worker is stateless if it stores zero client session context between requests; every request carries either the full context (e.g., a signed JWT or full message history) or a session key (sess_id) that any worker can fetch from an external shared store (Redis, DynamoDB, Postgres). Suppose an app instead stores sessions[sess_id] in a local Python dictionary inside each worker process. When Turn 1 arrives, the load balancer routes it to worker w_1 in {0, ..., N-1}, which allocates the session in its private RAM. On Turn 2:

  • Random or least-connections routing across N workers: Turn 2 lands on the same worker w_1 with probability 1 / N and misses with probability (N - 1) / N (50% miss at N = 2, 75% miss at N = 4, 90% miss at N = 10).
  • Strict round-robin routing: If turns arrive interleaved or sequentially across N workers, consecutive turns cycle through (w + 1) mod N. In our kata's 4-turn conversation across N = 2 workers, Turns 1 and 3 hit Worker 0 (succeeding) while Turns 2 and 4 hit Worker 1 (failing), yielding a 66.7% follow-up failure rate (50% overall). At N = 4, Turns 2, 3, and 4 all land on workers that never saw Turn 1, causing a 100.0% follow-up failure rate.

Why sticky sessions (session affinity) are a trap: Load balancers can hash a client IP or set an affinity cookie to pin a user to Worker A. While this hides the bug during sunny-day operation, any auto-scaling scale-in, deploy restart, or OOM crash on Worker A wipes out every active conversation pinned to it. Moreover, in AI workloads where a single power user runs heavy multi-turn agent loops, sticky sessions create severe load imbalance (hot-spotting) across workers.

Check: In an AI voice clinic assistant using WebSockets for live bidirectional audio, TCP connections are inherently long-lived and stateful on one worker while open. How do you make this horizontally scalable and crash-resilient?
Keep only the transient transport socket on the worker, and stream every finalized utterance transcript and state checkpoint asynchronously to shared Redis Streams or Postgres within milliseconds. If the worker dies mid-call, the client reconnects through the load balancer to any surviving worker, presents its call_id, hydrates the latest transcript state from Redis in ~1.5 ms, and resumes the conversation seamlessly.

3. The Universal Scalability Law (USL): Contention and Coherency

Even after you make the application tier 100% stateless, doubling workers from N = 16 to N = 32 rarely doubles throughput because all workers contend for downstream shared resources (database connection pools, Redis shards, lock managers). Neil Gunther's Universal Scalability Law (USL) models relative capacity C(N) for N workers as:

C(N) = N / (1 + alpha * (N - 1) + beta * N * (N - 1))

Look closely at the three terms in the denominator:

  • Linear concurrency (1): When alpha = 0 and beta = 0, C(N) = N (ideal linear scale-out).
  • Contention (alpha * (N - 1)): Serial waiting for a shared resource (e.g., a serialized Postgres sequence lock or single Redis primary queue). When beta = 0, USL reduces to Amdahl's Law, which asymptotically plateaus at a maximum speedup of 1 / alpha (for alpha = 0.04, speedup can never exceed 1 / 0.04 = 25x, no matter how many thousands of nodes you add).
  • Coherency / point-to-point coordination (beta * N * (N - 1)): Pairwise agreement overhead between N nodes (distributed lock arbitration, gossip protocols, cache invalidation broadcasts, Raft quorum acks). Because there are N(N - 1) / 2 pairs of nodes, this penalty grows quadratically as O(N^2). Differentiating C(N) with respect to N and setting dC/dN = 0 gives the exact worker count where capacity peaks before turning downward (retrograde scaling):
N_peak = sqrt((1 - alpha) / beta)

4. Modular monolith vs microservices: The synchronous fan-out tax

A common anti-pattern is confusing horizontal scaling with microservices. You can scale a well-structured modular monolith horizontally across 50 stateless containers behind a load balancer without paying a single inter-service network hop. Splitting a monolith into k synchronous microservices on the critical request path imposes three immediate engineering taxes:

  1. Compounded availability decay: If a user request requires k services in series, each with availability p = 99.9% (43.2 min/mo downtime), overall chain availability is p^k. At k = 5 hops, availability drops to 0.999^5 = 99.501% (215.6 min/mo downtime); at k = 10 hops, it drops to 99.004% (430.1 min/mo downtime).
  2. Serialization and tail-latency amplification: In-process function calls take nanoseconds; each gRPC/HTTP hop adds 2..5 ms of JSON/Protobuf serialization, kernel socket traversal, and TLS/mesh framing. Across 5 hops, our kata measures +22.5 ms of added p99 RPC latency before doing any business logic.
  3. Distributed data consistency: Replacing a single Postgres ACID transaction across two tables with two separate microservice databases forces eventual consistency, outbox pattern relays, idempotency keys, and Saga compensating rollbacks.

When to actually split a service: Extract a microservice only when (a) hardware resource profiles diverge sharply (e.g., splitting a GPU-bound LLM/embedding worker from a CPU/IO-bound CRUD web API so you do not buy GPUs to scale HTTP routing), (b) strict security/compliance blast radius requires isolated IAM/network boundaries (e.g., PII vault or payment tokenization), or (c) organizational scale exceeds ~30 engineers and independent deployment cadences are blocked by merge/release coordination.

Check: An engineering team wants to split their 6-engineer RAG application into 7 microservices (Auth, Gateway, Chunker, Embedder, VectorSearch, PromptBuilder, LLMProxy) "so it can scale". Which split is genuinely justified by hardware economics, and what should remain a modular monolith?
Only self-hosted GPU inference / embedding (if running local models on GPU nodes) justifies a separate service boundary so GPU instances scale on token queue depth independently of web I/O. Auth, Gateway, Chunker, VectorSearch orchestration, and PromptBuilder are all lightweight CPU/IO modules that should stay inside a single stateless modular monolith scaled horizontally across N replicas, avoiding 6 unnecessary RPC hops and 6 x 43.2 = 259 minutes of extra monthly downtime exposure.

Kata: Round-robin statefulness, USL ceiling, and microservice fan-out

We simulate 200 users running 4-turn conversations (800 requests total, 600 follow-up turns) behind an nginx round-robin load balancer across 1, 2, and 4 workers, comparing local process state against externalized Redis state, followed by the Universal Scalability Law curve and synchronous microservice availability decay.

kata.py

import random

random.seed(42)

def sim_cluster(n_workers, stateful_local, n_users=200, turns=4):
    """Simulate nginx round-robin over n_workers handling multi-turn chat sessions."""
    local_Mem = [{} for _ in range(n_workers)]
    shared_redis = {}
    rr_idx = 0
    ok, fail_404 = 0, 0
    latencies = []

    for u in range(n_users):
        sid = f"sess_{u}"
        for turn in range(turns):
            w = rr_idx % n_workers
            rr_idx += 1
            # Base worker compute latency ~18ms + jitter; Redis hop adds ~1.4ms
            lat = random.gauss(18.0, 2.5) + (0.0 if stateful_local else 1.4)
            latencies.append(lat)
            if turn == 0:
                if stateful_local:
                    local_Mem[w][sid] = 1
                else:
                    shared_redis[sid] = 1
                ok += 1
            else:
                store = local_Mem[w] if stateful_local else shared_redis
                if sid in store:
                    store[sid] += 1
                    ok += 1
                else:
                    fail_404 += 1

    total = ok + fail_404
    followups = n_users * (turns - 1)
    latencies.sort()
    p95 = latencies[int(0.95 * len(latencies))]
    # Throughput scales with workers minus coordination overhead
    rps_cap = n_workers * (1000.0 / (18.0 if stateful_local else 19.4))
    return total, ok, fail_404, followups, p95, rps_cap

What to notice

  1. Stateful horizontal scale-out fails deterministically: With N = 2 local-memory workers, Turn 1 (Worker 0) and Turn 3 (Worker 0) succeed while Turn 2 (Worker 1) and Turn 4 (Worker 1) fail with 404, causing 66.7% of follow-ups (400 / 600) to fail. Traps

Each one sounds right. Say what is wrong with it before you open it.

"Enabling sticky sessions on the load balancer makes a stateful in-memory application horizontally scalable just like a stateless architecture."
Wrong. Sticky sessions pin a user to one node's RAM, which means (1) any node crash, rolling deploy, or auto-scaler scale-in permanently destroys every active session on that node, and (2) heavy users or corporate NAT gateways sharing an IP create severe CPU hot-spots that cannot be rebalanced without dropping state.
"We need to break our monolith into microservices so that we can scale horizontally across multiple servers."
Wrong. A monolith is a packaging and deployment unit, not a single-server limit. A stateless modular monolith scales horizontally across dozens of instances behind a load balancer with zero inter-service RPC latency and 99.9% single-hop availability. Microservices scale teams and divergent hardware tiers, not basic request concurrency.
"If our application tier is 100% stateless, doubling the number of worker pods from 16 to 32 will double our system's throughput."
Wrong. Stateless workers still share downstream stateful databases, caches, and lock managers. Under the Universal Scalability Law, serial contention alpha and pairwise coherency beta bend the curve downward; in our kata with alpha = 0.04, beta = 0.0025, scaling from 20 to 32 workers actually reduces capacity from 7.38x to 6.78x.
"Round-robin load balancing guarantees even CPU utilization across all stateless worker instances."
Wrong when request service times have high variance (such as LLM prompts ranging from 100 tokens to 8,000 tokens or persistent HTTP/2 and gRPC connections). Round-robin equalizes request count, not active work; long requests pile up on one worker unless you use least outstanding requests (least_conn) or power-of-two-choices (P2C) load balancing.

Question bank

Answer aloud, then open. Grade yourself honestly.

1. Compare vertical scaling and horizontal scaling across four dimensions: ceiling, downtime/availability, consistency cost, and unit economics.
Ceiling: Vertical hits physical single-node RAM/CPU limits; horizontal scales out across hundreds of nodes. Availability: Vertical is a SPOF requiring reboot downtime to resize; horizontal survives node failures with rolling zero-downtime deploys. Consistency: Vertical uses fast local memory and ACID locks; horizontal requires externalized state and network hops. Economics: Vertical becomes exponentially expensive at extreme instance sizes; horizontal uses commodity VMs.
Follow-upWhen is vertical scaling actually the right first move in production? Answer: When traffic fits comfortably below ~50% of a mid-sized commodity node and DB contention dominates, upgrading Postgres from 8 to 32 vCPUs with more RAM for buffer cache takes 5 minutes and avoids months of sharding engineering.
2. Prove why an N-node stateful cluster behind a stateless load balancer suffers an (N - 1) / N session miss rate on Turn 2 under random routing and even worse under strict round-robin.
Under uniform random routing, Turn 1 places the session in the private RAM of 1 specific worker out of N. Turn 2 chooses among all N workers with probability 1/N each; since only 1 worker holds the session and N - 1 workers do not, the miss probability is (N - 1) / N. Under strict round-robin with a single user or synchronized turns, Turn 2 is deterministically sent to (w + 1) mod N != w, causing a 100% miss on Turn 2.
3. What is the difference between Amdahl's Law and Gunther's Universal Scalability Law, and how do you derive N_peak?
Amdahl's Law models only serial contention alpha: C(N) = N / (1 + alpha(N - 1)), which monotonically approaches an upper bound of 1 / alpha as N -> infinity. USL adds the pairwise coherency/coordination term beta N(N - 1): C(N) = N / (1 + alpha(N - 1) + beta N(N - 1)). Differentiating C(N) with respect to N sets (1 - alpha + alpha N + beta N^2 - beta N) - N(alpha + 2 beta N - beta) = 1 - alpha - beta N^2 = 0, yielding N_peak = sqrt((1 - alpha) / beta).
Follow-upGive one concrete engineering action that reduces alpha and one that reduces beta. Answer: Reducing lock hold time or sharding hot DB rows reduces contention alpha; replacing synchronous all-to-all cache invalidation broadcasts with local TTLs or partitioned ownership reduces coherency beta.
4. Why does round-robin fail for gRPC or WebSockets even when workers are completely stateless, and how do you fix it?
Both gRPC (built on HTTP/2) and WebSockets multiplex many logical requests or turns over a single long-lived TCP connection. An L4 TCP round-robin load balancer balances at connection establishment time, pinning all subsequent RPCs on that connection to a single pod and leaving newly scaled-out pods idle. Fix by deploying an L7 proxy (Envoy, nginx with grpc_pass) that balances individual HTTP/2 frames using least outstanding requests.
5. Calculate the availability and monthly downtime of a 5-service synchronous chain versus a modular monolith when each deployable has 99.9% availability.
A single modular monolith at 99.9% availability has 0.001 * 43,200 = 43.2 minutes of downtime per 30-day month. Five independent services in series succeed only if all five are up simultaneously: 0.999^5 = 0.99500999 ~ 99.501%, which equals (1 - 0.99501) * 43,200 = 215.6 minutes of downtime per month (a 5x degradation).
Follow-upHow do you prevent a downstream service outage from multiplying into your core availability SLA? Answer: Decouple non-essential dependencies asynchronously via a durable queue/event log, or wrap synchronous calls in a circuit breaker with a cached/degraded fallback response.
6. What is a "modular monolith", and how does it prevent turning into a big ball of mud while avoiding the microservice RPC tax?
A modular monolith deploys as a single binary or container image (zero network hops between modules, one CI/CD pipeline), but enforces strict compile-time or linter-enforced package boundaries inside the codebase: Module A can only call Module B through its public service interface and is forbidden from importing Module B's internal classes or joining directly against Module B's private database tables.
7. In an AI RAG + Agent backend, which component should be extracted out of the core web monolith first as traffic scales, and why?
Extract the GPU model inference / local embedding worker (or heavy long-running document OCR/ingestion worker) first. Web/API orchestration is I/O-bound (high concurrency on cheap 2-vCPU nodes), whereas model inference and PDF OCR are compute/VRAM-bound (requiring expensive GPU or high-CPU nodes scaled on queue depth and batch size). Keeping them in one deployable forces you to over-provision GPUs just to handle HTTP connection waiting.
Follow-upHow should the stateless web tier communicate with the heavy ingestion worker? Answer: Asynchronously via a work queue (Redis Streams, SQS, Kafka) with status polling or SSE push, so bursty document uploads never exhaust web worker threads.
8. When you scale stateless app workers from 4 to 40 behind a load balancer, what breaks in the database tier and how do you protect it?
Each new app worker opens its own database connection pool (e.g., 40 pods x 20 connections = 800 active connections), exhausting Postgres memory (~10 MB per backend process) and causing context-switch thrashing and lock contention (alpha). Protect the DB with a connection pooler like PgBouncer in transaction mode, read replicas for read-heavy queries, and a Redis cache-aside layer with singleflight request coalescing.

L04: According to Little's Law (L = lambda * W), if a single stateless worker processes requests with an average latency W = 20 ms and you want to keep in-flight concurrency at L = 1 to avoid queueing delay, what is its maximum throughput lambda?
lambda = L / W = 1 / 0.020 s = 50 RPS (or 55.6 RPS at our kata's 18 ms service time). Beyond that arrival rate, requests queue according to Kingman's formula W_q propto rho / (1 - rho).
A11: Why does backpropagation use reverse-mode VJP (v^T J) instead of forward-mode JVP (J u), and what step size eps is optimal for centered finite-difference checks in FP64?
Because neural net training minimizes a single scalar loss L in R^1 over n millions of parameters, reverse-mode VJP computes all n partial derivatives in 1 backward pass instead of n forward JVP passes. In FP64 (u = 1.11e-16), centered FD optimizes at eps* ~ u^(1/3) ~ 1e-5..1e-6 (error ~3.6e-11).
A09: If activation matrix X has shape (B, T, D) and weight matrix W has shape (D, V), what is the FLOP count of the linear projection X @ W?
Treating (B, T) as B * T tokens, multiplying a (B*T x D) matrix by a (D x V) matrix requires 2 * B * T * D * V FLOPs (one multiply and one add per inner-dimension element).

Short notes

Quick-memorization cheat sheet covering every subtopic on this page and the key facts to remember cold.

All subtopics on this page

  • Vertical vs Horizontal Scaling: Vertical scales up one machine (0 ms network hop, simple ACID, but hardware ceiling + SPOF); Horizontal scales out across N commodity nodes behind a load balancer (elastic + fault-tolerant, requires stateless workers).
  • Statelessness & Round-Robin Failure: Local in-memory sessions behind N nodes fail on (N-1)/N follow-ups under random routing and 66.7% (N=2) to 100% (N=4) under round-robin; externalizing state to Redis restores 100% accuracy for +1.4 ms latency.
  • Sticky Sessions Trap: Pinning users to one worker's RAM breaks auto-scaling and rolling deploys (node loss wipes sessions) and causes severe load hot-spots for heavy users.
  • Universal Scalability Law (USL): C(N) = N / (1 + alpha(N-1) + beta N(N-1)) models serial contention alpha (Amdahl limit 1/alpha) and pairwise coherency beta (retrograde peak at N_peak = sqrt((1-alpha)/beta)).
  • Modular Monolith vs Microservices: A stateless modular monolith scales horizontally across N pods with 0 RPC tax; splitting into k synchronous microservices decays availability as p^k (99.501% / 215.6 min/mo downtime for 5 hops at 99.9%) and adds ~4.5 ms p99 per hop.
Important things to remember
  • Core formulas: Stateful random miss rate = (N - 1) / N; USL capacity = N / (1 + alpha(N-1) + beta N(N-1)); Peak workers = sqrt((1 - alpha) / beta); Sync chain availability = p^k.
  • Load balancer choice for AI/LLM traffic: Never use plain round-robin for high-variance LLM generation times or persistent gRPC/WebSocket streams; use L7 least outstanding requests (least_conn).
  • Database protection when scaling out: Scaling from 4 to 40 pods multiplies DB connections 10x; always place a transaction pooler (PgBouncer) between stateless workers and Postgres.
  • When to split a microservice: Split only for divergent hardware profiles (GPU inference vs CPU web tier), strict security/compliance isolation, or large multi-team deployment independence.
