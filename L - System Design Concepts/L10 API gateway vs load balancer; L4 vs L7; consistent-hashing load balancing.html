The core idea

Modern production traffic passes through three distinct ingress tiers, each operating at a different layer of the network stack with a different state and CPU budget. At the outer edge, an L4 Load Balancer (OSI Layer 4, TCP/UDP) forwards packets at millions of packets per second using a fast 5-tuple hash (ECMP / Maglev) without inspecting payloads. Behind it, an L7 Load Balancer terminates TLS, parses HTTP/1.1 or HTTP/2 frames, and routes individual requests across healthy backend pools. An API Gateway is a policy-heavy L7 proxy that enforces business and security concerns: JWT/OAuth authentication, per-tenant token-bucket rate limiting, request validation, and usage billing.

For stateless microservices, L7 least-outstanding-requests (P2C, Power of Two Choices) works well. For stateful AI workloads like LLM KV-prefix caching, routing the same conversation or system-prompt prefix to the same GPU worker avoids recomputing prefill attention across tens of thousands of tokens. Naive modulo hashing (hash(key) % N) invalidates nearly the entire cluster cache ((N-1)/N keys) whenever a node joins or leaves. Consistent hashing maps both nodes and request keys onto a 32-bit unit circle [0, 2^32 - 1], assigning each key to the first node clockwise so scaling from N to N+1 nodes moves only 1/(N+1) of the keys.

How it works

1. L4 vs L7 load balancing vs API Gateway

An L4 Load Balancer (AWS NLB, Linux IPVS, Google Maglev) operates on TCP/UDP segments. It maps the 5-tuple to a backend via consistent flow tables, rewriting IP headers (NAT) or encapsulating packets (DSR, Direct Server Return) so response packets bypass the load balancer entirely. Because it never buffers payloads or decrypts TLS, L4 handles millions of concurrent connections with microseconds of overhead, but it cannot inspect URLs, headers, or multiplexed HTTP/2 streams. An L7 Load Balancer (Envoy, NGINX, AWS ALB) terminates the client TLS connection, parses HTTP headers/paths/gRPC frames, and opens pooled backend connections. An API Gateway (Kong, Apigee, Envoy AI Gateway) layers control-plane policy onto L7: authn/authz, per-tenant token-rate limits, canary splitting, and billing telemetry.

2. Why modulo hashing fails and consistent hashing moves only 1/(N+1)

Under modulo hashing node = hash(key) % N, changing the divisor from N to N + 1 shifts the remainder of almost every integer: the probability that h % N == h % (N + 1) over a large hash space approaches 1 / N, meaning a fraction (N - 1) / N of all keys change owners (8/9 = 88.89% when scaling 8 to 9 nodes). Consistent hashing fixes the modulus at 2^32 (a fixed ring [0, 2^32 - 1]). Both nodes and keys are hashed onto the ring, and a key routes to the first node at pos >= hash(key) using binary search (bisect_left) in O(log(N * V)) time. Adding an (N+1)-th node steals only the keys landing in the V arc segments immediately preceding its virtual nodes - an expected fraction of exactly 1 / (N + 1) (1/9 = 11.11%).

Modulo hashing churn (N -> N+1):      fraction moved = (N - 1) / N      (8 -> 9: 88.89% theory, 89.29% run)
Consistent hashing churn (N -> N+1):  fraction moved = 1 / (N + 1)      (8 -> 9: 11.11% theory, 10.29% run)
Virtual node load std-dev scaling:    sigma / mean   ~ 1 / sqrt(V)      (V=1: 48.9% -> V=150: 9.1%)

3. Virtual nodes (vnodes) and Bounded-Load consistent hashing

With only V = 1 position per physical node, random Poisson spacing on the circle produces severe load skew (std / mean ~ 49%). Assigning each physical node V = 100..200 virtual labels (gpu-0#v0 .. gpu-0#v149) interleaves every node's arcs uniformly around the ring, reducing load standard deviation by 1 / sqrt(V) (9.1% at V = 150) and ensuring that when one GPU crashes, its keys spread evenly across all N - 1 survivors instead of dumping 100% onto a single clockwise neighbor. Still, virtual nodes cannot split a single hot key (for example, one enterprise customer whose shared system prompt accounts for 35% of all requests). Consistent Hashing with Bounded Load (Mirrokni et al., 2017) sets a capacity ceiling per node for a window of L active requests:

Node capacity cap = ceil((L / N) * c)     where balance factor c = 1.25 (25% headroom above mean)

When a key's primary clockwise node reaches cap, the router walks clockwise to the next non-full node on the ring, bounding maximum GPU queue depth while keeping overflow deterministic so the secondary GPU also warms its KV cache.

Check: What are the lookup time complexity and memory footprint of a consistent hash ring with N physical nodes and V virtual nodes per physical node?
The sorted ring array stores M = N * V 32-bit or 64-bit positions. Each key lookup runs a binary search (bisect_left) in O(log(N * V)) time, and adding or removing a node inserts or deletes V entries. Even for N = 100 nodes and V = 150 vnodes (M = 15,000 entries), the ring occupies under 250 KB (fitting entirely in L2 CPU cache) and binary search takes at most 14 comparisons.
Check: Besides adding a node, what happens on a consistent hash ring with V = 1 vs V = 150 when one physical GPU node crashes?
When a node fails, all keys on its arc segments roll clockwise to the next node on the ring (only 1/N of total keys move). However, at V = 1, the dead node occupied a single contiguous arc, so 100% of its traffic dumps onto its single clockwise neighbor, doubling that neighbor's load to 2x and often triggering a cascading OOM collapse. At V = 150, the dead node's 150 small arcs are scattered randomly ahead of all remaining N - 1 nodes, so each surviving GPU absorbs an even 1 / (N - 1) share of the failed node's traffic.

import bisect
import hashlib
import math

def h32(s):
    return int.from_bytes(hashlib.md5(s.encode("utf-8")).digest()[:4], "big")

class ConsistentHashRing:
    def __init__(self, nodes, vnodes=150):
        self.vnodes = vnodes
        self.ring = []
        self.owner = {}
        for n in nodes:
            self.add_node(n)

    def add_node(self, node):
        for v in range(self.vnodes):
            pos = h32(f"{node}#v{v}")
            bisect.insort(self.ring, pos)
            self.owner[pos] = node

    def get_node(self, key):
        pos = h32(key)
        idx = bisect.bisect_left(self.ring, pos) % len(self.ring)
        return self.owner[self.ring[idx]]

    def route_bounded(self, keys, cap_factor=1.25):
        nodes = sorted(set(self.owner.values()))
        cap = math.ceil((len(keys) / len(nodes)) * cap_factor)
        counts = {n: 0 for n in nodes}
        hops = 0
        for k in keys:
            pos = h32(k)
            idx = bisect.bisect_left(self.ring, pos) % len(self.ring)
            while counts[self.owner[self.ring[idx]]] >= cap:
                idx = (idx + 1) % len(self.ring)
                hops += 1
            counts[self.owner[self.ring[idx]]] += 1
        return counts, cap, hops

Traps

Each one sounds right. Say what is wrong with it before you open it.

"Adding more virtual nodes (e.g. V = 200 per physical server) prevents a single viral prompt or hot tenant key from overloading one server on a consistent hash ring."
Wrong. Virtual nodes only smooth out load variance across many distinct keys by subdividing the ring into smaller interleaved arcs. Every request carrying the exact same key K computes the exact same hash h(K) and lands on the exact same single virtual node. Preventing single-key hot spots requires Bounded-Load consistent hashing (c = 1.25) or key-salting across K replicas.
"An L4 load balancer is strictly faster than an L7 load balancer, so you should always use L4 for internal gRPC and LLM inference routing."
Wrong. While L4 has lower per-packet overhead, it balances only at TCP connection setup (5-tuple). Because gRPC/HTTP/2 multiplexes thousands of RPCs over one long-lived TCP socket and L4 cannot read HTTP headers or prompt prefixes, L4 pins connections unevenly and achieves 1/N random prefix-cache hit rate instead of ~90% L7 prefix-affinity hit rate.
"When one server in an N-node consistent hash ring crashes, its traffic only affects one neighbor, which is safer than modulo hashing."
Half-true and dangerous if V = 1. Without virtual nodes (V = 1), 100% of the crashed node's traffic dumps onto its single clockwise neighbor, immediately doubling that neighbor's load to 2x and triggering a cascading domino collapse around the ring. Only with V >= 100 virtual nodes does the crashed node's 1/N share disperse evenly (1/(N-1) each) across all surviving nodes.

Follow-upWhat is Direct Server Return (DSR) at L4, and why is it impossible for standard L7 HTTP proxying? In DSR, the L4 LB forwards packets by rewriting only the MAC address (or IP-in-IP encapsulation) while keeping the client's source IP, so the backend sends large response packets directly back to the client bypassing the LB. An L7 proxy terminates the client's TCP/TLS session and opens a separate backend TCP socket, so return traffic must traverse the L7 proxy to be encrypted with the client TLS session key.
Prove why scaling from N to N+1 nodes moves (N-1)/N keys under hash(k) % N, but only 1/(N+1) keys on a consistent hash ring.
Under modulo hashing, a key with uniform integer hash H stays on the same node i in [0, N-1] only if H % N == H % (N + 1). Within each period N(N+1), only the first N integers [0..N-1] have identical remainders across both divisors, which is a fraction N / (N(N+1)) = 1/(N+1) staying put (or roughly 1/N), so ~ (N-1)/N move (88.89% for 8 -> 9). On a consistent hash ring of fixed circumference 2^32, adding the (N+1)-th node with V uniform virtual nodes claims an expected 1/(N+1) fraction of the circle's perimeter from existing arcs, leaving N/(N+1) of the ring untouched.
In our kata, how did increasing virtual nodes from V = 1 to V = 150 affect load balance across 8 GPUs (10,000 keys), and what is the algorithmic cost of higher V?
At V = 1, per-GPU load ranged from 330 to 2,376 keys with a standard deviation of 611.7 (48.9% of the 1,250 mean). At V = 150, load tightened to 1,085..1,465 keys with a standard deviation of 114.0 (9.1% of mean). Explain Consistent Hashing with Bounded Load (Mirrokni et al.) and quote our kata's numbers for a 35% hot-tenant spike with c = 1.25.
For L active requests across N nodes and balance factor c > 1 (e.g. c = 1.25), each node is given a hard cap cap = ceil((L / N) * c). When routing key k, the router finds the first clockwise node on the ring whose current load is < cap, walking clockwise along the ring if the primary node is full. In our kata (L = 10,000, N = 8), a 35% hot prefix sent 4,359 requests to one GPU without bounds; with c = 1.25, max GPU load was capped at 1,563 requests (2.79x reduction).
How does Rendezvous Hashing (Highest Random Weight, HRW) work, and how does it compare to a Consistent Hash Ring with virtual nodes?
In Rendezvous Hashing, to route key k across nodes n_1..n_N, the router computes a combined hash score score_i = hash(k, n_i) for every node and picks argmax_i score_i. Like a consistent ring, adding or removing a node moves only 1/(N+1) keys, and it achieves perfect uniform load balance without needing virtual nodes (O(N) memory instead of O(N * V)). Its drawback is O(N) lookup time per request instead of O(log(N * V)), though O(N) can be reduced to O(log N) using a binary tree of node groups (Skeleton HRW).
Follow-upWhen is Rendezvous Hashing preferred over a ring? When N is moderate (N <= 64 GPU workers or storage shards) and you want zero virtual-node memory overhead and trivial top-K replica selection (just pick the top K highest hash(k, n_i) scores).
What is Google Maglev hashing, and why do high-speed L4 software load balancers use it instead of a binary-search ring?
Maglev precomputes a fixed-size lookup table of prime length M (for example, M = 65,537 slots) where each backend node takes turns filling its preferred free slots via two permutation hashes until all M slots are populated. Packet lookup is an O(1) array index table[hash(5_tuple) % M] (a single L1/L2 cache read) instead of an O(log(N*V)) pointer/binary search, while maintaining consistent-hashing minimal disruption when rebuilding the table.
Why does sticky consistent hashing alone sometimes degrade p99 TTFT on LLM inference clusters with variable prompt lengths, and how do modern routers (like vLLM / SGLang routers) combine cache locality with load awareness?
Two requests may have the same QPS rate, but a 64,000-token prefill prompt locks a GPU for seconds while a 128-token prompt finishes in 15 ms. Pure hash-ring routing ignores actual GPU KV-cache occupancy and running token queue depth. Modern LLM routers compute a composite score alpha * prefix_match_ratio - beta * pending_token_load (or use Bounded-Load / Power-of-Two-Choices over the primary ring node and a random fallback node).
If you deploy 4 stateless L7 Envoy gateway pods in front of 16 GPU workers, what must be true for all 4 Envoy pods to route the same conversation ID to the exact same GPU worker?
Consistent hashing is deterministic: if all 4 Envoy pods use the exact same hash function + seed (xxHash64), the same virtual node multiplier V, the same canonical node naming string (ip:port#v), and have converged on the same active health-check membership list via service discovery (EDS), they construct bit-identical rings in memory without needing inter-proxy coordination on each request.

Mixed review

Three questions from earlier topics. Nobody tells you the topic in an interview.

L09: In our 16 x 768 float32 embedding benchmark, why was binary Protobuf 1.95x smaller and 11.18x faster to serialize than REST/JSON?
JSON formats every 4-byte float32 into 6-9 ASCII characters plus delimiters (7.84 B/float, 96,390 B) and parses decimal strings on decode. Protobuf copies raw packed IEEE-754 float32 bytes (4.00 B/float) with a 1-byte field tag and varint byte length (4.02 B/float, 49,376 B, only 224 B framing).
A12: Why does an autograd engine need both reverse topological order and += accumulation when computing gradients on a computational DAG?
When a node fans out to multiple consumers, the multivariable chain rule requires summing the Vector-Jacobian Products from every outgoing branch (+=). Reverse topological order guarantees all downstream consumers have finished adding into node.grad before node._backward() propagates that total upstream.
L08: What is the difference between HTTP 401 Unauthorized, 403 Forbidden, and 429 Too Many Requests at an API Gateway?
401 means unauthenticated (missing, expired, or invalid credentials/JWT); 403 means authenticated identity lacks permission (RBAC/scope denial; re-authenticating will not help); 429 means rate-limit quota exceeded (must include a Retry-After header).

Short notes

Quick-memorization cheat sheet covering every subtopic on this page and the key facts to remember cold.

All subtopics on this page

  • L4 vs L7 Load Balancer vs API Gateway: L4 routes TCP/UDP packets by 5-tuple hash (src/dst IP, port, proto) at multi-million PPS without TLS termination; L7 terminates TLS and routes individual HTTP/gRPC frames; API Gateway adds JWT/OAuth auth, per-tenant token-bucket rate limits, and billing.
  • Modulo vs Consistent Hashing Scale Churn: Scaling N -> N+1 nodes moves (N-1)/N keys under hash(k) % N (89.29% in our 8 -> 9 run) vs 1/(N+1) keys on a 32-bit consistent hash ring (10.29% in our run, keeping 7,900 / 10,000 GPU KV-prefix caches warm).
  • Virtual Nodes (vnodes): Placing each physical node at V random points interleaves arcs so load standard deviation drops as 1/sqrt(V) (from 48.9% at V=1 down to 9.1% at V=150) and disperses a crashed node's traffic evenly across all N - 1 survivors instead of overloading one neighbor.
  • Consistent Hashing with Bounded Load: Virtual nodes cannot split a single hot key; setting a per-node cap ceil((L / N) * c) (c = 1.25) spills excess hot-prefix traffic clockwise, cutting our 35% hot-tenant peak GPU load from 4,359 down to 1,563 requests.
  • Rendezvous (HRW) & Maglev Alternatives: Rendezvous picks argmax_i hash(k, node_i) in O(N) time with zero vnode memory; Maglev builds an M = 65,537 prime lookup table for O(1) array-indexed consistent hashing at L4/L7.
Important things to remember
  • Spine (4-7-G-R-B): L4 5-tuple packet forward -> L7 HTTP/2 frame proxy -> API Gateway auth/quotas -> Consistent Ring (1/(N+1) churn, V=150 vnodes, O(log(N*V)) lookup) -> Bounded Load (cap = ceil(c * L / N)).
  • Cold numbers (N=8 -> 9, 10k keys): Modulo moves 89.29% (8,929 keys) vs Ring 10.29% (1,029 keys); V=1 std-dev 48.9% (330..2376) vs V=150 std-dev 9.1% (1085..1465).
  • Interview trap: Virtual nodes fix random arc variance and failure dominoes, but only Bounded Load (c = 1.25) or key replication fixes a single hot key.
