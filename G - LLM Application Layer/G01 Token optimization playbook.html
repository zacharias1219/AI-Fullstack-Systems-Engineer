Token optimization playbook

How do you cut an LLM bill by 80% to 95% without breaking quality? This page covers the full 8-lever engineering playbook (measure, send less, reuse, generate less, cheaper models, batch, fewer calls, self-host) and where each lever stops working.

Study path

Before you read

Guess first. A wrong guess now makes the right answer stick later.

In a 20-turn chat (1,400-token system prompt, 120-token user turn, 420-token reply), what share of the 133,000 total input tokens comes from re-sending old chat history?
77% (102,600 of 133,000 input tokens). Because stateless LLM APIs require resending the full history every turn, history tokens grow quadratically as T(T - 1) / 2, which is 190 re-sent turn-pairs over 20 turns.
You turn on 90% prefix caching on that 20-turn chat ($168.33 per 1,000 chats). Next you add per-turn rolling summarization after turn 4, cutting total input tokens from 115,000 to 52,900. Does your bill go down or up?
It goes up 45%, from $168.33 to $244.47 per 1,000 chats. Rewriting the rolling summary every turn mutates the history prefix, busting the 90% cache and turning 112,100 discounted cached tokens into 38,000 full-price uncached tokens.
Output tokens are only 5.9% of total tokens in our baseline 20-turn chat (8,400 of 141,400). Why does capping output from 420 to 140 tokens still slash the Stage 3 bill by 55% ($244.47 to $109.23)?
Two compounding multipliers: decode tokens cost 3x to 5x more than input tokens because decode is memory-bandwidth bound, and every output token generated on turn t gets re-read as input on subsequent turns.

The core idea

Token optimization is not "write shorter prompts." Every LLM bill is the product of four measurable quantities: how many input tokens you send, what fraction hits a warm prefix cache, how many output tokens you decode, and which model tier and billing mode serves each call.

Engineers optimize tokens in strict order of leverage and risk. You measure a per-endpoint token ledger first, then strip waste and exploit KV prefix reuse before touching model quality, and only consider self-hosting GPUs once software levers are exhausted and steady utilization clears break-even.

Memory hook

M-S-R-G-C-B-F-S -> "My Server Runs Great: Cut Bloat, Fast Savings." Measure, Send less, Reuse, Generate less, Cheaper models, Batch, Fewer calls, Self-host.

How it works

1. Measure: the token accounting equation

Before changing a single prompt, build a token ledger: a structured log recording uncached input tokens, cached input tokens, output tokens, retry count, and model tier for every request. Track cost per completed task rather than cost per 1M tokens, because a cheap model that fails and triggers three agent retries can cost more than one clean frontier call.

Cost = (N_in_uncached * P_in + N_in_cached * d_cache * P_in + N_out * P_out) / 1,000,000
where d_cache is the cached-read multiplier (e.g., 0.10 for a 90% discount)

From D02 Tokenization, remember that whitespace, verbose JSON keys, and Markdown boilerplate all become tokens. Auditing your P95 requests almost always reveals one endpoint or one bloated tool schema driving most of the bill.

2. Send less: why multi-turn chat is quadratic

LLM inference APIs are stateless. On turn t (0-indexed), you resend the system prompt S, all previous user messages U and model outputs O, plus the new user message. Summing across T turns gives an exact closed-form input token count:

N_in(T) = T * (S + U) + (U + O) * T * (T - 1) / 2

The second term grows as O(T^2). For 20 turns with S = 1400, U = 120, and O = 420, static overhead is 30,400 tokens while re-sent history is 540 * 190 = 102,600 tokens (77% of input). Cutting unused tool definitions (dynamic tool loading) shrinks S; bounding history with a sliding window plus summary shrinks the quadratic term to O(T).

Check: Why does a 20-turn chat resend 190 turn-pairs of history instead of 20?
Turn 0 sends 0 prior turns, turn 1 sends 1, turn 2 sends 2, up to turn 19 sending 19. The arithmetic sum 0 + 1 + ... + 19 equals T(T - 1) / 2 = 20 * 19 / 2 = 190 turn-pairs.

3. Reuse: prefix caching vs semantic caching

From K05 Prefill vs decode, causal self-attention means token k attends only to tokens 1..k. If two requests share an identical token prefix from byte 0, the server can reuse the precomputed KV cache for that prefix and skip prefill compute. Providers pass this savings on as 50% to 90% off cached input reads (see G07 Prompt caching for TTL and write-premium mechanics).

The catch is strict prefix matching: putting a dynamic timestamp, request UUID, or unsorted JSON keys at byte 0 invalidates 100% of the cache. Always order prompts from most static to most dynamic (system prompt, sorted tool schemas, few-shot examples, history, then live user input). By contrast, semantic caching embeds the query and returns a stored answer when cosine similarity clears a threshold. It skips the entire LLM call for static FAQs, but risks serving stale or cross-tenant wrong answers if keys are not tightly scoped.

4. Generate less: the double penalty of output tokens

Decode generates one token per forward pass and reloads the entire model weights from HBM each step (K05), making it memory-bandwidth bound. That is why APIs price output tokens 3x to 5x higher than input tokens. In multi-turn chat or agent loops, every verbose output token pays a second tax: it is appended to history and re-read on every future turn.

Enforce tight output budgets with max_tokens, stop sequences, terse structured outputs (enums or compact JSON instead of prose), and turn off extended reasoning or chain-of-thought on classification and extraction calls where it adds zero accuracy.

Check: Why can adding per-turn rolling summarization raise your API bill when prefix caching is already active?
Because rewriting the summary on every turn changes the early tokens of the conversation history, which busts the prefix cache on every call and forces you to pay 100% uncached input price instead of 10% cached read price.

5. Cheaper models, batch, and fewer calls

Model routing and cascades (G17) send easy intents to a small model priced at roughly 0.10x of frontier, escalating to frontier only when confidence is low. If you route share r to a cheap model of relative cost c with escalation rate e (paying cheap plus frontier on retries), the effective cost multiplier is:

M_route = (1 - r) + r * (c + e)

For r = 0.75, c = 0.10, and e = 0.05, M_route = 0.3625 (a 63.8% cut). Next, move non-interactive jobs (offline evals, nightly summaries, voice-call post-processing) to an async Batch API for a flat 50% discount under a 24-hour SLA. Finally, make fewer calls: merge sequential prompt chains into one structured call, cap agent tool retries, and replace LLM parsing with plain regex or deterministic code.

6. Self-host: the utilization break-even

APIs bill per token; self-hosting bills per GPU-hour 24/7 even when traffic is zero (G19 Cost modeling). Your break-even throughput is Hourly_GPU_Cost / (Blended_API_Cost_Per_Token * 3600). If traffic is spiky (for example, clinic voice calls during business hours and empty overnight), idle GPU hours quickly erase any per-token advantage unless you autoscale aggressively or reserve GPUs only for the steady baseload while bursting peaks to an API.

Check: A router sends 75% of turns to a 0.10x cheap model, and 5% of those cheap turns escalate to the frontier model. What is the effective cost multiplier?
0.25 + 0.75 * (0.10 + 0.05) = 0.25 + 0.1125 = 0.3625, which is a 63.75% cost reduction compared to sending 100% of turns to the frontier model.

Kata: Token ledger

Simulates a 20-turn multi-turn chat, exposes quadratic history growth, and stacks 6 optimization levers one by one to print the real bill per 1,000 chats.

Run

python kata.py

kata.py

"""Token ledger: simulate a 20-turn chat, apply 6 levers, print the bill."""

TURNS = 20
SYS_BASE, SYS_TRIM = 1400, 500
USER_TOK = 120
OUT_BASE, OUT_CAP = 420, 140
WINDOW, SUMMARY_TOK = 4, 180

# Illustrative frontier baseline ($ per 1M tokens, 5:1 output-to-input ratio)
IN_PRICE, OUT_PRICE = 3.00, 15.00
CACHE_MULT = 0.10     # 90% discount on cached prefix reads
CHEAP_MULT = 0.10     # Small model at 10% of frontier price
BATCH_MULT = 0.50     # 50% discount for async batch workloads

# Break-it switches (flip one to True and re-run)
BREAK_CACHE_BUST = False   # Dynamic timestamp at byte 0 of system prompt
BREAK_VERBOSE_OUT = False  # Remove output cap (2x verbose replies)
BREAK_BAD_ROUTER = False   # Weak router: 20% cheap share + 25% fallback retries


def simulate(sys_tok, out_tok, use_cache=False, compact=False,
             route=False, batch=False):
    uncached_in = cached_in = total_out = 0
    for t in range(TURNS):
        turn_pair = USER_TOK + out_tok
        if compact and t > WINDOW:
            hist = SUMMARY_TOK + WINDOW * turn_pair
            prefix_cacheable = sys_tok  # rolling summary shifts history prefix
        else:
            hist = t * turn_pair
            prefix_cacheable = sys_tok + hist

        if use_cache and t > 0 and not BREAK_CACHE_BUST:
            c_in = prefix_cacheable
            u_in = (sys_tok + hist + USER_TOK) - c_in
        else:
            c_in = 0
            u_in = sys_tok + hist + USER_TOK

        uncached_in += u_in
        cached_in += c_in
        total_out += out_tok

    cost = (
        uncached_in * IN_PRICE
        + cached_in * IN_PRICE * CACHE_MULT
        + total_out * OUT_PRICE
    ) / 1_000_000

    if route:
        cheap_share = 0.20 if BREAK_BAD_ROUTER else 0.75
        retry_rate = 0.25 if BREAK_BAD_ROUTER else 0.05
        # Cheap turns pay cheap price; escalated ones also pay frontier
        eff_mult = (1 - cheap_share) + cheap_share * (CHEAP_MULT + retry_rate)
        cost *= eff_mult

    if batch:
        cost *= BATCH_MULT

    return uncached_in, cached_in, total_out, cost


def main():
    out_cap = OUT_BASE * 2 if BREAK_VERBOSE_OUT else OUT_CAP
    stages = [
        ("0. Baseline (raw 20-turn)",   SYS_BASE, OUT_BASE, False, False, False, False),
        ("1. Trim prompt + schemas",    SYS_TRIM, OUT_BASE, False, False, False, False),
        ("2. + Prefix caching (90%)",   SYS_TRIM, OUT_BASE, True,  False, False, False),
        ("3. + Rolling compaction",     SYS_TRIM, OUT_BASE, True,  True,  False, False),
        ("4. + Output cap (140 tok)",   SYS_TRIM, out_cap,  True,  True,  False, False),
        ("5. + Model routing (75/25)",  SYS_TRIM, out_cap,  True,  True,  True,  False),
        ("6. + Batch API (async 50%)",  SYS_TRIM, out_cap,  True,  True,  True,  True),
    ]

    print(f"20-turn chat token ledger (illustrative ${IN_PRICE:.2f}/${OUT_PRICE:.2f} per 1M in/out)")
    print(f"Flags: cache_bust={BREAK_CACHE_BUST} verbose_out={BREAK_VERBOSE_OUT} bad_router={BREAK_BAD_ROUTER}\n")
    hdr = f"{'Stage':<28} {'UncachIn':>9} {'CachIn':>9} {'OutTok':>7} {'$/1k chats':>11} {'Saved':>7}"
    print(hdr)
    print("-" * len(hdr))

    base_cost = None
    for name, s_tok, o_tok, cache, comp, route, batch in stages:
        u_in, c_in, o_all, cost = simulate(s_tok, o_tok, cache, comp, route, batch)
        if base_cost is None:
            base_cost = cost
        saved = (1.0 - cost / base_cost) * 100.0
        print(f"{name:<28} {u_in:>9,} {c_in:>9,} {o_all:>7,} ${cost*1000:>10.2f} {saved:>6.1f}%")


if __name__ == "__main__":
    main()

What to notice

  2. Prefix caching alone drops the bill by 67.9% ($471.00 to $168.33) by moving 112,100 input tokens onto the 0.10x cached read rate.

Break it
  1. Cache-busting timestamp. Set BREAK_CACHE_BUST = True (simulating a live timestamp at byte 0 of the system prompt). Predict what happens to Stage 2 and whether Stage 3 now saves money instead of costing money, then run.
  2. Unbounded verbose output. Reset the first flag and set BREAK_VERBOSE_OUT = True (doubling output to 840 tokens/turn). Predict how much Stage 4 jumps when both decode cost and history re-reads expand, then run.

Stretch. Replace per-turn rolling compaction with checkpoint compaction (compact only on turns 8 and 16 so the prefix stays immutable and cacheable between checkpoints). Measure whether Stage 3 now beats Stage 2's $168.33.

Scenario: Your clinic voice-AI scheduling assistant handles 10,000 15-turn calls/day and the LLM bill tripled after a release. How do you diagnose and cut the bill by over 70% without hurting booking accuracy?
  1. Pull the token ledger first: compare pre-release vs post-release uncached input, cached input, output tokens, and retries per call to pinpoint what tripled.
  2. Check prefix cache hit rate: a common regression is injecting live caller ID or current time at the top of the system prompt. Move caller metadata to the end so the static clinic instructions and EHR tool schemas cache at byte 0.
  3. Trim unused schemas and cap spoken output: load only scheduling tools during booking (not billing tools) and enforce terse 1 to 2 sentence spoken replies via max_tokens and concise prompt rules.
  4. Route simple turns and batch post-call work: route greetings, confirmations, and slot readbacks to a small fast model (keeping frontier for complex rescheduling), and move post-call QA summaries and evals to the 50% Batch API.
  5. Verify on a golden call eval set: confirm booking accuracy and slot-extraction F1 hold steady while tracking cost per completed booking.

Traps

Each one sounds right. Say what is wrong with it before you open it.

"Cutting our system prompt in half will cut our multi-turn chat bill in half."
Wrong. In a 20-turn chat, quadratic history growth (T(T - 1) / 2) dominates total input tokens (77% in our kata). Cutting the system prompt by 64% only saved 10.3% of the bill.
"Adding rolling summarization on every turn always lowers your token bill."
Wrong. If prefix caching is enabled, mutating a rolling summary on every turn invalidates the cached history prefix. In our kata, cutting input tokens by 54% this way raised the bill by 45% ($168.33 to $244.47).
"Output tokens are under 10% of our token count, so optimize input tokens first and ignore output."
Wrong. Output tokens carry a 3x to 5x price multiplier (decode is memory-bandwidth bound) AND every output token gets re-read as input on every later turn. Capping output cut our Stage 3 bill by 55%.
"Once your API bill hits $10k a month, self-hosting an open-weights model is always cheaper."
Wrong. Self-hosting charges 24/7 per GPU-hour regardless of traffic. If traffic is spiky and average GPU utilization sits below break-even (often 30% to 40%), plus engineering ops overhead, self-hosting costs more than pay-per-token APIs.

Walk through the 8 token optimization levers in execution order and explain why you start with measurement.
Measure, send less, reuse, generate less, cheaper models, batch, fewer calls, self-host. You measure a per-endpoint token ledger first because without knowing whether input, cache misses, output, or retries dominate, you optimize the wrong slice.
Follow-upWhich lever gives the biggest zero-quality-risk win in a multi-turn chat? Prefix caching (50% to 90% off repeated input with identical model outputs).
Why does multi-turn chat input token usage grow quadratically with turn count?
LLM APIs are stateless, so turn t resends all prior turns 0 through t - 1. Summing 0 + 1 + ... + (T - 1) yields T(T - 1) / 2 turn-pairs, which is O(T^2).
Follow-upHow many turn-pairs are re-sent in a 20-turn chat? 20 * 19 / 2 = 190 turn-pairs.
Why does prefix caching stop working at the first differing token in a prompt?
Under causal self-attention, each token's key and value states depend on every token before it. One changed token at position k invalidates the KV cache for position k and every token after it.
Follow-upWhat common coding mistake silently drops prefix cache hits to 0%? Putting a dynamic timestamp, request UUID, or unsorted dictionary keys at byte 0 of the system prompt.
Why are output tokens typically 3x to 5x more expensive than input tokens, and what is their second hidden cost in chat?
Prefill processes input tokens in parallel (compute-bound), whereas decode generates one token per forward pass and reloads weights from HBM each step (memory-bandwidth bound). The second cost is that every output token is appended to history and re-read on all later turns.
Follow-upName three concrete ways to reduce output tokens without switching models. Set max_tokens, use concise JSON/enum schemas instead of prose, and disable chain-of-thought on simple extraction tasks.
When does rolling history compaction actually increase your API bill, and how do you fix it?
When prefix caching is active, rewriting a rolling summary every turn busts the cached history prefix, swapping 0.10x cached tokens for 1.0x uncached tokens. Fix it with checkpoint compaction (compact every N turns so the prefix stays immutable between checkpoints).
Follow-upBesides cost, what quality risk does aggressive compaction introduce? Loss of exact identifiers, constraints, or earlier user preferences needed later in the thread.
How do you calculate whether a model router with fallback retries actually saves money?
Compute M_route = (1 - r) + r * (c + e), where r is cheap-model share, c is cheap-to-frontier price ratio, and e is escalation rate. If e is high, you pay both models and add latency, eroding savings.
What workloads fit the async Batch API, and why can you not use it for live chat?
Offline evals, nightly summaries, bulk enrichment, and post-call QA fit Batch API (flat 50% discount). Live chat cannot use it because Batch API trades real-time latency for an asynchronous 24-hour SLA.
Why should you measure cost per completed task instead of cost per 1M tokens?
A cheaper model or over-trimmed prompt can fail tool calls or hallucinate, triggering agent retries or user re-prompts. Lower price per token with 3x retries raises total cost per successful outcome.
When does self-hosting beat pay-per-token APIs, and what breaks the math?
Self-hosting wins when steady, high GPU utilization pushes hourly GPU cost per token below API pricing (or when data residency requires it). Spiky traffic with idle overnight GPUs and engineering ops overhead break the math.

Mixed review

Three questions from earlier topics. Nobody tells you the topic in an interview.

D02: Why do verbose JSON keys, repeated indentation, or UUIDs inflate token counts faster than plain prose?
Subword tokenizers (like BPE) split punctuation, whitespace runs, and high-entropy random strings (such as UUIDs) into many short subword tokens rather than single whole-word tokens.
K05: Why is prefill compute-bound while decode is memory-bandwidth bound, and how does that show up on your LLM bill?
Prefill processes all prompt tokens in parallel matrix multiplies (high arithmetic intensity), while decode generates one token at a time and reloads model weights from HBM per token. APIs reflect that bottleneck by pricing output tokens 3x to 5x higher than input tokens.
L03: When shipping a token optimization (like prompt trimming or model routing), why must you run a fixed golden eval set instead of checking five examples by eye?
Spot-checking hides tail regressions on rare tool schemas or edge cases; a fixed golden eval set quantifies quality delta alongside cost per completed task so you prove savings did not silently break accuracy.

  • 4. Generate less: Decode is memory-bandwidth bound (3x to 5x input price) and re-enters chat history; enforce max_tokens, terse schemas, and disable unnecessary CoT.
  • 5. Cheaper models: Route 70% to 80% of easy turns to small models (0.10x price); track effective multiplier (1 - r) + r * (c + e) and escalation rate e.
  • 6. Batch: Move non-interactive jobs (evals, nightly summaries) to async Batch API for a flat 50% discount under a 24-hour SLA.
  • 7. Fewer calls: Merge multi-step chains into one structured call, cap agent tool retries, and use deterministic code instead of LLMs for parsing.
  • 8. Self-host: Fixed 24/7 GPU-hour billing beats pay-per-token APIs only once software levers are maxed out and steady utilization clears break-even.
Important things to remember
  • Spine (M-S-R-G-C-B-F-S): Measure, Send less, Reuse, Generate less, Cheaper models, Batch, Fewer calls, Self-host.
  • Quadratic history math: N_in(T) = T(S + U) + (U + O) * T(T - 1) / 2. At T = 20, you resend 190 turn-pairs.
  • Cache-busting trap: Putting a timestamp at byte 0 or rewriting a rolling summary every turn invalidates prefix caching and can raise the bill.
  • Double output tax: Output tokens cost 3x to 5x input AND get re-read as input on every later turn.
  • North-star metric: Optimize cost per completed task against a fixed golden eval set, never raw cost per 1M tokens.
