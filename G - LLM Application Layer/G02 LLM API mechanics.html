LLM API mechanics

How a stateless HTTP call carries messages, roles, and decoding parameters to an LLM provider, streams tokens back over Server-Sent Events, and reports stop reasons and token usage. Structured output grammars live in G05, tool schemas and execution loops in G06, and retries or circuit breakers in G21.

Before you read

You enable streaming on an OpenAI Chat Completions call and log usage from every response. In the kata below, why did openai_no_usage report 0 accounted tokens even though it returned a full 8-token JSON object with HTTP 200?
When stream: true is set on OpenAI Chat Completions, the API omits the usage object by default. Unless you explicitly pass stream_options: {"include_usage": true}, no final usage chunk arrives before [DONE], so your billing logger silently records 0 tokens while the provider bills all 1,208 tokens.
In the kata, anth_truncated returned HTTP 200, billed 1,204 tokens, and crashed json.loads(). What single field in the stream tells your code to reject that payload before parsing?
The stop reason: stop_reason: "max_tokens" on Anthropic (or finish_reason: "length" on OpenAI). HTTP 200 only means the transport succeeded, not that the model finished its thought.
Both providers processed 1,200 total prompt tokens, of which 900 were cached. Why does OpenAI report prompt_tokens: 1200 while Anthropic reports input_tokens: 300?
OpenAI's prompt_tokens is inclusive of prompt_tokens_details.cached_tokens (300 uncached + 900 cached = 1,200). Anthropic's input_tokens counts only uncached tokens after the last cache breakpoint, so you must add cache_read_input_tokens (and cache_creation_input_tokens) to get total prompt size.

The core idea

Every standard LLM API call is a stateless HTTP POST carrying the entire conversation history as a typed array of messages plus decoding parameters. The server holds no session memory between turns (unless you opt into a stateful thread or cache layer), so turn 10 re-sends turns 1 through 9 as input tokens every time.

Because autoregressive decoding emits one token at a time, production clients request Server-Sent Events (SSE) instead of waiting for one giant JSON body. Your client is responsible for three wire contracts: assembling partial delta frames into complete text or tool JSON, branching on the final stop reason rather than trusting HTTP 200, and normalizing provider-specific usage fields so billing and observability stay accurate.

Memory hook

M-P-H-S-R-U ("My Prompt Hits Stream, Reason, Usage"): Messages (stateless history + roles), Parameters (budget + sampling), HTTP prefill (TTFT), SSE deltas (TPOT + buffering), stop Reason (complete vs truncated vs tool), Usage (uncached + cached + output).

How it works

Stateless messages and role hierarchy

Chat APIs model a turn as an ordered list of {role, content} objects. Roles establish instruction priority: system (or developer on newer OpenAI models) sets policy and persona, user carries untrusted caller input, assistant holds prior model replies or tool requests, and tool returns tool execution results. Because HTTP is stateless, multi-turn apps must resend the whole transcript on every request, so input token count grows quadratically across a long conversation unless you trim or summarize history.

Provider schemas diverge in small ways that break naive wrappers. OpenAI puts the system prompt inside messages[0], whereas Anthropic hoists system to a top-level request parameter and enforces strict user / assistant alternation (consecutive user messages must be merged, and tool results travel inside a user message block).

Request parameters and output budgets

Beyond model and messages, four parameter groups govern generation. Sampling controls (temperature, top_p, covered in D10) reshape the next-token distribution; set one, not both, and note Anthropic rejects requests that set both on newer models. Stop controls (stop or stop_sequences) halt generation cleanly the instant a delimiter string is emitted.

The budget cap (max_tokens or OpenAI's max_completion_tokens) is a hard circuit breaker, not a brevity hint. The model does not see max_tokens in its prompt, so it will happily start a JSON object at token 48 and get sliced in half at token 50. On reasoning models, max_completion_tokens covers hidden reasoning tokens plus visible output, so a small cap can return zero visible text while still hitting length.

Check: Why does setting max_tokens: 50 fail as a way to ask the model for concise JSON responses?
Because max_tokens is a server-side hard cutoff invisible to the model during decoding. The model plans a normal-length reply and gets cut mid-object at token 50, producing invalid JSON with finish_reason: "length" while still billing every prompt and partial output token.

Wire protocol: SSE streaming and latency math

Standard LLM APIs stream over Server-Sent Events (Content-Type: text/event-stream) on a regular HTTP POST response rather than WebSockets. Token generation is unidirectional after the request body is sent, so SSE works cleanly through standard HTTP load balancers, proxies, and TLS without connection upgrade overhead. Each SSE frame ends with a blank line (\n\n) and carries data: JSON lines, optionally preceded by a named event: line.

Streaming does not speed up total generation time, it decouples perceived latency from output length. If prefill takes time T_prefill and decoding emits N_out tokens at TPOT per token, then:

TTFT = T_network + T_prefill + TPOT
E2E  = TTFT + (N_out - 1) * TPOT

Without streaming, the caller waits the full E2E before seeing byte 1. For a voice AI clinic agent piping LLM text into TTS, streaming cuts silence from seconds to a few hundred milliseconds. On the wire, however, TCP packets can split a single SSE frame or a multi-byte UTF-8 character across chunks, and tool-call arguments arrive as raw JSON string fragments. Always decode with an incremental UTF-8 decoder, split on \n\n frame boundaries, and buffer tool argument strings until the stop reason arrives.

Check: Why does SSE streaming lower TTFT without lowering total E2E latency?
Prefill time and autoregressive decode time per token (TPOT) are unchanged on the server. Streaming delivers token 1 right after prefill (TTFT) instead of buffering all N_out tokens until the last token finishes (E2E).

Stop reasons: the only contract for completion

Never assume HTTP 200 means a valid, finished answer. Every provider returns an explicit stop reason that your application state machine must branch on:

Normal completion : OpenAI "stop"           | Anthropic "end_turn"
Token cap hit     : OpenAI "length"         | Anthropic "max_tokens"
Tool invocation   : OpenAI "tool_calls"     | Anthropic "tool_use"
Safety / refusal  : OpenAI "content_filter" | Anthropic "refusal"
Custom delimiter  : OpenAI "stop"           | Anthropic "stop_sequence"

Treating length or max_tokens like a normal stop causes silent truncation bugs: broken JSON, missing closing tags, or half-written clinical instructions. Treating tool_calls like plain text leaves the user staring at an empty string because content is null while arguments sit in tool_calls.

Usage accounting and provider schema traps

Accurate cost attribution requires normalizing every provider's usage payload into one internal ledger: uncached_input, cached_input, cache_write, output, and reasoning tokens. Three traps silently break cost dashboards in production.

First, OpenAI's prompt_tokens includes prompt_tokens_details.cached_tokens, so uncached input is prompt_tokens - cached_tokens. Anthropic's input_tokens excludes cache_read_input_tokens and cache_creation_input_tokens, so total prompt size is their sum. Swapping those formulas either double-bills cached tokens or produces negative uncached counts. Second, OpenAI streaming omits usage unless stream_options.include_usage is true, and when enabled it arrives in an extra trailing chunk where choices is empty ([]), which crashes naive parsers that index choices[0] unconditionally. Third, if a user cancels mid-stream and closes the socket, you never receive the final usage chunk, yet the provider still bills full prompt prefill plus every token generated before cancellation propagated.

Check: Your wrapper indexes chunk.choices[0].delta on every OpenAI SSE chunk. What happens the moment you turn on stream_options: {"include_usage": true}?
It throws an IndexError on the final usage chunk, because OpenAI sends usage in a trailing SSE frame with "choices": [] right before data: [DONE].

Kata: Dual-provider SSE parser and usage ledger

Simulates OpenAI and Anthropic SSE wire formats with real wall-clock timers, normalizes stop reasons and cached/uncached token usage, and exposes three production failure modes.

kata.py

import json, time

INCLUDE_USAGE = True        # Break-it 1: set False -> OpenAI logs 0 tokens
MAX_TOKENS = 32             # Break-it 2: set 5 -> truncates JSON mid-stream
BUFFER_TOOL_DELTAS = True   # Break-it 3: set False -> parses partial tool JSON

TOKENS = ['{"status":', ' "ok",', ' "slot":', ' "09:30",', ' "clinic":', ' "north",', ' "confirmed":', ' true}']
TOOL_ARGS = ['{"patient_id":', ' "p_42",', ' "action":', ' "book"}']

def sse_openai(tokens, max_tok, prefill_s, tpot_s, include_usage, tool_mode=False):
    time.sleep(prefill_s)
    emitted = tokens[:max_tok]
    reason = "length" if len(tokens) > max_tok else ("tool_calls" if tool_mode else "stop")
    for tok in emitted:
        time.sleep(tpot_s)
        delta = {"tool_calls": [{"arguments": tok}]} if tool_mode else {"content": tok}
        yield "data: " + json.dumps({"choices": [{"delta": delta, "finish_reason": None}]}) + "\n\n"
    yield "data: " + json.dumps({"choices": [{"delta": {}, "finish_reason": reason}]}) + "\n\n"
    if include_usage:
        usage = {"prompt_tokens": 1200, "prompt_tokens_details": {"cached_tokens": 900}, "completion_tokens": len(emitted)}
        yield "data: " + json.dumps({"choices": [], "usage": usage}) + "\n\n"
    yield "data: [DONE]\n\n"

def sse_anthropic(tokens, max_tok, prefill_s, tpot_s):
    time.sleep(prefill_s)
    yield "event: message_start\ndata: " + json.dumps({"message": {"usage": {"input_tokens": 300, "cache_read_input_tokens": 900}}}) + "\n\n"
    emitted = tokens[:max_tok]
    for tok in emitted:
        time.sleep(tpot_s)
        yield "event: content_block_delta\ndata: " + json.dumps({"delta": {"type": "text_delta", "text": tok}}) + "\n\n"
    reason = "max_tokens" if len(tokens) > max_tok else "end_turn"
    yield "event: message_delta\ndata: " + json.dumps({"delta": {"stop_reason": reason}, "usage": {"output_tokens": len(emitted)}}) + "\n\n"
    yield "event: message_stop\ndata: {}\n\n"

def consume(provider, stream, buffer_tools=True):
    t0, ttft, text, tool_buf = time.perf_counter(), None, [], []
    stop_reason, in_tok, cached_tok, out_tok, chunks, parse_err = None, 0, 0, 0, 0, None
    for frame in stream:
        ev, data = None, ""
        for line in frame.strip().splitlines():
            if line.startswith("event:"): ev = line[6:].strip()
            elif line.startswith("data:"): data = line[5:].strip()
        if not data or data == "[DONE]": continue
        obj = json.loads(data)
        if provider == "openai":
            if obj.get("usage"):
                u = obj["usage"]
                in_tok = u["prompt_tokens"] - u["prompt_tokens_details"]["cached_tokens"]
                cached_tok = u["prompt_tokens_details"]["cached_tokens"]
                out_tok = u["completion_tokens"]
            if obj["choices"]:
                c = obj["choices"][0]
                if c.get("finish_reason"): stop_reason = c["finish_reason"]
                d = c.get("delta", {})
                if d.get("content"):
                    if ttft is None: ttft = time.perf_counter() - t0
                    text.append(d["content"]); chunks += 1
                if d.get("tool_calls"):
                    if ttft is None: ttft = time.perf_counter() - t0
                    frag = d["tool_calls"][0]["arguments"]
                    tool_buf.append(frag); chunks += 1
                    if not buffer_tools and parse_err is None:
                        try: json.loads(frag)
                        except json.JSONDecodeError: parse_err = "partial_tool_json"
        else:
            if ev == "message_start":
                u = obj["message"]["usage"]
                in_tok, cached_tok = u["input_tokens"], u["cache_read_input_tokens"]
            elif ev == "content_block_delta":
                if ttft is None: ttft = time.perf_counter() - t0
                text.append(obj["delta"]["text"]); chunks += 1
            elif ev == "message_delta":
                stop_reason, out_tok = obj["delta"]["stop_reason"], obj["usage"]["output_tokens"]
    total = time.perf_counter() - t0
    tpot = ((total - ttft) / max(chunks - 1, 1)) if ttft is not None else 0.0
    payload = "".join(tool_buf if tool_buf else text)
    if parse_err is None:
        try: json.loads(payload)
        except json.JSONDecodeError: parse_err = "truncated_json"
    return {
        "ttft_ms": round((ttft or 0) * 1000, 1), "e2e_ms": round(total * 1000, 1),
        "tpot_ms": round(tpot * 1000, 1), "stop": stop_reason,
        "in_tok": in_tok, "cached_tok": cached_tok, "out_tok": out_tok,
        "acct_total": in_tok + cached_tok + out_tok, "err": parse_err or "ok",
    }

runs = [
    ("openai_ok",       "openai",    sse_openai(TOKENS, MAX_TOKENS, 0.070, 0.012, INCLUDE_USAGE)),
    ("anthropic_ok",    "anthropic", sse_anthropic(TOKENS, MAX_TOKENS, 0.095, 0.015)),
    ("openai_no_usage", "openai",    sse_openai(TOKENS, MAX_TOKENS, 0.070, 0.012, False)),
    ("anth_truncated",  "anthropic", sse_anthropic(TOKENS, 4, 0.095, 0.015)),
    ("openai_tool_buf", "openai",    sse_openai(TOOL_ARGS, MAX_TOKENS, 0.070, 0.012, INCLUDE_USAGE, True)),
]
print(f"{'run':16} {'ttft_ms':>7} {'tpot_ms':>7} {'e2e_ms':>7} {'stop':11} {'in':>4} {'cache':>5} {'out':>3} {'acct':>5} {'parse'}")
for name, prov, stream in runs:
    r = consume(prov, stream, BUFFER_TOOL_DELTAS)
    print(f"{name:16} {r['ttft_ms']:7.1f} {r['tpot_ms']:7.1f} {r['e2e_ms']:7.1f} {r['stop']:11} {r['in_tok']:4d} {r['cached_tok']:5d} {r['out_tok']:3d} {r['acct_total']:5d} {r['err']}")

Traps

Each one sounds right. Say what is wrong with it before you open it.

"Streaming makes the LLM generate tokens faster, so total request latency drops."
Wrong. Streaming does not change server prefill time or TPOT, so total E2E latency is essentially identical. Streaming lowers perceived latency from E2E down to TTFT by delivering token 1 right after prefill.
"If the LLM API returns HTTP 200, the response finished cleanly and is safe to pass straight to json.loads."
Wrong. Truncation (length / max_tokens), tool calls (tool_calls / tool_use), and safety refusals (content_filter) all return HTTP 200. You must check the stop reason before parsing.
"Setting max_tokens=100 tells the model to write a concise 100-token summary."
Wrong. The model cannot see max_tokens during decoding. It is a hard server cutoff that slices the output mid-sentence or mid-JSON at token 100. Ask for brevity in the prompt and set max_tokens as a safety ceiling.
"OpenAI prompt_tokens and Anthropic input_tokens measure the same thing, so you can sum them directly in one billing table."
Wrong. OpenAI prompt_tokens includes cached prompt tokens, whereas Anthropic input_tokens excludes cache_read_input_tokens and cache_creation_input_tokens. Treating them identically skews both cache-hit rate and dollar cost.

Question bank

Answer aloud, then open. Grade yourself honestly.

Why do LLM chat APIs require sending the entire conversation history on every turn?
Standard chat endpoints are stateless HTTP POSTs with no server-side session memory. The model needs every prior turn in the prompt to compute attention over context, so input tokens grow with conversation length unless truncated or summarized.
Follow-upDoes prompt caching eliminate resending the messages over the network? No. You still send the full messages array in the HTTP body; caching reuses server-side KV state for matching prefixes to cut prefill compute and cost.
How do OpenAI and Anthropic differ in how they represent system prompts and message turns?
OpenAI places the system or developer role inside the messages array. Anthropic hoists system to a top-level request field and requires strict alternating user and assistant messages, with tool results sent inside a user turn.
Why do LLM providers use Server-Sent Events (SSE) instead of WebSockets for text streaming?
Text generation is unidirectional after the request POST is sent. SSE runs over standard HTTP/1.1 or HTTP/2, works cleanly through existing load balancers and proxies without upgrade handshakes, and has trivial line-based framing.
Follow-upWhen would you actually choose WebSockets or WebRTC instead? For bidirectional, full-duplex real-time audio (voice agents with barge-in), where the client streams audio frames up while receiving audio frames down simultaneously.
Write the formula linking TTFT, TPOT, output tokens, and E2E latency, and explain what each term depends on.
E2E = TTFT + (N_out - 1) * TPOT. TTFT is dominated by network RTT plus prefill compute (scales with uncached prompt length and KV cache misses). TPOT is dominated by memory-bandwidth-bound autoregressive decode per token.
What happens on OpenAI Chat Completions when you set stream: true without stream_options.include_usage?
OpenAI omits token usage from every SSE chunk, so your client logs 0 tokens while still getting billed. Turning on include_usage: true emits one final chunk with choices: [] and the full usage object right before data: [DONE].
Follow-upWhat breaks in a naive streaming loop when you enable include_usage? Indexing chunk.choices[0] throws an IndexError on that trailing usage-only chunk because choices is empty.
How do you normalize cached and uncached input tokens across OpenAI and Anthropic?
For OpenAI: uncached = prompt_tokens - prompt_tokens_details.cached_tokens, cached = cached_tokens. For Anthropic: uncached = input_tokens, cached = cache_read_input_tokens, plus track cache_creation_input_tokens separately because cache writes have a different price.
Name the four main stop reasons and the exact action your application should take for each.
stop/end_turn: parse and return to user. length/max_tokens: reject incomplete output, retry with larger budget or continue prompt. tool_calls/tool_use: execute buffered tool arguments and send tool result turn. content_filter/refusal: surface safe fallback without retrying blindly.
Follow-upWhy is max_completion_tokens especially dangerous on reasoning models? Hidden reasoning tokens count toward the same cap, so a tight budget can burn all tokens thinking and emit 0 visible characters with finish_reason: "length".
Why do streamed tool calls fail if you parse JSON on each incoming SSE chunk?
The provider streams tool arguments as raw string fragments (for example {"patient_id": then "p_42"}), which are invalid JSON individually. You must concatenate fragments per tool call index and call json.loads only after the terminal stop reason arrives.
A user closes the browser tab halfway through a 500-token stream. Why does your internal token ledger disagree with the provider invoice?
Closing the socket prevents your server from receiving the final SSE usage chunk (or Anthropic's message_delta), so your logger records 0 output tokens. Meanwhile the provider bills full prompt prefill plus all tokens generated before cancellation reached the inference engine.
Follow-upHow do you close that accounting gap? On stream abort or timeout, emit a fallback usage record using a local tokenizer estimate for the prompt plus the chunks already received.
Why can a single SSE stream suddenly deliver all tokens in one burst after a 10-second freeze in production?
An intermediate reverse proxy (such as Nginx or an API gateway) is buffering the HTTP response body until its buffer fills or the upstream closes. Disable proxy buffering with X-Accel-Buffering: no and Cache-Control: no-cache, and flush after every chunk.

  • Three streaming traps: missing include_usage (0 logged tokens + choices: [] chunk), mid-JSON truncation on max_tokens, and unbuffered tool-call deltas or aborted streams.

Mixed review

Three questions from earlier topics. Nobody tells you the topic in an interview.

D10: Why does setting both temperature and top_p at the same time make decoding harder to reason about?
Temperature rescales all logits before softmax (flattening or sharpening the whole distribution), while top-p truncates the tail after softmax to cumulative probability p. Changing both interacts nonlinearly, so best practice is to tune one and leave the other at default.
D11: How do token logprobs let you detect low-confidence extractions without running a second judge model?
Logprobs expose the log-probability of each emitted token. Taking the exponent of the minimum or mean logprob over critical field tokens flags uncertain extractions (for example, p < 0.6 on a date or ID) at zero extra inference cost.
A02: Why should an async Python service handling 200 concurrent SSE LLM streams avoid blocking calls inside the event loop?
Asyncio runs on a single thread cooperatively yielding at await points. One synchronous network call or heavy CPU loop stalls all 200 open SSE streams simultaneously, spiking TTFT and causing upstream timeouts.

Short notes

Quick-memorization cheat sheet covering every subtopic on this page and the key facts to remember cold.

All subtopics on this page

  • Messages and roles: Stateless HTTP POST re-sending full history every turn; roles (system/developer, user, assistant, tool) set instruction priority; Anthropic hoists system top-level and enforces user/assistant alternation.
  • Parameters: Tune either temperature or top_p (not both); max_tokens/max_completion_tokens is a hard cutoff invisible to the model and includes hidden reasoning tokens on reasoning models.
  • SSE streaming: Unidirectional text/event-stream over HTTP cuts perceived wait from E2E to TTFT; split on \n\n, decode UTF-8 incrementally, and buffer tool-call JSON fragments until stream end.
  • Stop reasons: Always branch on finish_reason/stop_reason (stop/end_turn, length/max_tokens, tool_calls/tool_use, content_filter/refusal), never trust HTTP 200 alone.
  • Usage accounting: Enable stream_options.include_usage on OpenAI (guard against trailing choices: []), normalize OpenAI inclusive vs Anthropic exclusive cached input tokens, and log fallback estimates on aborted streams.
Important things to remember
  • Spine (M-P-H-S-R-U): Messages, Parameters, HTTP prefill (TTFT), SSE deltas (TPOT), Stop reason, Usage reconciliation.
  • Latency formula: E2E = TTFT + (N_out - 1) * TPOT. Streaming improves TTFT, not total E2E.
  • Cached-token math: OpenAI uncached = prompt_tokens - cached_tokens; Anthropic total_in = input_tokens + cache_read + cache_creation.
  • Silent failure rule: HTTP 200 + length/max_tokens = truncated payload billed in full; HTTP 200 + missing include_usage = 0 logged tokens on a real bill.
