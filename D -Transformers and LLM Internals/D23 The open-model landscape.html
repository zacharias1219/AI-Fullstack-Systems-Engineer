Before you read

Guess first. A wrong guess now makes the right answer stick later.

You deploy an FP16 model on a single 24 GB GPU serving 4 concurrent requests at 32,768 tokens each (131,072 active tokens). Which of Qwen 2.5 7B (7.62B params), Llama 3.1 8B (8.03B), and Gemma 2 9B (9.24B) fit without an out-of-memory crash?

Llama 3.1 8B crashes at 32.16 GB (16.00 GB KV cache), and Gemma 2 9B crashes at 60.41 GB (42.00 GB KV cache) because its 42 layers, 8 KV heads, and 256-dim heads use 336.0 KB/token vs Qwen's 56.0 KB/token.
DeepSeek-V2-Lite has 15.70B total parameters, almost double Llama 3.1 8B (8.03B). At 131,072 cached tokens, which model consumes more KV-cache VRAM, and by how much?
Llama 3.1 8B consumes 4.2x more KV-cache VRAM (16.00 GB vs 3.80 GB). DeepSeek uses Multi-head Latent Attention (MLA), compressing each layer's KV state into a 512-dim latent vector plus a 64-dim RoPE key (30.4 KB/token across 27 layers), whereas Llama 3.1 stores 8 full 128-dim K and V heads across 32 layers (128.0 KB/token).
Your legal team requires strict OSI-approved open-source licenses (Apache 2.0 or MIT) with zero monthly-active-user caps or mandatory branding notices. Which of the six flagship families (Llama 3.1, Qwen 2.5, Mistral 7B, Gemma 2, Phi-4, DeepSeek-V2-Lite) pass or fail?
Llama 3.1 8B and Gemma 2 9B fail; they are open-weight models governed by custom community terms (Llama 3.1 enforces a 700M MAU threshold, a "Built with Llama" notice, and acceptable-use restrictions; Gemma Terms include custom prohibited-use rules). Qwen 2.5 7B, Mistral 7B v0.3, and Phi-4 14B pass under Apache 2.0 or MIT (DeepSeek-V2-Lite code is MIT while model weights carry the permissive DeepSeek License).

The core idea

Engineers often treat open-weight models in the same parameter tier (such as 7B to 16B) as drop-in commodities that differ only in benchmark scores. In reality, a parameter count like "8B" hides three structural choices inside config.json that control your production latency, maximum batch size, and legal exposure: attention and feed-forward geometry (GQA ratio, head dimension, sliding-window layers, or MoE + MLA compression), vocabulary and positional range (how many parameters sit in the embedding table vs transformer blocks, and the RoPE base frequency theta), and license regime (true OSI Apache 2.0/MIT vs custom open-weight community agreements).

Think of an open model's config.json as a hardware and legal contract. Before you download weights or run an eval, five integers in that JSON file tell you exact FP16 weight footprint, exact KV-cache growth per token, whether long-context requests will overflow a 24 GB GPU, and whether your company can ship the weights commercially without renegotiating a license.

Memory hook

Remember W-K-V-L ("Weight, KV, Vocab, License") and the KV-cache ladder in KB/token: DeepSeek 30.4 < Qwen 56 < Llama/Mistral 128 < Phi-4 200 < Gemma 336.

How it works

1. Attention geometry and KV-cache scaling across model families

Every autoregressive transformer stores past Key and Value vectors so decoding a new token does not recompute prior tokens. For standard Grouped-Query Attention (GQA, covered deeply in D05), the FP16 KV-cache footprint per token is derived directly from the layer count L, the number of KV heads KVH, and the head dimension d_head (with 2 tensors for K and V, and 2 bytes per FP16 element):

KV_bytes_per_token (GQA) = 2 * L * KVH * d_head * 2
Qwen 2.5 7B     : 2 * 28 * 4 * 128 * 2 =  57,344 B =  56.0 KB/tok (7:1 GQA, 28 Q heads : 4 KV heads)
Llama 3.1 8B    : 2 * 32 * 8 * 128 * 2 = 131,072 B = 128.0 KB/tok (4:1 GQA, 32 Q heads : 8 KV heads)
Mistral 7B v0.3 : 2 * 32 * 8 * 128 * 2 = 131,072 B = 128.0 KB/tok (4:1 GQA, 32 Q heads : 8 KV heads)
Phi-4 14B       : 2 * 40 * 10 * 128 * 2 = 204,800 B = 200.0 KB/tok (4:1 GQA, 40 Q heads : 10 KV heads)
Gemma 2 9B      : 2 * 42 * 8 * 256 * 2 = 344,064 B = 336.0 KB/tok (2:1 GQA, d_head=256, alternating SWA)

Why do these numbers diverge so sharply? Qwen 2.5 7B uses an aggressive 7:1 GQA ratio (only 4 KV heads for 28 query heads), cutting KV cache to 56.0 KB/token. Gemma 2 9B doubles d_head to 256 across 42 layers with 8 KV heads, pushing its unwindowed KV footprint to 336.0 KB/token (to compensate, Gemma 2 alternates full global attention every other layer with 4,096-token Sliding Window Attention, or SWA, when the serving engine enables window eviction). DeepSeek-V2 and V3 go further with Multi-head Latent Attention (MLA): instead of caching separate KV heads, MLA projects K and V into a shared low-rank compressed vector (kv_lora_rank = 512 plus a 64-dim decoupled RoPE key), requiring only (512 + 64) * 2 = 1,152 bytes per layer, or 30.4 KB/token across 27 layers.

2. Vocabulary size, RoPE theta, and synthetic data density

A model's total parameter count includes its input and output token embedding matrices, each of shape V * d_model. Early open models like Mistral 7B v0.3 used a compact vocabulary of V = 32,768, spending only 2 * 32,768 * 4,096 = 268M parameters (3.7% of the model) on embeddings. Modern multilingual and code-heavy families expand V dramatically so non-English scripts and source code compress into fewer tokens: Llama 3.1 uses V = 128,256 (~1.05B params in untied input/output embeddings), Qwen 2.5 uses V = 152,064 (~1.09B params), and Gemma 2 uses V = 256,000 (even with tied embeddings, 256,000 * 3,584 = 918M params). A larger vocabulary reduces sequence length by 15% to 30% on code and multilingual text, directly cutting attention FLOPs and KV-cache length, at the cost of a heavier final lm_head logits projection.

Context window capability also tracks the Rotary Position Embedding (RoPE) base frequency theta. Models designed for 128k native context stretch the wavelength of low-frequency rotary dimensions by raising rope_theta from the classic 10,000 (used in Gemma 2 9B with 8k context and DeepSeek-V2-Lite with 32k context) to 250,000 (Phi-4, 16k context), 500,000 (Llama 3.1, 128k context), or 1,000,000 (Qwen 2.5 128k and Mistral v0.3 32k). Meanwhile, Microsoft's Phi-4 (14.66B) demonstrates the textbook-quality synthetic data thesis: by curating multi-stage synthetic reasoning corpora, a dense 14B model matches larger 70B models on STEM and coding benchmarks while keeping a 16k context window.

Check: Why does Qwen 2.5 7B use a 152,064-token vocabulary whereas Mistral 7B v0.3 uses 32,768, and what is the hardware tradeoff?
A 152,064-token vocabulary packs multilingual text, math, and code into fewer tokens per prompt, cutting prefill FLOPs, decode steps, and cached token count by 15% to 30% on non-English workloads. The price is ~1.09B parameters tied up in the embedding and lm_head tables (vs 268M in Mistral 7B) and a larger final softmax over 152,064 logits at every decode step.

3. Open-weight vs OSI open-source licensing

"Open weight" does not mean "open source" under the Open Source Initiative (OSI) definition. When choosing a base model for a commercial product, open models fall into two distinct legal buckets:

  • Permissive OSI licenses (Apache 2.0 and MIT): Used by Mistral 7B v0.3 (Apache 2.0), Qwen 2.5 7B / 14B / 32B / 72B (Apache 2.0; note that Qwen 2.5 3B and 1.5B use a custom Qwen Research/non-commercial or bespoke license, so always verify per checkpoint!), and Phi-4 14B (MIT). You can fine-tune, quantize, distill synthetic data to train any other architecture, and ship commercially at any user scale without usage caps.
  • Custom Open-Weight Community Licenses: Used by Llama 3.1 (Llama 3.1 Community License) and Gemma 2 (Gemma Terms of Use), with DeepSeek using MIT for repository code and the custom DeepSeek License (permissive commercial with an acceptable-use policy) for model weights. The Llama 3.1 license imposes three concrete legal requirements engineers get asked about in interviews: (1) a 700 million Monthly Active Users (MAU) commercial cap on the release date (exceeding 700M MAU requires a separate license from Meta), (2) mandatory "Built with Llama" attribution on user-facing documentation or interfaces, and (3) any derivative model distributed must begin its name with "Llama".
Check: A startup uses Llama 3.1 70B to generate synthetic training data and fine-tunes a custom Qwen 2.5 7B student model that they distribute publicly. What Llama 3.1 license rule applies?
Unlike Llama 2 (which forbade training non-Llama models on Llama outputs), the Llama 3.1 license explicitly permits using Llama outputs to train or distill other models, provided any publicly distributed derivative model states "Built with Llama" in its documentation and includes "Llama" at the start of its model name if it is a Llama derivative.

def kv_bytes_per_token(m, bytes_per_elem=2):
    if "mla_bytes_per_layer" in m:
        return m["L"] * m["mla_bytes_per_layer"]
    return 2 * m["L"] * m["KVH"] * m["d_head"] * bytes_per_elem

def total_vram_gb(m, batch_tokens=32768, bytes_per_weight=2):
    weight_gb = (m["params_b"] * 1e9 * bytes_per_weight) / (1024 ** 3)
    kv_gb = (kv_bytes_per_token(m, 2) * batch_tokens) / (1024 ** 3)
    overhead_gb = 1.2  # CUDA context + activation workspace
    return weight_gb, kv_gb, weight_gb + kv_gb + overhead_gb

What to notice

  1. Parameter count misleads on long-context VRAM: At a single 32k context window, Qwen 2.5 7B (7.62B) needs 17.14 GB while Llama 3.1 8B (8.03B) needs 20.16 GB. Once concurrency rises to Batch=4 (131,072 tokens), Llama's KV cache hits 16.00 GB (exceeding its 14.96 GB weights!) and crashes a 24 GB card at 32.16 GB, while Qwen's 7:1 GQA keeps KV cache at 7.00 GB and fits inside 24 GB at 22.39 GB.
  2. Gemma 2's wide heads and 42 layers create a 42.00 GB KV spike: Because Gemma 2 9B uses d_head = 256 with 8 KV heads across 42 layers, unwindowed KV cache consumes 336.0 KB/token, reaching 42.00 GB at 128k tokens (60.41 GB total VRAM). That is why Gemma 2 pairs global layers with 4,096-token sliding-window attention on alternating layers.
  3. MoE + MLA flips the weight-to-KV ratio: DeepSeek-V2-Lite 16B spends 29.24 GB on static FP16 weights (since all 15.70B parameters must load into VRAM), yet its MLA latent projection uses just 30.4 KB/token (3.80 GB for 131,072 tokens), making it ideal when weights are quantized to INT4/FP8 for high-concurrency serving.
  4. License compliance splits the table in half: Four models (Qwen 2.5 7B, Mistral 7B v0.3, Phi-4 14B, DeepSeek-V2-Lite) pass an OSI permissive filter, while Llama 3.1 8B and Gemma 2 9B require custom terms review.

Interview

Say this aloud against the clock. Three levels, about 90 seconds.

1 Outcome 20 sChoosing an open-weight model is not just picking the highest benchmark score at a parameter size. Two models in the seven-to-nine-billion class can differ by sixfold in KV-cache memory per token, use incompatible commercial licenses, and allocate billions of parameters to vocabulary embeddings rather than transformer layers.
2 Mechanism 45 sWe evaluate open model families across three axes: attention geometry, tokenizer allocation, and license compliance. For attention, standard Grouped-Query Attention scales KV-cache bytes per token as two times layers times KV heads times head dimension times two bytes in FP16. Qwen 2.5 7B uses four KV heads across twenty-eight layers for 56.0 kilobytes per token, while Llama 3.1 8B uses eight KV heads across thirty-two layers for 128.0 kilobytes per token, and Gemma 2 9B uses 256-dim heads across forty-two layers for 336.0 kilobytes per token. DeepSeek replaces GQA with Multi-head Latent Attention and Mixture-of-Experts, compressing KV state to 30.4 kilobytes per token while activating only 2.40 billion of 15.70 billion parameters per token.

Question bank

Walk through how you calculate the exact KV-cache memory per token from an open model's Hugging Face config.json, and compare Qwen 2.5 7B against Llama 3.1 8B.
Read num_hidden_layers (L), num_key_value_heads (KVH), and head_dim (or hidden_size / num_attention_heads). For standard GQA in FP16/BF16, multiply 2 (K and V) * L * KVH * d_head * 2 bytes. Qwen 2.5 7B has L=28, KVH=4, d_head=128 -> 2 * 28 * 4 * 128 * 2 = 57,344 bytes = 56.0 KB/token. Llama 3.1 8B has L=32, KVH=8, d_head=128 -> 2 * 32 * 8 * 128 * 2 = 131,072 bytes = 128.0 KB/token.
Follow-upWhy does that formula not work directly on DeepSeek-V2 or DeepSeek-V3? Because DeepSeek uses Multi-head Latent Attention (MLA), which caches a compressed joint KV latent vector (kv_lora_rank, e.g., 512) plus a single decoupled RoPE key vector (qk_rope_head_dim, e.g., 64) per layer rather than full K and V heads, dropping DeepSeek-V2-Lite to 27 * (512 + 64) * 2 = 30.4 KB/token.
How does DeepSeek-V2-Lite have 15.70B parameters yet run with fewer FLOPs per token and less KV-cache memory than an 8B dense model?
It combines two orthogonal mechanisms: fine-grained Mixture-of-Experts (MoE) for the feed-forward layers and Multi-head Latent Attention (MLA) for attention. MoE routes each token to a small subset of routed and shared experts so only 2.40B parameters execute per token (cutting matrix-multiply FLOPs and memory-bandwidth reads during decode by ~3.3x compared to an 8B dense model), while MLA compresses the KV cache to 30.4 KB/token (4.2x smaller than Llama 3.1 8B).
Follow-upWhat is the catch when deploying that 15.70B MoE model on a single edge GPU? All 15.70B parameters (29.24 GB in FP16) must stay resident in GPU VRAM because any expert can be selected on any token, so static weight memory scales with total parameters, not active parameters.
Compare the tokenizer vocabularies of Mistral 7B v0.3, Llama 3.1 8B, Qwen 2.5 7B, and Gemma 2 9B. How does a large vocabulary affect both memory and throughput?
Mistral 7B v0.3 uses V = 32,768; Llama 3.1 uses 128,256; Qwen 2.5 uses 152,064; and Gemma 2 uses 256,000. A larger vocabulary (128k to 256k) increases static parameter memory in the embedding and lm_head layers (roughly 0.9B to 1.1B parameters) and makes the final logits GEMM and softmax wider, but it compresses code and multilingual prompts into 15% to 30% fewer tokens, which directly reduces prefill FLOPs, total decode steps, and KV-cache length.
What architectural mechanisms does Gemma 2 9B use that differentiate it from a standard Llama-style decoder, and what operational care do they require?
Gemma 2 9B uses three distinctive design choices: (1) wider 256-dim attention heads across 42 layers (KVH=8), which would cost 336.0 KB/token if every layer used full context; (2) interleaved Sliding Window Attention (SWA), alternating 1 local layer (4,096-token window) with 1 global layer (8,192-token context) to halve KV growth when window eviction is supported; and (3) logit soft-capping (using tanh to bound attention and final logits) alongside knowledge distillation from larger teacher models.
Follow-upWhat happens if your inference engine does not implement Gemma 2's attention logit soft-capping or SWA buffer rotation? Disabling logit soft-capping degrades output perplexity on long generations, and disabling SWA buffer rotation forces all 42 layers to cache full sequence history at 336.0 KB/token, causing early OOMs.
When would you select Microsoft Phi-4 14B over Llama 3.1 8B or Qwen 2.5 7B, and when would you avoid it?
Select Phi-4 14B when you need an MIT-licensed dense model with maximum multi-step math, STEM, or code reasoning accuracy per GPU and your prompts fit inside its 16k context window. Avoid Phi-4 when you need 64k-128k long-document ingestion (where Llama 3.1 or Qwen 2.5 have 128k native context and rope_theta >= 500,000) or when your VRAM budget cannot hold 14.66B weights + 200.0 KB/token KV cache.
What are the three specific legal obligations in the Llama 3.1 Community License that do not exist in Apache 2.0 or MIT, and how did Llama 3.1 change the rule on synthetic data distillation?
The three obligations are: (1) a 700 million Monthly Active Users (MAU) cap on the release date (above which you must request a commercial license from Meta), (2) mandatory "Built with Llama" attribution on any product or documentation using the model, and (3) any distributed derivative model must start its name with "Llama" and include the license and acceptable use policy. Unlike Llama 2, Llama 3.1 explicitly allows using model outputs as synthetic data to train or distill other models.

Mixed review

Three questions from earlier topics. Nobody tells you the topic in an interview.

D01: What does a causal language model actually output at each forward pass before sampling takes place?
It outputs a raw, unnormalized logit vector of length V (the vocabulary size) for the next token position, which is then divided by temperature T and passed through a softmax to produce a probability distribution over the vocabulary.
K03: Why is the prefill phase of LLM inference compute-bound while the autoregressive decode phase is memory-bandwidth-bound?
Prefill processes all prompt tokens in parallel using matrix-matrix multiplications (high arithmetic intensity, reusing weights across many tokens), whereas decode generates one token at a time using matrix-vector multiplications that must stream all active model weights and the KV cache from HBM for every single token.
D01: Why does changing a single token at the start of a prompt invalidate the KV cache for every token that follows it?
Because causal self-attention computes each token's Key, Value, and hidden state as a function of all preceding tokens in the sequence; altering token i changes the attention outputs and K/V vectors at every position j >= i.
