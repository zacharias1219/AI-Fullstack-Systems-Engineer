Tokenization

How does text become the integers a model actually sees, and why does that one step set your cost, your context budget and which languages get a worse deal? This page covers byte-level BPE in depth, WordPiece and unigram briefly, special tokens, and the vocabulary size tradeoff. The embedding table itself is D03.

Study path

Before you read

Guess first. A wrong guess now makes the right answer stick later.

A tokenizer trained only on English sees a Telugu sentence and an English sentence with the same meaning. Does the Telugu one need about 1x, 2x or 5x the tokens?
About 5x. In the kata, the English-only tokenizer needs 337 tokens for the Telugu pair of sentences and 71 for the English pair, which is 4.75x. Even with no learning at all (pure bytes) Telugu is 3.01x, because each Telugu character takes 3 bytes in UTF-8. Learning English merges then widens the gap.
In a GPT-style tokenizer, are "token" and " token" (with a leading space) the same token, or different?
Different. In the kata, " token" is a single token while "token" without the space splits into t, o, k, en. The space is glued to the front of the word, so a word at the start of a text and the same word mid-sentence are different ids.
A byte-level BPE tokenizer meets a character it never saw in training. Does it emit an unknown token?
No. The base vocabulary is all 256 byte values, so any character can be written as 1 to 4 byte tokens. The price is length, not failure: a rare character costs several tokens instead of one.

The core idea

A network takes numbers, so text has to become integers. Characters give sequences that are far too long, and attention cost grows with the square of length. Whole words give a vocabulary that is huge and breaks on any word it never saw. Subword tokenization sits between the two: common strings get one token, rare strings are spelled out from smaller pieces.

Byte-pair encoding (BPE) builds that vocabulary greedily. Start with single units. Count adjacent pairs. Merge the most frequent pair into a new unit. Repeat until the vocabulary reaches the size you chose. In byte-level BPE the starting units are the 256 possible byte values, so every string in every language can be written down. The ordered list of merges is the tokenizer.

Mental model. A stenographer writes a shorthand dictionary. Each time they notice the same two symbols together again and again, they invent one new symbol for that pair. The dictionary stops when it hits its page limit. Writing a sentence in shorthand means replaying their inventions in the order they made them. The stenographer only learned shorthand for what they were shown, which is why a dictionary built from English text is poor at Telugu.

Memory hook

Bytes in, count pairs, glue the top pair, repeat until the vocabulary is full. The glue list in order is the tokenizer. Encoding replays the glue list. Vocabulary size is one dial between sequence length and table size.

How it works

Training: count, merge, repeat

Take a corpus as sequences of byte values. Count every adjacent pair, weighted by how often the word occurs. Pick the most frequent pair, give it the next unused id (256, then 257, and so on), and rewrite the corpus with that pair replaced. Repeat. After M merges the vocabulary has 256 + M entries. Each merge is recorded as a rule "pair (a, b) becomes id n". A small trace on the string aaabdaaabac:

aaabdaaabac   pairs: aa=4 ab=2 bd da ba ac  -> merge aa as Z
ZabdZabac     pairs: Za=2 ab=2 ...          -> tie, merge ab as Y
ZYdZYac       pairs: ZY=2 ...               -> merge ZY as X
XdXac         11 symbols became 5
Check: in the trace, why is the first merge aa and not ab, and what does a tie mean for your tokenizer?
aa occurs 4 times as an adjacent pair (the run aaa contains two overlapping aa pairs), ab only 2. A tie such as Za versus ab is broken by a fixed rule (for example the lowest ids first), and the choice changes which tokens exist. Two BPE trainers with different tie rules produce different tokenizers, so the tokenizer file is part of the model.

Encoding: replay the merges in rank order

To tokenize new text you do not search for the best split. You take each word as bytes and apply the merges in the order they were learned: merge 256 first if it applies anywhere, then 257, and so on. This is greedy replay, so BPE does not guarantee the shortest possible token sequence. Real implementations use the lowest-ranked adjacent pair at each step, which gives the same result as the full replay without scanning all merges.

Check: does BPE encoding find the segmentation with the fewest tokens?
No. It replays learned merges by rank, which is deterministic and fast but greedy. Unigram tokenizers (below) do search for the most probable segmentation with the Viterbi algorithm.

Why bytes, and what UTF-8 does to non-English text

UTF-8 writes ASCII in 1 byte, most accented Latin, Greek and Cyrillic in 2, most Indic scripts and Chinese in 3, and emoji in 4. A byte-level tokenizer starts from those bytes, so a Hindi character begins life as 3 tokens and can only get cheaper if the training corpus contained enough Hindi for those byte triples to win merges. Starting from bytes instead of characters means the base vocabulary is exactly 256 for every language, with no unknown token, and no character set to design.

Check: with zero merges, how many tokens does the kata's Hindi sentence pair need compared with English, and why?
289 versus 112, which is 2.58x. The Hindi pair is 109 characters but 289 UTF-8 bytes (about 2.65 bytes per character), the English pair is 112 characters and 112 bytes. With no merges, tokens equal bytes.

Pre-tokenization: where merges are not allowed to go

Before any merging, a regex cuts text into chunks, and BPE runs inside each chunk. GPT-2 style splitting attaches the leading space to the word (" token"), keeps letters, digits and punctuation apart, and keeps whitespace runs together. Without this step a merge like "s " (end of one word plus the space) can form and cross word boundaries, giving tokens that mean nothing on their own. Newer tokenizers tune this regex for digits and code. Two consequences you can use in interviews: a prompt that ends in a space leaves a lone space token, which the model rarely saw in that position, so strip trailing whitespace; and numbers are split into chunks by the regex, not by place value, which is one reason arithmetic is hard.

Other families: WordPiece and unigram

WordPiece (BERT) also grows a vocabulary by merging, but it picks the pair with the best likelihood score, roughly count(ab) divided by count(a) times count(b), not the raw count. It encodes by longest-match-first and marks continuation pieces with "##". Unigram (used in SentencePiece models such as T5) goes the other way: start with a large candidate vocabulary, fit a probability to each piece with EM, and repeatedly drop the pieces whose removal hurts the corpus likelihood least. It encodes with Viterbi and can sample alternative segmentations. SentencePiece is a library that runs BPE or unigram directly on raw text, treating the space as a symbol, so it needs no language-specific pre-splitting.

Check: name one concrete difference between BPE and unigram, in training direction and in encoding.
BPE grows from small units by merging, and encodes by replaying merges in rank order. Unigram shrinks from a large candidate set by pruning, and encodes by finding the highest probability segmentation, which can also be sampled.

Special tokens

Special tokens are ids added outside the learned merges: end of text, beginning of sequence, padding, and the role markers of a chat template. GPT-2 has one, <|endoftext|>, which is why its vocabulary is 256 + 50,000 + 1 = 50,257. The model learns what they mean during training. The danger is parsing: if your encoder turns the literal text "<|im_start|>" inside a user message into the real special id, the user can forge a system or assistant turn. This is a prompt injection path at the tokenizer layer, the same family of problem ROPE measures at the prompt layer.

Check: how do you stop user text from creating real special tokens?
Encode untrusted text with special-token parsing disabled so the literal characters become ordinary tokens, and only the template code inserts real special ids. Add a test that a user message containing a role marker string does not produce the special id.

Vocabulary size: the one dial

Raising vocabulary size V compresses text better, so sequences get shorter, which cuts prefill compute, decode steps and KV cache per piece of text. You pay three ways. The embedding table has V rows of width d, so V × d parameters. The output layer multiplies the hidden state by a d by V matrix every step, which is 2 × d × V FLOPs per generated token. And rare tokens appear so seldom in training that their vectors stay poorly trained. Compression gains shrink as V grows while the table grows linearly. Llama 3 moved from 32,000 to 128,256 tokens, so its table is 128,256 × 4,096 = 525,336,576 parameters, about 1.05 GB in bf16 (d is from memory, verify). The output matmul is about 1.05 GFLOPs per token against roughly 16 GFLOPs for the whole 8B model, so about 6.5 percent of per-token compute goes to scoring the vocabulary.

Check: compute the embedding table size in GB for V = 32,000 and d = 4,096 in bf16, and say what changed from 32,000 to 128,256.
32,000 × 4,096 = 131,072,000 parameters, times 2 bytes is 0.26 GB. At 128,256 it is 1.05 GB, four times larger, bought to get shorter sequences and better coverage of non-English text and code.

The multilingual tax

Cost, latency and context window are all measured in tokens, not characters. A tokenizer whose merges were learned mostly from English gives other scripts more tokens for the same meaning, so the same Telugu call costs more, prefills slower, and fits fewer turns in the context window. This matters directly for voice AI for clinics in Hindi or Telugu: price per token tells you nothing until you measure tokens per sentence in your own languages.

PRE = re.compile(r" ?\S+|\s+")  # pre-tokenize: a word keeps its leading space (GPT-2 style, simplified)

def merge(w, pair, new):
    out, i = [], 0
    while i < len(w):
        if i < len(w) - 1 and (w[i], w[i + 1]) == pair: out.append(new); i += 2
        else: out.append(w[i]); i += 1
    return tuple(out)

def train(text, n):
    vocab, merges = Counter(tuple(w.encode()) for w in PRE.findall(text)), []
    for _ in range(n):
        pairs = Counter()
        for w, c in vocab.items():
            for p in zip(w, w[1:]): pairs[p] += c
        if not pairs or pairs.most_common(1)[0][1] < 2: break  # a pair seen once teaches nothing
        best, new, nv = pairs.most_common(1)[0][0], 256 + len(merges), Counter()
        merges.append(best)
        for w, c in vocab.items(): nv[merge(w, best, new)] += c
        vocab = nv
    return merges

def encode(text, merges):
    ids = []
    for w in PRE.findall(text):
        t = tuple(w.encode())
        for k, p in enumerate(merges): t = merge(t, p, 256 + k)  # apply merges in the order they were learned
        ids += t
    return ids

def table(merges):
    tok = {i: bytes([i]) for i in range(256)}
    for k, (a, b) in enumerate(merges): tok[256 + k] = tok[a] + tok[b]
    return tok

text = EN + (" " + " ".join(OTHER.values()) if args.multi else "")
merges = train(text, args.merges)
tok = table(merges)
print(f"trained on {len(text)} chars ({'multilingual' if args.multi else 'English only'}); learned {len(merges)} merges; vocab = 256 + {len(merges)} = {256 + len(merges)}")
print("first merges (bytes):", [tok[256 + k] for k in range(min(8, len(merges)))])
for lang, s in EVAL.items():
    assert b"".join(tok[i] for i in encode(s, merges)).decode() == s  # lossless round trip
print(f"\n{'language':<9}{'chars':>6}{'bytes':>7}{'tokens':>8}{'bytes/tok':>11}{'x English':>11}")
base = len(encode(EVAL["English"], merges))
for lang, s in EVAL.items():
    n = len(encode(s, merges))
    print(f"{lang:<9}{len(s):>6}{len(s.encode()):>7}{n:>8}{len(s.encode()) / n:>11.2f}{n / base:>11.2f}")
print("\nsame word, with and without a leading space:")
for w in ["token", " token"]:
    print(f"  {w!r:9} -> {[tok[i].decode(errors='replace') for i in encode(w, merges)]}")

What to notice

  1. With zero merges, tokens equal bytes: English 112, Hindi 289, Telugu 337. Before any learning, Indic scripts already cost 2.58x and 3.01x because of UTF-8.
  2. After 108 English-only merges, English falls from 112 to 71 tokens (1.58 bytes per token) while Hindi stays at 289 and Telugu at 337. The multiple grows to 4.07x and 4.75x. Compression is learned, and only for what the corpus contained.
  3. The first merges are b' t', b'he', b'er', b' the'. Later merges build on earlier ones: ' the' is ' t' plus 'he'. The merge list is a tree of reuse.
  4. Training stopped at 108 merges, not the 300 allowed, because no pair repeated any more. A 714-character corpus cannot support a large vocabulary. Real tokenizers train on very large corpora.
  5. " token" is one token but "token" is t, o, k, en. The space belongs to the word, and the training text always had "token" after a space.
  6. These numbers come from a toy corpus and short held-out sentences. They show the direction and mechanism, not the size of the effect in a production tokenizer.
Break it
  1. Fewer merges. Run python kata.py --merges 20 and --merges 0. Predict first: how many tokens will Hindi need at 0, at 20, at 108? And what happens to the Telugu-to-English multiple as English gets better?
  2. Same budget, different corpus. Run python kata.py --multi --merges 108. Predict Hindi tokens and English tokens before you look. Who gains and who loses at a fixed vocabulary size? Look at the first merges: what are they?
  3. Remove pre-tokenization. Change the PRE line to re.compile(r"[\s\S]+") so the whole text is one chunk. Predict which kind of merge appears that did not before, and whether English tokens go up or down.

Stretch. Print encode("strawberry", merges) as pieces and ask how a model could count its r letters from those. Then replace the PRE regex with a GPT-2 style one that separates letters, digits and punctuation, and compare how it splits "2026-11-17".

Scenario: your clinic voice agent sends ASR transcripts to an LLM. A Telugu call costs about 4x an English call and answers arrive later. Finance asks why and what you will do.
  1. Measure before explaining: log input tokens and characters per call by language, and compute tokens per character with the model's own tokenizer on 50 real transcripts.
  2. Explain the mechanism: Telugu characters are 3 UTF-8 bytes and the merges favor English, so one meaning needs several times the tokens. Cost scales with tokens, prefill time scales with prompt tokens, and the KV cache grows with them.
  3. Fix cheaply first: cut and cache the fixed system prompt, trim old turns, summarize earlier transcript, keep instructions short.
  4. Compare models by tokens per sentence on your own transcripts, not by price per token. A larger vocabulary that covers Indic scripts better can be cheaper at a higher price per token.
  5. Re-run your eval set after any change, because a different tokenizer or shorter prompt can change accuracy.
  6. Report cost per call by language, not cost per token.

Interview

Say this aloud against the clock. Three levels, about 90 seconds.

1 Outcome 20 sA tokenizer turns text into integer ids drawn from a fixed vocabulary of subword pieces. The model only ever sees those ids, so cost, context length and latency are all counted in tokens. That makes the tokenizer the first place where price and quality get decided.
2 Mechanism 45 sMost modern LLMs use byte-level BPE. Start with the 256 byte values, so any string can be represented and nothing is unknown. Count every adjacent pair in a corpus, merge the most frequent pair into a new token, and repeat until the vocabulary reaches its target size. The ordered merge list is the tokenizer. To encode, split the text into words with a regex, convert each word to UTF-8 bytes, and replay the merges in the order they were learned. WordPiece picks merges by likelihood and encodes by longest match. Unigram starts large and prunes. Special tokens are extra ids for end of text and chat roles.
3 Internals and limits 25 sVocabulary size is the main dial. GPT-2 uses 50,257 tokens and Llama 3 uses 128,256, which costs a 128,256 by 4,096 table, about 1 GB in bf16, but shortens sequences. The tax lands on languages missing from training: in my toy run an English-only tokenizer needed 4.75 times the tokens for Telugu. Failure modes are undertrained rare tokens, letter-level tasks, and special-token injection.

Question: why does the same sentence cost more in Telugu than in English?

"The tokenizer is not as good at Telugu, so it uses more tokens, and tokens cost money."

"Telugu characters are 3 bytes in UTF-8, and the merge list was learned mostly from English, so few Telugu pairs earned merges. In my toy run, an English-only tokenizer took 337 tokens for a Telugu pair of sentences against 71 for the English pair, 4.75x. A production tokenizer is far better than my toy, but the direction holds, so I would measure tokens per character per language with the real tokenizer before pricing anything."

The strong answer names the mechanism (UTF-8 bytes, merge learning), gives a number, and ends with a decision. Those 4.75x and 71 figures come from the toy kata, so say that they are illustrative and not production results.

Traps

Each one sounds right. Say what is wrong with it before you open it.

"Tokens are basically words, so a 1,000-token prompt is about 1,000 words."
English averages about 0.75 words per token (from memory, verify), and other scripts are much worse. In the kata, " token" is one token, "token" without a space is four, and Hindi needs 289 tokens for 109 characters. Tokens are pieces of bytes, so always count with the model's tokenizer.
"BPE tokenizes a sentence by searching for the split that gives the fewest tokens."
No. BPE replays the learned merges in rank order, which is greedy and deterministic. It does not search. Unigram tokenizers are the ones that search with Viterbi for the most probable segmentation.
"A bigger vocabulary is always better, because the sequences get shorter."
Shorter sequences are the gain, but the embedding table grows by V × d, the output matmul costs 2 × d × V per generated token, and rare tokens are undertrained. Compression gains flatten while the table grows linearly. The best V depends on the languages, the code share and the model size.
"A byte-level tokenizer can still produce an unknown token for a very rare character."
No. All 256 byte values are in the base vocabulary, so any character is representable. The failure is cost: a rare character becomes up to 4 tokens. A different problem is generation stopping inside a character, which gives invalid UTF-8 until the next token arrives.

Explain tokenization to me in 90 seconds.
Use the three levels above: outcome, then byte-level BPE training and encoding, then vocabulary size, the multilingual tax and failure modes, each with its number.
Follow-upWhy not just use words, or just characters? Words give a huge vocabulary and unknown words. Characters give sequences several times longer, and attention cost grows with the square of length. Subwords sit between the two.
Corpus aaabdaaabac. Which pair merges first, and what does the text become after two merges?
aa, which occurs 4 times, giving ZabdZabac. The second step ties between Za and ab at 2 each. With ab merged, the text is ZYdZYac. The tie rule affects the result, so tokenizers must ship their merge list.
Why does the same meaning cost more tokens in Hindi or Telugu?
Indic characters are 3 bytes in UTF-8 and the merge list was learned from data dominated by English. In the kata even zero merges give 2.58x for Hindi, and English-only merges widen it to 4.07x.
Follow-upHow do you fix it for a product? Measure tokens per sentence in your languages with candidate models, prefer a tokenizer with better coverage even at a higher price per token, shorten and cache prompts, and track cost per call by language.
How do you choose a vocabulary size?
Pick the size where extra compression stops paying for the larger table and output matmul. Consider the language and code mix, model width and the training token budget. GPT-2 used 50,257, Llama 3 uses 128,256.
Follow-upWhat does the vocabulary add to per-token compute? The output projection costs 2 × d × V FLOPs, about 1.05 GFLOPs for V = 128,256 and d = 4,096, roughly 6.5 percent of an 8B model's per-token compute.
Compare BPE, WordPiece and unigram.
BPE merges the most frequent pair and encodes by replaying merges. WordPiece merges by a likelihood score and encodes by longest match with "##" continuations. Unigram prunes a large vocabulary by likelihood and encodes with Viterbi, so it can sample segmentations.
Follow-upWhich one has an unknown token problem? WordPiece and word-level schemes can emit [UNK]. Byte-level BPE cannot, because every byte is in the base vocabulary.
What breaks when training and serving use different tokenizers or chat templates?
The ids no longer mean what the model learned, so outputs degrade or roles are ignored. Load the tokenizer and template from the same checkpoint, and add a test that renders a fixed conversation and compares the ids.
Why is the leading space part of the token, and what does that mean for prompts?
GPT-style pre-tokenization attaches the space to the word, so " token" is one id and "token" is another. A prompt ending in a space leaves a lone space token that rarely appears there in training, so strip trailing whitespace.
Why do LLMs struggle to count the r letters in a word or do long-digit arithmetic?
The model sees token ids, not letters, so spelling must be memorized per token. Digits are split by a regex into chunks, not by place value. Use a tool for counting and arithmetic.
Follow-upWould a bigger vocabulary help? Not reliably. It changes the chunks but still hides letters. Tool use or character-level inputs fix the task.
What is a special token and how can it be abused?
An id added outside the learned merges, for end of text or chat roles. If untrusted text is encoded with special-token parsing on, a user can forge a system turn. Disable parsing for user text and test it.
How would you estimate the token cost of Telugu clinic call transcripts before launch?
Sample 50 real transcripts, tokenize them with each candidate model's own tokenizer, record tokens per character and tokens per call, then multiply by price per token and calls per day. Include the system prompt and output tokens.
Follow-upWhat else would you track after launch? Billed usage versus your estimate, p95 prompt length, and the share of calls near the context limit, split by language.
Why start from 256 bytes instead of characters?
The base vocabulary is exactly 256 for every language and no character can be unknown. A character-based base would need tens of thousands of entries and would still meet unseen characters.

Mixed review

Three questions from earlier topics. Nobody tells you the topic in an interview.

D01: what does the model predict at each position during training, and how does inference differ?
Training predicts the next token at every position in parallel from the true previous tokens, and the loss is cross-entropy over the vocabulary. Inference generates one token at a time and feeds its own output back in, so it is sequential.
A02: why does one blocking call such as time.sleep inside an async handler slow every other request?
asyncio runs coroutines on one event loop thread. A blocking call holds that thread, so no other coroutine runs until it returns. Use an awaitable version or move the work to a thread with asyncio.to_thread.
L01: you are asked to design a chatbot for a clinic. Name four clarifying questions before drawing anything.
Who the users are and how many at peak; the latency target (p95); data sensitivity and rules such as PHI, GDPR or DPDPA; which languages are needed; what a wrong answer costs. Each one changes the design.
